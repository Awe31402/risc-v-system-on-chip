# 4.3 Wally Style Guidelines

> 原書 p.181–190（Chapter 4: HDL Design Practices）
> 涵蓋 4.3.1 Signals、4.3.2 Spacing and Indentation、4.3.3 Synchronous Design、
> 4.3.4 Modules、4.3.5 Configurable Hardware、4.3.6 Comments

## 這節在講什麼

**44 條 Wally 的程式碼風格規範。**

這節看起來像瑣碎的排版規定，但**其中約三分之一其實是「避免 bug」的規則**，
不只是美觀問題：pipeline 級後綴、同步設計、宣告所有訊號、模組介面不隨組態改變——
這些寫錯了會真的出事。

**讀法建議：排版類的掃過去就好，
重點放在 4.3.1.2（後綴前綴）、4.3.3（同步設計）、4.3.5（可組態硬體）這三組。**

本節開頭那句引言定調了整體態度。

## 關鍵點

### 風格規範的態度

> "A foolish consistency is the hobgoblin of little minds."
> — Ralph Waldo Emerson（p.181 引言）

> "Most organizations and experienced designers establish a set of HDL style guidelines
>  for large projects with multiple contributors to speed development, maintain
>  consistency, and reduce errors. Many reasonable choices exist, but consistency is
>  valuable for readability across the design, and **the designer must be empowered to
>  break these guidelines when the need arises.**"
> — p.181

中文解釋：**態度很明確：一致性有價值，但不是教條。**
引言（「愚蠢的一致性是小心靈的妖怪」）和最後那句「設計者應被授權在必要時打破規範」
要一起讀。

**重要限定（p.181 邊欄）：**
> "These style guidelines apply to synthesizable code. Testbenches are an entirely
>  different matter and generally look more like software."

**這些規範只適用於可合成的程式碼；testbench 比較像軟體，不適用。**

另外兩份業界風格指南（p.181）：
- **lowRISC**：github.com/lowRISC/style-guides/blob/master/VerilogCodingStyle.md
- **Freescale**：people.ece.cornell.edu/land/courses/ece5760/Verilog/FreescaleVerilog.pdf

### 大小寫慣例（Guidelines 4.1–4.3）

中文解釋：**Table 4.3（p.182）的五種慣例：**

| 範例 | 名稱 |
| --- | --- |
| `regwrite` | flatcase |
| `regWrite` | camelCase / dromedaryCase |
| **`RegWrite`** | **UpperCamelCase / PascalCase** |
| `reg_write` | snake_case |
| `REG_WRITE` | MACRO_CASE |

**Wally 的三條規則：**
- **Guideline 4.1：`clk` 和 `reset` 用 flatcase**（幾乎每個模組都有，要好打）
- **Guideline 4.2：訊號用 UpperCamelCase**
- **Guideline 4.3：常數與巨集用 MACRO_CASE**

**選擇理由（p.182）值得一讀，因為它承認了主觀性：**
- flatcase 適合短名字（如 C 標準函式庫），但複雜的多字名難讀
- snake_case 要用右手小指按底線鍵，**作者覺得打起來很累**
- camelCase 單字變數不用大寫、多字名可讀性高，是**作者寫程式時的個人偏好**
- **UpperCamelCase 在 HDL 設計中常見，在方塊圖上看起來自然**，
  而且是 Patterson 和 Hennessy 在《Computer Organization and Design》圖中的選擇
  ——**Wally 間接繼承自那本書**
- MACRO_CASE 最難打，但**讓常數和巨集從變數中凸顯出來**

**一個有趣的實證**（p.182）：
> "In an empirical study, Binkley found that camelCase leads to higher accuracy and faster
>  recognition than snake_case [Binkley09]."

**SystemVerilog 是大小寫敏感的**——`RegWrite`、`regwrite`、`regWrite` 是三個不同訊號。
**大小寫不一致會導致：搜尋不到、或同一個訊號在不同地方大小寫不同而接不起來**（p.181）。

（邊欄補充：**VHDL 大小寫不敏感，反而會造成 EDA 工具的問題**，
因為 Tcl 是大小寫敏感的，可能找不到訊號，p.181 邊欄。）

### 後綴與前綴（Guidelines 4.4–4.5）——最重要的一組

> "In pipelined systems, the same signal often exists in multiple pipeline stages and must
>  be named in a way to distinguish the stage. HDL designers normally do this with a
>  suffix. For example, the Wally pipeline has Fetch, Decode, Execute, Memory, and
>  Writeback stages. The suffix may be one letter (F, D, E, M, or W) or an abbreviation
>  (FET, DEC, EXE, MEM, WRB). **Signals outside the pipeline (e.g., in the bus interface
>  or hardware page table walker) have no suffix.**"
> — p.183

中文解釋：**這是讀 Wally 程式碼最需要的知識**（呼應 2.7 節）。

- **Guideline 4.4：所有和 pipeline 級有關的訊號都要加後綴**（F、D、E、M、W）
- **pipeline 外的訊號沒有後綴**——**這本身就是資訊**：看到沒後綴就知道它不在 pipeline 裡

**跨級元件的命名規則（p.183）——這是 bug 的常見來源：**
> "While pipeline registers accept inputs from one pipeline stage and produce outputs for
>  the next stage and, normally, combinational logic accepts inputs and produces outputs
>  within the same pipeline stage, **some components operate across multiple pipeline
>  stages. Such components are a common source of bugs, and care must be taken in signal
>  naming.**"

三個必然跨級的元件（p.183）：
| 元件 | 跨哪些級 |
| --- | --- |
| **暫存器檔案** | Decode 級讀、Writeback 級寫 |
| **外部匯流排介面** | 接受 Fetch 和 Memory 級的請求 |
| **hazard 單元** | 合併多級的 hazard，送 stall/flush 給每一級 |

**命名規則（p.183）：**
> "For such components, signals generated within the pipeline use the suffix of the
>  pipeline stage in which they were produced. **Signals generated outside the pipeline
>  (i.e., in the hazard unit) use the suffix of the stage in which they will be used.**"

**在 pipeline 內產生的 → 用「產生它的那一級」；
在 pipeline 外產生的（如 hazard 單元）→ 用「會被使用的那一級」。**
（所以會看到 `StallF`、`StallD`、`FlushE` 這種命名，呼應 2.7 節 Fig. 2.11。）

**Guideline 4.5：用前綴區分不同來源的相關訊號**（p.183）
> "For example, the datapath uses IEUResultM, MDUResultW, and SCResultW to distinguish
>  results from the IEU, MDU, and store conditional units. Source units are typically
>  abbreviated in all caps (e.g., IEU, IFU, LSU, FPU, SC, and MDU)."

**前綴 = 來源單元（全大寫縮寫），後綴 = pipeline 級。**
所以 `IEUResultM` 讀作「IEU 產生的 Result，在 Memory 級」。

### 宣告訊號（Guidelines 4.6–4.10）

- **Guideline 4.6：宣告所有內部訊號，包括 1-bit 訊號。**
  **"Undeclared signals are a source of bugs."**（p.183）
  （Verilog 允許隱含宣告，但打錯字就變成一個新的 1-bit 訊號——經典 bug。）
- **Guideline 4.7：只在頂層晶片模組使用雙向 `inout` 接腳，定義為 `inout tri`。**
  雙向接腳只該用在外部 I/O 標準的必要部分（如 GPIO）；
  **內部用單向匯流排和多工器，不要用雙向匯流排和 tristate**（p.183–184，呼應 4.2.2.3）
- **Guideline 4.8：其他訊號都宣告為 `logic`。**
  `logic` 除了 tristate 網路以外到處都能用，支援 x 和 z，
  **避免老派 Verilog 中 `wire` 和 `reg` 的醜陋規則**（p.184）
- **Guideline 4.9：匯流排宣告為 little-endian**（`[31:0]` 而非 `[0:31]`），
  與主流慣例一致
- **Guideline 4.10：盡量不要透過埠傳遞陣列**；必要時埠宣告為 `var logic`（p.184）

Code Example 4.44（p.184）示範了這些規範：
```systemverilog
module ifu import cvw::*;  #(parameter cvw_t P) (
  input     logic              clk, reset,                    // Lower case
  input     logic              StallF, StallD, StallE, ...,   // Suffix
  input     logic              FlushF, FlushD, FlushE, ...,   // Suffix
  input     logic [P.XLEN-1:0] SATP_REGW,                     // Little-endian
  input var logic [7:0]        PMPCFG_ARRAY_REGW[P.PMP_ENTRIES-1:0],  // Passing array
  output    logic              InstrAccessFaultF);
```

### 埠連接（Guidelines 4.11–4.15）

呼應 4.2.4.5 節：
- **Guideline 4.11：簡單的通用模組（正反器、多工器）按順序連接**——最簡潔
- **Guideline 4.12：其他模組按名稱連接。**
  同名用 `.sig`，不同名用 `.sig(name)`
- **Guideline 4.13：只用一次的非通用模組，埠名和連接的訊號名取相同。**
  **"Tracing logic is easiest when signals don't change names unnecessarily at module
  boundaries."**（p.185）——**這也讓 `.sig` 簡寫可用**
- **Guideline 4.14：除了 wrapper 模組，避免 `.*`**
  （p.185 邊欄定義：**top-level module** 是設計階層最高的模組，通常是結構化的；
  **wrapper module** 把訊號映射到目標介面，例如 FPGA 上接到系統時脈、開關的接腳）
- **Guideline 4.15：實例化時把多個埠連接擠在同一行。**
  **"Brevity improves the ability to see the big picture."**（p.185）

Code Example 4.45（p.185）的實例：
```systemverilog
mux2 #(P.XLEN) ieuresultmux(ALUResultE, AltResultE, ALUResultSrcE, IEUResultE);
mmu #(.TLB_ENTRIES(P.DTLB_ENTRIES), .IMMU(0)) dmmu(
  .clk, .reset, .SATP_REGW, .STATUS_MXR, .STATUS_SUM,
  .STATUS_MPRV, .STATUS_MPP,
  .PrivilegeModeW, .DisableTranslation(SelHPTW),
  .PAdr(PreLSUPAdrM), .VAdr(IEUAdrM),
  ...
  .PMPCFG_ARRAY_REGW, .PMPADDR_ARRAY_REGW);
```
**mux2 用順序（一行搞定），mmu 用名稱（複雜，需要清楚）。**

### 空白與縮排（Guidelines 4.16–4.25）

中文解釋：**這組純屬排版，掃過即可：**

| Guideline | 規則 |
| --- | --- |
| 4.16 | **用空白不用 tab**（不同編輯器對 tab 解讀不同） |
| 4.17 | **每層縮排兩個空白**（本書版面空間有限） |
| 4.18 | 區塊內的訊號宣告要對齊 |
| 4.19 | 運算子前後、`if`/`case`/`for` 後面留空白 |
| 4.20 | 分號、逗號、右括號前，以及模組實例化的左括號後、匯流排寬度宣告內，不留空白 |
| 4.21 | **只在區塊需要超過一個敘述時才用 `begin`/`end`** |
| 4.22 | 可行時把 `begin` 擠在同一行 |
| 4.23 | **每行最多 95 字元**（本書版面能容納的最大值；歷史上的 80 字元也合理但已非必要） |
| 4.24 | 空行要少用，只用來邏輯上分隔程式碼 |
| 4.25 | **banner 註解要少用**，只在階層不是好選擇時用來分隔複雜模組的主要部分 |

### 同步設計（Guidelines 4.26–4.28）——第二重要的一組

> "**Guideline 4.26** Use synchronous sequential design.
>  Every component should be a positive edge-triggered flip-flop, a standard memory, or
>  combinational logic. All components should share a common clock named clk. **Avoid
>  latches, negative edge-triggered flip-flops, and asynchronous components.** Exceptions
>  to synchronous design should only occur when essential (e.g., at an interface with an
>  asynchronous peripheral) and should be carefully documented with comments and reviewed."
> — p.187

中文解釋：**這條是所有規範中最重要的一條**，呼應 4.2 節的 synchronous sequential discipline。

**只允許三種元件：正緣觸發正反器、標準記憶體、組合邏輯。共用一個 `clk`。**

**要避免：latch、負緣觸發正反器、非同步元件。**
例外只在必要時（如接非同步周邊），而且**必須寫註解並經過審查**。

**多時脈域的現實（p.187）：**
> "Large systems with multiple subsystems inevitably have more than one clock domain. For
>  example, a RISC-V core might run at a different frequency than a Wi-Fi packet processor
>  or GPU or DRAM controller. Use synchronous sequential design within a clock domain.
>  **Clock domain crossings, sending signals between clock domains, are beyond the scope of
>  this book.**"

**同步設計是「在一個時脈域內」的規範；跨時脈域是另一個（很難的）主題，本書不談。**

**Guideline 4.27：用模組實例化記憶體和正反器**（p.187）
> "This makes it easier to identify the number of bits of state in the system and to swap
>  out synchronous or asynchronous reset, scan, or low-power features."

**好處：容易統計系統有多少狀態位元，也容易整批換掉 reset 方式或加掃描鏈/低功耗功能。**

**例外（p.187 邊欄）：FSM 的狀態暫存器常用列舉型別，和正反器模組的 `logic` 型別不相容，
所以直接在 FSM 裡用 `always_ff` 定義。**（呼應 4.2.3.2 的 Code Example 4.16。）

**Guideline 4.28：除了 testbench 不用 `#` 延遲**（呼應 4.2.4.4）。

### 模組（Guidelines 4.29–4.36）

| Guideline | 規則 |
| --- | --- |
| 4.29 | **每個模組放在同名檔案裡**。例外：關係密切的小模組（如通用多工器）可共用一個檔案 |
| 4.30 | 模組名後緊接 `(`，未參數化時輸入輸出埠和模組名同一行開始 |
| 4.31 | 參數化時，參數和 `(` 和模組宣告同一行；埠放後續行縮排兩格；`);` 放最後一個埠那行 |
| 4.32 | **每行一個 `input` 或 `output` 關鍵字**，同極性同寬度的埠宣告在同一行；每行水平對齊：`input`/`output`、位元寬度、訊號名 |
| **4.33** | **葉節點（通用區塊和控制區塊）用行為描述風格** |
| **4.34** | **資料通路區塊盡量用結構化風格** |
| 4.35 | **用階層讓模組保持小而易懂** |
| 4.36 | **避免會遮蔽所隱含硬體的程式語言構造** |

**4.33 和 4.34 的分工是核心（p.188）：**
- **控制區塊最容易用行為描述**（`if`、`case`）
- **資料通路要用多工器、正反器和其他功能區塊描述；把非平凡的控制推到獨立模組**
  （**有時資料通路需要用 `assign` 做 bit swizzling**）

（呼應 2.7 節的 datapath / controller 分離。）

**Guideline 4.35 的取捨（p.188）很現實：**
> "This guideline sometimes trades off against using too much hierarchy that makes logic
>  difficult to trace and wastes designer time declaring ports. **We have reviewed a
>  commercial microprocessor that has approximately 200 substantial modules averaging
>  about 4,000 lines each.**"

**階層太少難讀，太多則追訊號困難又浪費時間宣告埠。**
那個商用處理器的數字（200 個模組、平均 4000 行）可以當參考尺度。

**Guideline 4.36 的具體例子（p.189）：**
> "For example, SystemVerilog has constructs called *functions* and *tasks* that resemble
>  function calls in C rather than hardware modules. These can be useful in testbenches,
>  but **our coding style avoids them in synthesizable blocks.**"

**`function` 和 `task` 在可合成區塊中避免使用**——因為它們看起來像函式呼叫，
會誤導讀者以為是軟體（呼應 4.2.1 的 instantiate vs call）。

**邊欄的平衡觀點（p.188 邊欄）：**
> "Industrial code often uses behavioral style in datapaths when the designers and readers
>  are experienced enough to readily visualize the hardware implied."

**業界的資料通路也常用行為描述——前提是所有人都能看見隱含的硬體。**

### 可組態硬體（Guidelines 4.37–4.42）

呼應 4.2.5 節：

| Guideline | 規則 |
| --- | --- |
| 4.37 | **適當時定義通用的可組態模組**（mux、flop，也包括 MMU、cache 元件等複雜共用區塊） |
| 4.38 | **用 parameter structure 傳參數給頂層和子模組**；頂層從 `config.vh` 讀參數 |
| 4.39 | 個別模組的參數用 `#parameter` 定義 |
| **4.40** | **不論功能有沒有啟用，模組介面都應保持相同** |
| 4.41 | 省略條件產生與產生迴圈外的 `generate`/`endgenerate` 關鍵字 |
| 4.42 | **generate 區塊含有實例或訊號宣告時，在 `begin` 後加冒號命名該區塊** |

**Guideline 4.40 的理由（p.189）：**
> "Tie unused outputs to 0 with a conditional generate statement. **Avoid using `ifdef to
>  omit unused signals entirely; simulation files are more difficult to write when signals
>  don't exist in certain configurations.**"

**這就是 4.2.5.1 節「綁 0 而不是 `` `ifdef ``」的規範化版本。**
關鍵理由是**模擬檔案（testbench）在訊號有時存在有時消失的情況下很難寫**。

**Guideline 4.41 作者自己承認有爭議（p.189）：**
> "Brevity! This is a controversial guideline; some teams require generate/endgenerate."

**Guideline 4.42 的理由（p.189）：**
命名 generate 區塊，**除錯時訊號或實例才有一致的名字可用**
（呼應 4.2.5.3：不命名的話會變成 `top.genblk0.mdu`）。

### 註解（Guidelines 4.43–4.44）

**Guideline 4.43：每個檔案開頭放 banner 註解**，
包含檔名、作者姓名與 email、日期、模組用途、授權。
**"Including your name and date establishes your copyright ownership."**（p.189）

**Guideline 4.44：註解解釋大局，不要複述程式碼在做什麼**（p.189–190）
> "Comments at the beginning of a module that explain the principles of operation are most
>  valuable. **Good variable name choices eliminate the need for many line-by-line
>  comments.**"

**書上給的對照非常好（p.190）：**
```systemverilog
// Bad Example:
assign ab = ~a;          // Flip the bits
assign minusa = ab + 1;  // Add one

// Good example:
assign minusa = ~a + 1;  // Take the 2's complement to negate a
```
**壞例子逐行解釋「做了什麼」（看程式碼就知道），
好例子解釋「為什麼」（這是在取二補數做負號）。**

## 名詞表

| 名詞 | 意思 |
| --- | --- |
| flatcase / camelCase / **UpperCamelCase** / snake_case / MACRO_CASE | 五種大小寫慣例。Wally：`clk`/`reset` 用 flatcase、**訊號用 UpperCamelCase**、常數用 MACRO_CASE |
| Pipeline 級後綴 | F、D、E、M、W。**pipeline 外的訊號沒有後綴** |
| 跨級元件的命名 | pipeline 內產生 → 用產生它的級；**pipeline 外產生（hazard 單元）→ 用會被使用的級** |
| 來源前綴 | 全大寫縮寫的來源單元（IEU、IFU、LSU、FPU、SC、MDU） |
| Top-level module | 設計階層最高的模組，通常是結構化的 |
| Wrapper module | 把訊號映射到目標介面（如 FPGA 接腳）的模組 |
| Clock domain crossing | 跨時脈域傳訊號。本書範圍外 |
| `function` / `task` | 類似 C 函式呼叫的構造。**testbench 可用，可合成區塊避免** |

## 所以呢

**44 條規範裡，真正會影響正確性的是這幾條：**
1. **Guideline 4.4–4.5：pipeline 級後綴與來源前綴**——
   讀 Wally 程式碼的必要知識，`IEUResultM` = IEU 在 Memory 級產生的 Result。
   **跨級元件的命名規則（hazard 單元用「會被使用的級」）是 bug 高發區。**
2. **Guideline 4.26：同步設計**——只用正緣正反器、標準記憶體、組合邏輯，共用一個 `clk`。
3. **Guideline 4.40：模組介面不隨組態改變**——用綁 0 而非 `` `ifdef ``，
   否則 testbench 沒法寫。
4. **Guideline 4.6：宣告所有訊號**——避免打錯字變成新的 1-bit 訊號。

其餘的排版規則照做即可，而且作者自己說了：**必要時可以打破。**

下一節（4.4）講 Wally 的組態檔怎麼組織。
