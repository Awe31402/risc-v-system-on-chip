# 13.4 Summary

> 原書 p.576–577（Chapter 13: Instruction Fetch Unit）

## 這節在講什麼

第 13 章總結，五段。

**結構是「IFU 的組態光譜 → 三個預測元件各一段 → 整合與恢復」。**

**最有價值的是它把三個預測元件的「各自解決什麼問題」再說了一次，
而且用了一個很精準的框架。**

## 關鍵點

### IFU 的組態光譜

> "**Like the LSU, the IFU is highly configurable. In the simplest configuration, it has only an IROM, PC + 4 logic,
>  and a branch multiplexer. In the most sophisticated configuration, it interfaces to the EBU for main memory access,
>  has an instruction cache to service most accesses, and contains an MMU with PMA and PMP physical address checkers
>  and a TLB for virtual to physical address translation. Moreover, the IFU adds a branch predictor.
>  The full PC logic chooses the next program counter from one of PC + 4, the predicted BTA, the trap vector, or the
>  trap return address.**"
> — p.576

中文解釋：**兩個極端，和 LSU 完全平行（呼應 12.7 節）：**

| | **最簡單** | **最完整** |
| --- | --- | --- |
| 記憶體 | **只有 IROM** | **I$ + EBU** |
| 位址檢查 | 無 | **MMU（PMA + PMP + TLB）** |
| PC 邏輯 | **PC + 4 + 一個分支多工器** | **四選一：PC + 4、預測的 BTA、trap vector、trap 返回位址** |
| 預測 | 無 | **分支預測器** |

**「PC 邏輯選四種下一個 PC」這個總結很清楚**——
對應 13.3.2 節那條多工器鏈的四個最終來源。

### Gshare：方向預測

> "**Gshare is a widely-used and reasonably effective branch predictor. It maintains a PHT of 2-bit branch predictions.
>  It also adds a GHR that tracks the direction of recent branches. The PHT is indexed with an XOR of the least
>  significant bits of the PC and the GHR, so it can make predictions that depend on both the branch being executed
>  and the history of recent branch directions. The branch predictor takes some time to warm up the PHT.
>  After warming up, a PHT with 4-Ki-entries achieves accuracy around 96%.**"
> — p.576

中文解釋：**三個要素再確認一次：**
1. **PHT（2-bit 預測）**
2. **GHR（最近分支的方向）**
3. **索引 = PC 低位元 ⊕ GHR**

**效果：「依賴『執行的是哪個分支』和『最近的分支歷史』兩者」——
這一句把 Gshare 的價值講得很精準。**

**「需要暖機」和「4 Ki 項約 96%」是兩個要記住的實務數字。**

### BTB：目標位址預測

> "**The branch predictor needs to provide the predicted BTA in the Fetch stage to update the PC even though the Wally
>  pipeline does not determine the actual target address until the Execute stage. Therefore, the branch predictor
>  adds a BTB, which caches the target address of recent branches. It can be viewed as a direct-mapped cache indexed
>  by the less significant bits of the PC.**"
> — p.576

中文解釋：**BTB 存在的理由講得最清楚：**

**「Fetch 級就需要 BTA 來更新 PC，但 pipeline 要到 Execute 級才算出真正的目標位址。」**

**這個「需要的時間」和「知道的時間」之間的落差，就是 BTB 的存在理由。**
（同樣的落差邏輯也適用於方向預測器和 IC 預測器。）

### RAS：函式返回

> "**When a function is called from multiple places in a program, a standard BTB is not good at predicting where to
>  return. However, a RAS that tracks the return addresses of recent function calls can easily determine the return
>  address.**"
> — p.576

中文解釋：**問題的本質再確認：**
**「同一個函式從程式的多個地方被呼叫」→ 同一條 `ret` 的目標位址每次不同
→ BTB（只記一個位址）沒用 → 需要堆疊。**

### 整合與恢復

> "**The complete branch predictor includes a Gshare direction predictor, BTB, and RAS. The true branch outcome is
>  calculated in the Execute stage. If the prediction was wrong, the pipeline must flush the incorrectly fetched
>  instructions and restart at the true address. The predictor also updates the BHT/PHT, GHR, BTB, and RAS based on
>  the branch outcome. Subtle logic is needed to handle stalls and flushes and to repair incorrect predictions.**"
> — p.577

中文解釋：**最後一句是全章的誠實註腳：**

**「需要微妙的邏輯來處理 stall 和 flush，以及修復錯誤的預測。」**

**回顧 13.3 節，那些「微妙的邏輯」具體是：**

| 機制 | 解決什麼 |
| --- | --- |
| **延遲到 Memory 級更新** | **被 flush 的分支不能更新預測器** |
| **GHR forwarding** | **GHR 落後 PC 四個週期** |
| **方向 forwarding** | 在飛的分支索引相同時要用最新預測 |
| **RAS 的三種修復** | **pop 發生在 Fetch 級，但「是不是 return」要到 Decode 級才知道** |
| **`NextValidPCE` 選擇** | 先前的誤預測讓 `PCE` 可能無效 |

**四個更新目標：BHT/PHT、GHR、BTB、RAS。**

### 三個預測元件的統一框架

中文解釋：**把三段整合起來，可以歸納出一個共同的模式：**

| 預測器 | 需要答案的時間 | 真正知道的時間 | 落差 |
| --- | --- | --- | --- |
| **方向預測器** | **Fetch 級** | **Execute 級** | 2 級 |
| **BTB** | **Fetch 級** | **Execute 級** | 2 級 |
| **IC 預測器** | **Fetch 級** | **Decode 級** | 1 級 |
| **RAS** | **Fetch 級** | **Decode 級**（是不是 return） | 1 級 |

**所有預測器解決的都是同一個問題：「必須現在決定，但答案稍後才知道」。**

**而所有的複雜度都來自同一個後果：
「稍後發現猜錯時，要能正確地恢復」。**

## 所以呢

**第 13 章給處理器加上了分支預測。三件最該帶走的事：**

1. **三個預測元件解決三個不同的問題**：
   **Gshare 答「會不會跳」（4 Ki 項約 96%）、
   BTB 答「跳去哪」（256 項就 99.7%）、
   RAS 答「函式返回跳去哪」（3–16 項就夠）。**

2. **所有預測器的本質都一樣**：
   **Fetch 級必須決定下一個 PC，但真正的答案要到 Decode 或 Execute 級才知道。**
   落差越大，猜錯的代價越高。

3. **複雜度不在「怎麼猜」，而在「猜錯了怎麼恢復」**：
   **延遲更新（避免 flush 的分支汙染預測器）、
   GHR forwarding（補上在飛的分支）、
   RAS 修復（pop 和確認之間的落差）。**

**還有一個貫穿第 12、13 章的對稱性：
IFU 和 LSU 的結構幾乎一樣（cache、MMU、匯流排介面、stall、Committed），
IFU 多了 PC 邏輯和分支預測器，少了寫入、subword 和端序邏輯。**
