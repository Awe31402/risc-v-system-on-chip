# 2.3 Have a Hart

> 原書 p.45–51（Chapter 2: Introduction to RISC-V）
> 涵蓋 2.3.1–2.3.6 全部子節

## 這節在講什麼

從「指令怎麼編碼」跳到「程式怎麼在系統裡跑」。核心概念是 **hart**（hardware thread）。

這節要建立一整套詞彙的層級關係，很容易搞混，所以先把地圖畫出來：

```
process（行程）── 一個執行中的程式，有自己的記憶體空間
  └─ software thread（軟體執行緒）── 共用記憶體，OS 排程
       └─ virtual hart（虛擬 hart）── OS 給每個軟體執行緒一個
            └─ physical hart（實體 hart）── 硬體真的有的那些 context
                 └─ core（核心）── 含功能單元；一個 core 可有多個 physical hart
```

另外三件事：**privilege mode**（M/S/U 三層特權）、
**trap**（例外和中斷的統一處理機制）、
**execution environment**（程式跑在什麼環境上：裸機、OS、還是模擬器）。

**這節是第 8 章（Privileged Operations）的預告片**，概念先建立，細節後面補。

## 關鍵點

### Hart = hardware thread 的縮寫，而且不一定是硬體

> "A *hardware thread* has physical registers containing its context (values of the
>  program counter and registers) and hardware to fetch and execute instructions
>  independently of other hardware threads."
> — p.45

> "A RISC-V *hart* is an abstraction of a *ha*rdware th*r*ead. A hart may be physical,
>  virtual, or simulated."
> — p.45

> "From the program's perspective, all of these kinds of harts are indistinguishable
>  from a true hardware thread except, perhaps, in performance."
> — p.45

中文解釋：**hart 這個字是 HARdware Thread 拼出來的**（書上用斜體標出 ha...r...t）。

**為什麼要發明這個字，而不直接說「核心」或「執行緒」？**
因為 ISA 規格需要一個詞來指「**一個獨立執行指令的東西**」，
而不管它實際上是真硬體、OS 分時模擬的、還是 QEMU 模擬出來的。

三種 hart：
- **physical hart**：硬體真的有一套 PC + 暫存器 + CSR
- **virtual hart**：OS 把多個虛擬 hart 分時映射到較少的實體 hart 上
- **simulated hart**：模擬器（Spike、QEMU）在別的 ISA 的機器上模擬出來的

**最後那句是關鍵**：對程式來說三者無法區分，**只有效能會不一樣**。
這就是抽象的價值——同一份程式在真晶片和在 QEMU 上跑，行為完全一致。

### 三個特權模式：M / S / U

> "*Privilege modes* provide security and prevent programs from interfering with
>  each other. RISC-V harts may run in machine, supervisor, or user privilege modes."
> — p.46

> "RISC-V processors boot in *machine mode*, which is the highest privilege mode and
>  has full control over all processor capabilities."
> — p.46

> "For example, whereas an OS such as Linux typically runs in supervisor mode,
>  application programs run in user mode. A malicious program shouldn't be able to
>  modify the OS or steal data from another program. Thus, the user-level program
>  can only invoke the OS through a *system call* using the ecall instruction, which
>  causes a trap, transferring control to the OS trap handler."
> — p.46

中文解釋：三層權限，由高到低：

| 模式 | 誰在跑 | 權限 |
| --- | --- | --- |
| **M-mode**（machine） | 韌體 / 最底層 | 最高，完全控制 |
| **S-mode**（supervisor） | OS 核心（如 Linux） | 中，可管記憶體與 CSR |
| **U-mode**（user） | 應用程式 | 最低 |

**兩個要記住的事實：**
1. **開機時一定在 M-mode。** 這很合理——開機時還沒有 OS，需要完全控制權。
   S 和 U 模式是**選配的**（"Processors may also optionally support..."）。
   簡單的嵌入式處理器可以只有 M-mode。
2. **往上升級權限的唯一途徑是 trap。**
   使用者程式想叫 OS 做事，只能用 `ecall` 觸發 trap，
   由 OS 的 trap handler 檢查參數後決定要不要做
   （"validates the parameters to reject illegal requests, such as opening a file
   for which the program lacks permission"，p.46）。

**這就是作業系統安全的硬體基礎**：不是靠軟體自律，是靠硬體不讓你直接跳進 OS 的程式碼。

### CSR：每個特權模式各有一組

> "Each privilege mode is associated with a set of CSRs that holds information such
>  as flags from a floating-point operation, which RISC-V features are enabled, and
>  where to go when a trap occurs. The CSRs also include performance counters to
>  track things such as the number of cycles the processor has run, the number of
>  instructions that have retired (i.e., finished successfully), and other
>  implementation-dependent data."
> — p.46

中文解釋：CSR（Control and Status Register，控制與狀態暫存器）是**通用暫存器之外的另一組暫存器**，
放「機器的狀態」而不是「程式的資料」。

裡面裝三類東西：
1. **狀態旗標**（例如浮點運算的例外旗標）
2. **設定**（哪些功能啟用、trap 發生要跳去哪）
3. **效能計數器**（跑了幾個週期、retire 了幾條指令）

**"retired" 這個詞要記住**：指令「退休」= 成功執行完畢並確定生效。
在亂序處理器裡，執行完 ≠ 退休（可能被推測執行後丟棄），第 14 章會很重要。

CSR 是按特權模式分組的：M-mode 的 CSR 名字以 m 開頭（`mepc`、`mtvec`），
S-mode 的以 s 開頭（`sepc`、`stvec`）。**高權限模式看得到低權限的 CSR，反之不行。**

書上邊欄有個值得注意的提醒（p.46 邊欄）：
"The RISC-V Privileged Specification...is longer and more complex than the main
instruction set specification." ——**特權規格比主指令集規格還長還複雜。**
這很反直覺：基礎指令只有 40 條，但讓多個程式安全共存的機制非常龐大。

### Process、thread、core、hart 的層級關係

> "A *process* is a running program. In an application processor with a multitasking
>  OS, each user process generally has the illusion of owning the entire computer
>  even though there are usually more processes than cores."
> — p.46

> "A process may be divided into one or more *software threads* that share a common
>  memory and code space."
> — p.46

> "A *core* is an individual processor on a chip that fetches and executes instructions.
>  At a minimum, it includes the context (PC, registers, and CSRs) and functional
>  units needed to run a thread."
> — p.47

中文解釋：**process 和 thread 的差別在「記憶體共不共用」**：
- **process**：各自有獨立記憶體，彼此不能直接干擾（除非明確要求共享區）
- **thread**：**共用記憶體和程式碼空間**，所以溝通便宜但要自己處理同步

Fig. 2.5（p.47）畫了一個 core 跑兩個 process、每個 process 兩個 thread 的圖：
Process 0（文書處理）有「列印」和「編輯」兩個 thread，
Process 1（影片編輯）有「算第 i 格」和「算第 i+1 格」兩個 thread。
**圖上只有 Thread 0 被標示為正在 core 上執行**——
這就是分時的意思："Only one thread (in this case, Thread 0...) runs on the core
at any given time."（p.47）

書上給的兩個使用 thread 的理由（p.47）：
1. **一個程式要同時做好幾件事**（文書處理一邊列印一邊讓你編輯）
2. **提升效能**（影片編輯在多核上同時算很多格）

常見的實作是 **POSIX threads（pthreads）**（p.47）。

### Multithreaded 與 multicore 的差別

> "A *multithreaded* core has multiple copies of the PC and registers so that it can
>  quickly switch between executing one thread and another by multiplexing between
>  the contexts for each thread while sharing the common execution units.
>  A *multicore* processor has two or more cores on the same chip, along with an
>  interconnection network and usually an upper-level cache."
> — p.47

中文解釋：**這兩個詞很容易混，差別在「複製了什麼」：**

| | 複製了什麼 | 沒複製什麼 |
| --- | --- | --- |
| **Multithreaded core** | PC、暫存器、CSR（context） | **功能單元是共用的** |
| **Multicore** | 整個 core（含功能單元） | 通常共用上層 cache 和互連網路 |

**multithreaded 便宜但只能提升利用率**（某個 thread 卡住時換另一個上，功能單元不閒置）；
**multicore 貴但是真的平行**。

Fig. 2.6（p.48）三張圖畫得很清楚：
- **(a) multicore**：4 個 core，每個含一套 PC/RF/CSR + Functional Units = 4 個 physical hart
- **(b) 2-way multithreaded cores**：4 個 core，**每個 core 裡有兩套 PC/RF/CSR
  但只有一組 Functional Units** = 8 個 physical hart
- **(c) virtual harts**：記憶體裡躺著很多組 PC/RF/CSR（由 OS 管理），
  箭頭指向 8 個 physical hart，表示 OS 把它們輪流載進去跑

書上給的 hart 計數規則（p.47）：
- multicore：**每個 core 是一個 physical hart**
- k-way multithreaded core：**每個 core 有 k 個 physical hart**
  （4 核 × 2-way = 8 個 physical hart）
- OS 為每個使用者軟體執行緒建一個 **virtual hart**，分時映射到 physical hart 上

**context switch 的定義也在這裡**（p.47）：
OS scheduler 收到計時器中斷 → 把目前 virtual hart 的 context 存到記憶體 →
把下一個 virtual hart 的 context 載進來。**每幾毫秒發生一次。**

順帶記一個 SoC 術語（p.47 邊欄）：微處理器常分成
**core**（核心）和 **uncore**（非核心：周邊、共享記憶體、上層 cache、外部介面）兩部分。

### Trap：例外和中斷的統一機制

> "In RISC-V, an *exception* is an unusual condition caused by a program, such as an
>  illegal instruction, an access to nonexistent memory, or an OS call.
>  An *interrupt* is an asynchronous external event such as a timer reaching some
>  trip point or a serial port indicating that a new piece of data has arrived.
>  Both exceptions and interrupts cause a *trap*, which is a transfer of control from
>  the current program to a *trap handler*."
> — p.49

中文解釋：**三個詞的關係一定要分清楚：**

| 詞 | 意思 | 來源 |
| --- | --- | --- |
| **Exception**（例外） | 程式造成的異常狀況 | **內部、同步**（非法指令、存取不存在的記憶體、`ecall`） |
| **Interrupt**（中斷） | 外部非同步事件 | **外部、非同步**（計時器到點、序列埠收到資料） |
| **Trap**（陷阱） | **上面兩者共同的處理機制**：轉移控制權到 trap handler | — |

**關鍵區分是「同步 vs 非同步」**：
exception 是「這條指令做了不該做的事」，時間點可預測；
interrupt 是「外面發生了事」，隨時可能來。

**但硬體用同一套機制處理**——這就叫 trap。這是很漂亮的統一。

### Trap 發生時，硬體做了什麼

> "When a trap to machine mode occurs, the current program counter is stored in the
>  *machine exception program counter* (mepc) CSR. A code indicating the trap's cause
>  is stored in the *machine cause* (mcause) CSR. Supplementary information, such as
>  the illegal instruction or illegal address being accessed, may be stored in the
>  *machine trap value* (mtval) CSR. The processor changes to machine mode and jumps
>  to the address specified by the *machine trap-vector base-address* (mtvec) CSR."
> — p.49

中文解釋：**這是 trap 的完整動作，第 8 章會實作，值得背下來：**

| CSR | 存什麼 | 白話 |
| --- | --- | --- |
| **mepc** | 目前的 PC | **回家的路** |
| **mcause** | trap 原因代碼 | **為什麼來** |
| **mtval** | 補充資訊（非法指令內容、非法位址） | **細節** |
| **mtvec** | trap handler 的位址 | **要去哪**（這個是預先設定的，不是 trap 時寫入的） |

動作順序：存 mepc → 存 mcause → 存 mtval → **切到 M-mode** → 跳到 mtvec。

S-mode 的 trap 完全對稱，只是換前綴：**`sepc`、`scause`、`stval`、`stvec`**（p.49）。

**回程用 `mret` / `sret`**：
"returns to the address in mepc or sepc and restores the previous privilege level."（p.49）
——注意 `mret` 做**兩件事**：跳回去，**而且降回原本的特權等級**。
少做第二件事就是安全漏洞。

trap handler 做的事舉例（p.49）：執行 OS 呼叫、把序列埠新資料放進緩衝區、
或是終止那個執行了非法指令的程式。

### Execution Environment：程式跑在什麼上面

> "A hart runs within an *execution environment* (EE) such as an OS. An *execution
>  environment interface* (EEI) allows programmers to interact with its EE and
>  defines the initial state of the program, the number and types of harts, including
>  the privilege modes and instruction set they support, the memory map, and how traps
>  are handled."
> — p.49

> "The simplest EE is *bare metal*, in which the processor runs in machine mode with
>  no OS. The programmer has direct access to all features and memory. Physical harts
>  directly correspond to physical cores. There are no virtual harts and no protection
>  between programs."
> — p.49

中文解釋：**EE 就是「你的程式底下墊著什麼」。**
EEI 是這層的契約，規定了：初始狀態、有幾個什麼樣的 hart、記憶體映射、trap 怎麼處理。

**bare metal（裸機）是最簡單的 EE**：沒有 OS、全程 M-mode、沒有保護、
physical hart 直接對應 physical core。
**這本書前半部做的 Wally 就是從這裡開始**——先不管 OS，直接跑。

### ABI 和 SBI：兩層介面

> "Fig. 2.7 shows two common EEIs, an *application binary interface* (ABI) and a
>  *supervisor binary interface* (SBI). An ABI enables applications to interact with
>  their EE, and an SBI enables the OS to interact with its EE, also called its
>  runtime environment: peripherals, timers, and so on."
> — p.50

> "The SBI allows the same OS to run on different RISC-V chips by only modifying the
>  platform runtime firmware."
> — p.50

中文解釋：Fig. 2.7（p.50）畫了三層堆疊，**由上而下**：

```
Application 1 ... Application N        (U-Mode)
         ↕  ABI（system calls）
OS: Operating System Kernel            (S-Mode)  ← 這層是應用程式的 EE
         ↕  SBI（SBI calls）
Platform Runtime Firmware              (M-Mode)  ← 這層是 OS 的 EE
```

**每一層都是下一層提供的 EE。** 兩個介面各自解決一個移植問題：
- **ABI**：讓應用程式不用管是哪個 OS 版本（系統呼叫介面穩定）
- **SBI**：**讓同一份 OS 能跑在不同的 RISC-V 晶片上，只要換韌體**

第二點特別重要——它是 RISC-V 生態系能運作的關鍵。
沒有 SBI，每顆晶片都要改 Linux 核心。

補充：OS（kernel）跑在 S-mode，替每個應用程式提供**自己的虛擬記憶體空間**，
所以應用程式之間不會互相干擾（p.50）。
ABI 定義的系統呼叫用來管理行程、記憶體、檔案、以及使用者層執行緒的同步（第 3.3.3 節）；
SBI 用來存取周邊和服務，例如設定系統計時器、啟動/停止/同步核心（第 3.3.4 節）。

系統呼叫的實際做法（p.50）：**參數放 a0–a7，然後執行 `ecall`**。
`ebreak` 則是交給除錯器。兩者都跳到 `mtvec` 或 `stvec` 指的 handler。

### 模擬器 vs 模擬機，以及它們的速度差距

> "A purely software EE is a RISC-V *simulator* or *emulator*, such as Spike, Sail,
>  or QEMU, which runs RISC-V programs on underlying hardware such as an x86-based
>  computer. In this case, there are no physical RISC-V cores, so the harts are
>  simulated."
> — p.51

> "Sometimes the term *simulator* is used for a tool that models only the harts and
>  RAM, while an *emulator* also models *peripherals*, that is, input/output (I/O)
>  devices such as keyboards, serial UART connections, and so forth."
> — p.51

> "Whereas fast simulators such as QEMU use *binary translation* to convert a program
>  from the instruction set being simulated to the native instruction set, simpler
>  simulators interpret programs one instruction at a time. QEMU runs approximately
>  1 billion instructions per second. Spike runs about 100 million instructions per
>  second. Sail is focused on provable correctness rather than performance and runs
>  only about 1 million instructions per second."
> — p.51

中文解釋：**simulator vs emulator 的區分**：
simulator 只模擬 hart 和 RAM；**emulator 還模擬周邊**（鍵盤、UART 等）。
按這個定義：**Spike 是 simulator，QEMU 和 Sail 是 emulator**
（它們模擬 CLINT 計時器、PLIC 中斷控制器、UART——開 Linux 需要的東西）。
但書上也說 simulator 常被當通稱用。

**速度差距是 1000 倍，而且理由不同，這張表很實用：**

| 工具 | 速度 | 手法 / 定位 |
| --- | --- | --- |
| **QEMU** | ~10 億指令/秒 | **binary translation**（把 RISC-V 翻成 x86 原生碼再跑） |
| **Spike** | ~1 億指令/秒 | 逐條解譯 |
| **Sail** | ~100 萬指令/秒 | **重點是可證明的正確性**，不是速度 |

**選工具的判準就在這張表**：要快用 QEMU，要當黃金參考模型用 Spike，
要形式驗證用 Sail。第 3 章會實際用到這三個。

最後書上舉了一個混合 EE 的例子（p.51）：
硬體沒有 FPU 時，跑到浮點指令會觸發 illegal-instruction exception，
**由 exception handler 用軟體算完浮點再繼續**。
使用者程式完全不知道發生了什麼——這就是 EE 抽象的力量。

## 名詞表

| 名詞 | 意思 |
| --- | --- |
| Hart | HARdware Thread。獨立執行指令的抽象單位；可為 physical / virtual / simulated |
| Privilege mode | 特權模式。M（machine）> S（supervisor）> U（user）；開機在 M-mode |
| CSR | 控制與狀態暫存器。存旗標、設定、效能計數器；按特權模式分組 |
| Retired | 指令退休 = 成功執行完畢並生效 |
| Process / software thread | 行程（獨立記憶體）/ 軟體執行緒（共用記憶體與程式碼空間） |
| Core / uncore | 核心（取指令並執行）/ 非核心（周邊、共享記憶體、上層 cache、外部介面） |
| Multithreaded core | 複製多份 context（PC/暫存器），但共用功能單元 |
| Multicore | 同晶片上多個完整 core，加互連網路與上層 cache |
| Context switch | 上下文切換。存下目前 virtual hart 的 context，載入下一個 |
| Exception / Interrupt / Trap | 例外（程式造成、同步）/ 中斷（外部、非同步）/ 兩者共同的控制權轉移機制 |
| mepc / mcause / mtval / mtvec | 回家的路 / 原因 / 補充資訊 / handler 位址（S-mode 對應 sepc/scause/stval/stvec） |
| `mret` / `sret` | 從 trap 返回，跳回 mepc/sepc 並還原原本的特權等級 |
| EE / EEI | 執行環境 / 執行環境介面 |
| Bare metal | 裸機。無 OS，全程 M-mode，無保護 |
| ABI / SBI | 應用程式二進位介面（app↔OS）/ 監督者二進位介面（OS↔韌體） |
| Binary translation | 二進位翻譯。QEMU 把被模擬的指令翻成原生指令來加速 |

## 所以呢

**這節建立了「程式在哪裡跑」的整套詞彙：hart 是執行單位、
三層特權模式提供隔離、trap 是唯一的跨層通道、EE 決定底下墊著什麼。**
最實用的兩樣：**trap 的四個 CSR（mepc/mcause/mtval/mtvec）**——第 8 章要實作；
以及**三個模擬器的速度與定位**——第 3 章馬上要用。
