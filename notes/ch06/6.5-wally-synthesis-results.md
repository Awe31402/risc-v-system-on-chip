## 關鍵點

### 為什麼要用衍生組態

> "The primary configurations have large memories, so they can run arbitrary test programs during
>  logic verification. For example, **rv32i has an 8-MiB DTIM. Design Compiler does not gracefully
>  build such a large memory from flip-flops. The runtime and memory are huge, and the synthesis
>  usually fails.** Therefore, we use derived configurations, that is, configurations with some
>  tweaks such as smaller memories."
> — p.287

中文解釋：**問題很實際：主組態的記憶體太大（8 MiB DTIM），
Design Compiler 用正反器做不出來——執行時間和記憶體用量爆炸，而且通常失敗。**

（呼應 6.2.3 節：flop bit cell 是 1.89 μm²，8 MiB = 6700 萬 bit，
用正反器做要 1.27 億 μm²。顯然不可行。）

**Table 6.6（p.288）的三組衍生組態：**

| 衍生組態 | 基礎 | 調整 |
| --- | --- | --- |
| `syn_rv32e`、`syn_rv32i`、`syn_rv32imc`、`syn_rv32gc`、`syn_rv64i`、`syn_rv64gc` | 各基礎組態 | **縮小記憶體尺寸**（依 Table 6.7），讓沒有 SRAM 的製程也跑得動 |
| `syn_sram_rv32e` … `syn_sram_rv64gc` | 同上 | **TSMC28 使用 SRAM 庫** |
| `syn_rv64gc_pmp0`、`syn_rv64gc_noPriv`、`syn_rv64gc_noFPU`、`syn_rv64gc_noMulDiv`、`syn_rv64gc_noAtomic` | 逐層衍生 | **逐步關掉功能以探索關鍵路徑** |
| `syn_sram_rv64gc_*`（同上五個） | | 同上，但使用 SRAM 庫 |

**注意第三組是「逐層衍生」**：
`noPriv` 基於 `pmp0`、`noFPU` 基於 `noPriv`、`noMulDiv` 基於 `noFPU`……
**每一步只關掉一樣功能，這樣才能歸因。**（6.5.4 節會用。）

**Skywater 和 TSMC 的差別（p.287）：**
- **Skywater 的 `syn_*`：縮小 DTIM、IROM、cache 和分支預測器記憶體**（因為沒有 SRAM）
- **TSMC 的 `syn_sram_*`：只縮小 DTIM/IROM，cache 和分支預測記憶體用 SRAM 做**

### Table 6.7：核心記憶體組態

中文解釋：**Table 6.7（p.289）列出每個組態的記憶體。摘要：**

| 元件 | 組態 | USESRAM | 大小 | 實作 |
| --- | --- | --- | --- | --- |
| **D$, I$** | rv{32/64}gc | **0** | 每個 1 way、512 B/way、8 條 64B line | **rv32gc: 4,272 flops；rv64gc: 4,448 flops**（×2 caches） |
| | | **1** | 每個 4 ways、4 KiB/way、64 條 512-bit line | **4 個 `ram1p1rwbe_64x128` + 1 個 `ram1p1rwbe_64x44`**（×4 ways ×2 caches） |
| **BHT** | rv{32/64}gc | 0 | 2⁵ entries × 2 bits | 64 flops |
| | | 1 | **2¹⁰ entries × 2 bits** | 1 個 `ram2p1r1wbe_64x32` |
| **BTB** | rv{32/64}gc | 0 | 2⁵ entries × 36 或 68 bits | 1,152–2,176 flops |
| | | 1 | **2¹⁰ entries × 68 bits** | 1 個 `ram2p1r1wbe_1024x68` |
| DTIM | rv32i, rv32imc | N/A | 128 words × 32 bits | 4,096 flops |
| | rv64i | N/A | 64 words × 64 bits | 4,096 flops |
| DTLB, ITLB | rv{32/64}gc | N/A | 各 32 entries × 61 或 106 bits | 1,952–3,392 flops |
| PMP | rv{32/64}gc | N/A | 16 entries × 64 bits | 1,024 flops |
| **Register File** | **rv32e** | N/A | **16 entries × 32 bits** | **512 flops** |
| | rv32{i/imc/gc} | N/A | 32 entries × 32 bits | 1,024 flops |
| | rv64{i/gc} | N/A | 32 entries × 64 bits | **2,048 flops** |

**兩個觀察：**
1. **USESRAM=1 時 cache 和分支預測器大很多**（BHT 從 2⁵ 到 2¹⁰ entries，32 倍）
   ——**因為 SRAM 便宜，所以可以放更多。**
2. **暫存器檔案的縮放：512 → 1,024 → 2,048 flops**
   （rv32e 的 16 個暫存器省了一半，呼應 2.5 節）

### 掃描目標週期：最佳可達是 28–32 FO4

中文解釋：Fig. 6.21（p.290）是 rv32e 在三種製程下，面積與延遲 vs 目標週期的散佈圖。

**書上的解讀（p.287–289）：**
> "Synthesis achieves its timing goals at long target cycle times, as indicated by the gray dots.
>  **As the cycle time decreases, the area increases slightly because synthesis trades area for
>  faster and more parallel logic. However, Fig. 6.20 shows that 38% of the area is consumed by
>  the register file, with flip-flop area being independent of cycle time, so overall area does
>  not increase too much with frequency.** At shorter cycle times, synthesis is unable to achieve
>  the target cycle time, as indicated by the blue dots. **The achieved cycle time and area
>  plateau at a point nearly independent of the target cycle time**, although there is some
>  synthesis noise resulting in slight variations from one point to another."

**兩個觀察：**
1. **面積隨頻率上升只小幅增加**——因為 **38% 的面積是暫存器檔案，
   而正反器面積與週期無關。**
2. **超過某點後，達成的週期和面積就進入平台期**（呼應 6.2.2 節的方法論）。

**最重要的結論（p.289）：**
> "**Normalizing delay in terms of fanout-of-4 (FO4) inverter delays helps compare designs across
>  processes. The best achievable cycle time is 28-32 FO4.**"

**三種製程下，rv32e 的最佳可達週期都是 28–32 FO4。**
（呼應 2.8.6 節：Wally 各組態是 29–108 FO4。）

**三製程的實際數字對比（p.289）：**
> "**The TSMC28 feature size is about 5 times smaller than SKY130. The area is about 15 times
>  smaller, and the clock period is about 8 times shorter. The best achievable cycle time is
>  similar for all designs when normalized to FO4 delays.**"

| | 比例 |
| --- | --- |
| 特徵尺寸 | TSMC28 是 SKY130 的 **1/5** |
| **面積** | **小 15 倍** |
| **時脈週期** | **短 8 倍** |
| **FO4 正規化後** | **幾乎一樣** |

**Dennard 理論的預測 vs 現實（p.289 邊欄）——這段很有洞見：**
> "**Ideal Dennard scaling would predict that a 5x feature size reduction makes a design 25x
>  smaller and 5x faster; market requirements favor improving performance, typically at a cost of
>  more area.**"

**理想 Dennard：5 倍縮小 → 面積小 25 倍、速度快 5 倍。
實際：面積小 15 倍、速度快 8 倍。
市場要求偏好效能，代價是面積沒省那麼多。**

**（也就是說：設計者把一部分「該省的面積」拿去換「額外的速度」了。）**

### 怎麼跑這些實驗

```bash
$ cd $WALLY/synthDC
$ ./wallySynth.py --freqsweep 330  --tech sky130
$ ./wallySynth.py --freqsweep 870  --tech sky90
$ ./wallySynth.py --freqsweep 2800 --tech tsmc28psyn
$ ./extractSummary.py
```

中文解釋（p.291）：
- **`--freqsweep` 掃描以指定值為中心的一系列目標頻率**（870 MHz = 1.15 ns）
- `wallySynth.py -h` 看更多選項
- **`extractSummary.py` 從所有執行結果產生圖**，放在 `wallyplots/freqsweep*`
- **會出現一些訊息，因為其他實驗還沒跑**

看圖（Linux）：`$ feh wallyplots/freqSweep_sky90_rv32e.png`

**兩個工具提示（p.291 邊欄）：**
- **`wallySynthAll.py` 自動跑完本節所有模擬**
- **`extractSummary.py` 需要 Python 套件：`matplotlib`、`scipy`、`sklearn`、`adjustText`**

### `--maxopt`：兩個最佳化開關

> "Fig. 6.22 shows the same results when the `--maxopt` flag is added to the wallySynth.py
>  invocation. **Curiously, TSMC28 gets markedly faster, but SKY90 does not improve much.**
>  The `--maxopt` flag turns on the following Design Compiler optimizations to get better area and
>  delay at the cost of more runtime:
>  - **`flatten`**: Allow optimizations across all modules but lose module names
>  - **`optimize_registers`**: Move logic across pipeline stages to improve critical paths"
> — p.291

中文解釋：**兩個最佳化的意義：**

| 選項 | 做什麼 | 代價 |
| --- | --- | --- |
| **`flatten`** | 跨所有模組最佳化 | **失去模組名稱**（報告難讀，呼應 6.1、6.4.2 節） |
| **`optimize_registers`** | **在 pipeline 級之間搬移邏輯**以改善關鍵路徑 | 執行時間長 |

**`optimize_registers` 就是 6.1 節說的「邏輯設計工程師會做的事」的自動化版本
——retiming（重定時）。**

**「TSMC28 明顯變快，但 SKY90 沒什麼改善」**——
書上用了 "Curiously"（奇怪的是），沒有解釋原因。
**這又是一個「對數據保持懷疑」的例子。**

（從 Fig. 6.22 可以看出 TSMC28 的最小週期從約 0.38 降到約 0.32 ns。）

### 掃描組態：rv64gc 比 rv32e 大 72 倍

```bash
$ ./wallySynth.py --configsweep --tech sky130    --targetfreq 1000
$ ./wallySynth.py --configsweep --tech sky90     --targetfreq 3000
$ ./wallySynth.py --configsweep --tech tsmc28psyn --targetfreq 10000 --usesram
$ ./extractSummary.py --sky130freq 1000 --sky90freq 3000 --tsmcfreq 10000
```

中文解釋（p.291）：**「目標頻率設得遠超過可達成的，以估計最小週期。」**
（呼應 6.2.3 節那個 10 GHz 的技巧。）

**Fig. 6.23（p.293）是面積 vs 週期的散佈圖，六個組態各一點。**
**注意 TSMC28 用完整尺寸的 RAM，而 Skywater 用縮小的 flop-based 記憶體。**

**Table 6.8（p.294）各模組面積（μm²，TSMC28，USESRAM=1）——最實用的表：**

| 模組 | rv32e | rv32i | rv32imc | rv32gc | rv64i | rv64gc |
| --- | --- | --- | --- | --- | --- | --- |
| `ifu` | 1,071 | 906 | 1,967 | **208,720** | 1,605 | **221,465** |
| `ieu` | 4,951 | 6,522 | 6,673 | 7,618 | **13,645** | 16,795 |
| `lsu` | 470 | 15,328 | 15,325 | **164,555** | 16,071 | **183,752** |
| `hazard` | 33 | 11 | 56 | 66 | 16 | 70 |
| `ebu` | 294 | | 261 | 318 | | 475 |
| `privileged` | | | 12,040 | 16,001 | | 18,729 |
| `mdu` | | | 8,358 | 4,107 | | 9,883 |
| `fpu` | | | | 31,776 | | **38,575** |
| **Total** | **6,831** | 22,836 | 44,810 | **433,212** | 31,355 | **489,759** |

**書上的解讀（p.294），五個觀察：**
> "**The rv{32/64}gc configurations are far larger than the others because of the large caches and
>  branch predictor. The rv32e IEU is 30% smaller than rv32i because it has 16 rather than 32
>  registers. The rv64 IEU is about twice the size of rv32 because of the wider datapaths.
>  The rv32 and rv64 LSU and FPU are comparable in size because most of the structures are
>  independent of XLEN. In some configurations, a module is more critical than in others and
>  hence trades greater area for greater speed. The full-featured rv64gc application processor is
>  11x larger than the rv32imc embedded core and 72x larger than the minimal rv32e core.**"

1. **gc 組態大很多，因為 cache 和分支預測器**（IFU 和 LSU 各暴增到 20 萬）
2. **rv32e 的 IEU 比 rv32i 小 30%**（16 vs 32 個暫存器）
3. **rv64 的 IEU 約是 rv32 的兩倍**（資料通路寬一倍）
4. **rv32 和 rv64 的 LSU 與 FPU 大小相近**——
   **因為多數結構與 XLEN 無關**（FPU 用 FLEN，LSU 主要是 cache）
5. **rv64gc 是 rv32imc 的 11 倍，是 rv32e 的 72 倍**

### 元件類型的分解

**Table 6.9（p.295）面積（μm²）與 Table 6.10（p.295）元件數：**

| 元件類型 | rv32e 面積 | rv64gc 面積 | rv32e 數量 | rv64gc 數量 |
| --- | --- | --- | --- | --- |
| **RAMs** | 0 | **313,997** | 0 | **42** |
| Flip-flops | 2,866 | 54,878 | 1,180 | 22,404 |
| Inv/Buf | 463 | 15,737 | 1,101 | 34,900 |
| Logic | 3,502 | 105,146 | 4,204 | 143,283 |
| **Total** | — | — | **6,485** | **200,629** |

**書上的三個觀察（p.294）：**
> "**In the rv{32/64}gc configurations, the cache and branch predictor memories account for
>  65%−70% of the area.** These configurations have 42 RAMs: (4 data subarrays and one tag array
>  in each way) × 4 ways/cache × two caches, along with a BHT and BTB. **Flip-flops add 15%−36% to
>  the logic cell count but 60%−100% more area because they are larger than the average logic
>  cell. Inverters and buffers also add 15%−30% to the logic cell count but only 10%−15% more area
>  because they are smaller than the average logic cell.**"

1. **記憶體佔 gc 組態的 65–70% 面積**（呼應 2.8.6 節 Fig. 2.14 的布局圖）
2. **42 個 RAM 的組成**：(4 個資料子陣列 + 1 個 tag 陣列) × 4 ways × 2 caches = 40，加 BHT 和 BTB = 42
3. **正反器數量佔 15–36% 但面積佔 60–100%**（比平均邏輯元件大）；
   **反相器/緩衝器數量佔 15–30% 但面積只佔 10–15%**（比平均小）

### Table 6.11：各組態的關鍵路徑（很有洞見）

中文解釋：**Table 6.11（p.295）列出每個組態的關鍵路徑，這張表值得細看：**

| 組態 | 關鍵路徑 |
| --- | --- |
| **rv32e** | Execute 級：**轉發暫存器 → 比較 → 分支成立 → flush pipeline** |
| **rv32i** | Execute 級：轉發暫存器 → 比較 → 分支成立 → **PC register** |
| **rv32imc** | Execute 級：**轉發暫存器 → 整數乘法** |
| **rv32gc** | **Memory 級：HPTW、VAdr、ReadDataWord、AMO、LineWriteData** |
| **rv64i** | Execute 級：轉發暫存器 → 比較 → 分支成立 → PC register |
| **rv64gc** | **Fetch 級：PMPAdr、PMP check、InstrAccessFault** |

**這張表講了一個故事：隨著功能增加，瓶頸會換位置。**
- **簡單組態**：瓶頸在 **Execute 級的分支路徑**（呼應 6.4.4 節）
- **加了乘法器**：瓶頸變成**整數乘法**
- **加了虛擬記憶體**：瓶頸移到 **Memory 級的位址轉換**
- **完整組態**：瓶頸移到 **Fetch 級的 PMP 檢查**

**書上對 rv64gc 的結果表示意外（p.294 邊欄）：**
> "**The rv64gc path through the PMP checker from the pmpaddr register (signal name: PMPAdr) is
>  unexpected. We anticipate that the PMP path would start with the TLB physical address
>  translation. This is a sign that something might be wrong in the synthesis experiment; it
>  remains an open question at the time of this writing.**"

**「這是合成實驗可能有問題的徵兆，目前仍是未解的問題。」**
——又一次的誠實。（呼應 5 章結尾的謙卑態度。）

**Fig. 2.14（第 2 章那張布局圖）的再解讀（p.294）：**
> "Observe how the RAMs account for most of the area and **how the units that communicate on
>  critical paths are placed close to each other.**"

**布局工具會把關鍵路徑上互相溝通的單元放在一起。**

**`--maxopt` 在 configsweep 的問題（p.294）：**
> "**Synthesizing with --maxopt does not make much difference for the various configurations in
>  rv64gc. It detects that rv32i and rv64i don't drive outputs and, thus, optimizes away the
>  entire processor. It also runs much more slowly and sometimes crashes on designs with
>  flop-based memories.**"

**`flatten` 太激進會把整顆處理器最佳化掉**（因為 rv32i/rv64i 沒有驅動輸出）——
**這是「過度最佳化」的經典陷阱。**

### 掃描功能：關掉功能看誰吃掉資源

```bash
$ ./wallySynth.py --featuresweep --tech sky130     --targetfreq 1000
$ ./wallySynth.py --featuresweep --tech sky90      --targetfreq 3000
$ ./wallySynth.py --featuresweep --tech tsmc28psyn --targetfreq 10000 --usesram
$ ./extractSummary.py --sky130freq 1000 --sky90freq 3000 --tsmcfreq 10000
```

中文解釋：**Table 6.12（p.297）的實驗設計，注意是「累積關掉」：**

| 組態 | PMP Entries | Privileged Unit | FPU | MDU | Atomic Ops |
| --- | --- | --- | --- | --- | --- |
| **orig** | 16 | Y | Y | Y | Y |
| **PMP0** | **0** | Y | Y | Y | Y |
| **noPriv** | 0 | **N** | Y | Y | Y |
| **noFPU** | 0 | N | **N** | Y | Y |
| **noMulDiv** | 0 | N | N | **N** | Y |
| **noAtomic** | 0 | N | N | N | **N** |

**每一列只比上一列多關一樣——所以面積和延遲的差就是那個功能的成本。**

**Fig. 6.24（p.296）是三種製程的結果散佈圖。SKY130 的數字（從圖上讀）：**
- **orig：約 10.1 ns、3,150,000 μm²**
- **PMP0：約 10.0 ns、2,880,000 μm²**（關掉 PMP 省約 27 萬 μm²）
- **noPriv：約 7.8 ns、1,650,000 μm²**（**關掉特權單元省超過一半面積！**）
- noFPU：約 7.9 ns、1,500,000 μm²
- noMulDiv：約 7.9 ns、1,250,000 μm²
- **noAtomic：約 6.1 ns、1,200,000 μm²**

**整體趨勢（p.297）：**
> "**The SKY90 and TSMC28 results generally show the cycle time improving and area shrinking as
>  features turn off. The area benefits are more pronounced on SKY130 and SKY90 because they use
>  tiny flop-based memories; in TSMC28, the large RAMs account for most of the area.**"

**Skywater 的面積效益更明顯，因為它用小的 flop-based 記憶體；
TSMC28 的面積主要是大 RAM，關功能省不了多少。**

**又一個異常（p.297 邊欄）：**
> "**In SKY130, it is unexpected that PMP0 is slower than the baseline design (orig) and that
>  noFPU and noMulDiv are slower than noPriv, calling into question the quality of the library
>  models. Sometimes, you get what you pay for.**"

**「關掉功能反而變慢」是不合理的，質疑元件庫模型的品質。
『有時候一分錢一分貨。』」**——對免費的開源 PDK 的委婉評價。

## 名詞表

| 名詞 | 意思 |
| --- | --- |
| Derived configuration | 衍生組態。縮小記憶體或關閉功能，讓合成跑得動（見 Table 6.6） |
| `--freqsweep` / `--configsweep` / `--featuresweep` | 掃描目標頻率 / 組態 / 功能開關 |
| `wallySynth.py` / `wallySynthAll.py` / `extractSummary.py` | 單次掃描 / 跑完全部 / 產生圖表 |
| **`--maxopt`** | 開啟 `flatten`（跨模組最佳化，失去模組名）與 `optimize_registers`（跨 pipeline 級搬邏輯） |
| `optimize_registers` / retiming | 在 pipeline 級之間搬移邏輯以改善關鍵路徑 |
| USESRAM | 使用 SRAM 庫取代 flop-based 記憶體 |

## 所以呢

**這節提供了 Wally 的實際 PPA 數據，四個最該記住的結論：**

1. **FO4 正規化後，三種製程的最佳可達週期都是 28–32 FO4。**
   TSMC28 相對 SKY130：特徵尺寸小 5 倍、**面積小 15 倍、時脈快 8 倍**
   （理想 Dennard 會預測面積小 25 倍、快 5 倍——**市場偏好用面積換效能**）。

2. **rv64gc 是 rv32imc 的 11 倍、rv32e 的 72 倍。**
   **gc 組態的 65–70% 面積是 cache 和分支預測器的記憶體。**

3. **關鍵路徑會隨組態換位置**（Table 6.11）：
   簡單組態在 Execute 級的分支路徑 → 加乘法器變成乘法 →
   加虛擬記憶體移到 Memory 級 → 完整組態移到 Fetch 級的 PMP 檢查。

4. **`--maxopt` 要小心**：`flatten` 可能把沒驅動輸出的設計整個最佳化掉。
