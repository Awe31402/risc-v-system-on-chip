# 22.3 Booting Linux

> 原書 p.784.e70–784.e76（Chapter 22: Linux）
> 涵蓋 22.3.1 Booting Linux on QEMU、22.3.2 Booting Linux on Wally using a Logic Simulator、22.3.3 Modifying Buildroot

## 這節在講什麼

前兩節講原理和內部細節，這節是實際操作：在 QEMU 上跑（幾秒）、在 Verilog 模擬上跑（20 小時）、以及怎麼改 Buildroot 的設定。

三個平台的時間差距是這節最有資訊量的部分——**同一份 Linux 映像，QEMU 幾秒、FPGA 幾分鐘、RTL 模擬 20 小時**。這個 5 個數量級的差距說明了為什麼驗證流程要分層。

## 關鍵點

### 三個平台的速度差距

> "Linux boots in seconds on the fast QEMU emulator. It takes hours or days to boot Linux on the Wally SystemVerilog code in simulation. Booting Wally on an FPGA takes only minutes"
> — p.784.e70

中文解釋：這正是第 13 章驗證分層的實務理由：

| 平台 | 開機時間 | 用途 |
| --- | --- | --- |
| QEMU | 幾秒 | 快速確認軟體堆疊正確 |
| FPGA | 幾分鐘 | 真實硬體、可以互動、能跑大量測試 |
| Verilog 模擬 | 20 小時 | 唯一能看到每個訊號波形的地方 |

**開發時的正確順序是由快到慢**——軟體問題在 QEMU 上解決，硬體邏輯問題才進模擬。

### QEMU：先把軟體堆疊確認好

> "Our Linux image boots on the QEMU virt platform, which provides software emulation of common hardware such as a UART. It requires the firmware, kernel, root file system, device tree, and CPU configuration passed on the command line. qemuBoot.sh sets all these options to match Wally. These images are loaded into memory before the boot starts so that virt does not have to emulate any mass storage devices."
> — p.784.e70

中文解釋：`cd $WALLY/linux && ./qemuBoot.sh`，打 `root` 登入就能玩。

**注意「映像直接載入記憶體」**——跳過了從 SD 卡讀取的階段。這和 22.2.5 講的「ZSBL 只是跳過去」是同一件事：模擬環境裡不需要真的模擬儲存裝置。第 23 章的 FPGA 才會需要真的從 SD 卡讀。

### 開機訊息裡看得到前面幾章的成果

Fig. 22.3 的 OpenSBI banner 值得對照 22.2 的內容看：

> "Boot HART Base ISA : rv64imafdc / Boot HART ISA Extensions : time,sstc / Boot HART PMP Count : 16 / Boot HART MIDELEG : 0x0000000000001666"
> — p.784.e71

中文解釋：
- `rv64imafdc` = 第 14–18 章那些擴充
- `sstc` = 22.2.11.2 講的計時器優化擴充，**firmware 偵測到硬體有這個功能**
- `PMP Count: 16` = 第 11 章的 PMP
- `MIDELEG` = 22.2 里程碑表裡 `csrw mideleg` 寫進去的值
- `DomainO RegionOO ... M: (I,R,W) S/U: ()` = 22.2.6.3 講的 PMP 保護，**S/U 欄位是空的**

Linux 的訊息也有：`riscv: ISA extensions acdfim`、`plic: plic@c000000: mapped 53 interrupts with 1 handlers for 2 contexts`（正是第 20.3 節的 PLIC 配置）、`riscv-timer: Timer interrupt in S-mode is available via sstc extension`。

### 用 QEMU monitor 檢查記憶體佈局

> "To view the physical addresses of the boot files from Table 22.3, press <Ctrl-a> c to enter the QEMU monitor. Then type info roms"
> — p.784.e73

中文解釋：輸出直接驗證了 Table 22.3：

```
addr=0x1000       size=0x28      name="mrom.reset"     ← ZSBL
addr=0x80000000   size=0x1f7d8   name="fw_jump.elf ..."← OpenSBI
addr=0x80200000   size=0x46a8c00 name="Image"          ← kernel
addr=0x88200000   size=0x3af9c00 name="rootfs.cpio"    ← rootfs
addr=0x8fe00000   size=0x5ff     name="fdt"            ← device tree
```

**這是一個很實用的除錯技巧**——懷疑載入位址有問題時，直接問 QEMU。

### Verilog 模擬：20 小時與 5.81 億條指令

> "$ wsim buildroot buildroot --args '+INSTR_LIMIT=600000000' --lockstep"
> — p.784.e73

> "Linux does not naturally terminate, so the INSTR_LIMIT argument specifies how many instructions to run; 1,600,000 is enough to reach the OpenSBI banner, and 600 million is more than enough to reach the login prompt. ... The Linux boot presently executes about 581 million instructions and takes about 20 hours on a high-performance PC with ImperasDV lockstep in Questa or 2 hours in Verilator without lockstep."
> — p.784.e74

中文解釋：三個實用細節：
1. **Linux 不會自己結束**，所以要給指令數上限
2. **1,600,000 就能看到 OpenSBI banner**——想快速確認 firmware 有沒有跑起來，不用等 6 億
3. **lockstep 的代價是 10 倍**（20 小時 vs 2 小時）。lockstep（第 5.6 節、5.11.9 節）是每條指令都和 ImperasDV 參考模型比對，能抓到細微的錯誤但很慢

### 自動登入：為了自動化測試

> "/etc/inittab is modified from the default version to cause the system to login and start up a shell without any user input for username or password ... The /.profile file contains some test commands executed before initiating an actual login prompt, as shown in Fig. 22.5. This way, shell commands can be tested without requiring user input (which may cause complications in QEMU record/replay mode)."
> — p.784.e75

中文解釋：這是一個很實際的工程考量。`/etc/inittab` 裡把正常的 `getty`（會要求輸入帳號密碼）註解掉，改成 `console::respawn:-/bin/sh` 直接開 shell。

`/.profile` 裡放一連串測試指令（`touch`、`mkdir`、`mv`、`cat`、`chmod`、`ln -s`、`df -h`、`ps`），開機完自動執行。**這樣就能在完全無人介入的情況下驗證「檔案系統、權限、符號連結、行程管理都正常」**——對 20 小時才跑完一次的模擬來說，不能有任何需要人手動輸入的地方。

### 改設定的三個層次

> "Buildroot provides an interactive menuconfig interface for configuration, which consists of three files and configuration tools: .config (menuconfig), linux.config (linux-menuconfig), and busybox.config (busybox-menuconfig)."
> — p.784.e76

中文解釋：三層各管各的——Buildroot 本身、Linux kernel、BusyBox。Wally 的設定來自 `$WALLY/linux/br2-external-tree/configs/wally_defconfig`。

改完之後重建：
```
$ cd $WALLY/linux
$ make Image      BUILDROOT=$(RISCV)/buildroot
$ make disassemble BUILDROOT=$(RISCV)/buildroot
$ make dumptvs
```

### rootfs overlay：把檔案塞進最終的檔案系統

> "$WALLY/linux/br2-external-tree/board/wally/rootfs_overlay contains files that are meant to go in the root filesystem of the final machine. These files aren't strictly necessary for booting Linux but can be helpful for testing purposes."
> — p.784.e75

中文解釋：overlay 是 Buildroot 的標準機制——**把一個目錄的內容疊到產生的 rootfs 上**，不用改 Buildroot 本身。前面講的 `/etc/inittab` 和 `/.profile` 就是放在這裡。

## 名詞表

| 名詞 | 意思 |
| --- | --- |
| QEMU virt platform | QEMU 的通用虛擬硬體平台 |
| `qemuBoot.sh` | 設定好所有 QEMU 選項以匹配 Wally 的腳本 |
| QEMU monitor | 按 Ctrl-a c 進入的互動除錯介面 |
| `info roms` | QEMU monitor 指令，列出載入記憶體的映像與位址 |
| `INSTR_LIMIT` | 模擬的指令數上限（Linux 不會自己結束） |
| lockstep | 每條指令與參考模型（ImperasDV）比對，慢 10 倍 |
| `record/replay` | QEMU 的記錄重播模式，需要確定性的輸入 |
| `getty` | 提供登入提示的程式（自動登入時被停用） |
| `respawn` | inittab 的動作，程式結束就重新啟動 |
| rootfs overlay | 疊加到產生的 rootfs 上的檔案目錄 |
| `menuconfig` | Buildroot 的互動式設定介面 |
| `wally_defconfig` | Wally 的 Buildroot 設定檔 |
| `savedefconfig` | 把目前設定存回 defconfig 的指令 |

## 所以呢

這節的實務重點是**分層使用三個平台**：QEMU 驗軟體、FPGA 做互動與大量測試、RTL 模擬看波形。以及一個小而重要的工程手法——**把測試腳本塞進 `/.profile`**，讓 20 小時的模擬能完全無人值守地驗證系統功能。

下一節 22.4 做總結，然後第 23 章把 Wally 真的燒進 FPGA，讓它變成一台可以用鍵盤打字的電腦。
