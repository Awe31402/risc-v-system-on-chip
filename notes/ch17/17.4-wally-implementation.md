# 17.4 Wally Implementation

> 原書 p.706–712（Chapter 17: Extensions: A (Atomic)）
> 涵蓋 17.4.1 Atomic Module（AMO ALU、LRSC module、Atomic Hazards）、17.4.2 Timing Diagrams

## 這節在講什麼

Wally 加原子指令的成本出奇地低——因為它是單核心循序處理器，17.1 講的那些難題（coherence、consistency、livelock monitor）大部分**根本不存在**。實作只需要在 LSU 裡加一個 `atomic` 模組，裡面兩個東西：一個 AMO ALU 和一個追蹤預約的 LRSC 模組。這節也是一個好例子，說明「實作成本取決於你處在架構光譜的哪個位置」。

## 關鍵點

### Wally 天生就滿足大部分要求

> "Wally is an in-order single-core processor, so it is inherently sequentially consistent. It also has a single instruction cache and single data cache, so caches are inherently coherent except that store operations are not reflected in the instruction cache. ... In Wally, all other fences are treated as nops, and the acquire/release bits of atomic instructions are ignored."
> — p.706

中文解釋：這段把整章的概念負擔幾乎全部消掉了：
- 循序單核心 ⟹ sequentially consistent ⟹ `fence` 是 nop
- 只有一套 I$ 和 D$ ⟹ 天生 coherent ⟹ 只需要 `fence.i` 處理自我修改程式碼，`sfence.vma` 處理 TLB
- 沒有其他核心 ⟹ `aq`/`rl` 可以忽略

但這不代表 A 擴充沒用——單核心多執行緒的 race condition 仍然真實存在（17.1.1、17.2 開頭都強調過），原子指令還是必要的。

### atomic 模組的位置與前提

> "It is relatively simple because it does not need to handle interactions with other cores. The LSU does not have an FSM to sequence atomic read-modify-write operations over multiple cycles, so the atomic module relies on the LSU having a data cache. The Wally PMA checker only allows atomic operations on cachable main memory. The cache read (ReadDataWordM), modify (IMAWriteDataM), and write (LSUWriteDataM) take place in the same cycle."
> — p.706

中文解釋：這是整個實作的關鍵設計決定：**讀-改-寫全部在同一個 cycle 裡完成**。能這麼做的前提是「資料在快取裡」——快取讀取在 Memory 級開頭、寫入在 Memory 級結尾，中間剛好塞得下一個 ALU 運算。如果要從外部記憶體抓，就得跨多個 cycle，那就需要一個 FSM 來保證中間不被打斷。所以 PMA checker 只在可快取的主記憶體上允許原子操作。

### 原子指令怎麼複用既有的 LSU 硬體

> "The atomic module takes advantage of the existing LSU hardware to add atomic support with minimal change. LoadReserved resembles an ordinary load but adds state to keep track of which address is reserved. StoreConditional resembles an ordinary store but is squashed if the address is no longer reserved. ... AMO operations take the read result, perform an ALU operation on it in the atomic module, and mux this ALU result back into the write path."
> — p.707

中文解釋：三句話講完三種指令的實作：
- `lr` = 普通 load + 記下位址
- `sc` = 普通 store + 條件成立才真的寫（不成立就 squash）
- `amo` = 普通 load + ALU + 普通 store，全在同一 cycle

完整的資料流（Fig. 17.4）：LSU 在 Memory 級開頭讀出 `ReadDataM` → `atomic` 模組把它和暫存器來的 `IHWriteDataM` 做 ALU 運算，得到 `IMAWriteDataM` → 經過 subword muxing 和 endian swap 變成 `LSUWriteDataM` → 在 Memory 級結尾寫回快取。

### 為什麼 AMO ALU 不共用整數 ALU

> "The AMO ALU uses dedicated hardware rather than sharing the integer ALU because sharing would add busses and multiplexers between the IEU and LSU and would introduce a dependency that would stall the Execute stage when an AMO instruction needed the shared ALU. The extra hardware is modest in the context of a full-featured application core."
> — p.710

中文解釋：這是一個「複製比共用便宜」的例子，和第 16 章「共用 unpack/postprocess」的取捨方向相反。原因有兩個：
1. **位置不對**：整數 ALU 在 Execute 級，AMO 需要在 Memory 級運算（因為它的一個運算元是剛從記憶體讀出來的資料）。
2. **會造成停頓**：共用就會有結構性冒險。

而「extra hardware is modest」是關鍵前提——AMO ALU 只要九種運算（Fig. 17.6：maxu、minu、max、min、and、or、xor、swap、add），比整數 ALU 簡單。而且四個比較器（`a>b` unsigned、`a>b` unsigned、`a>b` signed、`a<b` signed）關係緊密，可以**共用一條 carry chain**。RV64 另外加上 32 位元運算的符號擴展多工器。

### LRSC 模組：用位址暫存器而非快取線位元

> "During a LoadReserved instruction, the module records the physical address of the reservation and marks the reservation valid. Any StoreConditional instruction invalidates the reservation. If the StoreConditional does not match the physical address of a valid reservation, the LRSC module asserts SquashSCM to squash the store. This squash turns off the LSURWM write enable and writes a 1 to the destination register to indicate failure."
> — p.710

中文解釋：Fig. 17.7 的 `lrsc` 模組。注意這裡的實作選擇與 17.2.3.2 講的通用做法**不同**：

> "Observe that this implementation tracks the reservation with an address register rather than a bit on each cache line. Therefore, the size of the reservation set is the native word size (4 bytes on RV32 and 8 bytes on RV64)."
> — p.710（邊欄）

中文解釋：存位址暫存器的好處是 reservation set 只有一個字——**完全沒有 false sharing**。這在單核心上是負擔得起的（只要一個暫存器 + 一個比較器），但多核心就不行了，因為每個核心都要知道別人寫了什麼，用快取線的一致性協定來追蹤才實際。

另外注意 `sc` 失敗時要做兩件事：關掉寫入致能（不改記憶體），以及**寫 1 到目的暫存器**（回報失敗）。後者需要在 IEU 的 `Result` 多工器（Fig. 7.13）多接一路 `{0, SquashSCW}`（Fig. 17.8）。

### 原子指令的冒險：不用新硬體

> "As described in Section 10.4.2.3, the cache is unable to perform a load immediately after a store because both instructions would need to use the data SRAM's address in the same cycle. For the same reason, the cache cannot perform an AMO after a store or AMO or before a load. The StoreStallD logic that detects load after store also detects these AMO cases because they use the same MemRW signals, so no extra hardware is needed."
> — p.710

中文解釋：這是設計上的意外紅利。AMO 既讀又寫，所以它和 store 有完全相同的結構性冒險；而既有的 `StoreStallD` 邏輯是看 `MemRW` 訊號判斷的，AMO 的 `MemRW` 編碼自然落在同一類，**一行都不用改**。

### 時序波形解讀

> "The timing for atomic operations is similar to other LSU operations. They rely on a data cache in the LSU. Loads, including LoadReserved, read the cache at the start of the Memory stage. Stores, including StoreConditional, write the cache at the end of the Memory stage. AMOs read memory at the start of the Memory stage, perform an operation, and write the result back to the cache at the end of the Memory stage."
> — p.711

中文解釋：Code Example 17.19 + Fig. 17.9 是一個完整的走查。程式跑在 RV32IA、little-endian、關閉虛擬記憶體，位址 0x80001000 初值 42：

```
li   a0, 0x80001000
li   a1, 2
lr.w t0, (a0)          # t0 = 42，預約 0x80001000
addi t0, t0, 1         # t0 = 43
sc.w t1, t0, (a0)      # 成功：寫 43，t1 = 0
sc.w t2, t0, (a0)      # 失敗（預約已清除）：t2 = 1
amoadd.w s0, a1, 0(a0) # s0 = 43，mem = 43 + 2 = 45
```

波形上的關鍵訊號：`MemRWM` 是 10（load）、01（store）、**11（AMO）**；`LSUAtomicM` 是 00（非原子）、**01（lr-sc）**、**10（AMO）**。第一個 `sc.w` 在 cycle 4 成功，寫 0 到 t0 並在 cycle 5 清掉 `ReservationValidW`；第二個 `sc.w` 在 cycle 5 發現預約無效，拉起 `SquashSCM`、在 cycle 6 清掉 `LSURWM` 阻止寫入、回傳 1。`amoadd` 在 cycle 6 從記憶體讀 43、從 a1 讀 2，寫 45 回記憶體並回傳 43 給 s0。

### livelock 在單核心不是問題

> "Wally has a single core, so lr-sc will not livelock and requires no monitor to ensure eventual success. The OS is responsible for invalidating a reservation during a context switch by performing a StoreConditional to a scratch memory address."
> — p.708

中文解釋：呼應 17.2 的兩點——單核心不需要 livelock monitor，但 OS 還是要在 context switch 時用「`sc` 到暫存位址」清掉預約。這是硬體把責任留給軟體的例子。

## 名詞表

| 名詞 | 意思 |
| --- | --- |
| `ZAAMO_SUPPORTED` / `ZALRSC_SUPPORTED` | Wally 設定檔中啟用 AMO ／ lr-sc 的參數 |
| `atomic` 模組 | LSU 裡處理 AMO 與 lr-sc 的模組，含 `amoalu` 與 `lrsc` |
| `amoalu` | AMO 專用 ALU，九種運算，在 Memory 級運作 |
| `lrsc` | 追蹤預約位址與有效性、產生 `SquashSCM` 的模組 |
| `ReadDataM` / `IHWriteDataM` / `IMAWriteDataM` / `LSUWriteDataM` | AMO 資料流上的四個訊號（讀出／暫存器值／ALU 結果／最終寫入值） |
| `SquashSCM` / `SquashSCW` | 壓制失敗的 StoreConditional 的訊號 |
| `LSUAtomicM` | 標示這次存取是非原子（00）、lr-sc（01）還是 AMO（10） |
| `MemRWM` = 11 | AMO 的讀寫編碼 |
| `StoreStallD` | 偵測 load-after-store 結構冒險的既有邏輯，AMO 直接沿用 |
| carry chain 共用 | 四個比較器共用同一條進位鏈以節省面積 |
| scratch address | OS 用來清除預約的暫存記憶體位址 |

## 所以呢

A 擴充在 Wally 上的實作總成本：一個九運算的小 ALU、一個位址暫存器加比較器、IEU 結果多工器多一路輸入，以及零行新的冒險邏輯。這個「便宜」完全來自 Wally 是單核心循序處理器——換成多核心亂序，同樣的指令語意會需要一致性協定、預約監控、livelock monitor 和真正會動作的 fence。這正是這章一開始就把概念（17.1）和實作（17.4）分開講的原因。
