# 14.3 Wally Implementation

> 原書 p.582–590（Chapter 14: Extensions: C (Compressed)）
> 涵蓋 14.3.1 Instruction Decompression、14.3.2 PC Logic、14.3.3 Spills

## 這節在講什麼

**壓縮指令在 Wally 裡只影響 IFU，而且只有三處改動。**

| 改動 | 在哪 | 複雜度 |
| --- | --- | --- |
| **`decompress` 模組** | Decode 級開頭 | **低**（一個大多工器） |
| **PC 邏輯加 2 而非 4** | Fetch 級 | **低**（一個多工器） |
| **`spill` 模組** | Fetch 級 | **高**（一個 FSM + 三週期流程） |

**最該精讀的是 14.3.3 的 spill**——它是本章唯一真正困難的部分。

## 關鍵點

### 組態參數與一個有趣的細節

> "**Wally uses the ZCA_SUPPORTED, ZCB_SUPPORTED, ZCF_SUPPORTED, and ZCD_SUPPORTED configuration parameters to enable
>  compressed instructions. There is no C_SUPPORTED parameter. Instead, the C bit of the `misa` register is set if
>  Zca is supported and either Zcd (and D) or Zcf (and F) are supported. Wally does not presently implement Zcmp or
>  Zcmt and, therefore, does not support Zce.**"
> — p.582

中文解釋：**沒有 `C_SUPPORTED` 參數——這反映了 14.1 節的設計：
C 擴充已經被拆解成 Zc* 家族，「C」只是一個組合的簡寫。**

**`misa` 的 C 位元是推導出來的：**
```
misa.C = ZCA && ((ZCD && D) || (ZCF && F))
```

**Wally 不支援 Zcmp、Zcmt，所以也不支援 Zce。**

### 三處改動

> "**Fig. 14.1 shows the Wally IFU changes required to support compressed instructions. Wally uses an optional
>  decompression unit (`decompress`, abbreviated to `decomp` in Fig. 14.1), which receives 16-bit compressed
>  instructions and inflates them to their equivalent 32-bit instructions. The decompression takes place at the start
>  of the Decode stage and must complete in time to access the integer register file (`regfile`, shown as IRF in
>  Fig. 14.1). The PC logic adds 2 instead of 4 for compressed instructions. The IFU takes multiple cycles to handle
>  spills, when an instruction wraps a cache line or IROM word.**"
> — p.582

中文解釋：**`decompress` 的時序要求值得注意：**
**「在 Decode 級開頭進行，而且必須及時完成以存取整數暫存器檔案」。**

**這是關鍵路徑上的一個新延遲**——
因為暫存器檔案的位址來自解壓縮後的指令。
（呼應 7.2 節：Decode 級要「解碼 + 讀暫存器」。）

### `decompress`：一個巨大的多工器

> "**As shown in Fig. 14.2, `decompress` is combinational logic with a 32-bit input InstrRawD and a 32-bit output
>  InstrD. If InstrRawD is uncompressed (detected by bits [1:0] = 11), it is passed through to InstrD. Otherwise, the
>  combinational logic examines at least bits [15:13] and [1:0] to determine the type of compressed instruction and to
>  inflate it to a 32-bit output, InstrD.**"
> — p.582

中文解釋：**Fig. 14.2（p.584）的結構極簡：**
```
InstrRawD[31:0] ──┬──────────────────→ mux (1) ──→ InstrD
                  └─[15:0]─→ 16→32 decompress ──→ mux (0)
                     選擇訊號 = (InstrRawD[1:0] == 11)
```

**「一個 AND 閘檢查 `[1:0]` 就決定要不要解壓縮」**——
這就是 14.1 節「編碼不重疊」的設計回報。

**Code Example 14.1（p.585）的實際程式碼，示範了解壓縮的本質：**
```systemverilog
assign op    = instr16[1:0];
assign rs1p  = {2'b01, instr16[9:7]};      // x8-x15
assign rdp   = {2'b01, instr16[4:2]};
assign rs2p  = {2'b01, instr16[4:2]};
assign rds1  = instr16[11:7];

assign immCL = {5'b0, instr16[5], instr16[12:10], instr16[6], 2'b00};
assign immCS = {5'b0, instr16[5], instr16[12:10], instr16[6], 2'b00};
assign immCI = {{7{instr16[12]}}, instr16[6:2]};

always_comb
  if (op == 2'b11) InstrD = InstrRawD;     // Noncompressed instruction
  else case ({op, instr16[15:13]})         // Inflate compressed instruction
    5'b00010: InstrD = {immCL, rs1p, 3'b010, rdp, 7'b0000011};                    // c.lw
    5'b00110: InstrD = {immCS[11:5], rs2p, rs1p, 3'b010, immCS[4:0], 7'b0100011}; // c.sw
    5'b01000: InstrD = {immCI, rds1, 3'b000, rds1, 7'b0010011};                   // c.addi
    ...
```

**四個值得注意的實作細節：**

1. **`{2'b01, instr16[9:7]}`**——**3-bit 暫存器編號加上前綴 `01` 就變成 x8–x15**。
   （因為 x8 = 0b01000，所以前綴是 `01`。）**一行程式碼完成暫存器映射。**

2. **`immCL` 和 `immCS` 的位元重排**：
   `{5'b0, instr16[5], instr16[12:10], instr16[6], 2'b00}`——
   **立即值的位元在壓縮指令裡是打散的，要重新拼起來**
   （和 2.2 節未壓縮指令的 bit swizzling 同一個道理）。
   **末尾的 `2'b00` 是因為 `c.lw` 的偏移量是 4 的倍數。**

3. **`immCI` 的符號延伸**：`{{7{instr16[12]}}, instr16[6:2]}`——
   **用 bit 12 做符號延伸，正是 14.1 節說的「msb 永遠在 bit 12」。**

4. **`c.addi` 展開成 `{immCI, rds1, 3'b000, rds1, 7'b0010011}`**——
   **`rds1` 同時填進 rs1 和 rd 欄位**，這就是「第一個來源也當目的」的實作。

**書上的總結（p.585）：**
> "**Thus, the decompressor can be viewed as a giant multiplexer that selects fields from the compressed instruction
>  to emit an uncompressed instruction.**"

**加 Zcb 的成本（p.585）：**
> "**Adding Zcb support simply involves extending the `decompress` module with more opcodes.**"

**只要加 case 分支——這就是「膨脹回 32-bit 用既有 datapath」設計的最大好處。**

### PC 邏輯：加 2 而非 4

> "**When the IFU fetches an instruction, it asserts CompressedF if the instruction is compressed. Fig. 14.3 shows how
>  the PC logic is modified to add 2 to PCF instead of 4 for compressed instruction, with the mux that selects 2 or 4
>  highlighted in bright blue.**"
> — p.585

中文解釋：**Fig. 14.3（p.586）的改動只有一個多工器：**
```
CompressedF ? 2 : 4  →  加法器  →  PCPlus2or4F
```

**連帶的兩個影響：**

**（1）指令位址未對齊 fault 消失（p.585）：**
> "**As described in Section 8.2.5.2, instruction address-misaligned faults ordinarily occur if the branch or jump
>  target address is not a multiple of 4. When compressed instructions are supported, that fault is not permitted
>  because target addresses may be multiples of 2.**"

（呼應 8.2.5.3、11.2.3 節：有 C 擴充就不可能發生指令位址未對齊例外。）

**（2）BHT 索引要改（p.585–586）——這段很有意思：**
> "**The branch predictor of Section 13.3 aligned the BHT (branch history table) to a 4-byte boundary, such that a
>  2^k-entry table used PC[k+1:2] to index the BHT. Because compressed instructions align to 2 bytes, the branch
>  predictor should include PC[1]. A typical program contains a mix of 32- and 16-bit instructions, so using PC[k:1]
>  reduces the effective capacity of the BHT when most instructions are 32 bits. By indexing the BHT with
>  {PC[k+1] ⊕ PC[1], PC[k:2]}, it maintains most of the capacity if the program has few compressed instructions.**"

**問題：**
- **用 `PC[k+1:2]`（忽略 bit 1）→ 壓縮指令會和相鄰指令衝突**
- **用 `PC[k:1]`（包含 bit 1）→ 但 bit 1 常常是 0（32-bit 指令居多），
  等於浪費一個索引位元**

**解法：`{PC[k+1] ⊕ PC[1], PC[k:2]}`**——
**把 bit 1 用 XOR 折進最高位元**。
**壓縮指令少時，行為接近原本的 `PC[k+1:2]`（保住容量）；
壓縮指令多時，bit 1 也能區分。**

（呼應 13.3.3.2 節邊欄對 BTB 索引的同樣討論。）

### Spill：本章唯一困難的部分

> "**Recall that a spill occurs when a 32-bit instruction spans two instruction cache lines or two IROM words.
>  If PC is an odd multiple of 2 that maps to the end of a cache line, the cache can only return the first 16 bits of
>  the instruction. If that instruction is 32 bits long, the IFU must read the next cache line to retrieve the
>  remaining 16 bits.**"
> — p.586

中文解釋：**Fig. 14.4（p.586）的具體例子：
`li s8, 0x3D` = `0x03D00C13` 在位址 0x31E，cache line 是 32 bytes：**
```
Cache line j   ： 位址 0x31E–0x31F 放著 0x0C13（指令的低半）
Cache line j+1 ： 位址 0x320–0x321 放著 0x03D0（指令的高半）
```
**I$ 先從 0x31E 讀出 0x0C13，然後 IFU 把 PCF 加 2 從 0x320 讀出 0x03D0，
`spill` 邏輯把兩半串接成完整的 32-bit 指令。**

**（p.586 邊欄的替代方案：**「雙埠 cache 可以同時讀兩條 cache line；
**但雙埠 SRAM 佔的面積顯著更多。**」**
——這是「用時間換面積」的取捨。）

### Spill 的三個步驟

> "**When an instruction fetch spills, the `spill` module pipelines the fetch over 3 cycles:
>  - **Step 1:** The I$/IROM sets up to read the instruction at PCNextF.
>  - **Step 2:** The I$/IROM outputs the first 2 instruction bytes, and the `spill` module saves them to a local
>    register. The I$/IROM also sets up the next read with PCF+2.
>  - **Step 3:** The I$/IROM outputs the next instruction bytes, and the `spill` module merges the two half
>    instructions to form the full 4-byte instruction. The PC logic also sets PCNextF to PCF+4 to set up the read for
>    the next instruction.**"
> — p.587

中文解釋：**三個週期，每一步都同時做兩件事（讀這次 + 設定下次）——這是 pipeline 的典型做法。**

**代價（p.587）：**
> "**The spill adds one stall cycle of latency when both halves hit the I$/IROM. A cache miss in either half behaves
>  like a conventional I$ miss.**"

**兩半都命中時只多一個 stall 週期**——代價不大。

**（p.587 邊欄的一個細節：**「和 I$ 不同，**分支預測器繼續用 `PCNextF` 讀取，
因為它們不需要為指令的第二半做另一次預測。**」**
——這很合理：一條指令只需要一次預測。）

### `spill` 模組的硬體

> "**Fig. 14.5 shows the complete IFU. Compared to Fig. 13.12, the new spill circuitry is highlighted in blue.
>  The `spill` module adds a +2 adder and muxes to generate PCSpillNextF and PCSpillF. PCSpillNextF drives the IROM
>  address or the set bits of the I$. PCSpillF goes through the MMU for address translation to become the physical
>  program counter PCPF. Finally, the spill logic adds a register and mux to merge together the two halves of the
>  instruction.**"
> — p.587–588

中文解釋：**Fig. 14.6（p.588）的 `spill` 模組內部，四個部分：**

**（1）Spill 偵測**
```
SPILLTHRESHOLD 比較器：PCF[4:1] == 1111 → SpillF
（32-byte cache line 時，PCF[4:1] 全 1 表示指令跨越邊界）
CompressedF & ... → TakeSpillF
```

**（2）位址產生**
```
PCPlus2F = PCF + 2
PCSpillF     = SelSpillF ? PCPlus2F : PCF
PCSpillNextF = SelSpillNextF ? PCPlus2F : PCNextF
```

**（3）指令合併**
```
InstrFirstHalfF 暫存器（SpillSaveF 時載入 InstrRawF[15:0]）
PostSpillInstrRawF = SelSpillF ? {InstrRawF[15:0], InstrFirstHalfF} : InstrRawF
```

**（4）Stall**
```
SelSpillNextF → IFUStallF（stall pipeline）
```

**（p.588 邊欄的一個實作最佳化很有意思：**
「Fig. 14.6 顯示一個加法器產生 `PCPlus2F`，**但 RTL 實際上用多工器來省硬體。**
當 `PCF[1] = 0` 時，加 2 只是設定 `PCF[1]`：`PCPlus2F = {PCF[XLEN-1:2], 2'b10}`。
否則 `PCPlus2F = {PCPlus4F[XLEN-1:2], 2'b00}`。
例如 `PCF = 1100 = 12` 時 `PCPlus2F = 1110 = 14`（設定 `PCF[1]`）；
`PCF = 0010 = 2` 時 `PCPlus4F = 0110 = 6` 而 `PCPlus2F = 0100 = 4`（清除 `PCPlus4F[1]`）。」**

**「加 2 只是切換 bit 1」——用多工器取代加法器。**
（這和 10.4.4 節 pLRU、11.4.1.3.3 節 `tlbmixer` 是同一類「利用常數簡化硬體」的手法。）

### `spillfsm`：兩狀態機

中文解釋：**Fig. 14.7（p.589）的狀態機極簡：**
```
       ┌─ TakeSpillF（自環）
       ↓
    ┌──────┐  TakeSpillF / SpillSaveF, SelSpillNextF  ┌───────┐
    │Ready │ ──────────────────────────────────────→  │ Spill │
    └──────┘  ←──────────── else ─────────────────── │SelSpillF=1│
                                                       └───────┘
                                    StallF / SelSpillNextF = IFUCacheBusStallF（自環）
```

**書上的說明（p.588）：**
> "**The spill FSM in Fig. 14.7 stays in the Ready state on a regular instruction read and to read an instruction.
>  When the FSM detects a spill (TakeSpillF = 1), it transitions to the Spill state where it waits for the upper half
>  of the instruction read to complete.**"

### 完整的 spill 時序（含兩次 cache miss）

中文解釋：**Fig. 14.8（p.589）配 p.590 的逐週期說明。
抓取 `li` 指令（0x03D00C13）從位址 0x31E，兩條 line 都 miss：**

| Cycle | 發生什麼 |
| --- | --- |
| **1** | **Step 1**：IFU 嘗試從 `PCF = 0x31E` 抓取，**`SpillF` assert** |
| **2–3** | **IFU stall，等 I$ 抓取缺失的 cache line** |
| **4** | **Step 2**：I$ 回傳 `InstrRawF = 0x00000C13`。**`spill` 偵測到 spill（位址跨兩條 line），
raise `TakeSpillF`**，於是 `spillfsm` raise **`SpillSaveF`**（把低半存進 `InstrFirstHalf` flop）
和 **`SelNextSpillF`**（選 `PCSpillF = 0x320` 當 I$ 的輸入）。FSM 轉到 **Spill 狀態** |
| **5–7** | **IFU stall，等 I$ 從 0x320 抓取缺失的 line** |
| **8** | **Step 3**：I$ 回傳 `InstrRawF = 0x000003D0`。**`spill` 取出低位元 0x03D0，
`PostSpillInstrRawF` 多工器合併兩半成 `0x03D00C13`** |

**注意第 4 步的三個動作同時發生：存下低半、設定下次讀取、轉狀態。**

**而且「兩次 cache miss」讓總共花了 8 個週期**——
**單純的 spill 只多 1 個週期，但 miss 的代價會疊加。**

### 替代方案：Fetch Buffer

> "**An alternative solution is to place a small *fetch buffer* between the Fetch and Decode stages. The three-entry
>  circular buffer fetches ahead of the PC, and the decoder can pull 2 or 4 bytes of instruction as necessary,
>  avoiding a stall if the next entry is in the buffer. A fetch buffer also decouples the Fetch stage from later-stage
>  stalls, potentially improving the critical path. Wally does not yet support fetch buffers.**"
> — p.590

中文解釋：**Fetch buffer 的三個好處：**
1. **預先抓取，下一條在 buffer 裡就不用 stall**（解決 spill 的延遲）
2. **解碼器可以按需取 2 或 4 bytes**（統一處理壓縮和未壓縮）
3. **把 Fetch 級和後面級的 stall 解耦，可能改善關鍵路徑**

**Wally 沒有實作**——這是一個明確標示的改進空間。

**（這也解釋了為什麼高效能處理器都有 fetch buffer 或 instruction queue：
它一次解決了 spill、對齊、和 stall 解耦三個問題。）**

## 名詞表

| 名詞 | 意思 |
| --- | --- |
| `ZCA/ZCB/ZCF/ZCD_SUPPORTED` | 組態參數；**沒有 `C_SUPPORTED`**，`misa.C` 由它們推導 |
| **`decompress`** | 組合邏輯，把 16-bit 壓縮指令膨脹成 32-bit；**本質是一個巨大的多工器** |
| `CompressedF` | 抓到的指令是壓縮的；控制 PC 加 2 還是 4 |
| **BHT 索引 `{PC[k+1] ⊕ PC[1], PC[k:2]}`** | **把 bit 1 用 XOR 折進最高位元**，兼顧容量與壓縮指令的區分 |
| **`spill`** | 處理跨 cache line 的 32-bit 指令；**三週期流程** |
| `SpillF` / `TakeSpillF` | 偵測到位址跨界 / 確認需要 spill |
| `SpillSaveF` / `SelSpillF` / `SelSpillNextF` | 存下低半 / 選合併後的指令 / 選 `PCPlus2F` 當下次位址 |
| `InstrFirstHalfF` | 存放指令低半的暫存器 |
| `PostSpillInstrRawF` | 合併後的完整指令 |
| SPILLTHRESHOLD | 判斷是否跨界的比較值（32-byte line 時是 `PCF[4:1] == 1111`） |
| **Fetch buffer** | Fetch 與 Decode 之間的小型環形緩衝區；**Wally 尚未支援** |

## 所以呢

**壓縮指令只影響 IFU，三處改動中兩處很簡單、一處很難。**

四件最該帶走的事：

1. **`decompress` 本質是一個巨大的多工器**——
   `{2'b01, instr16[9:7]}` 一行就完成 x8–x15 的映射，
   `rds1` 同時填進 rs1 和 rd 就實現了「來源也當目的」。
   **加 Zcb 只要加 case 分支。**

2. **BHT 索引用 `{PC[k+1] ⊕ PC[1], PC[k:2]}`**——
   **把「常常是 0」的 bit 1 用 XOR 折進最高位元**，
   兼顧「壓縮指令要能區分」和「32-bit 指令居多時不浪費容量」。

3. **Spill 是唯一困難的部分**：三週期流程（設定 → 存低半並設定下次 → 合併），
   **兩半都命中時只多 1 個 stall 週期**，但 miss 會疊加。

4. **一個值得學的硬體最佳化**（p.588 邊欄）：
   **「加 2」不需要加法器——只是切換 bit 1**，
   用多工器就能實現。

**最後，Wally 沒有 fetch buffer**——
而那正是「一次解決 spill、對齊、stall 解耦」的標準做法。
