# 23.4 Interesting Bugs

> 原書 p.784.e100–784.e104（Chapter 23: FPGA Implementation）
> 涵蓋 23.4.1 Bug 1: AHB Bursts、23.4.2 Bug 2: Concurrent Exceptions、23.4.3 Critical Path Analysis
> 註：書中正文把這節誤編為「23.3 INTERESTING BUGS」（章首目錄作 23.4），子節編號亦作 23.3.x

## 這節在講什麼

全書最好的除錯故事。兩個 bug 的共通點是：**標準回歸測試完全抓不到，只在 FPGA 上跑 Linux 時才出現**。

原因很簡單——回歸測試跑幾百萬條指令，Linux 開機跑五億條。有些狀態組合需要極特殊的時序巧合才會發生，指令數不夠多就撞不到。這節也示範了怎麼用 ILA 從「卡住了」一路追到根因。

## 關鍵點

### 為什麼需要 FPGA 除錯

> "FPGAs aid ASIC verification by emulating and validating RTL functionality in a much higher-performance environment compared to simulation. Wally's FPGA implementation found numerous functional and performance bugs that the standard regression tests did not."
> — p.784.e100–e101

中文解釋：這是 23.1 講的 emulation 的實際回報。**速度換來的是「能跑到更深的狀態空間」。**

## Bug 1：AHB Burst 打斷取指

### 症狀

> "When we added burst mode, Wally passed all regression tests, but the FPGA implementation failed. When booting Linux, it did not display the OpenSBI banner and then got stuck in an infinite loop. Unfortunately, nothing obvious, such as an illegal instruction, provided a good starting point for investigation."
> — p.784.e101

中文解釋：**最糟的一種 bug——回歸測試全過、沒有例外、只是卡住。** 沒有任何線索告訴你從哪裡開始查。

### 追查過程

> "We used the ILA to record a short 16,384 clock sample of Wally's internal state. After failing to boot, we noticed Wally was frequently in the Linux trap handler. Eventually, we found an instruction in the trap handler was causing another trap into OpenSBI M-mode. This instruction generated an unexpected load-access fault. We set up an ILA trigger on this instruction and TrapM = 1 and restarted Wally to catch the first instance of the trap."
> — p.784.e101

中文解釋：追查的邏輯鏈值得學：
1. 隨便抓一段波形 → 發現一直在 trap handler 裡
2. 往回看 → trap handler 裡有一條指令又觸發 trap
3. 是一個**非預期的 load-access fault**
4. 設觸發條件抓「第一次」發生的時刻

> "Because the ILA only captures 16,384 clock cycles, backtracking to the root cause may not be visible within a single ILA capture. This required reconfiguring the ILA multiple times and restarting the whole boot process repeatedly before finding the timeframe that showed a discrepancy between data written to memory and data read from memory"
> — p.784.e101

中文解釋：**這是 FPGA 除錯的核心痛點**——ILA 的視窗只有 16,384 個週期，而 bug 的根因可能在幾百萬個週期之前。只能反覆調整觸發條件、重跑整個開機。這也解釋了為什麼 23.3 節說「大 FPGA 的主要價值是更大的 ILA」。

### 根因：三個被違反的假設

> "The external bus unit (EBU) relied on three main assumptions about the instruction fetch unit (IFU) and LSU memory requests. 1. The IFU makes an AHB request and finishes before another request is made. 2. The LSU makes an AHB request and finishes before another request is made. 3. Or both make an AHB request on the same cycle, and the LSU is given precedence."
> — p.784.e101

中文解釋：EBU（第 9 章）假設 IFU 和 LSU 的請求**不會重疊**。

> "The FPGA challenged these assumptions by showing it was possible for the LSU to make an AHB request while the IFU already had an AHB request in flight. If the I$ and data translation lookaside buffer (DTLB) miss in the same cycle, but the hardware page table walker's (HPTW's) first memory request to the D$ hits, the I$ will be granted access to the AHB. If later HPTW requests miss in the D$, the LSU attempts to make a request while the IFU already has access to the bus, thus violating the above assumptions and interrupting the IFU's burst request."
> — p.784.e102

中文解釋：**這個時序巧合非常刁鑽**，需要四件事同時成立：
1. I$ 失誤（IFU 要上匯流排）
2. DTLB 同時失誤（要啟動 HPTW，第 11 章）
3. HPTW 的**第一次**記憶體請求在 D$ 命中（所以 LSU 這時沒佔匯流排，IFU 拿到）
4. HPTW 的**後續**請求在 D$ 失誤（LSU 這時才要上匯流排，但 IFU 已經在跑 burst）

> "The nonburst implementation worked because only one word was transferred at a time, so it was possible for the IFU to have transferred part of the cache line and then have the EBU give the LSU bus access. Then, after the LSU completed, the IFU was again given bus access to finish its requests. However, with burst mode enabled, the LSU could preempt the IFU's AHB request with only part of the I$ line transferred."
> — p.784.e102

中文解釋：**為什麼沒有 burst 時不會壞**——非 burst 模式下每次只傳一個字，LSU 插進來也只是「兩次獨立的單字傳輸之間」，IFU 之後可以繼續。有了 burst，LSU 打斷的是**一個進行到一半的 burst**，快取線只填了一部分就被當成完整的用——**讀回來的是垃圾**。

這正是前面看到的「寫進記憶體的資料和讀出來的資料不一致」。

### 用 trigger state machine 驗證假設

> "The ILA has an advanced trigger mode called trigger state machine, which allows for sequenced triggers. This allowed us to check the above assumption by first having the IFU make a memory request and then having the LSU make a request. If the trigger occurred, then we knew the assumption failed"
> — p.784.e102

中文解釋：**這是一個很漂亮的驗證手法**——不是抓波形慢慢看，而是**把「假設被違反」本身寫成觸發條件**。如果觸發了，假設就是錯的，而且順便拿到當下的處理器狀態。

### 之後加進回歸測試

> "The ahb_ram tests use variations of the rv64gc configuration and run the floating-point fadd_b11-01 test. These enable or disable burst mode and change latencies between the caches and main memory to be 0, 1 or 2 cycles, which latencies are designed to specifically trigger this scenario."
> — p.784.e102

中文解釋：**找到 bug 之後，把觸發條件變成可重現的測試**。關鍵是「調整快取與主記憶體之間的延遲為 0、1 或 2 個週期」——**用可控的延遲人工製造出那個時序巧合**，不再需要靠運氣。這是驗證工程的標準做法：bug 修好之後，要有測試防止它復發。

## Bug 2：同時發生的例外

### 症狀

> "The Linux boot involves an M-mode timer interrupt with a concurrent instruction page fault. Because the page fault is handled in S-mode, the M-mode timer interrupt has higher priority and should be handled first; however, some really strange behavior emerged. mcause oscillated between 0x800...007 (machine timer interrupt) and 0x7 (store access fault), settling on 0x7 after several cycles. Then, the IFU fetched an invalid address that was neither the mepc or sepc."
> — p.784.e102

中文解釋：**`mcause` 在兩個值之間震盪**——這是一個很不尋常的症狀。`mcause` 是 CSR，正常來說一個 trap 只會寫一次。震盪表示它是由**組合邏輯**驅動的，而那個組合邏輯的輸入還在變。

### 根因

> "The oscillating mcause pointed to a possible root cause. Committed{F/M} indicate the IFU/LSU are processing an in-flight bus transaction. When either is high, it prevents a TrapM and would also clear the msb of mcause. The LSU correctly disables bus access on TrapM; however, the IFU did not. In the first cycle of the trap, mcause was set correctly to 0x800...007, but because the bus fetched data from an invalid region due to a branch misprediction, CommittedF raised, which forced InterruptM to go low and made the trap look like an exception (0x7). The solution was to disable bus accesses on TrapM."
> — p.784.e102

中文解釋：事件的連鎖：
1. M-mode 計時器中斷發生，`mcause = 0x800...007`（最高位元 = 1 表示中斷）
2. 但因為**分支預測錯誤**，IFU 正在從一個無效位址取指
3. 那次取指讓 `CommittedF` 拉高（表示「匯流排交易進行中」）
4. `CommittedF` 高就會壓掉 `InterruptM`，**把 `mcause` 的最高位元清掉** → 變成 0x7（看起來像例外而不是中斷）
5. 於是 `mcause` 在兩者間震盪

**修法是一行：trap 發生時 IFU 也要停止匯流排存取**（LSU 本來就有做，IFU 漏了）。

**這個 bug 的教訓**：`Committed{F/M}` 這個機制（第 12 章）的用意是「交易已經發出去就不能反悔」，但它被套用在一次**根本不該發生的取指**（分支預測錯誤的路徑）上。

## 23.4.3 關鍵路徑分析：把時脈從 15 MHz 提到 20 MHz

### 起點

> "The first Wally version to boot Linux on the Arty A7 FPGA only ran at 15 MHz or a critical path of 1/15 MHz = 66.7 ns. By analyzing the timing paths, it was possible to increase the clock speed to 20 MHz with some simple RTL modifications."
> — p.784.e103

中文解釋：**33% 的時脈提升，只靠幾個 RTL 小改動**。

### 問題路徑：PC+4 加法器拖累 HPTW

> "Instructions spanning two virtual pages make two ITLB accesses. The PC + 4 adder that increments the virtual address is part of the unoptimized critical path. ... the critical path begins at the PCF register pcreg/q_reg[3]/Q and passes through the PC + 4 adder PCPlus4F_inferred_i_4/O[0], through the spill logic (PCSpillF), and into the HPTW. The HPTW uses PCPlus4F to walk the page table on a TLB miss and produce HPTWAdr."
> — p.784.e103

中文解釋：這條路徑串了三個東西：
```
PCF 暫存器 → PC+4 加法器 → spill 邏輯 → HPTW → 頁表位址
```

**為什麼會有這條路徑？** 因為一條指令可能跨越兩個虛擬頁（第 14 章的 spill，第 11 章的 ITLB）。跨頁時要用 `PC+4` 的位址去查第二個頁——所以 HPTW 的輸入依賴於加法器的輸出。

### 解法：multicycle path

> "This greatly increases the critical path by placing the PC + 4 adder at the start of the path. However, this incremented address is not required in the same cycle. This is called a multicycle path, which can be resolved in two ways. First, a register in the HPTW samples PC + 4 to prevent the path from existing. Second, we write a multipath timing constraint which specifies this path takes 2 cycles. The first option is easier but consumes extra hardware. It also has the advantage of carrying over to the ASIC implementation. The second option uses less hardware but is hard to maintain if the hardware is updated."
> — p.784.e103–e104

中文解釋：**關鍵洞察是「這個遞增的位址不需要在同一個週期用到」**——所以它根本不該算在關鍵路徑裡。

兩種解法的取捨：

| 方法 | 優點 | 缺點 |
| --- | --- | --- |
| 在 HPTW 加一個暫存器 | 簡單、**ASIC 也能受惠** | 多一點硬體 |
| 寫 multicycle timing constraint | 不花硬體 | 硬體改動時容易失效、難維護 |

**Wally 選了第一個**（Fig. 23.11 顯示路徑起點不再是 `PCF`）。這是一個好的工程判斷：約束檔是「告訴工具別檢查這條路」，一旦設計改了而約束沒跟著改，就會產生真正的時序違規而且**沒有任何警告**。

### 通用策略

> "By repeatedly iterating over the timing report and updating the RTL, we increased the FPGA's clock speed from 15 to 20 MHz. The general strategy checks if late arriving combinational inputs can be moved later into the critical path. For example, the LSU cancels bus and cache requests by lowering BusRW and CacheRW, respectively, during a trap. An early RTL implementation first fed TrapM into the cachefsm which then output BusRW and CacheRW, resulting in very long paths. We refactored the code, so these late arriving signals do not go through the cachefsm logic, which then reduced the critical path."
> — p.784.e104

中文解釋：**「把晚到的訊號往後推」是關鍵路徑優化的通用手法**。

第二個例子很典型：`TrapM` 是一個很晚才確定的訊號（要等所有例外條件都判斷完）。原本的寫法是 `TrapM → cachefsm → BusRW/CacheRW`，等於在一條已經很晚的訊號後面又串了一整個狀態機。重構後讓 `TrapM` **直接**去關掉 `BusRW`/`CacheRW`（繞過 `cachefsm`），路徑就短了。

原則是：**晚到的訊號應該只驅動最後一級的邏輯（通常是一個 AND 或多工器），不要讓它穿過一整串組合邏輯。**

## 所以呢

這節的三個教訓值得帶走：

1. **回歸測試通過 ≠ 沒有 bug**。兩個 bug 都需要極特殊的時序巧合，只有跑五億條指令的 Linux 開機才撞得到。這是 FPGA emulation 存在的理由。

2. **除錯的關鍵是把假設變成可檢測的條件**。Bug 1 的突破點是用 trigger state machine 直接檢測「EBU 的假設被違反」，而不是盯著波形猜。找到之後再用可控延遲把它變成回歸測試。

3. **關鍵路徑優化的核心是「晚到的訊號要放在最後」**。33% 的時脈提升來自兩個觀察——`PC+4` 不需要在同一週期用到、`TrapM` 不該穿過 `cachefsm`。這兩個都不是「讓邏輯變快」，而是「重新安排邏輯的順序」。
