# 5.9 Functional Coverage

> 原書 p.221–226（Chapter 5: Design Verification）
> 含 5.9.1 riscvISACOV、5.9.2 Directed Tests、5.9.3 Constrained Random Tests

## 這節在講什麼

**補上程式碼覆蓋率補不了的那一半。**

兩者的分工一句話講完：
- **程式碼覆蓋率**：**寫出來的程式碼**有沒有都跑過
- **功能覆蓋率**：**該有的功能**有沒有都測過

**差別在於：程式碼覆蓋率偵測不到「某個功能根本沒被寫出來」**（5 章導論 p.195 明說）。

內容四塊：
1. 架構覆蓋率 vs 微架構覆蓋率
2. **covergroup / coverpoint / bin 的三層結構**
3. **riscvISACOV**：現成的 RISC-V 架構覆蓋點集合（Table 5.5 是精華）
4. 兩種產生測試的工具：**testgen.py（directed）和 riscv-dv（constrained random）**

## 關鍵點

### 功能覆蓋率的兩個層次

> "**Code coverage measures whether all code is exercised, while functional coverage measures
>  whether all features have been exercised** [Mehta20]. Functional coverage includes
>  *architectural* coverage, which applies to any core supporting a particular extension, and
>  *microarchitectural* coverage, which is specific to an implementation, stressing features
>  such as pipeline hazards, interrupts, cache and bus systems, and branch prediction."
> — p.221

中文解釋：**兩種功能覆蓋率的區分很重要：**

| 類型 | 適用範圍 | 測什麼 |
| --- | --- | --- |
| **架構覆蓋率** | **任何支援該擴充的核心**（可共用！） | 指令、暫存器、運算元的各種組合 |
| **微架構覆蓋率** | **特定實作專屬** | **pipeline hazard、中斷、cache 與匯流排系統、分支預測** |

**架構覆蓋率可以共用**——這就是 riscvISACOV 能當成現成套件的原因（5.9.1）。
**微架構覆蓋率必須自己寫**——因為它測的是「你的實作」的特性
（呼應 1.2 節的 architecture / microarchitecture 分離）。

**微架構覆蓋率的四個重點正是本書後面的章節**：
hazard（第 7 章）、中斷（第 8 章）、cache 與匯流排（第 9、10 章）、分支預測（第 13 章）。

### 好的覆蓋點很難設計

> "Functional coverage begins with the DV plan defining what features need to be covered. For
>  example, in RISC-V, every instruction should be covered, using every register and corner
>  cases appropriate to that instruction. **Experience shows that coverage that is easy to
>  describe doesn't catch many bugs, and coverage that catches hard bugs takes a lot of
>  thought to describe.**"
> — p.221

中文解釋：**最後那句是本節最誠實的一句話，值得記住：**

**「容易描述的覆蓋抓不到什麼 bug；能抓到難 bug 的覆蓋需要花很多心思才描述得出來。」**

這解釋了為什麼功能覆蓋率是個工程——
「每條指令都執行過」很好寫但價值有限；
「這條指令的目的暫存器和來源暫存器相同時，且前一條指令剛好寫了那個暫存器」
才是抓 bug 的覆蓋點，但要想得到才寫得出來。

（呼應 5.2 節：DV plan 的子功能要包含「來源與目的重疊的所有組合」。）

### covergroup / coverpoint / bin 的三層結構

> "SystemVerilog covergroup and coverpoint statements define how the coverage is measured.
>  **A covergroup consists of related coverpoints sampled at a particular time, such as
>  coverpoints for a particular instruction. The coverpoints define the specific coverage,
>  such as using every destination register. Each coverpoint has one or more bins. For
>  example, the destination register coverpoint has 32 bins, one for each possible register.**"
> — p.222

中文解釋：**三層結構，用具體例子理解：**

```
covergroup add_cg           ← 一個 covergroup = add 這條指令的所有覆蓋點
├── coverpoint cp_rd        ← 一個 coverpoint = 「目的暫存器有沒有都用到」
│   ├── bin x0              ← 32 個 bin，每個暫存器一個
│   ├── bin x1
│   └── ... bin x31
├── coverpoint cp_rs1       ← 另一個 coverpoint
└── coverpoint cp_rd_sign   ← 2 個 bin（正、負）
```

**「sampled at a particular time」（在特定時間取樣）是關鍵**——
covergroup 不是持續監看，而是在某個事件發生時（這裡是指令完成時）採樣一次。

### 怎麼量測，以及和 lock-step 的關係

> "Functional coverage measurement involves running tests while the simulator monitors which
>  coverpoint bins and assertions were hit. **By also running the tests in lockstep mode
>  against a reference model, you can ensure that the RTL produces the correct results for
>  each of these coverpoints.**"
> — p.222

中文解釋：**這裡揭露了一個關鍵的組合——覆蓋率和正確性是兩件事：**

- **功能覆蓋率只說「這個情況有測到」**
- **lock-step 才說「這個情況的結果是對的」**

**兩者一起跑，才同時得到「測夠了」和「測對了」。**
（呼應 5.6 節：RVVI-TRACE 一份輸出餵兩個用途。）

**停止準則（p.222）：**
> "When functional coverage reaches 100%, the verification engineer knows enough tests have
>  been run and all features in the DV plan have been exercised."

**功能覆蓋率 100% = DV plan 裡所有功能都測過了。**

**directed 和 random 的分工（p.222）：**
> "Functional coverage tests can be directed or random. Many features are easy to test with
>  directed tests, **but some corner cases are hard to reach and are easier to cover with
>  constrained random tests.**"

（呼應 5.1.1 節：兩者互補。）

### riscvISACOV：現成的架構覆蓋點

> "riscvISACOV is a set of SystemVerilog architectural functional coverpoints developed by
>  Imperas (now Synopsys). They cover most of the common RISC-V extensions. **A set of RV32I
>  coverpoints are on a public repository [github.com/riscv-verification/riscvISACOV], and a
>  larger set are available under a commercial license.**"
> — p.222

中文解釋：**RV32I 的部分是公開的，完整的要商業授權。**

**組織方式（p.222）：**
> "riscvISACOV has coverage definition files for every extension it supports (e.g., RV32I,
>  RV64I, RV64M, etc.). Each file contains a covergroup for each instruction in that extension.
>  Each covergroup contains various coverpoints."

**每個擴充一個檔案 → 每條指令一個 covergroup → 每個 covergroup 多個 coverpoint。**

**取得狀態的方式（p.222）：**
> "riscvISACOV uses the RVVI interface (see Section 5.6.1) to access the architectural state.
>  **The ins variable contains the current instruction sampled on the rising edge of the clock
>  when it completes**, including information such as the name, source and destination register
>  identifiers and values, and whether a trap occurs."

**又是 RVVI——同一個介面第三次出現**（lock-step、功能覆蓋率、這裡的狀態存取）。

### Table 5.5：RV{32/64}I 的覆蓋點清單（本節精華）

中文解釋：**這張表（p.223）就是「一條整數指令該測哪些面向」的完整清單，
非常值得記，因為它可以直接套用到任何 ISA 的驗證：**

| 覆蓋點 | 說明 | bin 數 |
| --- | --- | --- |
| `cp_asm_count` | **這條指令有被用到嗎** | 1 |
| `cp_rd` / `cp_rs1` / `cp_rs2` | **每個暫存器都被使用過** | 各 32 |
| `cp_rd_sign` / `cp_rs1_sign` / `cp_rs2_sign` | 正、負 | 各 2 |
| `cp_offset` | | 2 |
| `cp_imm_sign` | 0、正、負 | 3 |
| **`cr_rs1_rs2`** | **來源符號的 cross-product** | 4 |
| `cr_rs1_imm` | | 6 |
| **`cmp_rd_rs1_eq` / `cmp_rd_rs2_eq`** | **目的與來源使用同一個暫存器** | 各 32 |
| **`cmp_rd_rs1_rs2`** | **三個暫存器全部相同** | 32 |
| `cmp_rd_rs1_eqval` / `cmp_rd_rs2_eqval` | 暫存器內容相同 | 各 2 |
| **`cp_rd_toggle` / `cp_rs1_toggle` / `cp_rs2_toggle`** | **每個位元都出現過 0 和 1** | 各 2×XLEN |
| **`cp_rd_maxvals` 等** | **0, 1, 2^XLEN−1, 2^(XLEN−1)−1, 2^(XLEN−1)+1, 2^XLEN−1** | 各 6 |
| **`cp_gpr_hazard`** | **None、RAW、WAR、WAW** | 4 |
| `cp_mem_hazard` | None、RAW | 2 |
| `cp_mem_unaligned` | 是、否 | 2 |

**五個值得注意的設計：**
1. **`cross`（`cr_` 前綴）**：兩個覆蓋點的**組合**，不只是各自都測過
2. **`cmp_rd_rs1_eq` 這組（目的與來源重疊）**——呼應 5.2 節說的 bug 高發區
3. **`toggle` 覆蓋**：**每一個位元都要出現過 0 和 1**——
   這正是 5.1.1 節那個邊欄擔心的「某一欄接錯」的檢測手段
4. **`maxvals` 就是 5.1.1 節的 corner case 清單**
5. **`cp_gpr_hazard`（RAW/WAR/WAW）是微架構覆蓋率**混在架構覆蓋點裡——
   pipeline hazard 是實作特性（第 7 章）

### riscvISACOV 的實際程式碼

中文解釋：Fig. 5.5（p.224–226）是 `add` 指令 covergroup 的節錄。
**幾個值得學的語法模式：**

**（1）covergroup 宣告與取樣函式**
```systemverilog
covergroup add_cg with function sample(ins_rv32i_t ins);
  option.per_instance = 1;
  option.comment = "Add";
```

**（2）基本 coverpoint，用 `iff` 排除 trap**
```systemverilog
cp_asm_count : coverpoint ins.ins_str == "add"  iff (ins.trap == 0)  {
    option.comment = "Number of times instruction is executed";
    bins count[]  = {1};
}
```
**`iff (ins.trap == 0)` 出現在幾乎每一個 coverpoint**——
**發生 trap 時指令沒有正常完成，不該計入覆蓋。**

**（3）用範圍定義 bin**
```systemverilog
cp_rd_sign : coverpoint int'(ins.current.rd_val)  iff (ins.trap == 0)  {
    bins neg  = {[$:-1]};      // 從最小值到 -1
    bins pos  = {[1:$]};       // 從 1 到最大值
}
```
**`$` 代表該型別的極值**——這樣寫和 XLEN 無關，可攜性好。

**（4）cross coverage**
```systemverilog
cr_rs1_rs2 : cross cp_rs1_sign, cp_rs2_sign  iff (ins.trap == 0) {
    option.comment = "Cross coverage of RS1 sign and RS2 sign";
}
```
**`cross` 關鍵字產生組合覆蓋**（2 × 2 = 4 個 bin）。

**（5）wildcard bins 做 toggle 覆蓋**
```systemverilog
cp_rd_toggle : coverpoint unsigned'(ins.current.rd_val)  iff (ins.trap == 0) {
    wildcard bins bit_0_0  = {32'b???????????????????????????????0};
    wildcard bins bit_0_1  = {32'b???????????????????????????????1};
    wildcard bins bit_1_0  = {32'b??????????????????????????????0?};
    ...
    wildcard bins bit_31_1 = {32'b1???????????????????????????????};
}
```
**`wildcard bins` 配上 `?` 做 don't care**——
**每個位元兩個 bin（0 和 1），32 位元共 64 個 bin。**
（`?` 的用法呼應 4.2.2.2 節的 `casez`。）

**（6）maxvals 用具名的具體值**
```systemverilog
cp_rd_maxvals : coverpoint unsigned'(ins.current.rd_val)  iff (ins.trap == 0) {
    wildcard bins zeros = {0};
    wildcard bins min   = {32'b10000000000000000000000000000000};
    wildcard bins max   = {32'b01111111111111111111111111111111};
    wildcard bins ones  = {32'b11111111111111111111111111111111};
}
```

**（7）用 `` `ifdef `` 分級**
```systemverilog
`ifdef COVER_LEVEL_COMPL_EXT
  ...
`endif
`ifdef COVER_LEVEL_DV_UP_BAS
  ...
`endif
```
**覆蓋率有分等級**——基本等級和完整等級，依需要開啟。

**（8）hazard 覆蓋用函式**
```systemverilog
cp_gpr_hazard : coverpoint check_gpr_hazards(ins.hart, ins.issue)  iff (ins.trap == 0) {
    option.comment = "GPR Hazard";
    bins hazards[] = {NO_HAZARD, RAW_HAZARD, WAR_HAZARD, WAW_HAZARD};
}
```

### 兩種測試產生器

**（1）testgen.py：產生 directed 測試（5.9.2，p.222、226）**

> "Test generators produce directed tests to cover the easy functional coverage cases
>  systematically and efficiently."
> — p.222

> "The addins/cvw-arch-verif/bin/testgen.py script produces directed tests in assembly
>  language. They are placed in addins/cvw-arch-verif/tests. **testgen.py reads the coverage
>  files from the fcov directory to determine which directed tests to create for which
>  instructions.**"
> — p.226

中文解釋：**這個設計很聰明：測試產生器「讀覆蓋率定義檔」來決定要產生什麼測試。**

**覆蓋點定義 → 自動產生對應的 directed 測試。**
這樣「要測什麼」只需要寫一次（在覆蓋率檔案裡），測試自動跟著走。

（執行方式見第 5.11.12 節。書上邊欄提醒：**這些路徑會隨測試演進而改變**，p.226 邊欄。）

**（2）riscv-dv：constrained random（5.9.3，p.226）**

> "riscv-dv is a widely used open-source constrained random test generator for RISC-V
>  [github.com/chipsalliance/riscv-dv]. **It was originally developed at Google and is now
>  maintained by Chips Alliance. It consists of Python scripts that invoke SystemVerilog UVM
>  modules that emit assembly language test files.** riscv-dv is included as a submodule in
>  Wally."
> — p.226

中文解釋：**架構是「Python 腳本 → SystemVerilog UVM 模組 → 組合語言測試檔」。**
（這是 5.1 節 Table 5.1 說的 object-oriented 子集的實際用途。）

**但書上邊欄很誠實（p.226 邊欄）：**
> "At the time of this writing, **Wally is not regularly using riscv-dv, and scripts have
>  broken.**"

**Wally 目前沒有固定在用 riscv-dv，腳本壞掉了。**
——這是開源工具生態的現實：**工具存在不等於能用。**

## 名詞表

| 名詞 | 意思 |
| --- | --- |
| **Functional coverage** | 功能覆蓋率。量測**所有功能**有沒有被測過（對比程式碼覆蓋率量測程式碼） |
| **Architectural coverage** | 架構覆蓋率。適用於任何支援該擴充的核心，**可共用** |
| **Microarchitectural coverage** | 微架構覆蓋率。實作專屬：pipeline hazard、中斷、cache、分支預測 |
| **covergroup / coverpoint / bin** | 相關覆蓋點的集合（特定時間取樣）/ 具體的覆蓋項目 / 覆蓋項目的分類槽 |
| `cross` | 交叉覆蓋。兩個覆蓋點的組合 |
| `iff (ins.trap == 0)` | 條件取樣。**trap 時指令未正常完成，不計入覆蓋** |
| `wildcard bins` | 用 `?` 做 don't care 的 bin，常用於 toggle 覆蓋 |
| **Toggle coverage** | 每個位元都出現過 0 和 1 |
| RAW / WAR / WAW hazard | Read-after-write / Write-after-read / Write-after-write 相依 |
| **riscvISACOV** | Imperas（現 Synopsys）開發的 RISC-V 架構功能覆蓋點集合；RV32I 部分公開 |
| `testgen.py` | **讀覆蓋率定義檔，自動產生對應的 directed 測試** |
| riscv-dv | 開源 constrained random 測試產生器（Google 起源，Chips Alliance 維護） |

## 所以呢

**程式碼覆蓋率問「寫的程式碼跑過沒」，功能覆蓋率問「該有的功能測過沒」——
只有後者能發現「這個功能根本沒寫」。**

三件帶得走的事：
1. **Table 5.5 是「一條指令該測哪些面向」的通用清單**：
   每個暫存器、符號組合（cross）、**目的與來源重疊**、**每個位元的 toggle**、
   極值、**hazard 類型**。這份清單可以套用到任何 ISA 的驗證。
2. **功能覆蓋率 + lock-step 要一起跑**——
   前者說「測到了」，後者說「結果對」，缺一不可。
3. **`testgen.py` 的設計值得學**：**測試產生器讀覆蓋率定義檔**，
   所以「要測什麼」只需要在一個地方定義。

還有一句該記住的話：
**「容易描述的覆蓋抓不到什麼 bug；能抓難 bug 的覆蓋需要花很多心思才寫得出來。」**

下一節（5.10）是驗證的終極目標：用數學證明而非測試。
