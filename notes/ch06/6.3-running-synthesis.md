# 6.3 Running Synthesis

> 原書 p.268–269（Chapter 6: Logic Synthesis）

## 這節在講什麼

**很短，就是「怎麼跑合成」的操作說明。**

三件事：
1. **基本指令與四個參數**（DESIGN、TECH、CONFIG、FREQ）
2. **執行結果放在哪、包含什麼**
3. **三種模式**：一般合成、**physical synthesis（topographical mode）**、使用 SRAM

**最值得記的是那四個參數，以及 rv32e 幾分鐘 vs rv64gc 超過一小時的差距。**

## 關鍵點

### 基本指令

> "Run synthesis with:"
> — p.268

```bash
$ cd $WALLY/synthDC
$ make synth DESIGN=wallypipelinedcore TECH=sky130 CONFIG=syn_rv32e FREQ=330
```

中文解釋：**四個參數的意義：**

| 參數 | 意義 | 範例 |
| --- | --- | --- |
| **`DESIGN`** | 頂層設計模組 | `wallypipelinedcore` |
| **`TECH`** | 目標製程 | `sky130`、`sky90`、`tsmc28`、**`tsmc28psyn`** |
| **`CONFIG`** | Wally 組態 | `syn_rv32e`、`syn_rv64gc`、`syn_sram_rv32gc` |
| **`FREQ`** | 目標頻率（MHz） | `330`、`3000`、`10000` |

**（`CONFIG` 選項在第 6.5.1 節說明；工作目錄是 `$WALLY/synthDC`。）**

**Makefile 用兩個檔案（p.268）：**
> "The Makefile uses `.synopsys_dc.setup` and `scripts/synth.tcl`, **both of which are necessary
>  to read to follow this section.**"

**書上明說這兩個檔案「必須讀過才能跟上這一節」。**

**目標頻率的選法（p.268）：**
> "The target frequency is 330 MHz, **a little faster than achievable.**"

**故意設得比可達成的稍快一點**——這樣工具才會盡力最佳化
（呼應 6.2.2 節「掃描目標頻率取最右邊灰點」的方法）。

### 執行時間：兩個數量級的差距

> "**Synthesis takes only a few minutes to run because the rv32e configuration is simple.
>  In contrast, synthesizing the rv64gc configuration with 16-KiB caches can take more than an
>  hour. Watch for warnings and errors in the messages printed.**"
> — p.268

中文解釋：**rv32e 幾分鐘，rv64gc 超過一小時。**
**這個差距決定了開發節奏**——改完 RTL 先用 rv32e 快速確認，
最後才跑 rv64gc。（呼應 5.11.6 節的兩層回歸策略。）

### 執行結果的組織

> "The synthesis results are stored in `runs` within a directory named for the design,
>  configuration, technology, frequency, date, and git hash for future reference."
> — p.268

中文解釋：**目錄名稱包含六樣資訊**：
設計、組態、製程、頻率、**日期、git hash**。

例如：`wallypipelinedcore_rv32e_orig_sky130nm_330_MHz_2023-11-03-07-38__5e84d5e6`

**把 git hash 放進目錄名是很好的做法**——
**幾個月後看到某個合成結果，可以精確回到當時的程式碼。**
（第 6.4 節邊欄會說明怎麼用：`git checkout HASH`。）

**磁碟管理警告（p.268 邊欄）：**
> "**The run results can be large. You should delete the contents of the run directory
>  (`rm -rf runs`) periodically to save disk space** unless you need to refer to old runs."

### 執行過程做了什麼

> "The scripts copy all the Verilog code into a subdirectory called `hdl`. **The first time
>  synthesis is run, it analyzes the Liberty (.lib) file, which describes the cell library, and
>  caches the analyzed library in a directory called `alib-52`.**"
> — p.268

中文解釋：**Liberty（`.lib`）檔案描述元件庫**
（延遲、功耗、面積、電容——呼應 6.2 節的 `libppa.pl`）。
**第一次分析後快取起來，之後就不用重跑。**

**組態與 wrapper（p.268）：**
> "The scripts copy the specified configuration into the `config` subdirectory. As discussed in
>  Section 4.2.5.6, the parameterized top-level module requires a wrapper to load the config.vh
>  file and parameter-defs.vh. **This file (e.g., `wallypipelinedcorewrapper`) is automatically
>  generated by synth.tcl using wrapperGen.py in the run hdl subdirectory if the top-level design
>  module contains the keyword cvw_t. synth.tcl synthesizes the wrapper to pass the parameters to
>  the top-level module but generates reports for the top-level module.**"

中文解釋：**wrapper 的角色（呼應 4.2.5.6 和 4.3.1.4 節）：**
- **偵測方式**：頂層模組含有關鍵字 `cvw_t` 就自動產生 wrapper
- **產生工具**：`wrapperGen.py`
- **合成的是 wrapper（為了傳參數），但報告是針對頂層模組產生的**

**這個區分很重要**：wrapper 只是為了餵參數，不該出現在報告裡。

### synth.tcl 的三個關鍵指令

> "The synth.tcl script mostly uses commands that are custom to Design Compiler, but it also uses
>  native Tcl commands to read environment variables, copy files, and perform actions
>  conditionally. **The key Design Compiler commands are `analyze`, `elaborate`, and
>  `compile_ultra`, which read the Verilog and run synthesis.**"
> — p.269

中文解釋：**三個指令正好對應 6.1 節說的合成步驟：**

| 指令 | 對應步驟 |
| --- | --- |
| **`analyze`** | 語法檢查，轉成 HDL 無關的中間格式 |
| **`elaborate`** | 映射到技術無關的通用庫 |
| **`compile_ultra`** | **映射到實際元件庫並最佳化**（`ultra` 表示最高努力等級） |

### 三種合成模式

**（1）一般合成（SKY130）**
```bash
$ make synth DESIGN=wallypipelinedcore TECH=sky130 CONFIG=syn_rv32e FREQ=330
```

**（2）TSMC28（更高頻率、更小面積）**
```bash
$ make synth DESIGN=wallypipelinedcore TECH=tsmc28 CONFIG=syn_rv32e FREQ=3000
```
**注意頻率從 330 MHz 跳到 3000 MHz**——差了約 9 倍，
和 6.2 節 FO4 延遲的比例（99.5 / 11.6 ≈ 8.6）吻合。

**（3）Physical synthesis / topographical mode（p.269）**
```bash
$ make synth DESIGN=wallypipelinedcore TECH=tsmc28psyn CONFIG=syn_rv32e FREQ=3000
```
> "With suitable technology files (called Milkyway and TLU+), Design Compiler can run *physical
>  synthesis*, creating an internal model of cell placement at the same time it maps Verilog onto
>  logic gates. **This allows Design Compiler to estimate wire lengths and optimize appropriately,
>  producing area and delay that agree with final placement and routing results to within about
>  5%. This synthesis is also called *topographical mode*. TSMC28 results in this chapter are
>  produced using topographical mode for best accuracy.**"

中文解釋：**physical synthesis 的價值：邊映射邊估計擺放位置，
所以能估算線長，結果與最終 P&R 相差約 5% 以內。**
（呼應 6.1 節：「線長顯著影響時序」。）

**`TECH=tsmc28` 是無 physical synthesis，`TECH=tsmc28psyn` 是有。
本章的 TSMC28 結果都用 topographical mode。**

**（4）使用 SRAM（p.269）**
```bash
$ make synth DESIGN=wallypipelinedcore TECH=tsmc28psyn CONFIG=syn_sram_rv32gc FREQ=3000 USESRAM=1
```
> "When the USESRAM configuration is set, the synthesis scripts will also load the memory
>  libraries from Section 6.2.3 for most compact cache RAM, and branch predictor tables."

（呼應 6.2.3 節 Table 6.5：SRAM 讓 cache 和分支預測器表小很多。）

**Design Compiler 使用者手冊（p.269 邊欄）：**
> "The Design Compiler User Guide is proprietary. Licensed institutions can download it from
>  solvnet.synopsys.com. **If you are serious about optimizing your synthesis results, it is worth
>  reading.**"

## 名詞表

| 名詞 | 意思 |
| --- | --- |
| `DESIGN` / `TECH` / `CONFIG` / `FREQ` | 合成的四個參數：頂層模組 / 製程 / 組態 / 目標頻率（MHz） |
| `.synopsys_dc.setup` / `scripts/synth.tcl` | Design Compiler 的設定檔 / 合成腳本 |
| **Liberty（`.lib`）檔** | 描述元件庫的延遲、功耗、面積、電容；分析後快取在 `alib-52` |
| `wrapperGen.py` | 偵測到 `cvw_t` 關鍵字時自動產生參數 wrapper |
| **`analyze` / `elaborate` / `compile_ultra`** | Design Compiler 的三個核心指令，對應合成三步驟 |
| **Physical synthesis / topographical mode** | 合成時同時建立擺放模型以估算線長；**與最終 P&R 相差約 5%** |
| Milkyway / TLU+ | physical synthesis 所需的技術檔案 |
| `tsmc28` vs `tsmc28psyn` | 無 physical synthesis / 有 |
| `USESRAM=1` | 載入記憶體庫，用 SRAM 取代 flop-based 記憶體 |

## 所以呢

**跑合成的四個參數：`DESIGN`、`TECH`、`CONFIG`、`FREQ`。**

三件實務要點：
1. **rv32e 幾分鐘，rv64gc 超過一小時**——先用小組態快速迭代。
2. **目標頻率設得比可達成的稍快一點**，工具才會盡力最佳化。
3. **TSMC28 要用 `tsmc28psyn`（topographical mode）**——
   它會估算線長，結果與最終 P&R 相差 5% 以內。

還有一個好習慣：**執行目錄名稱包含 git hash**，
幾個月後能精確回到當時的程式碼。但**記得定期 `rm -rf runs` 清磁碟。**
