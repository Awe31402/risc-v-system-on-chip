## 關鍵點

### 組態與基本結構

> "**Wally has optional configurable level 1 instruction and data caches (L1I$/L1D$). Currently, it does not
>  have any higher-level caches.... It contains three main submodules: `cacheway`, `cachefsm`, and
>  `cacheLRU`. An N-way associative cache stores lines in N `cacheway` modules, each of which contains data,
>  tag, and status bits for each line. The {I/D}CACHE_NUMWAYS configuration parameter specifies N.**"
> — p.443

**Table 10.1（p.444）的組態參數，這張表是本節所有圖的基準：**

| 參數 | 名稱 | 值 | 說明 |
| --- | --- | --- | --- |
| **Line size** | `LINELEN` | **64 bytes** | 512 bits = 2⁶ bytes = 8 doublewords |
| **Number of ways** | `NUMWAYS` | **4** | |
| **Number of sets** | `NUMSETS` | **64** | 2⁶ sets |
| **Way size** | | **4 KiB** | NUMSETS × LINELEN |
| **Cache size** | | **16 KiB** | NUMWAYS × NUMSETS × LINELEN |

### I$ 和 D$ 共用同一份程式碼

> "**The I$ and D$ both use the same configurable SystemVerilog `cache` module. The module has a
>  READ_ONLY_CACHE parameter, which is 0 for the D$ and 1 for the I$. Both types of caches support reads,
>  but only data caches support writes, writebacks, and flushing dirty lines (READ_ONLY_CACHE = 0).
>  Both instruction and data caches support invalidation.**"
> — p.444

中文解釋：**一個參數切換兩種 cache**（呼應 4.2.5 節的參數化設計）。

| 功能 | I$ | D$ |
| --- | --- | --- |
| 讀 | ✓ | ✓ |
| **寫、writeback、flush dirty line** | **✗** | **✓** |
| **Invalidate** | **✓** | **✓** |

### 兩個階段：Address 與 Data

> "**The caches use synchronous memories that expect the address, control, and write data to set up before
>  the rising edge of the clock. They read or write on the rising edge. Unlike the rest of the CPU core, the
>  caches do not use suffixes F, D, E, M and W to denote the pipeline stage because the same SystemVerilog
>  code (RTL) is used for both caches. Caches operate in two pipeline stages, Address and Data.**"
> — p.444

中文解釋：**cache 不用 F/D/E/M/W 後綴，因為同一份 RTL 給兩個 cache 用**
（呼應 4.3.1.2 節：pipeline 外的訊號沒有後綴）。

**兩階段的分工（p.444–445）：**

| 階段 | 做什麼 |
| --- | --- |
| **Address** | **`NextAdr` 的低位元（`NextSet`）在時脈邊緣前 setup，指出要讀哪個 set** |
| **Data** | **cache 讀出各 way，檢查 valid 位元、比對 tag 與 `PAdr` 的上位元判斷是否命中** |

**`PAdr` 比 `NextAdr` 晚一個週期；啟用虛擬記憶體時還會被 MMU 轉譯（第 11 章）。**

**一個關鍵的最佳化（p.445）：**
> "**The cache only needs a few of the address bits, called NextSet or Set, to specify which set to access.
>  These bits are the same in the virtual and physical addresss, so accessing the cache does not have to
>  wait for translation.**"

**set 位元在虛擬和實體位址中相同，所以存取 cache 不用等位址轉譯。**
**這就是「way size ≤ page size」的價值**（呼應 10.1.6 節）。

### `cacheway`：儲存陣列的實作

> "**It uses the following:
>  - Separate SRAM arrays to hold the data and tags
>  - Arrays of flip-flops to hold the status (valid and dirty) bits for each cache line so these bits can be
>    easily written or reset**"
> — p.446

中文解釋：**為什麼 status 位元用 flip-flop 而非 SRAM（p.447）：**
> "**The status bits may be modified independent of writing the data and tag arrays, so they are most
>  conveniently built from flops. The valid bits are reset on startup or invalidation. The data, tag, and
>  dirty bits are ignored if the valid bit is 0, so they do not require the overhead of reset circuitry.**"

**三個理由：**
1. **status 位元可以獨立於 data/tag 修改**
2. **valid 位元要能在啟動或 invalidate 時重置**（SRAM 沒有 reset）
3. **valid = 0 時 data/tag/dirty 都被忽略，所以它們不需要 reset 電路**

**面積最佳化（p.446）：**
> "**`cacheway` is one of the largest modules in Wally, so it is designed for area efficiency. The large data
>  and tag arrays are built from SRAM for density and energy efficiency. SRAM generators have a maximum
>  width, typically around 128 bits. Therefore, the 64-line × 512-bit wide data array is partitioned into
>  four 64 × 128-bit banks of SRAM. The arrays have byte write enables to support writing words or bytes
>  within the line. They also have chip enable pins to save power and retain their old data output when
>  disabled. When the hazard unit stalls the pipeline, the chip enable is turned off, so the cache retains
>  its output.**"

**三個實作細節：**
- **SRAM generator 最大寬度約 128 bit → 512-bit 的資料陣列切成 4 個 bank**
- **byte write enable 支援寫入 line 內的字或位元組**
- **chip enable 在 stall 時關閉以省電並保留輸出**

**（p.446 邊欄：Table 6.5 顯示 **SRAM 密度約是 flop-based 的 4 倍，能量約是一半**。）**

### 讀取命中的兩階段時序

> "- **Address stage: `CacheSetTag` sets up to read the tag and status arrays. `CacheSetData` sets up to read
>    the data array. CacheSetTag = CacheSetData = NextSet.**
>  - **Data stage: The SRAM arrays output the tag and data bits, ReadTag and ReadDataLine, and the valid
>    array outputs the valid bit, ValidWay. A hit occurs when the requesting address tag and the line's tag
>    match and that line is valid.**"
> — p.447–448

**Example 10.6（p.448–449）的完整追蹤：**
> "A processor loads 4 unsigned bytes from address 0x00_0000_8000_0384.... The cache line contains
>  0x0...0_AAAA_5555_1111_2222."

| Cycle | 階段 | 發生什麼 |
| --- | --- | --- |
| **0** | Address | `CacheSet{Tag/Data} = NextAdr[11:6] = 001110₂` = 14，**設定讀 line 14** |
| **1** | Data | 讀出 `ReadDataLine`、`ReadTag`、`Valid`；**tag 相符 → `HitWay = 1`、`SelectedWay = 1`**；`ReadDataLineWay` 輸出整條 line；**`subcachelineread` 用 word offset `PAdr[5:2] = 0001` 選出 `ReadDataWord = 0xAAAA_5555`** |

### 為什麼 tag 和 data 要分開定址（關鍵設計）

> "**Separate set signals, CacheSet{Tag/Data}, are needed to access the tag/status arrays and data arrays to
>  avoid structural hazards during back-to-back writes. Writes set up in the Address stage to read the tag
>  and status arrays (but, unlike reads, not the data array) and then set up in the Data stage to write the
>  data array.**"
> — p.448

中文解釋：**這是本節最重要的設計技巧。**

**寫入的兩階段（p.448）：**
| 階段 | 寫入時 |
| --- | --- |
| **Address** | `CacheSetTag = NextSet`，**讀 tag 和 status 陣列** |
| **Data** | tag/valid 輸出；**命中時 `CacheSetData = PAdr[11:6]`，設定寫入資料陣列** |

**好處（p.450）：**
> "**By not reading the data array in the Address stage (which is unnecessary for stores), back-to-back
>  stores do not have to stall because only the tag array is used in the Address stage, and only the data
>  array is used in the Data stage.**"

**Fig. 10.15（p.450）的時序：三個連續 store 命中，完全不用 stall。**
```
Cycle:    0                1                2                3
Store 1: [Setup read Tags][Setup Write Data]
Store 2:                  [Setup read Tags][Setup Write Data]
Store 3:                                   [Setup read Tags][Setup Write Data]
```

**「對 store 而言 `CacheSetData` 比 `CacheSetTag` 晚一個週期」**（p.451）。

**（p.450 邊欄的補充：**「status 陣列在兩個階段都會用到：Address 階段讀，
寫入時在 Data 階段寫。所以 **status 陣列是雙埠的**，可以在同一週期讀和寫。
相對地，**tag 和 data 陣列是單埠的，一個週期只能讀*或*寫**。」**）

### `SelectedWay`：三種來源

> "**The SelectedWay mux chooses whether a given cache way is selected to read or write a line.
>  SelectedWay equals:
>  - HitWay for regular loads and stores
>  - FlushWay for flushes (when FlushCache = 1)
>  - VictimWay for writing back a dirty line (when SelVictim = 1)**"
> — p.448

**分散式 AND-OR 多工器（p.448）：**
> "**The cache uses a distributed AND-OR multiplexer to read out the selected way. Each `cacheway` ANDs its
>  data (ReadDataLine) with SelectedWay, so only the selected way has a nonzero ReadDataLineWay.
>  The top-level cache module ORs these signals from each way to deliver ReadDataLineCache.**"

（呼應 4.2.5.5 節、9.2.2 節；Fig. 10.25 是這個結構的圖。）

### 寫入命中的時序

**Example 10.7（p.450–451）：寫 0x12345678 到 0x…0388，再寫 0xAABBCCDD 到 0x…03C8。**

| Cycle | 發生什麼 |
| --- | --- |
| **0** | store 1 的 Address 階段：`CacheSetTag = NextAdr[11:6] = 14` |
| **1** | store 1 的 Data 階段：**命中 → `SetDirtyWay = 1`**；`CacheSetData = PAdr[11:6] = 14`；**word offset `PAdr[5:2] = 1` → `LineByteMask = 0x…00F0`**；`LineWriteData = 0x12345678_…_12345678`（複製滿）。**同時**是 store 2 的 Address 階段：`CacheSetTag = 15` |
| **2** | store 2 的 Data 階段：word offset = 2 → `LineByteMask = 0x…0F00`，寫入 word 2 |

### 結構危障：store 後接 load

> "**Whereas back-to-back stores do not cause hazards, a store followed by a load does.... The hazard occurs
>  in cycle 1, where both the store and load want to access the data array: the store sets up to write the
>  data array and the following load wants to read the data array, so the load must stall by one cycle.**"
> — p.451–452

中文解釋：**Fig. 10.17（p.452）的衝突：
store 在 Data 階段要寫資料陣列，load 在 Address 階段要讀資料陣列——
但資料陣列是單埠的。**

**（p.452 邊欄：**「這個 hazard 和 7.2.2.3 節討論的 DTIM store delay hazard 完全相同。
IEU 的 controller 在 load 後接使用時 assert `LoadStallD`、
store 後接 load 時 assert `StoreStallD`。」**）

### Line fetch 的五個步驟

> "**If no cache way hits during a memory access (HitWay for all `cacheway`s is 0), the cache misses and must
>  fetch the data from the next level of the memory hierarchy. This requires the following:
>  - Selecting a cache way for the new line, potentially needing to evict a line to make room
>  - Writing back the evicted line if it is dirty
>  - Fetching a new line using the AHB cache interface (`ahbcacheinterface`) word by word into a fetch buffer
>  - For a store miss, merging WriteData into the appropriate position in the fetch buffer
>  - Writing the fetch buffer into the line of the selected way while updating the tag from PAdr and setting
>    the Valid bit. Dirty is set to 1 for a write or cleared to 0 for a read.**"
> — p.452

中文解釋：**五個步驟對應 `cachefsm` 的幾個狀態。**
**注意第四步：store miss 也要先把整條 line 抓進來再合併寫入資料**
（呼應 10.1.4 節）。

### Line writeback

> "**If a `cacheLRU` selects a dirty line for eviction, the line must first be written back to the next level
>  of the memory hierarchy. Fig. 10.18 shows how the victim way outputs its tag and data. When a cache way
>  evicts a line, FlushCache = 0 and VictimWay = 1. The cache's controller drives SelVictim = 1, so
>  SelectedDirty = 1. SelectedDirty is ANDed with the status array's dirty bit to check if the victim line
>  is dirty. The SelectedWay mux chooses VictimWay, which is 1, so the cache way outputs TagWay and
>  ReadDataLineWay. The cache writes the line in ReadDataLineWay back to the address indicated by TagWay and
>  CacheSetTag.**"
> — p.452

**寫回的位址 = `{TagWay, CacheSetTag, 000000}`**（呼應 Table 10.3）。

### Way Invalidation 與 `fence.i`

> "**The Zifencei RISC-V extension defines `fence.i` to ensure coherence between the I$ and D$. For example,
>  the OS may load a program or parts of a program into memory by copying them from other regions of memory.
>  Because this is performed using loads and stores in the OS code, these writes go through the D$ rather
>  than the I$, so the I$ may contain incorrect stale instructions. The `fence.i` instruction flushes the D$
>  to main memory and invalidates the I$ so that the I$ is forced to fetch the new instructions.
>  `fence.i` is an expensive operation, so fences should be used sparingly.**"
> — p.453

中文解釋：**`fence.i` 的具體場景：OS 用 load/store 把程式複製到記憶體，
這些寫入走 D$，所以 I$ 裡可能有過期的指令。**
（呼應 10.1.8、10.2 節。）

**Valid 陣列用可重置的 flip-flop，收到 reset 訊號時在時脈上升緣平行清除所有 valid 位元**（p.453）。

### `cachefsm`：七狀態機

> "**Fig. 10.19 shows the cache FSM (`cachefsm`), which handles cache misses and flushes. The FSM resets to
>  the Access state, where it accepts read, write, invalidate, and flush requests from the CPU. If the cache
>  hits on a read or write, it services the request immediately and remains in the Access state. Otherwise,
>  `cachefsm` sequences the multicycle operations to write-back, fetch, or flush cache lines.**"
> — p.454

中文解釋：**Fig. 10.19（p.454）的七個狀態與轉移：**

```
                    ┌─ AnyMiss & FlushCache（自環）
                    ↓
    Writeback ←── Access ──→ Flush
        │  ↑  AnyMiss&LineDirty  │  ↑
        │  └── AnyMiss&~LineDirty│  │ LineDirty
        ↓            ↓            ↓  │
      Fetch ──→ WriteLine ──→ AddressSetup ←── FlushWriteback
       (CacheBusAck)              ↑  (Stall 自環)
```

**Miss 的路徑（p.454）：**
> "**Read and write misses assert AnyMiss, select a victim line to evict using the `cachelru` module, write
>  back the victim if dirty, and fetch the missing line. If the victim is dirty, it must be evicted by
>  writing the line back over the bus (in the Writeback state). Each bus operation waits for CacheBusAck to
>  continue. Then the cache fetches the missing line over the bus (in the Fetch state). The cache writes the
>  missing line and tag into the selected way and sets the valid bit in the WriteLine state. Also in the
>  WriteLine state, writes merge the new word from WriteData into LineWriteData and set the dirty bit; reads
>  clear the dirty bit.**"

**`AddressSetup` 狀態的用途（p.454）：**
> "**Misses pass through the AddressSetup state before returning to the Access state because the next access
>  needs a cycle to set up the cache address (set bits) to the cache before accessing it.... If the other
>  cache is also stalling the pipeline, Stall is asserted to hold the read data (in the AddressSetup
>  state).**"

**Invalidate 在 Access 狀態發生（同時重置所有 valid 位元）；
Flush 走 Flush → FlushWriteback 的迴圈逐條寫回。**

**一個省週期的最佳化（p.456）：**
> "**After fetching a cache line, the `cachefsm` asserts SelFetchBuffer in the Writeline state to bypass the
>  `cacheway` SRAMs and select the desired word from the fetch buffer (supplied by the AHB cache interface)
>  instead. This saves a cycle as compared to waiting for the fetch buffer to be written to the cache and
>  then reading the desired word from the cache.**"

**直接從 fetch buffer 取字，不用等寫進 cache 再讀出來——省一個週期。**

### pLRU 的硬體實作（本節最精彩的部分）

> "**An N-way associative cache puts the pLRU tree into an (N-1)-bit LRU signal associated with each set.
>  On a miss, the cache selects the victim way from these LRU bits. The cache also updates the LRU bits after
>  each access.**"
> — p.456

**LRU 位元的編號規則（p.457）：**
> "**LRU[N-2] is the direction of the top node, and the remaining bits map to the lower bits, top to bottom
>  and left to right in the tree. In Fig. 10.20(a), LRU = 1100010.**"

**Fig. 10.20(a)（p.456）的 8-way 樹：**
```
                LRU[6]=1
        ┌──────────┴──────────┐
     LRU[5]=1              LRU[4]=0
    ┌────┴────┐          ┌────┴────┐
 LRU[3]=0  LRU[2]=0   LRU[1]=1  LRU[0]=0
  ┌─┴─┐     ┌─┴─┐      ┌─┴─┐     ┌─┴─┐
  0   1     2   3      4   5     6   7
                           ↑
                        LRU Way
```
**LRU = 1100010（從 LRU[6] 到 LRU[0]）。**

**找 victim 的遞迴（p.457）：**
> "**Fig. 10.20(b) shows the tree of multiplexers used to find the *new victim* way. Each node calculates its
>  new victim (LRU) way in its log₂N-bit NV (new victim) signal and then passes that signal to the node
>  above it. The overall victim way is the top node's new victim, NV[N-2], in this case NV[6].
>  In this example, LRU[6] = 1 chooses the victim from ways 4−7. LRU[4] = 0 chooses the victim from ways 4
>  and 5, and LRU[1] = 1 selects the victim as way 5 (NV[1] = 5). The signal (NV[1] = 5) is passed up the
>  tree using the multiplexers to make the new victim way 5 (NV[6] = 5).**"

**每個節點用自己的 LRU 位元選左右子樹的 NV，往上傳遞。**

**硬體大幅簡化（p.457）——這段很有洞見：**
> "**Fig. 10.20(b) uses (N-1) log₂N 2:1 muxes to select the victim way. However, the way numbers (0−7) are
>  constant, so the hardware simplifies dramatically, as shown in Fig. 10.21. The top multiplexer selects
>  ways 0−3 (000−011) when LRU[6] = 0 and ways 4−7 (100−111) when LRU[6] = 1, so this reduces to the msb of
>  NV[6][2] = LRU[6]. The lower multiplexers follow a similar pattern. The next most significant bit of the
>  victim (NV[6][1]) will be either LRU[5] or LRU[4], and the lsb will be LRU[3], LRU[2], LRU[1], or LRU[0].
>  In the example figure, NV[6][2:0] = {LRU[6], LRU[4], LRU[1]} = 101.**"

**關鍵洞見：way 編號是常數，所以整棵多工器樹簡化成「從 LRU 位元中挑出對應的三個」。**

```
VictimWayEnc[2] = LRU[6]                        （直接就是）
VictimWayEnc[1] = LRU[6] ? LRU[4] : LRU[5]      （2 選 1）
VictimWayEnc[0] = 從 LRU[3:0] 中依前兩位選一個  （4 選 1）
```

**8-way 的 victim 選擇只要 1 個 2:1 mux 和 1 個 4:1 mux。**

### `cacheLRU` 模組

**Fig. 10.22（p.458）分兩塊：Victim Way 和 Update LRU。**

**Victim Way 邏輯（p.457–458）：**
> "**The Victim Way logic in Fig. 10.22 selects either an invalid way, when available, or the victim way
>  calculated by the pLRU logic. AllValid is the bit-wise AND of ValidWay[N-1:0], a signal showing the valid
>  way, using one bit per way.
>  - When all ways are valid (AllValid = 1), the new victim is chosen as the pLRU output, (VictimWayEnc =
>    NV[6]).
>  - Otherwise, the victim is an unused way; `priorityonehot` selects the lowest-numbered unused way
>    (FirstZero), and the `encoder` converts the 1-hot output to binary (FirstZeroWay), which is then sent to
>    the binary encoded victim way, VictimWayEnc.
>  - The `decoder` then converts the binary VictimWayEnc signal to the 1-hot VictimWay output.**"

**優先順序：有空的 way 就用空的（選編號最小的），全滿才用 pLRU。**
**這很合理——空的 way 不用 evict 任何東西。**

**（p.457 邊欄：**「LRU 陣列用 flip-flop 而非 SRAM，因為它小、需要 reset、而且每個週期都讀和寫。」**）

### Update LRU 的四個訊號

> "**The Update LRU logic at the bottom of Fig. 10.22 updates the LRU array to point *away* from the accessed
>  way by calculating:
>  - **LRUUpdate**: An array with 1s for traversed nodes in the path to the accessed way; 1s indicate which
>    nodes should be updated to point away from the accessed way.
>  - **Way**: The accessed way number.
>  - **WayExpand**: The direction each node points to reach the accessed way.
>  - **NextLRU**: Updated LRU bits, which are the original LRU bits for nontraversed nodes, and the inverse of
>    WayExpand for traversed nodes, so that these nodes point away from the accessed way.**"
> — p.458–459

中文解釋：**四個訊號的關係：**
```
LRUUpdate：路徑上的節點為 1，其餘為 0（「哪些要更新」）
WayExpand：到達該 way 時每個節點的方向（「原本該指哪」）
NextLRU[i] = LRUUpdate[i] ? ~WayExpand[i] : LRU[i]
             （路徑上的取反相 = 指向遠離；不在路徑上的保持不變）
```

**`WayExpand` 的構造（p.459）：**
> "**WayExpand replicates each bit of Way for each successive level of the pLRU tree. For example, if the
>  accessed way (Way) is 5 (101), then WayExpand is 1001111. That is, to access way 5, the top-level node
>  (LRU[6]) points right (1), the next-level nodes (LRU[5:4]) point left (00), and the lowest-level nodes
>  (LRU[3:0]) point right (1111). Exactly one node at each pLRU tree level will be traversed to access a
>  given way. Thus, because LRU[6] points right, only LRU[4]'s direction is relevant. And because LRU[4]
>  points left, only LRU[1]'s direction is relevant.**"

**`WayExpand` 就是把 way 編號的每個 bit 複製到對應層級的所有節點
（第 0 層 1 個、第 1 層 2 個、第 2 層 4 個）。**
**然後 `LRUUpdate` 負責挑出真正在路徑上的那幾個。**

**Example 10.8（p.459）的完整計算：**
> "Using Fig. 10.22, show the process for calculating NextLRU during an access to way 6 given LRU = 1100010."
>
> **Solution:**
> - `LRUUpdate = 1010001`（路徑上的節點 6、4、0）
> - `Way = 110`（6）→ `WayExpand = 1110000`
> - `NextLRU` 對每個 bit 依 `LRUUpdate` 選 `LRU` 或 `~WayExpand`：
>   - bit 5、3、2、1 取原本的 LRU（`-1-001-`）
>   - bit 6、4、0 取 `~WayExpand`（`0-0---1`）
> - **`NextLRU = 0100011`**

**（Fig. 10.23（p.459）畫出存取 way 6 前後的樹，更新後 LRU way 變成 way 2。）**

### Top-level cache 的六塊邏輯

> "**- Address selection: Selects CacheSet{Tag/Data} from NextAdr, PAdr, or FlushAdr.
>  - Way selection: Delivers the tag, read cache line, dirty, hit, and valid bits from the selected way using
>    a distributed AND-OR read mux.
>  - Read selection: Selects a word from the cache line for reads and writebacks.
>  - Write selection: Merges WriteData into FetchBuffer (using the bottom LineWriteData mux) during write
>    misses and forms the byte mask for the line (DemuxedByteMask).
>  - Bus logic: Selects the address to send to the bus for fetches, writebacks, and flushes.
>  - Flush logic: Sequences through the lines and ways during a cache flush.**"
> — p.460

中文解釋：**Fig. 10.24（p.461）是完整的 cache 模組圖，這六塊都在上面。**

**分散式 AND-OR mux 的兩個好處（p.460）：**
> "**Benefits of the distributed AND-OR mux over a traditional mux include its ability to directly use the
>  one-hot HitWay signals (at most one HitWay signal is hot (1) across all ways) instead of having to encode
>  that signal and reduced power because at most one ReadDataLineWay bus is nonzero.**"

**（1）直接用 one-hot 訊號，不用編碼；（2）省電，因為最多只有一條匯流排非零。**

**（p.460 邊欄：**「分散式 AND-OR mux 會在第 11.4.1.3.1–11.4.1.3.3 節的 TLB 再次出現。」**）

### Table 10.3：`CacheBusAdr` 的三種來源

中文解釋：**Table 10.3（p.463）：**

| {FlushCache, SelWriteback} | CacheBusAdr | 說明 |
| --- | --- | --- |
| **00** | **{PAdr[55:6], 000000}** | **Fetch** |
| **01** | **{Tag, PAdr[11:6], 000000}** | **Writeback** |
| **10** | **{Tag, FlushAdr, 000000}** | **Flush** |

**三者的共同點：低 6 bit 都是 0（對齊到 64-byte cache line）。**
**差別在 tag 和 set 的來源：**
- **Fetch 用造成 miss 的那個存取的 `PAdr`**
- **Writeback 用被逐出 line 的 tag，set 來自 `PAdr`**
- **Flush 用被逐出 line 的 tag，set 來自 `FlushAdr` 計數器**

### Read Selection 的三種情況

> "**- Read hit: The SCR mux selects a word within the cache line using the lower bits of the address:
>    WordOffset = PAdr[5:3].
>  - Read miss: The early return mux selects a word from the fetch buffer (SelFetchBuffer = 1) instead of the
>    cache ways during a read miss. This saves a cycle at the end of the miss instead of waiting for the
>    fetched cache line to be written to the cache before reading it.
>  - Writeback: The cache must writeback the cache line to external memory word by word. Thus,
>    `ahbcacheinterface` asserts SelBeatCount so the SCR mux uses WordOffset = BeatCount to output each word
>    of the cache line in sequence.**"
> — p.463

中文解釋：**`WordOffset` 的三種來源就是三種情況：**

| 情況 | WordOffset |
| --- | --- |
| **Read hit** | **`PAdr[5:3]`** |
| **Read miss** | （走 early return mux 從 fetch buffer 取） |
| **Writeback** | **`BeatCount`**（依序輸出每個字） |

### Cache Flush 的硬體

> "**Fig. 10.26 highlights the flush logic, which contains two counters to sequence through the lines and
>  ways. The FlushAdr counter counts through the lines in binary. The FlushWay counter uses a one-hot shift
>  register to count through the ways. System reset initializes both counters, FlushAdr to 0 and FlushWay to
>  0...01. FlushWayFlag and FlushAdrFlag are inputs to the cache FSM. FlushWayFlag asserts when all ways in a
>  given set have been flushed, and FlushAdrFlag asserts while flushing the last set in a cache. So, the
>  entire cache has been flushed when FlushFlag = FlushWayFlag & FlushAdrFlag asserts.**"
> — p.463

中文解釋：**兩個計數器，用不同的編碼：**

| 計數器 | 編碼 | 為什麼 |
| --- | --- | --- |
| **`FlushAdr`**（set） | **二進位** | 要當位址用 |
| **`FlushWay`**（way） | **one-hot 移位暫存器** | **直接當 `SelectedWay` 用，不用解碼** |

**Flush 的流程（p.464）：**
1. IEU assert `FlushCache` → FSM 從 Access 轉到 Flush 狀態
2. 轉移時 `FlushWay = 1`、`FlushAdr = 0`，所以下一週期讀出 way 0 set 0
3. **如果該 line valid 且 dirty → `LineDirty` assert → 轉到 FlushWriteback**
4. **同時計算位址 `{ReadTag, FlushAdr, 0…0}` 並 assert `CacheBusRW[0]` 開始匯流排寫入**
5. 匯流排完成（`CacheBusAck`）→ 回到 Flush 狀態並遞增 `FlushWay`
6. **`ClearDirty` 在 Flush → FlushWriteback 的轉移時 assert**
7. **line 乾淨（`LineDirty = 0`）→ 直接遞增 `FlushWay`**
8. **`FlushWay` 到最後一個 way（10…0）→ 繞回 0…01，並遞增 `FlushAdr`**
9. 兩個計數器都到最大值 → flush 結束，重置計數器並回到 Access

**一個微妙的最佳化（p.464）：**
> "**The dirty bit is cleared before data is written to the bus to minimize the number cycles spent on
>  writeback. ClearDirty must be asserted for the current way and set (as indicated by FlushWay and
>  FlushAdr).**"

**（p.464 邊欄的多核警告：**
> "**For a single core, clearing the dirty bit before the writeback begins is safe. However, a multicore or
>  multithreaded implementation may use a cache coherency mechanism, which requires the line to be cleared
>  after writeback is completed.**"）

### Flush 的成本（很重要的數字）

> "**Flushing the cache is time-consuming because the cache must check each cache line's dirty bit and write
>  back any dirty lines. In the best case, all lines are clean so run time takes (the number of sets × the
>  number of ways) cycles. The rv64gc configuration has 64 sets and 4 ways for a total of 256 cycles.
>  If all lines are dirty and each writeback takes 15 cycles (in addition to the 1 cycle to check the dirty
>  bit), the D$ flush will take 64 × 4 × (1+15) cycles = 4,096 cycles! Fortunately, D$ flushes are rare
>  events.**"
> — p.465

中文解釋：**兩個極端：**

| 情況 | 週期數 |
| --- | --- |
| **全部乾淨** | **256**（64 sets × 4 ways） |
| **全部 dirty** | **4,096**（64 × 4 × 16） |

**「4,096 個週期！」——這解釋了為什麼 10.4.2.6 節說
「`fence.i` 是昂貴的操作，fence 應該少用」。**

**Fig. 10.27（p.465）的逐週期追蹤（p.465）：**

| Cycle | 發生什麼 |
| --- | --- |
| **0** | FSM 收到 `FlushCache`，在 Access 狀態設 `CacheSet{Tag/Data} = FlushAdr` 讀 set 0 |
| **1** | **set 0 way 0 不 dirty → 不用寫回，`FlushWay`（one-hot）左移一位** |
| **2** | **set 0 way 1 是 dirty → assert `ClearDirty`；位址 `CacheBusAdr = 0x00_0000_000F_F000`**（tag 串接 `FlushAdr` 和六個 0）；`CacheBusRW[0] = 1` 開始匯流排寫入 |
| **3** | 轉到 FlushWriteback 狀態，**保持 `FlushAdr` 和 `FlushWay` 不變直到交易完成** |
| **19** | **`CacheBusAck` 升起表示匯流排完成 → 回 Flush 狀態並遞增 `FlushWay`** |
| 之後 | 重複直到所有 line 都檢查並寫回；**到最後（set 0x3F = 63、way 3）flush 完成，計數器重置，經 AddressSetup 回到 Access** |

**（p.466 邊欄：**「`FlushAdr` 設定要讀哪個 set（Address 階段），
`FlushWay` 選要讀哪個 way（Data 階段）。因為 cache 讀取是 pipeline 的，
一個在 Data 階段、下一個在 Address 階段。**當最後一個 way 被讀取（`FlushWay = 1000`）時，
set 也遞增**，這樣 cache 就在 Data 階段設定好讀新的 set。」**）

### Pipeline Stall 的互動

> "**Any time either the I$ or D$ misses or performs a cache flush, it asserts CacheStall to stall the entire
>  pipeline while fetching or flushing. CacheStall remains asserted until the `cachefsm` returns to the
>  Access or AddressSetup state.**"
> — p.466

中文解釋：**`CacheStall` → `LSUStallM` / `IFUStallF` → stall pipeline**（呼應 9.5.5 節 Fig. 9.33）。

**反方向（p.466）：**
> "**Conversely, the hazard unit stalls the LSU or IFU by asserting StallW or StallD, respectively.
>  These stalls are renamed to Stall as an input to the `cache` and `ahbcacheinterface` because these modules
>  are instantiated by both the LSU and IFU.**"

**兩個 cache 同時 miss 的處理（p.466）——這段很值得看：**
> "**Both caches can simultaneously miss, stalling the entire pipeline. Both cache FSMs concurrently request
>  the missing line or writeback a dirty cache line. However, as discussed in Section 9.5.5, the external bus
>  unit (EBU) gives priority to the LSU (D$ requests), so the D$ fetches its missing line first. The D$ then
>  waits in the AddressSetup state, retaining ReadDataWord, until the I$ also fetches its missing line and
>  the pipeline resumes. In AddressSetup, the D$ lowers CacheStall to signal the cache is no longer busy and
>  reads from the FetchBuffer rather than `cacheway`. While the I$ is busy, the hazard unit asserts StallW,
>  which is connected to the cache's Stall input. In the AddressSetup state the `cachefsm` only reads the
>  next memory request when Stall asserts. This allows AddressSetup to behave like the Access State to set up
>  CacheSetTag and CacheSetData in the Address stage.**"

**關鍵：D$ 先完成後停在 AddressSetup 狀態等 I$，
並且保持 `ReadDataWord`、從 `FetchBuffer` 讀取。**

### 例外與中斷

> "**At the beginning of a memory operation, the MMU, which is introduced in Chapter 11, checks the validity
>  of the operation and generates an exception if the access is bad. Such exceptions, as well as other
>  exceptions and interrupts, assert TrapM, which flushes the entire pipeline including pending cache
>  operations.**"
> — p.466

> "**A pipeline flush raises FlushStage in the I$ or D$, which is connected to receive FlushD and FlushW,
>  respectively. Note that these signals indicate pipeline flushes, *not* cache flushes. FlushStage resets
>  the given cache's `cachefsm` and aborts any ongoing writes to its `cacheway` and `cachelru`.**"
> — p.466–467

中文解釋：**又一次強調 `FlushStage` 是 pipeline flush 不是 cache flush。**

**中斷的處理（p.467）：**
> "**Interrupts are asynchronous, arriving at any time, even when the pipeline is stalled for a bus access or
>  cache miss. When a bus transaction is in flight, the bus cannot be interrupted without potentially
>  corrupting memory. Just as the `busfsm` asserts BusCommitted when a bus transaction is in progress (see
>  Section 9.5.5), the `cache` asserts CacheCommitted when `cachefsm` is busy (i.e., in the middle of a
>  fetch, flush, or write back). The LSU or IFU raises their CommittedM or CommitedF signal when either the
>  bus or cache is busy. Pending interrupts are delayed until CacheCommitted falls, using the hardware from
>  Fig. 9.35.**"

**`CacheCommitted` 和 `BusCommitted` 是完全平行的機制**（呼應 9.5.5 節）：
```
CommittedM = BusCommittedM | CacheCommittedM
CommittedF = BusCommittedF | CacheCommittedF
Committed  = CommittedM | CommittedF   → 擋住 ValidIntsM
```

## 所以呢

**這節是全書最細的實作章節之一。五件最該帶走的事：**

1. **Tag 和 data 陣列分開定址（`CacheSetTag` / `CacheSetData`）**——
   **這讓連續的 store 完全不用 stall**（store 在 Address 階段只用 tag、Data 階段只用 data）。
   **但 store 後接 load 仍然衝突**（兩者都要碰 data 陣列）。

2. **pLRU 的硬體簡化很漂亮**：
   理論上要 (N−1)·log₂N 個多工器，
   **但因為 way 編號是常數，實際上簡化成「從 LRU 位元中挑出 log₂N 個」**——
   8-way 只要一個 2:1 和一個 4:1 多工器。

3. **Flush 很貴**：**全部 dirty 時 rv64gc 的 D$ flush 要 4,096 個週期**。
   這就是「`fence.i` 應該少用」的量化理由。

4. **三個省週期的最佳化**：
   **read miss 直接從 `FetchBuffer` 取字**、
   **writeback 前先清 dirty bit**、
   **有空 way 時優先用空的而非 pLRU 的 victim**。

5. **`CacheCommitted` 和 `BusCommitted` 是完全平行的機制**——
   兩者都在「操作進行中不能被中斷」時 assert，
   一起餵進 trap 單元的 `Committed`。
