1. **計畫與參考模型**（5.11.1–5.11.2）

## 關鍵點

### 目標：兩種 TRL 等級

> "Wally targets **TRL3 verification of all configurations and TRL5 verification of the rv64gc
>  configuration.**"
> — p.227

中文解釋：**分層目標很務實**（呼應 5.1.5 節）：
- **所有組態**達到 TRL3（能編譯、能開 Linux、有 CoreMark 結果）
- **只有 rv64gc** 追求 TRL5（100% 程式碼與功能覆蓋率）

**因為 TRL5 的成本太高，不可能每個組態都做。**

### DV plan：一張表看完所有測試

中文解釋：**Table 5.6（p.228）是整個驗證工作的總覽，非常實用：**

| 測試 | 節 | TRL3 適用組態 | TRL5 |
| --- | --- | --- | --- |
| **Verilator Lint** | 5.3, 5.11.4 | 所有組態 | rv64gc |
| **riscv-arch-test** | 3.7 | 所有組態 | rv64gc |
| **wally-riscv-arch-test** | 3.7 | 所有組態 | rv64gc |
| TestFloat | 5.11.8, 16.5.2 | rv{32/64}gc + 衍生組態 | rv64gc |
| CoreMark | 21.1 | 多種組態 | rv64gc |
| Embench | 21.2 | rv32* | n/a |
| Cache PV | 21.3.1 | rv{32/64}gc | rv64gc |
| BranchPred PV | 21.3.2 | rv{32/64}gc | rv64gc |
| **Linux Boot** | 22.3.2 | rv64gc | rv64gc |
| **ImperasDV Lock-Step** | 5.6, 5.11.9 | — | **rv64gc（只有 TRL5）** |
| FPGA Linux Boot | 23.2 | — | rv64gc |
| **Code Coverage** | 5.11.11 | — | **rv64gc（只有 TRL5）** |
| **Functional Coverage** | 5.11.12 | — | **rv64gc（只有 TRL5）** |

**注意最後三項（lock-step、程式碼覆蓋率、功能覆蓋率）只在 TRL5 欄有值**——
**這三項就是 TRL3 和 TRL5 的差距。**

（"PV" = performance verification，效能驗證，用來抓效能 bug，p.228。）

**兩個起手指令（p.228）：**


**最新的 DV plan 在 `docs/testplans`**（p.228）。

### 參考模型的分工

> "RISCOF uses Sail as the reference model to generate reference signatures. Recall from
>  Section 3.7.2 that RISCOF crosschecks Sail signatures against Spike. The wally-riscv-arch-test
>  tests that use CSRs, interrupts, and peripherals that are not supported by Sail set the
>  NO_SAIL=True directive and use a manually written reference signature. **The flow of GCC,
>  RISCOF, Sail, and Verilator compile and simulates regression tests entirely with open-source
>  tools.**"
> — p.229

> "Wally also uses the commercial ImperasDV as a reference model for rv64gc lock-step-compare.
>  **ImperasDV confirms that the manually written signatures are correct, catches subtle
>  discrepancies that might not appear in a signature, and detects bugs in Sail.** For example,
>  ImperasDV detected an incorrect implementation of the Zfa fcvtmod.w.d instruction in Sail."
> — p.229

中文解釋：**兩段各有一個重點。**

**第一段**：**整條開源流程（GCC + RISCOF + Sail + Verilator）完全免費**——
對自學者是好消息。

**第二段是很重要的觀察：ImperasDV 有三個作用，其中第三個最有趣——
它「偵測 Sail 裡的 bug」。**

**書上給了具體例子：ImperasDV 發現 Sail 對 Zfa 的 `fcvtmod.w.d` 指令實作錯誤。**

**這是驗證方法論上的深刻一課：連「黃金參考模型」本身也可能有 bug。**
（呼應 3.3.8 節邊欄：「golden 這個詞有爭議，因為它暗示完美」。）
**所以有第二個獨立的參考模型很有價值**——這正是 5.1.2 節「不同團隊寫」原則的延伸。

**同時也補上了 3.7.3 節那個缺口**：
wally-riscv-arch-test 的手寫 signature 沒有參考模型驗證——
**現在 ImperasDV 來確認它們是對的。**

### Top-level testbench 做什麼

> "The riscv-arch-test *pool* of programs is divided into suites (e.g., RV32 integer
>  instructions, or RV64 multiply/divide instructions), each of which contain files....
>  **A key issue is that most of the files are small and run in less than a second, but the
>  startup time to launch the simulator and compile Wally takes many seconds. Therefore, the
>  testbench is designed to simulate all of the files in a suite, one after another, to reduce
>  the startup overhead.**"
> — p.229

中文解釋：**這個設計決定很值得學：啟動成本主導，所以一次跑一整個 suite。**
測試檔很小（不到一秒），但**啟動模擬器和編譯 Wally 要好幾秒**——
**如果一個檔案開一次模擬，時間全花在啟動上。**

**testbench 的完整職責（p.229–230）：**
1. 依 `TEST` 引數從 `tests.vh` 選一組測試套件
2. 實例化 `wallypipelinedsoc` 當 DUT
3. 產生時脈、脈衝重置
4. **用 `riscvassertions` 模組確認組態自洽**（呼應 4.4、5.7.1 節）
5. 提供儀器來解碼指令名稱和標籤
6. 對套件中每個程式：
   - **從 `test.elf.memfile` 以十六進位格式載入到 0x80000000**（呼應 3.7.2 節的輸出）
   - 執行到程式進入無限迴圈或 `write_tohost`
   - **把資料 cache 寫回記憶體（flush）** ← **關鍵步驟，否則結果還在 cache 裡**
   - 比對指定記憶體範圍與 `test.signature.output`
   - 回報成功或失敗

**第 6 步的「flush data cache」很容易被忽略但至關重要**——
signature 寫進了 cache 但還沒進記憶體的話，比對就會失敗。

**特殊案例：buildroot（p.230）**
> "The buildroot test case is different than the others. It simply runs the first 1.6 million
>  instructions of the Buildroot Linux boot and **verifies that it does not hang.**"

**只驗證「沒有卡住」——這是最低限度的整合測試。**
（完整的 lockstep Linux boot 是**多日的模擬**，見 22.3.2 節。）

### Lint：`lint-wally`

> "After making significant edits, start by running lint and fixing any warnings.... The
>  lint-wally script runs lint on **rv32e, rv64gc, rv32gc, rv32imc, rv32i, rv64i, and
>  fdqh_rv64gc configurations to detect configuration-dependent problems.**"
> — p.230

```bash
$ lint-wally
```

中文解釋：**關鍵字是 "configuration-dependent problems"（組態相依的問題）。**

**為什麼要對七種組態各跑一次 lint？**
因為 Wally 用 generate 大量開關功能（4.2.5 節）——
**某個組態下沒問題的程式碼，在另一個組態下可能有未驅動訊號或寬度不符。**

用 `-I` 旗標指向所需組態，並用 `testbench/wallywrapper.sv`
**wrapper 模組**載入組態參數並實例化頂層 `wallypipelinedsoc`（p.230，呼應 4.3.1.4 節的 wrapper 定義）。

### 模擬：`wsim` 包裝腳本

> "Wally uses the wsim wrapper script to invoke simulation using Verilator, Questa, or VCS."
> — p.231

中文解釋：**`wsim` 是一個統一介面，包住三種模擬器。用法（p.231）：**

```
usage: wsim [-h] [--elf ELF] [--sim {questa,verilator,vcs}] [--tb {testbench,testbench_fp}]
            [--gui] [--ccov] [--fcov] [--args ARGS] [--params PARAMS]
            [--define DEFINE] [--vcd] [--lockstep] [--lockstepverbose] [--rvvi]
            config [testsuite]
```

**常用選項速查：**

| 選項 | 作用 |
| --- | --- |
| `config` / `testsuite` | 組態檔 / 測試套件（**兩個位置引數**） |
| `--sim, -s {questa,verilator,vcs}` | 選模擬器 |
| `--tb {testbench, testbench_fp}` | 選 testbench（**浮點有專用的**） |
| **`--gui, -g`** | **用 GUI 模擬**（除錯用） |
| `--ccov, -c` | 程式碼覆蓋率 |
| `--fcov, -f` | 功能覆蓋率 |
| `--vcd` | 產生 `testbench.vcd` 波形檔 |
| **`--lockstep, -l`** | **執行 ImperasDV lock-step 比對** |
| `--lockstepverbose, -lv` | lock-step 且開啟追蹤 |

**Example 5.1（p.231–233）的實際用法，很實用：**

```bash
# 在 Questa 上跑 rv64gc 的整數測試
$ wsim rv64gc arch64i
# rv64i_m/I/src/add-01.S succeeded.  Brilliant!!!
# SUCCESS! All tests ran without failures.

# 開 GUI 除錯
$ wsim rv64gc arch64i --gui

# 浮點加法測試（用專用 testbench）
$ wsim f_rv64gc add --tb testbench_fp

# Verilator 跑 rv32imc 的乘除測試，產生 VCD
$ wsim -s verilator rv32imc arch32m --vcd
$ gtkwave -f $WALLY/sim/verilator/testbench.vcd

# VCS
$ wsim -s vcs rv64gc arch64i
```

**兩個實務警告：**
- **VCD 檔可能佔好幾 GB，用完要刪**（p.232）
- **Verilator 第一次執行前要用 `ulimit` 增加堆疊大小**，這在 `setup.sh` 裡做（p.232 邊欄）

**底層機制（p.233）**：`wsim` 依模擬器啟動不同流程。Questa 用 `wally.do`（一個 TCL do file），
**用 `+TEST` 旗標覆寫 testbench 變數 `TEST`**，
並且**依組態和測試套件命名 library，讓多個模擬能在回歸時並行執行**。
`wave.do` 把常用訊號分組到方便的群組。
`+incdir` 引數讓編譯器找到正確的 `config.vh`。

### 回歸：`regression-wally`

> "The regression-wally script launches lint-wally and all the test suite simulations in
>  parallel and reports any failures. **It uses Verilator because this simulator is free and
>  fast.**"
> — p.233

> "**To keep the repository in always-working state, it is essential to run regression-wally
>  before committing any changes.**"
> — p.234

中文解釋：**最後那句是紀律**（呼應 5.1.6 節的 always-working 策略）：
**提交任何改動前一定要跑 `regression-wally`。**

**失敗時的處理（p.234）：**
1. 到 `logs` 子目錄看 `<config>_<suite>.log`
2. 修掉所有編譯器警告和錯誤
3. **如果是 Verilog 裡真的邏輯問題，可能需要用 `wsim` 模擬來追蹤**

**注意某些套件會在多個組態上重複跑**（p.233–234）：
例如 arch32i 整數測試會在 **rv32i、rv32imc、rv32gc** 上都跑一次，檢查所有這些組態。

### Nightly regression 與 nightly build

> "Regression testing confirms that a recent change has not broken the system. The basic Wally
>  regression tests (regression-wally) run architecture compatibility tests on the main Wally
>  configurations. **Experience has shown that it is important to run a larger suite of tests
>  on a regular basis. These take longer to run, so they are often run automatically while the
>  designer is away and are called *nightly regression*.**"
> — p.234

中文解釋：**兩層回歸的分工：**

| | 何時跑 | 內容 |
| --- | --- | --- |
| **`regression-wally`** | **每次提交前** | 主要組態的架構相容性測試（快） |
| **`regression-wally --nightly`** | **每晚自動** | 完整套件（慢） |

**Nightly regression 的完整清單（p.234）：**
- `regression-wally` **擴展到所有衍生組態**（4.4 節）
- **`lint-wally` 在所有衍生組態上**
- **一般的 `regression-wally` 在 Verilator、Questa 和 VCS 三個模擬器上**
  ← **三個模擬器都跑，因為它們可能有不同的行為**
- **ImperasDV lock-step 測試**（rv64gc：riscv-arch-test、wally-riscv-arch-test、覆蓋率、Linux boot）
- 所有浮點組態的 **TestFloat**
- 功能覆蓋率測試
- Cache 效能測試
- CoreMark 和 Embench benchmark

（未來還會加入分支預測器效能驗證測試。）

**Nightly build（5.11.6.2，p.234–235）更進一步：**
> "The nightly_build.py script **clones a fresh copy of the cvw repository**, makes all of the
>  test cases, and runs these regression tests using regression-wally --nightly. It sends an
>  email to a user or mailing list with a summary of the results, highlighting any failures."

**關鍵是 "clones a fresh copy"（重新 clone 一份乾淨的 repo）**——
**這樣才能發現「只有在我的機器上才能編譯」這類問題。**

```bash
$ nightly_build.py --path ~/nightly --target all --tests all \
  --send_email ben@hmc.edu, alyssa@hmc.edu
```

**排程（p.235）：用 `crontab -e` 設定每晚 9 點自動執行：**
```
0 21 * * * curl -L https://raw.githubusercontent.com/openhwgroup/cvw/refs/heads/main/bin/nightly_build.py | /opt/riscv/riscv-python/bin/python - --path PATH/TO/NIGHTLY --target all --tests all --send_email ...
```

**磁碟管理（p.235）：`nightly_build.py` 會刪除舊檔案，
只保留最近一份 repo 和最近 30 天的 log。**

### 除錯實戰：三個 bug（本節精華）

> "This section introduces a few bugs into the design and then shows how to systematically find
>  them. The bugs will include:
>  - A syntax error caught by lint
>  - A compilation error caught by Questa
>  - A logic error in the design caught by a regression failure"
> — p.235

中文解釋：**這段把整章的工具串成一個實際的除錯流程，非常值得完整讀。**

**故意植入的三個 bug（p.235）：**
1. `ieu/ieu.sv`：把某個 `input` 埠拼錯成 `inputt`
2. `ieu/datapath.sv`：把 `fbemux` 的輸出從 `ForwardedSrcBE` 改成 `ForwardedSrcAE`
   （那也是 `faemux` 的輸出，**造成競爭**）
3. `ieu/alu.sv`：把 OR 閘那行從 `A | CondMaskInvB` 改成 `A + CondMaskInvB`

**注意這三個 bug 是刻意由淺到深排列的：語法 → 結構 → 邏輯。**

---

**Bug 1：lint 抓到的語法錯誤**

```bash
$ lint-wally
Error: ../src/ieu/ieu.sv:31: syntax error, unexpected logic, expecting ')' or ','
  inputt logic      clk, reset,
         ^~~~~
%Error: ../src/ieu/ieu.sv:33: syntax error, unexpected input
```

**最重要的除錯原則（p.236）：**
> "**Focus on the first error reported and don't get distracted by the many other errors.**
>  Carefully reading the message, we see an error right after inputt that points us to fix the
>  misspelling."

**「專注在第一個錯誤，不要被後面一堆錯誤分心。」**
——語法錯誤會產生連鎖的假錯誤，**第一個才是真的。**

---

**Bug 2：編譯錯誤（多重驅動）**

```bash
$ regression-wally
...
Regression failed with 72 failed configurations
```

**「幾乎每個測試都失敗」這個現象本身就是線索（p.236）：**
> "Given that almost every test failed, **there's clearly something majorly wrong with the code.
>  Look at any one of the failing log files** and scroll through until you find the error
>  reported:"

```bash
$ tail $WALLY/sim/questa/logs/rv32gc_arch32m.log
# ** Error (suppressible): ../src/ieu/datapath.sv:(108): (vopt-7045)
'ForwardedSrcAE' is driven by more than one continuous assignment. See ../src/ieu/datapath.sv:(109).
```

**"driven by more than one continuous assignment"（被多個連續賦值驅動）**——
這正是 4.2.2.3 節說的**多重衝突驅動源會產生 x**。

**除錯策略的對比很重要：**
- **全部失敗 → 隨便挑一個 log 看就行**（是共通的大問題）
- **部分失敗 → 要挑對的那個**（見 Bug 3）

修法：把 `fbemux` 的輸出改回 `ForwardedSrcBE`。

---

**Bug 3：邏輯錯誤（最完整的除錯流程）**

**步驟 1：從回歸結果挑一個失敗（p.237）**
```bash
$ regression-wally
rv32e passed lint
rv64gc passed lint
wsim --sim questa  rv32i arch32i > .../rv32i_arch32i.log: Failures detected in output
wsim --sim questa  rv32imc arch32c > .../rv32imc_arch32c.log: Failures detected
wsim --sim questa  rv32imc wally32periph > .../rv32imc_wally32periph.log: Success
...
```
**挑選原則（p.237）：**
> "Pick either the first failure or a failure in a test suite that you are most familiar with.
>  **The arch32i tests are a good choice because they relate to simple integer instructions
>  that we understand well.**"

**「挑你最熟悉的測試套件」——這是很實際的建議。**

**步驟 2：讀 log 找出哪個測試、哪個值錯了（p.237）**
```bash
$ less $WALLY/sim/questa/logs/rv32imc_arch32i.log
# Error on test rv32i_m/I/src/or-01.S result 2: adr = 80006118 sim (D$) 00000004
  signature = 00000002
```
**`or-01` 測試的第 2 個結果：預期 00000002，模擬算出 00000004。**

**步驟 3：讀測試的反組譯，找出是哪條指令（p.237）**
在 `tests/riscof/work/riscv-arch-test/rv32i_m/I/src/or-01.S/ref/ref.elf.objdump`：
```
80000130 <inst_1>:
80000130: 00200313    li   t1,2
80000134: 00200313    li   t1,2
80000138: 006368b3    or   a7,t1,t1
8000013c: 0111a223    sw   a7,4(gp)
```
**關鍵指令是 `2 OR 2`，答案應該是 2（和 signature 一致）。**

**步驟 4：把失敗的測試移到最前面（p.238）——很實用的技巧**
> "To make the failure occur early in the simulation, edit tests.vh and place the failing
>  simulation at the beginning of the suite of tests:"
```systemverilog
string arch32i[] = '{
  `RISCVARCHTEST,
  "rv32i_m/I/or-01",    # Added this test at start
  "rv32i_m/I/add-01",
  ...
```
**不用等前面一堆測試跑完才到達失敗點。**

**步驟 5：用 GUI 看波形（p.238）**
```bash
$ wsim --gui rv32imc arch32i
```
> "You may see harmless errors about no object matching certain signal names **because some
>  configurations do not have all signals.**"

**步驟 6：從結果往回追（p.238）——這段的方法論最值得學**
1. 展開 Memory Stage 波形群組，點 `IEUAdrM`（load/store 位址）
2. **在搜尋框輸入壞掉的 store 位址（80006118），點搜尋下一個**
3. 放大到波形清晰
4. 展開 "alu execution stage" 群組，**往回看兩個週期**：
   `SrcAE` 和 `SrcBE` 都是 00000002，但 **`ALUResultE` 是 00000004**（錯了）
5. **點 `ALUResultE`，用 Add → To Wave → Contributing Signals 選單**
   加入所有造成 `ALUResultE` 的訊號 → `PreALUResult` 出現
6. **再對 `PreALUResult` 做一次 → `FullResult` 出現**
7. 再對 `FullResult` 做一次
8. 讀出：**A = 2、CondMaskInvB = 2、ALUSelect = 6、FullResult = 4**

**"Contributing Signals" 這個功能是關鍵——它自動往上游追溯訊號來源。**
**這是「從症狀往回推到原因」的系統化方法。**

Fig. 5.6（p.239）是這個過程的波形截圖（原書此處為波形圖），
可以看到 Memory Stage 群組、alu execution stage 群組，
以及一層層展開的 Contributors。

**步驟 7：對照程式碼找出錯誤（p.238）**
```systemverilog
always_comb
  case (ALUSelect)
    3'b000: FullResult = Sum;                      // add or sub
    3'b001: FullResult = Shift;                    // sll, sra, or srl
    3'b010: FullResult = {{(WIDTH-1){1'b0}}, LT};  // slt
    3'b011: FullResult = {{(WIDTH-1){1'b0}}, LTU}; // sltu
    3'b100: FullResult = A ^ CondMaskInvB;         // xor, xnor, binv
    3'b101: FullResult = ... : Shift;              // bext (or IEU shift)
    3'b110: FullResult = A + CondMaskInvB;         // or, orn, bset   ← 錯！
    3'b111: FullResult = A & CondMaskInvB;         // and, bclr
  endcase
```
**`ALUSelect = 6` 選到了 `A + CondMaskInvB`，但註解說這該是 or。
把 `+` 改回 `|` 就修好了。**

**最後：重跑 `regression-wally` 確認修好（p.239）。**

**這整個流程的通用結構值得記住：**
**回歸失敗 → 讀 log 找出錯誤的值 → 讀測試找出哪條指令 →
把失敗測試移到最前面 → GUI 看波形 → 用 Contributing Signals 往回追 →
對照程式碼。**

### FPU 單元測試

> "The riscv-arch-test vectors exercise the floating-point unit (FPU). The Berkeley TestFloat
>  vectors... exercise the FPU in different ways that have detected bugs not found by
>  riscv-arch-test. **They also test quad precision, which is not part of riscv-arch-test** at
>  the time of this writing."
> — p.239

> "TestFloat has a large number of vectors, so it is well-suited to unit-level testing.
>  **Such testing is faster because it only runs the FPU execution units, rather than the
>  entire core, and because it applies vectors directly to the execution units rather than
>  running supporting code to move values into registers and write signatures to memory.**"
> — p.239

中文解釋：**這是全書唯一大量使用單元測試的地方，理由講得很清楚**
（呼應 5.1.3 節：單元測試通常不划算，但這裡划算）：
1. **TestFloat 向量數量龐大**——整核測試會太慢
2. **只跑 FPU 執行單元，不跑整個核心**
3. **向量直接施加到執行單元**，不必跑搬資料進暫存器、寫 signature 的輔助程式碼

**用 `testbench/testbench-fp.sv` 和 `tests/fp/vectors` 的向量**（p.240）。
`regression-wally --nightly` 會對所有支援的精度（半、單、雙、四）跑 TestFloat。

### Lock-step 實戰

> "As discussed in Section 5.6, ImperasDV performs lock-step-compare of running an ELF file on
>  the Verilog model and on an Imperas reference model. It captures any discrepancies between
>  the state of the system, including registers, the PC, CSRs, and memory. **The reference model
>  watches memory/peripheral reads from the Verilog to return the same values. It also watches
>  the Verilog to take interrupts at the same time. This technique has located at least 20 bugs
>  in Wally** [Thompson23]."
> — p.240

中文解釋：**「至少找到 20 個 Wally 的 bug」——這是 lock-step 價值的量化證據。**

**注意參考模型的兩個「跟隨」機制**（呼應 5.6 節的難處）：
1. **監看 Verilog 的記憶體/周邊讀取，回傳相同的值**
2. **監看 Verilog 以在相同時間接收中斷**

```bash
$ wsim rv64gc $WALLY/tests/riscof/work/riscv-arch-test/rv64i_m/I/src/add-01.S/ref/ref.elf --lockstep
# Info (IDV) ImperasDV VERIFICATION REPORT
# Info (IDV)   Total compares  : 24,371
# Info (IDV)   Mismatches      : 0
```
**24,371 次比對、0 個不符**——這就是 lock-step 的粒度。

**詳細模式（p.240）：**
```bash
$ wsim rv64gc ... --lockstepverbose > log
```
log 節錄（p.240）：
```
# Info 1: 'refRoot/cpu', 0x0000000080000000(rvtest_init): Machine 7d5c0837 lui x16,0x7d5c0
# Info   MEMX 0x80000000 0 0837
# Info   MEMX 0x80000002 0x80000000 2 7d5c
# Info   x16 0000000000000000 -> 000000007d5c0000
```
**逐條記錄：位址、特權模式、機器碼、組語，然後是記憶體讀取和暫存器變化。**

（**ImperasDV 是商用工具，需要授權，不在 Synopsys 學術包裡**，p.240 邊欄。）

### 覆蓋率排除的兩個實例

**Wally 的 `GetLineNum` 機制（p.241）——很聰明的工程解法：**
> "Questa excludes coverage based on ranges of lines. **This is unstable in that code changes
>  that change line numbering break the exclusions in ways that are difficult to maintain.**
>  Wally defines a GetLineNum function that looks for a particular string in the code and
>  substitutes the corresponding line number."

**問題**：Questa 的排除是按行號指定的——**改一行程式碼，所有後面的排除都錯位。**
**解法**：在程式碼裡放一個獨特的註解標籤，**用 `GetLineNum` 函式搜尋那個字串來取得行號。**

```systemverilog
// exclusion-tag: cache AnyMiss
```

**這是「按內容定位而非按位置定位」的典型手法。**

---

**實例一：非法指令測試案例（5.11.11.1，p.242–243）**

**問題**：控制器解碼分支指令時：
```systemverilog
assign BFunctD = (Funct3D[2:1] != 2'b01);   // 合法分支
...
7'b1100011: if (BFunctD) // Branches
              ControlsD = `CTRLW'b0_010_11_00_000_1_0_0_0_0_0_0_0_00_0;
```
**`Funct3 = 010` 或 `011` 的分支是非法的，應該拋出 Illegal Instruction 例外——
但這種畸形分支不在 riscv-arch-test 裡。**

**解法（p.242）：加一行測試**
```systemverilog
.word 0x00002063  // Illegal branch instruction
```
> "Note that the .word assembler directive is used because **there is no assembly language
>  opcode for an illegal branch.**"

**「沒有非法分支的組語助憶符，所以用 `.word` 直接寫機器碼」——很實用的技巧。**

**驗證這個測試有價值（p.242）：把這行註解掉，重跑覆蓋率：**
```
------IF Branch------
  211              15647    Count coming in to IF
  211        2     15647
                 ***0***    All False Count
Branch totals: 1 hit of 2 branches = 50.00%
```
**`if (BFunctD)` 從來沒有為 false**——**只測到一半的分支。**
恢復那行測試後，就有 `BFunctD = 0` 的案例了。

---

**實例二：無法到達的邏輯（5.11.11.2，p.243–245）**

**問題（p.243）：**
> "The instruction and data caches share the same code. As shown in bolded line 112 of Code
>  Example 5.15, cachefsm receives an InvalidateCache signal used to invalidate the instruction
>  cache; **this signal is never asserted for data caches. Therefore, it is impossible for tests
>  to exercise this cachefsm code for the data cache.**"

```systemverilog
STATE_ACCESS: if(InvalidateCache)      // ← 資料 cache 永遠不會進來
                NextState = STATE_ACCESS;
              else if (FlushCache & ~READ_ONLY_CACHE)
              ...
```

**報告顯示（Code Example 5.16，p.244）：**
```
Branch Coverage for instance /core/lsu/bus/dcache/dcache/cachefsm
------IF Branch------
  112    1    405537    Count coming in to IF
  112    2    ***0***                            ← 從來沒進來過
Branch totals: 4 hits of 5 branches = 80.00%
```

**解法（p.244）：加標籤 + 加排除**
```systemverilog
// exclusion-tag: dcache InvalidateCheck
```
```tcl
coverage exclude -scope /dut/core/lsu/bus/dcache/dcache/cachefsm -linerange
  [GetLineNum ../src/cache/cachefsm.sv "exclusion-tag: dcache InvalidateCheck"] -item b 2
```
**三個關鍵選項：**
- **`-scope`**：**只對資料 cache 豁免，不對指令 cache 豁免** ← **精準豁免，很重要**
- `-linerange [GetLineNum ...]`：**用標籤字串找行號**
- `-item b 2`：排除該分支的第 2 項

**這個例子完美示範了 5.8 節說的「排除要小心」——
用 `-scope` 限定範圍，就不會連指令 cache 的覆蓋也一起放過。**

### 功能覆蓋率實戰

> "**Wally presently focuses on architectural functional coverage.** It uses cvw-arch-verif,
>  which is an extension of the nonproprietary riscvISACOV functional covergroups. Wally runs
>  Questa simulations of test programs in lockstep with ImperasDV to detect logic bugs while
>  measuring coverage. **The goal is to have adequate covergroups for every RISC-V feature,
>  test programs that give 100% coverage of these covergroups, and no logic bugs.**"
> — p.245

中文解釋：**最後那句是 TRL5 的完整定義：
足夠的 covergroup + 100% 覆蓋 + 零邏輯 bug。**

**注意「in lockstep with ImperasDV」——覆蓋率和正確性同時量測**（呼應 5.9 節）。

**完整流程（p.245）：**
```bash
$ cd $WALLY/addins/cvw-arch-verif
$ make --jobs
$ regression-wally --fcov
```

**`make` 做的兩件事，這個流水線設計很值得學：**
```
testplans/*.csv  →  covergroupgen.py  →  fcov/ 的 covergroup
                                            ↓
                                        testgen.py  →  tests/ 的組語測試
```
1. **`covergroupgen.py` 讀 `testplans` 目錄的 `.csv` 檔**
   （指定 RV32/RV64 各擴充的哪些非特權指令適用哪些覆蓋點），
   **產生 `fcov` 子目錄的功能 covergroup**
2. **`testgen.py` 讀這些 covergroup，產生 `tests` 子目錄的組語測試，
   以命中每個覆蓋點**

**一份 CSV 測試計畫 → covergroup → 測試程式。全部自動產生。**
（呼應 5.2 節：DV plan 要「人讀得懂又機器能執行」——這就是機器能執行的部分。）

**`regression-wally --fcov`** 在 lockstep 下跑這些程式，
從 `$WALLY/config/<configuration>/coverage.svh` 指定的 covergroup 清單收集覆蓋率，
**每個測試產生 `.ucdb`，合併後把報告放在 `work` 目錄。**

**實際報告（p.246）：**

**摘要（Code Example 5.18）：**
```
Covergroup Coverage:
    Covergroups                79        na      na    69.70%
        Covergroup Bins     30958     20426   10532    65.97%
  Covergroup instance obj_add     100.00%  100  -  Covered
  Covergroup instance obj_addi    100.00%  100  -  Covered
  Covergroup instance obj_auipc    88.57%  100  -  Uncovered
  Covergroup instance obj_beq      96.42%  100  -  Uncovered
```

**細節（Code Example 5.19）——`beq` 為什麼沒滿分：**
```
TYPE .../beq_cg                      96.42%  100  -  Uncovered
  Coverpoint cp_asm_count            100.00% ... Covered
  Coverpoint cp_rs1                  100.00% ... Covered
  ...
  Coverpoint cp_offset                50.00% ... Uncovered
      bin neg     0    1    -    ZERO          ← 沒有測到
      bin pos   539    1    -    Covered
```

**書上的解讀（p.245）：**
> "For example, the beq hits 100% of the bins in each coverpoint **except that it does not yet
>  test backward branches.**"

**`cp_offset` 的 neg bin 是 0——表示測試裡沒有向後跳的分支。**
**這就是功能覆蓋率的價值：它明確指出「缺了哪一種情況」，
而不只是「某個地方沒跑到」。**

**現況與展望（p.245–246）：**
> "By the time you read this, the unprivileged instructions are likely to be fully covered.
>  **Functional coverage will eventually include covergroups and tests for privileged features,
>  including virtual memory, PMP, and CSRs.**"

**特權功能的功能覆蓋率還沒做**——又一次呼應 3.7.3 節的缺口。

## 所以呢

**這節是整章方法論的實作對照，日常最常用的是四個指令：
`lint-wally` → `wsim` → `regression-wally` → `regression-wally --nightly`。**

四件最該帶走的事：

1. **5.11.7 的除錯流程是通用的**：
   **回歸失敗 → 讀 log 找錯誤值 → 讀測試找指令 → 把失敗測試移到最前面 →
   GUI 看波形 → 用 Contributing Signals 往回追 → 對照程式碼。**
   兩個原則：**「專注第一個錯誤」**、**「全部失敗看任一個 log，部分失敗挑你熟的」**。

2. **ImperasDV 找到了 Sail 的 bug**——
   **連黃金參考模型也會錯，所以第二個獨立參考模型有價值。**

3. **`GetLineNum` 的設計值得學**：
   用註解標籤定位而非行號定位，讓覆蓋率排除不會被程式碼改動破壞。
   而 `-scope` 讓排除精準到只豁免該豁免的實例。

4. **`covergroupgen.py` + `testgen.py` 的流水線**：
   **CSV 測試計畫 → covergroup → 測試程式，全自動。**
   「要測什麼」只在一個地方定義。
