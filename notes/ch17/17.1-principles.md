# 17.1 Principles

> 原書 p.673–698（Chapter 17: Extensions: A (Atomic)）
> 涵蓋 17.1.1 Concurrency、17.1.2 Coherence、17.1.3 Consistency、17.1.4 Synchronization、17.1.5 Deadlock, Livelock, and Starvation

## 這節在講什麼

前 16 章都在講「一個 hart 怎麼把指令做對做快」。這章換軸線：多個執行緒同時存取同一塊記憶體會出什麼事。四個相關但不同的概念要分清楚：
- **Concurrency（並行）**：多個執行緒同時跑。這是需求，不是問題。
- **Coherence（一致性／同址）**：對**同一個位址**的讀寫行為——每個核心的快取最終都要看到同一個值。
- **Consistency（一致性／異址）**：對**不同位址**的讀寫**順序**——這是程式設計師看得到的模型。
- **Synchronization（同步）**：用鎖、條件變數等機制避免錯誤的交錯。

最後還有三種卡住的方式：deadlock、livelock、starvation。這一整節都是概念，硬體支援（A 擴充）要到 17.2 才出現。

## 關鍵點

### 四個關鍵詞的定義

> "Consistency describes the order in which memory accesses are seen across the machine. Coherence is when all threads and cores eventually see the same values stored in memory. Often a specific order of memory accesses is necessary for correct operation; ensuring a specified order is called synchronization."
> — p.673

中文解釋：記住區別的訣竅——**coherence 管同一個位址，consistency 管不同位址之間的順序**。atomic 這個字來自希臘文 *atomos*，意思是「不可分割」。

## 17.1.1 Concurrency

### 單核心也有並行

> "Concurrency arises for a single core running multiple threads, for multiple cores sharing memory, and for distributed systems that communicate through message passing."
> — p.674

中文解釋：很多人以為並行問題只在多核心才有。錯。單核心 OS 靠 timer interrupt 做 context switch，隨時可能在任意兩個指令之間切走，一樣會產生 race condition。書上後面會反覆用這點提醒。

### 現代機器的規模

> "In 2025, a low-end processor might have only 4−8 cores, but a high-performance AMD or Intel laptop processor has 16−24 cores, and a high-performance server may have 2−8 sockets for chips, each containing up to 60−288 cores."
> — p.674–675

中文解釋：Fig. 17.1 的 AMD Epyc 9004 主機板是具體例子：兩個 socket、12 通道 DDR5、24 個 DIMM 插槽（插滿 768 GiB）。AMD 9684X 是 multichip module，一顆封裝裡有 13 個 die（I/O controller + 12 個 TSMC 5nm CPU die），96 核 192 執行緒，1,152 MB 的 L3 快取用**垂直堆疊**在 CPU die 上的快取晶片實作，最高 400 瓦。峰值吞吐 2 sockets × 96 cores × 3.7 GHz × 4 instructions/cycle = **每秒 2.8 兆條指令**。每個 Zen 4 核心有 32 KiB L1 I$/D$、1 MiB 8-way L2$、1,536 + 7,168 entry 的兩層分支預測器、64 + 512 entry ITLB、72 + 3,072 entry DTLB。

## 17.1.2 Coherence

### coherence 要保證什麼

> "The goal of cache coherence is to ensure that the memory system behaves as if the caches were not there. In particular, every store to memory must eventually be seen by subsequent loads from the same memory address."
> — p.676

中文解釋：「彷彿快取不存在」是很好的定義。注意 *eventually*——coherence 不保證「馬上」看到，只保證「最終」看到。至於「最終」是多久、中間的順序如何，那是 consistency 的事。

### 兩種維持 coherence 的機制

> "Early shared-memory multiprocessors used snooping to maintain coherence. In such systems, when one core writes to its cache, the write address is also broadcast over a shared bus. Other cores snoop the bus and invalidate any cache entries at this address. Snooping does not scale gracefully because of contention for the shared bus. Larger multiprocessors use directory-based coherence, maintaining a shared or distributed directory of cache lines. They often use the MESI protocol, in which each line is marked as Modified, Exclusive, Shared, or Invalid [Hennessy19]."
> — p.676

中文解釋：snooping（窺探）簡單但不 scale——所有核心搶同一條匯流排。directory（目錄）維護一份「誰有這條快取線」的紀錄，只通知需要的核心。MESI 的四個狀態就是每條快取線的生命週期：Modified（我改過，別人沒有）、Exclusive（只有我有，但沒改）、Shared（好幾個人有）、Invalid（無效）。

### 單核心也需要 coherence

> "Although cache coherence is primarily a consideration for multicore processors, coherence between the instruction and data caches is also important for single-core processors. If the processor writes to a certain memory address and then executes an instruction from that same address, the processor should see the new instruction. As discussed in Sections 10.4.2.6 and 10.4.5.4, the processor must perform a fence operation to flush any dirty lines from the data cache and invalidate them in the instruction cache to keep the caches coherent."
> — p.676

中文解釋：這是 self-modifying code（自我修改程式碼）的問題，`fence.i` 指令就是為此而生。JIT 編譯器、動態載入器都會遇到。連 Wally 這種單核心處理器都必須處理。

### 超大系統放棄 coherence

> "Very large systems would pay an unacceptable overhead keeping memory coherent across all the cores. Instead, such clusters or warehouse-scale computers are built from distributed processors with independent memories tied together on a high-speed network. Processors that wish to communicate pass messages over the network rather than using shared memories."
> — p.676

中文解釋：這是一個重要的分水嶺。共享記憶體好寫但不 scale；訊息傳遞（message passing）難寫但能擴展到整個資料中心。

## 17.1.3 Consistency

### 一個讓人意外的例子

> "Surprisingly to many programmers, c and d could both be 0. For example, Intel and AMD processors have write buffers to improve performance. If T1 and T2 executed concurrently on different cores, the writes to a and b could both be placed into buffers on each core. The other thread on the other core would read the old value of these variables (0) because the writes are not yet visible to a cache coherence system."
> — p.677

中文解釋：Code Example 17.1 是經典的 store buffer 例子。T1 做 `a=1; c=b;`，T2 做 `b=1; d=a;`，a、b、c、d 初始都是 0。直覺上不可能 c 和 d 同時是 0（總有一個先跑），但實際上會發生，有兩個原因：
1. **write buffer**：寫入先進緩衝區，還沒對其他核心可見。
2. **out-of-order execution**：T1 可以先做 `c=b` 再做 `a=1`，因為執行緒內部沒有資料相依性。

注意這兩個原因都不違反單執行緒的正確性——這正是麻煩的地方。

### Sequential Consistency：最直覺但最慢

> "Memory accesses by a particular thread occur in program order; Memory accesses by multiple threads are arbitrarily interleaved"
> — p.678

中文解釋：Lamport 1979 提出的模型，兩條規則就講完。Table 17.1 列出 Code Example 17.1 在 SC 下所有可能的六種交錯，c=d=0 從來不出現。

> "Just as coherence makes caches invisible, sequential consistency makes shared memory look like a single memory module. ... However, it comes at a high cost to performance. It prohibits out-of-order memory accesses that are legal in a nonconcurrent program. More significantly, it makes shared-memory multiprocessors painfully slow at writing because a write to one cache cannot complete until it invalidates any lines containing the same address in different caches."
> — p.678

中文解釋：這個對比句很好記：coherence 讓快取隱形，sequential consistency 讓共享記憶體看起來像一顆單一的記憶體。代價是每次寫入都要等所有其他快取的失效完成——在多核心系統上這是災難級的延遲。

### TSO：放寬一條規則

> "It is similar to sequential consistency except that it allows memory accesses by a particular thread to perform loads before a previous store completes, as long as the accesses are to distinct memory addresses. Stores, however, must occur in program order."
> — p.679

中文解釋：TSO（total store ordering）由 SPARC 提出、x86 採用。用 17.1.3.3 的記號說：SC 要求 R→R、R→W、W→R、W→W 四種順序都保持，**TSO 只拿掉 W→R**。這一條就足以讓 store buffer 合法（寫入可以先進緩衝區，後面的讀取不用等）。代價就是 c=d=0 這種結果會出現。書上強調「大多數有好好做同步的程式在 SC 和 TSO 下沒有差別」。

### fence 的代價

> "A fence ensures that all memory operations before the fence are seen by all threads to complete before any memory operation after the fence occurs. The fence can be implemented by stalling the core(s) until the write buffers finish updating the caches. A fence can be an expensive (time-consuming) operation, especially in large systems with long memory latencies."
> — p.679

中文解釋：fence 也叫 memory barrier（membar）或 sync。Code Example 17.2 在兩個執行緒中各插一個 FENCE，就能在 TSO 機器上排除 c=d=0。但 fence 不是免費的——它要等寫入緩衝區排空。

### Release Consistency：最鬆的模型

> "Relaxed ordering comes in several subtly different flavors, but the release consistency model, which requires the programmer to perform explicit synchronization on shared variables when order matters, is widely used; it is the model for RISC-V, ARMv8, and MIPS."
> — p.680

中文解釋：四種模型的階梯（從嚴到鬆）：
- **Sequential consistency**：R→R、R→W、W→R、W→W 全部保持
- **Total store order (TSO)**：拿掉 W→R
- **Partial store order**：拿掉 W→R 和 W→W（讓 coalescing write buffer 能合併寫入）
- **Relaxed ordering**：任意重排獨立的記憶體存取

release consistency 的哲學是：**只在程式設計師說「這裡有關係」的地方才保證順序**，其餘完全放給硬體最佳化。好處是「避免在不共享的變數上引入不必要的順序」；代價是程式設計師必須很懂同步。

### 生產者-消費者的例子

> "Under sequential consistency, c = d = 1. Under TSO, the program also produces c = d = 1 even when there are no fences, because T2 will never see flag = 1 until after T1 stores 1 into a and b. However, under release consistency, without fences, the stores could be reordered arbitrarily."
> — p.680

中文解釋：Code Example 17.3 的生產者-消費者。T1 寫 a、b 然後設 flag；T2 等 flag 變 1 才讀 a、b。在 TSO 下這自然正確（因為 W→W 有保持）；在 release consistency 下會壞，而且有兩種壞法：T2 可能在 a、b 變 1 之前就看到 flag=1（**寫入被重排**），或者 T2 自己先把 a、b 的讀取提前到看到 flag=1 之前（**讀取被重排**）。第二種更不直覺。

### fence 是保守的

> "Notice that the fence is conservative. For example, if T1 performed other subsequent loads or stores to independent variables, they could not be reordered before the fence even if that wasn't important to program operation."
> — p.681

中文解釋：這句話帶出下一個概念——fence 會順便排序所有東西，包括你根本不在乎的。

### Acquire / Release 約束：更精準的工具

> "Fences are sufficient but can be overkill because they order all operations, not just the essential ones. Moreover, each fence is another instruction to fetch and execute, slowing program performance. To address these issues, release consistency models provide acquire and release constraints to specify ordering of certain memory operations. These constraints are typically specified by bits in the memory operation, so no separate fence instruction is needed."
> — p.681

中文解釋：兩個好處：更精準（只排序需要的）、不用額外指令（用現有指令裡的 bit 標註）。三個定義：
- **acquire operation**：所有執行緒會在「T 裡任何後續的記憶體操作」之前看到這個操作（**後面的不能提前到我之前**）
- **release operation**：所有執行緒會在「T 裡所有先前的記憶體操作」之後看到這個操作（**前面的不能延後到我之後**）
- **sequentially consistent operation**：兩者都有

Code Example 17.4 把 17.3 的 fence 換成標註：T1 對 flag 的 store 加 release 約束、T2 對 flag 的 load 加 acquire 約束。想像成一個單向柵欄：release 擋住前面的往後跑，acquire 擋住後面的往前跑。

## 17.1.4 Synchronization

### race condition 與 critical section

> "This is an example of a race condition in which the result depends on the order of operations in the interleaved threads. To solve this problem, the program must use mutual exclusion, where code within a critical section cannot interleave."
> — p.684

中文解釋：Code Example 17.5 是提款/存款的銀行例子，Table 17.2 顯示交錯後媽媽的 300 元存款消失了。關鍵觀察：**最終結果不確定是可以接受的**（先提款餘額走 500→100→400，先存款走 500→800→400），**但兩條路都要得到 400**。critical section 就是那段「從 getBalance 到 setBalance」不能被打斷的程式碼。

### 三種實作 lock 的方法

> "In method (a), the lock function waits until L is 0, then sets L to 1. This is called spinning. ... This approach has a subtle bug. Imagine that T1 and T2 execute lock() concurrently. Both detect that L is 0 and exit the while loop. Both advance to *L = 1 and think they have claimed the lock."
> — p.685

中文解釋：Code Example 17.7 的三種做法：
- **(a) 純軟體**：`while(*L); *L = 1;` —— **有 bug**。檢查和設定之間有空隙，兩個執行緒可以同時通過。單核心也會出這個錯（context switch 剛好插在中間）。
- **(b) 關中斷**：單核心可行，但缺點一堆——持鎖太久會餓死其他執行緒、系統沒反應、壞程式可能永不放鎖把系統掛住。所以 OS 通常不讓 user code 關中斷。而且**多核心根本無效**（兩個核心各自關中斷還是會撞）。
- **(c) TestAndSet**：靠硬體原子指令。

### 原子指令為什麼能解決問題

> "Atomic instructions cannot be interrupted in the middle; the read and write happen back to back such that no other thread may access the memory system in between the read and write."
> — p.685

中文解釋：關鍵就是「中間不可插入」。`TestAndSet` 讀出位址的值、寫入 1、回傳讀到的值——三件事一體。即使 T1 和 T2 同時發出，記憶體系統會仲裁，一次只讓一個過。這個指令可以追到 1960 年代的 Burroughs B5000。

> "Theoreticians have devised clever algorithms to reliably lock without atomic instructions [Dijkstra65]. These algorithms are tricky, and they are even trickier when they must support more than two threads. Moreover, these algorithms require sequential consistency, which most computers don't provide."
> — p.686

中文解釋：純軟體的解（如 Dekker、Peterson 演算法）存在但不實用。這段是在解釋「為什麼 ISA 必須提供原子指令」。

### 好的鎖要 fair 和 efficient

> "A good lock should not just protect the critical section but also be fair and efficient. ... The lock from Code Example 17.7(c) is called a spin lock and is simple but neither efficient nor fair."
> — p.686

中文解釋：三種鎖的比喻很好記：
- **spin lock（自旋鎖）**：像搶熱門演唱會票——一直刷新網頁。浪費 CPU，而且運氣不好的執行緒可能永遠搶不到（**starvation**）。
- **ticket lock（號碼牌鎖）**：像熟食店抽號碼牌。還是要等，但保證輪得到（**fair**）。
- **sleep lock（睡眠鎖）**：像客服電話留電話號碼回撥。最有效率但 context switch 也貴，所以實務上是**先自旋一小段時間，搶不到才睡**。

### 五種典型的原子指令

> "Typical atomic instructions include TestAndSet, Swap, FetchAndIncrement, CompareAndSwap, and the LoadReserved-StoreConditional pair."
> — p.686

中文解釋：能力由弱到強：
- **TestAndSet**：讀 + 寫 1 + 回傳舊值。夠做 spin lock。
- **Swap**：讀 + 寫入可設定的值 + 回傳舊值。比 TestAndSet 通用一點。
- **FetchAndIncrement**：讀 + 加一 + 寫回 + 回傳舊值。夠做 ticket lock 和 semaphore。
- **CompareAndSwap (CAS)**：三個輸入（位址、比較值、交換值）。讀出來如果等於比較值就寫入交換值，無論如何回傳讀到的值。最強，能實作前面三個（Code Example 17.8）。IBM 370 從 1970 年就有，x86、ARM 都支援。
- **lr-sc**：RISC-V 的選擇。

### 為什麼 RISC-V 不用 CompareAndSwap

> "CompareAndSwap does not play as gracefully with RISC architectures because it requires three source operands."
> — p.687

中文解釋：純粹是指令格式的問題。RISC-V 的 R-type 指令只有 rs1、rs2 兩個來源暫存器欄位，CAS 需要三個。（邊欄提到 RISC-V 後來定義了 Zacas 擴充加入 `amocas.w`，它讀 rd 當第三個運算元，但這需要修改管線。）

另外 CAS 有 **ABA problem**：記憶體中的值從 A 變成 B 又變回 A，CAS 看不出中間發生過事。常見解法是用雙倍寬的運算元，一半放值、一半放計數器。

### lr-sc 怎麼運作

> "LoadReserved (lr) acts like a normal load, but it also flags that the memory address is reserved. StoreConditional (sc) attempts to write a value to a memory address. If the address is still reserved, the write succeeds, and sc returns a success code (e.g., 0). If the reservation is no longer valid, the store is rejected, and sc returns a failure code (e.g., nonzero). The reservation is invalidated by another lr to a different address, or an sc to any address."
> — p.687

中文解釋：這是一個很優雅的設計。它把「原子性」從「一個複雜指令」拆成「兩個簡單指令 + 一個預約狀態」。三個好處（書上明列）：
1. 支援和 CAS 一樣的同步演算法
2. 避免「讀超過兩個暫存器」的實作困難
3. 避免在單一複雜指令裡讀-改-寫記憶體

代價是：**可能失敗、要重試**，而重試可能造成 livelock（17.1.5.2 會講）。Code Example 17.9 示範用 lr-sc 實作 TestAndSet、Swap、FetchAndIncrement、CompareAndSwap 和 spin lock，全都是 `while(1) { lr; if (sc(...) == 0) return; }` 這個模式。

### Ticket lock 的結構

> "The lock consists of two parts: turn and ticket. The ticket counts up, like a deli counter. Each thread that requests the lock takes the next value of the ticket. The turn also counts up, indicating which ticket is presently being served, like the 'Now Serving' sign at the deli counter."
> — p.688

中文解釋：Code Example 17.10。取鎖需要原子操作（`FetchAndIncrement(&ticket)` 或 lr-sc），**但放鎖不需要**（`turn++` 只有持鎖者會做，沒有競爭）。這是 ticket lock 的一個小優點。

### 生產者-消費者與條件變數

> "When a consumer thread finds the buffer empty, it should wait by going to sleep until it gets a signal that a new result is in the buffer. Likewise, if a producer finds the buffer full, it should wait until it gets a signal that the buffer has room. This coordination is called handshaking. Condition variables are used to synchronize producer and consumer threads."
> — p.690

中文解釋：這是**第二類**同步問題（第一類是 mutual exclusion）。也叫 bounded buffer 問題。Apache web server 就是這個模式：接收 HTTP 請求丟進佇列（producer），另一批執行緒取出處理（consumer）。

Code Example 17.11 是沒同步的版本，書上列出它的三種壞法：
1. `entries = entries + 1` 不是原子的——producer 讀了 k、被切走、consumer 減到 k−1、切回來寫 k+1，結果系統以為有 k+1 筆但實際只有 k 筆。
2. 多個 producer 同時看到 `entries < SIZE` 就一起放，造成 overflow。
3. 大家都在 spin，浪費 CPU。

Code Example 17.12 加上一個 lock L 和兩個條件變數 `putEntry`、`getEntry`。關鍵細節：

> "When the producer wakes back up, it checks the while loop condition once more to ensure the buffer really has space. (Another thread might have swooped in and refilled the buffer before this producer woke up.)"
> — p.692

中文解釋：這就是為什麼 `cond_wait` 一定要包在 **while 迴圈**裡而不是 if。被叫醒不代表條件還成立。這是並行程式設計最常見的 bug 之一。

### Semaphore（號誌）

> "A semaphore is an integer that is initialized to the number of shared resources available. The semaphore is atomically decremented or incremented using the OS calls sem_wait and sem_post to take or release resources, respectively. If the semaphore becomes negative because no resource is available, sem_wait puts the thread to sleep. If any threads are sleeping, sem_post wakes one."
> — p.692

中文解釋：Dijkstra 1968。號誌可以同時實作鎖和條件變數：
- **當鎖用**（Code Example 17.13）：`S = 1`，`lock` 就是 `sem_wait(S)`、`unlock` 就是 `sem_post(S)`。因為會睡而不是自旋，這是 sleep lock。
- **當條件變數用**（Code Example 17.14）：兩個號誌 `empty = SIZE`、`full = 0`。producer 先 `sem_wait(&empty)` 確保有空位，放完 `sem_post(&full)`；consumer 反過來。**但 put/get 本身仍是 critical section，還是要用 lock 包起來。**

### Futex：把常見情況留在 user mode

> "Semaphores use OS calls, which have a high overhead of context switching and saving/restoring registers. For applications such as multithreaded databases that need extensive locks but rarely face contention, the OS call overhead is enormous. A futex [Franke02] solves this problem by attempting to take a lock in U-mode and only calling the OS if the lock is contended."
> — p.693–694

中文解釋：futex = **f**ast **u**ser mu**tex**。核心洞察是：**大部分時候鎖根本沒人搶**。沒搶的情況完全在 user mode 用原子指令解決，只有真的撞上才進 kernel。這比 semaphore 快很多（semaphore 即使沒競爭也要 OS call），也比 spin lock 好（不會長時間空轉）。Linux 和 Windows 都提供 futex，是目前最有效率的同步原語。

`futex_wait(int *F, int expected)`：如果 futex 變數不等於 expected 就立刻回傳，否則睡到被喚醒。
`futex_wake(int *F, int num)`：叫醒 num 個等待者（通常 1，有時 INT_MAX 全叫醒）。

Code Example 17.15 的鎖用三個狀態：0 = 沒人拿、1 = 一個執行緒拿著、2 = 有人拿著而且**還有人在等**。這個「2」是精髓——`unlock` 靠它判斷要不要花成本呼叫 `futex_wake`。流程是：先自旋 100 次試 CAS，失敗才設成 2 並 `futex_wait`。

### 為什麼要用標準同步函式庫

> "A study of 12 major programs such as Apache Web Server, Mozilla Firefox, and MySQL discovered that every one of the programs had some ad-hoc synchronization and that 22%−67% of the ad-hoc synchronization contained undetected bugs [Xiong10]."
> — p.695

中文解釋：這個數字是整節最有說服力的一句話。**連 Apache、Firefox、MySQL 這種等級的專案，自己手寫的同步程式碼有 22%–67% 藏著未發現的 bug。** 所以用 POSIX thread（`pthread_mutex_lock`、`pthread_cond_wait`、`sem_wait`…）而不是自己造輪子。標準函式庫的四個好處：容易辨識同步點、可攜、包含該 CPU 記憶體模型所需的 fence、經過徹底除錯。

## 17.1.5 Deadlock, Livelock, and Starvation

### 三者的區別

> "Deadlock occurs when two or more threads are waiting for each other and are unable to proceed. Livelock is closely related to deadlock; the threads continue taking action but never make forward progress. Starvation occurs when a lower priority thread never gets resources because it is outcompeted by higher priority threads."
> — p.696

中文解釋：**deadlock 是卡住不動、livelock 是一直動但沒進展、starvation 是別人一直插隊**。

### Coffman Conditions：死結的四個必要條件

> "Mutual exclusion: Threads take exclusive control of resources they require. Hold and wait: Threads hold allocated resources while waiting for additional resources. No preemption: Resources cannot be forcibly removed from a waiting thread. Circular wait: A circular chain of threads exists such that each holds a resource requested by the next thread."
> — p.696

中文解釋：Dijkstra 的 dining philosophers（哲學家用餐問題，Fig. 17.2）：五個哲學家圍桌，每人左右各一支叉子，吃麵要兩支。每人都先拿左邊那支——全部卡住。這個問題同時滿足四個條件。

**關鍵是：四個條件缺一不可，所以打破任何一個就能避免死結。** 書上給了對應的四種策略：
- **破 mutual exclusion**：用 lock-free 資料結構（每個盤子放兩支叉子）
- **破 hold and wait**：一次要求全部資源，拿不到就不動（同時拿兩支叉子）
- **破 no preemption**：拿不到就把手上的全放掉、等隨機時間再試（放下左叉子，想一會兒再試）
- **破 circular wait**：規定取得資源的順序（叉子編號 1–5，一律先拿編號小的）

最後一個最常用，也最實用。

### 三種不預防的做法

> "Avoidance: When a thread requests a resource, the OS denies the request if granting the resource would put the system in an unsafe state. Detection and recovery: The OS detects deadlock and removes resources until the deadlock is solved. Ignorance: Assume deadlock will not occur. Let the user reboot the computer when it occurs."
> — p.697

中文解釋：第三個「無視」不是玩笑——書上直接點名「Windows OS is notorious for using this strategy, and even Linux is susceptible to this for certain deadlocks」。如果死結比其他系統故障罕見，重開機是可以接受的工程取捨。

### lr-sc 的 livelock 風險

> "A disadvantage of lr-sc over CompareAndSwap is that the former can enter livelock. Two threads might spin to acquire the same lock. If they exactly interleave, each might invalidate the other thread's reservation such that neither ever successfully completes the StoreConditional."
> — p.698

中文解釋：這是 lr-sc 設計的**代價**。兩個執行緒完美交錯時，各自的預約一直被對方作廢，兩邊的 `sc` 都永遠失敗——一直在動，但沒進展。RISC-V 的解法是定義「constrained lr-sc loops」（17.2.3.2 會講），保證符合特定形式的迴圈最終一定會成功。

### starvation 的解法

> "Starvation is avoided by fair synchronization algorithms such as ticket locks (see Section 17.1.4.1) or by raising the priority of a thread that has been waiting too long."
> — p.698

中文解釋：兩招：公平的演算法（ticket lock），或動態提高等太久的執行緒的優先權（aging）。

## 所以呢

這節建立了整個並行問題的地圖：coherence 和 consistency 是硬體提供的保證，synchronization 是軟體用這些保證蓋出來的機制，deadlock/livelock/starvation 是蓋歪了會出的事。RISC-V 在這張地圖上的位置是：release consistency（RVWMO）+ fence 指令 + A 擴充的原子指令（AMO 與 lr-sc）。下一節 17.2 就講這些指令的具體編碼與語意。
