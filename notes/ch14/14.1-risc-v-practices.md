# 14.1 RISC-V Practices

> 原書 p.579–582（Chapter 14: Extensions: C (Compressed)）
> 含章首導論、14.1.1 Zc* Extension

## 這節在講什麼

**壓縮指令的動機、編碼設計，以及 Zc* 擴充家族。**

**核心論點只有一句：程式碼小 25–30%，
而 IROM（非揮發性程式記憶體）是嵌入式系統最貴的元件之一。**

**最該精讀的是「編碼如何與未壓縮指令優雅共存」那段**——
它示範了 ISA 設計中「向後相容」和「新功能」如何兼顧。

## 關鍵點

### 為什麼需要壓縮指令

> "**Most reduced instruction set computer (RISC) architectures were developed with 32-bit instruction encodings.
>  As they began to compete with 16-bit microcontrollers in cost-sensitive markets, RISC was at a disadvantage
>  because compiled programs typically require more nonvolatile memory, which is one of the costliest parts of the
>  system. Moreover, fewer 32-bit instructions fit in a cache, resulting in higher miss rates.**"
> — p.579

中文解釋：**兩個成本，一個競爭壓力：**

| 問題 | 後果 |
| --- | --- |
| **非揮發性記憶體是系統最貴的元件之一** | 程式碼大 = 成本高 |
| **32-bit 指令在 cache 裡裝得少** | **miss rate 提高** |
| **要和 16-bit 微控制器競爭** | RISC 處於劣勢 |

（呼應 2.5 節：「嵌入式處理器的非揮發性程式記憶體往往是最貴的元件」。）

**解法（p.579）：**
> "**Therefore, many RISC architectures have introduced compressed instruction sets that provide 16-bit
>  representations of commonly used instructions. These compressed instructions are mostly a subset of the full
>  instruction set and can be "inflated" back to 32 bits to be executed by the normal execution units.**"

**關鍵設計決定：「膨脹回 32 bit，用一般的執行單元執行」**——
**不需要新的 datapath，只需要一個解壓縮器。**

**（p.579 邊欄：**「其他 RISC 的壓縮指令集包括 **ARM Thumb、MIPS16e、PowerPC VLE、Hitachi SHcompact**。」**）

### Spill：壓縮指令的代價

> "**A processor that supports compressed instructions may execute both compressed and regular 32-bit instructions
>  in the same program. So, a 32-bit instruction might be fetched from a 16-bit boundary, crossing cache lines or
>  IROM words. This is called a *spill* and requires two memory accesses to fetch both halves of the instruction.**"
> — p.579

中文解釋：**Spill 是壓縮指令的主要實作代價**——
**因為指令不再保證 4-byte 對齊，32-bit 指令可能跨越兩條 cache line。**
（呼應 10.2 節。14.3.3 節會詳述。）

### 編碼設計的三個巧思

> "**All compressed instructions are 16 bits long. To achieve this, the first source register is generally also used
>  as the destination, and immediates are shorter than in ordinary instructions. Compressed instruction use many
>  formats, trading regularity for density. The formats have different numbers of function (`funct`) bits.
>  Some instructions only allocate 3 bits to specify a register, so they are restricted to using only eight registers
>  (x8-x15).**"
> — p.579

中文解釋：**三個省位元的手法：**

| 手法 | 說明 |
| --- | --- |
| **第一個來源暫存器也當目的暫存器** | 省 5 bit |
| **立即值較短** | — |
| **只用 3 bit 指定暫存器** | **只能用 x8–x15 八個暫存器** |

**「trading regularity for density」（用規律性換密度）**——
這是壓縮指令集的本質取捨，**和第 2 章 RISC-V 強調的「編碼規律性」正好相反。**

**（x8–x15 的選擇不是隨意的**——回顧 2.1 節的暫存器命名邊欄：
編號刻意安排成「只用 x0–x15 時每一類用途都還有得用」。）

### 和未壓縮指令優雅共存

> "**The compressed instruction format is cleverly chosen to play gracefully with uncompressed instructions.
>  Whereas the two least significant bits of uncompressed instructions are always 11, these bits have a different
>  value for compressed instructions. Thus, the instruction encodings do not overlap for compressed and uncompressed
>  instructions, and a program can freely use both. The register fields, when present, are in the same place in all
>  compressed formats to reduce the cost of decompression, and the most significant bit of the immediate is always
>  in instruction bit 12 to simplify sign extension.**"
> — p.579–580

中文解釋：**三個設計決定，每一個都對應一個硬體成本：**

| 設計 | 解決什麼 |
| --- | --- |
| **未壓縮指令的 `instr[1:0]` 永遠是 11** | **編碼不重疊 → 一個 bit 檢查就能分辨壓縮與否** |
| **暫存器欄位在所有壓縮格式中位置相同** | **降低解壓縮的成本**（不需要多工器） |
| **立即值的 msb 永遠在 bit 12** | **簡化符號延伸**（fanout 最大的訊號位置固定） |

**後兩者和第 2.2 節未壓縮指令的設計原則完全一致**——
**「欄位位置固定省多工器」、「符號位元位置固定省延遲」。**

### 膨脹的機制

> "**Every compressed instruction maps onto an equivalent 32-bit instruction. Therefore, instead of adding a whole
>  new datapath, a RISC-V processor can decompress compressed instructions and then execute that decompressed
>  instruction normally on the existing datapath.**"
> — p.580

**Example 14.1（p.580）的具體編碼，值得跟一遍：**

**`c.add x5, x6` 的 16-bit 編碼：**
```
funct4  rd/rs1  rs2    op
1001    00101   00110  10    = 0x929A
```
（CR-type，`op = 10`，`funct4 = instr[15:12] = 1001`，rd/rs1 = 5，rs2 = 6。）

**膨脹成 `add x5, x5, x6` 的 32-bit 編碼：**
```
funct7   rs2    rs1    funct3  rd     op
0000000  00110  00101  000     00101  0110011  = 0x006282B3
```

**注意兩件事：**
1. **`c.add x5, x6` 展開成 `add x5, x5, x6`**——**rd/rs1 欄位同時填進 rd 和 rs1**
2. **壓縮版的 `op = 10`，未壓縮版的 `op[1:0] = 11`**——編碼不重疊

**（p.580 邊欄：**「少數壓縮指令會解壓縮成**兩條或更多**標準 RISC-V 指令。」**）

### 效益與一個相容性陷阱

> "**According to the RISC-V Unprivileged Specification 20240411, a compiler that uses compressed instructions when
>  possible reduces code size by 25%−30% for typical programs [RISCV-Unprivileged].**"
> — p.580

> "**To make best use of the limited encoding space, certain compressed machine language opcodes expand into
>  different instructions in different ISAs. For example, the instruction with op = 01, instr[15:13] = 001 is
>  `c.jal` in RV32IC but is `c.addiw` in RV64IC. The instruction with op = 00, instr[15:13] = 011 is `c.flw` in
>  RV32ICF but is `c.ld` in RV64IFC. Therefore, a program compiled for RV32IC will not run correctly on RV64IC.**"
> — p.580

中文解釋：**這是一個重要的相容性陷阱：**

**同一個壓縮編碼在 RV32 和 RV64 表示不同的指令。**

| 編碼 | RV32IC | RV64IC |
| --- | --- | --- |
| `op = 01, instr[15:13] = 001` | **`c.jal`** | **`c.addiw`** |
| `op = 00, instr[15:13] = 011` | **`c.flw`**（RV32ICF） | **`c.ld`**（RV64IFC） |

**後果：「為 RV32IC 編譯的程式在 RV64IC 上不會正確執行」。**

**這打破了「RV32 是 RV64 的子集」這個直覺**——
壓縮指令為了榨乾編碼空間，犧牲了這個性質。

### Zc* 擴充家族

> "**The Zc* family of extensions provides additional compressed instructions to improve code density even more than
>  the original compressed (C) extension, especially for embedded processors where the IROM is a major part of system
>  cost.**"
> — p.580

中文解釋：**六個擴充，各自的職責（p.581）：**

| 擴充 | 內容 |
| --- | --- |
| **Zca** | **C 擴充的所有指令，但排除 Zcf 和 Zcd 的 F/D load/store** |
| **Zcf** | **壓縮的單精度 load/store**（需要 F 擴充，**僅 RV32**）：`c.flw`, `c.flwsp`, `c.fsw`, `c.fswsp` |
| **Zcd** | 壓縮的雙精度 load/store（需要 D 擴充）：`c.fld`, `c.fldsp`, `c.fsd`, `c.fsdsp` |
| **Zcb** | **subword 與其他基本整數指令**：`c.lbu`, `c.lh`, `c.lhu`, `c.sb`, `c.sh`, `c.zext.b`, `c.not`；Zbb only: `c.sext.b`, `c.zext.h`, `c.sext.h`；M only: `c.mul`；RV64 only: `c.zext.w` |
| **Zcmp** | **Push/pop 壓縮指令**（opcode 和 Zcd 衝突）：`cm.push`, `cm.pop`, `cm.popret`, `cm.popretz`, `cm.mva01s`, `cm.mvsa01` |
| **Zcmt** | **Table jump 指令**（opcode 和 Zcd 衝突）：`cm.jt`, `cm.jalt` |

**Zca 的動機（p.580）：**
> "**The Zca extension is a subset of the C extension that omits these compressed floating-point load/stores to save
>  hardware in embedded processors with no floating-point unit (FPU).**"

**Zcb 的動機（p.581）——這段的推理很有意思：**
> "**Zcb defines more compressed instructions overlooked in C. When code density is important, data density is also
>  important, so the Zcb extension adds instructions to load and store bytes and half-words. Subword arithmetic can
>  overflow into the upper part of the word, so it is often followed by sign- or zero-extension to discard the
>  overflow. Zcb includes these subword zero-/sign-extension instructions. Zcb also provides compressed multiply and
>  NOT instructions, which are common in integer programs.**"

**「程式碼密度重要時，資料密度也重要」——所以要加 subword load/store。
而 subword 運算會溢位到字的上半部，所以常跟著符號/零延伸——所以也要加那些指令。**

**Zcmp 和 Zcmt 的動機（p.581）：**
> "**Saving and restoring registers on the stack takes many instructions in RISC-V. Other architectures have
>  discovered dedicated PUSH and POP instructions improve code density by saving or restoring multiple registers with
>  a single instruction. `cm.popret` pops registers and also returns from a function call. These operations decompress
>  into two or more standard RISC-V instructions.... Similarly, the Zcmt extension defines table jumps, which improve
>  code density for jumps and function calls. They use a new *jump vector table* (JVT) CSR that points to a table of
>  jump addresses; table jumps do not correspond to standard RISC-V instructions.**"

**兩個「不對應標準 RISC-V 指令」的擴充：**
- **Zcmp 的 push/pop 會解壓縮成兩條以上的標準指令**
- **Zcmt 的 table jump 用一個新的 JVT CSR，根本不對應標準指令**

**這是 C 擴充哲學的突破**——不再只是「32-bit 指令的 16-bit 表示」。

### Profile 的組合關係

> "**The RV32GC/RV32IFDC extension implies Zca + Zcf + Zcd. RV64GC/RV64IFDC implies Zca + Zcd; they do not support
>  Zcf because these instruction encodings are reused for 64-bit integer loads and stores.
>  An RV64GC_Zcb_Zbb processor implements Zca + Zcb + Zcd, but not Zcmp or Zcmt.**"
> — p.582

> "**Zce is shorthand for Zca + Zcb + Zcmp + Zcmt. In RV32F, Zce also includes Zcf. It excludes Zcd, whose opcodes are
>  reused for Zcmp and Zcmt. Benchmark results show that Zce provides an average 11% further code size reduction over
>  the C extension [codesize]. Zce is a natural replacement for the C extension in embedded processors.**"
> — p.582

中文解釋：**兩個組合：**

| 組合 | 內容 | 適用 |
| --- | --- | --- |
| **RV32GC** | Zca + Zcf + Zcd | |
| **RV64GC** | **Zca + Zcd**（**沒有 Zcf**，編碼被 64-bit 整數 load/store 重用） | |
| **Zce** | **Zca + Zcb + Zcmp + Zcmt**（RV32F 加 Zcf，**排除 Zcd**） | **嵌入式處理器** |

**Zce 的效益：比 C 擴充再省 11% 程式碼大小。**

**注意 Zcd 和 Zcmp/Zcmt 互斥**（opcode 衝突）——
**所以要「雙精度浮點壓縮」還是「push/pop 和 table jump」，只能二選一。**
**這是編碼空間耗盡的直接後果。**

## 名詞表

| 名詞 | 意思 |
| --- | --- |
| **Spill** | 32-bit 指令跨越兩條 cache line 或 IROM 字，需要兩次記憶體存取 |
| **`instr[1:0] = 11`** | **未壓縮指令的標記**；壓縮指令用其他值，所以編碼不重疊 |
| Inflate / decompress | 把 16-bit 壓縮指令展開成等價的 32-bit 指令 |
| x8–x15 | 只用 3 bit 指定暫存器的壓縮指令能用的八個暫存器 |
| **Zca** | C 擴充扣掉浮點 load/store |
| **Zcf / Zcd** | 壓縮的單精度（僅 RV32）/ 雙精度浮點 load/store |
| **Zcb** | subword load/store、零/符號延伸、`c.mul`、`c.not` |
| **Zcmp / Zcmt** | push/pop（含 `cm.popret`）/ table jump（用 **JVT** CSR）；**與 Zcd 的 opcode 衝突** |
| **Zce** | Zca + Zcb + Zcmp + Zcmt；**比 C 再省 11% 程式碼** |
| JVT | Jump vector table CSR，指向跳躍位址表 |

## 所以呢

**這節建立了壓縮指令的動機和設計。四件最該帶走的事：**

1. **效益：程式碼小 25–30%**（Zce 再多 11%）。
   **動機是嵌入式系統的 IROM 成本和 I$ 的 miss rate。**

2. **編碼設計的三個巧思**：
   **`instr[1:0] = 11` 標記未壓縮（編碼不重疊）、
   暫存器欄位位置固定（省解壓縮的多工器）、
   立即值 msb 固定在 bit 12（簡化符號延伸）。**
   **和第 2.2 節未壓縮指令的設計原則一致。**

3. **代價有三個**：
   **spill**（指令可能跨 cache line）、
   **「用規律性換密度」**（格式很多、只能用 8 個暫存器）、
   **RV32 和 RV64 的壓縮編碼不相容**（同一個編碼是不同指令）。

4. **編碼空間已經耗盡**——
   **Zcd（雙精度壓縮 load/store）和 Zcmp/Zcmt（push/pop 和 table jump）互斥。**
