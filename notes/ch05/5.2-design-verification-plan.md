# 5.2 Design Verification Plan

> 原書 p.202–203（Chapter 5: Design Verification）

## 這節在講什麼

**很短，但它是整章的組織核心。**

DV plan（設計驗證計畫，也叫 test plan）要同時滿足兩個看似衝突的需求：
- **人讀得懂**——審查者能判斷「所有功能都測到了嗎」
- **機器能執行**——驗證工程師能照著寫出測試，並量測覆蓋率

**解法是「高階敘述 + 試算表」的兩層結構**，
以及一張規定好欄位的表格——這節的主要內容就是那五個欄位。

## 關鍵點

### DV plan 的雙重要求

> "A design verification plan (DV plan or test plan) needs to be organized in a way that
>  human reviewers can determine if all features of the system are tested and in a way that
>  the verification engineer can write tests to cover each feature and measure whether each
>  feature was covered."
> — p.202

中文解釋：呼應 5 章導論那句話（p.194）：
**"It must cover both the trees and the forest"**——**既要見樹又要見林。**
> "it must have enough detail that a verification engineer can translate each requirement
>  into a machine-readable test but also be organized in a way that the reader can be
>  confident that all the system's functions are covered."

**這兩個需求方向相反**：細節多才能執行，但細節多就看不出全貌。
**所以要分層。**

### 兩層結構：高階敘述 + 試算表

> "This generally involves a high-level statement enumerating the major areas (e.g., base
>  instruction set, unprivileged extensions, privileged instructions, privileged extensions),
>  pointing to spreadsheets that list each feature and subfeature."
> — p.202

中文解釋：**上層是「有哪些大領域」，下層是試算表列出每個功能與子功能。**

RISC-V 的四大領域（p.202）：
**基礎指令集、非特權擴充、特權指令、特權擴充。**

（這個分法對應 2.5 節的 base + extensions，以及 2.3 節的特權架構。）

### 功能怎麼拆成子功能

> "For example, a spreadsheet for the M extension could contain a feature for each
>  instruction. Each feature would contain subfeatures, such as the following:
>  - Using all registers for each source and destination
>  - Using all combinations where source and destination register match
>  - Corner cases of inputs: (0, 1, 2, random number, max positive, max negative, −1)"
> — p.202

中文解釋：**M 擴充的例子很有代表性。每條指令是一個 feature，底下三類 subfeature：**

| 子功能類型 | 內容 | 為什麼需要 |
| --- | --- | --- |
| **所有暫存器** | 每個來源和目的都試過所有暫存器 | 抓「某個暫存器接錯」的 bug |
| **來源與目的重疊的所有組合** | 如 `mul x1, x1, x2`、`mul x1, x2, x1`、`mul x1, x1, x1` | **抓寫回時序的 bug**（呼應 2.7 節的 hazard） |
| **輸入的 corner case** | 0、1、2、隨機數、最大正數、最大負數、−1 | 邊界行為（呼應 5.1.1 節） |

**第二類「來源與目的重疊」特別容易被忽略**，但它是硬體 bug 的高發區。

書上邊欄補充（p.202 邊欄）：
**"Division instructions have additional subfeatures for specific corner cases, such as
division by 0 and overflow."** ——**除法還要多測除以 0 和溢位。**

### 試算表的五個欄位（本節最實用的部分）

> "The spreadsheet should contain the following columns for each feature and subfeature.
>  - A reference to a specification
>  - A description of the feature to be verified
>  - A description of the required stimulus to exercise the feature
>  - A method of checking the correct operation of the feature
>  - The coverage specification that indicates that the feature was actually verified
>  - A reference to the coverage specified in the previous point"
> — p.202–203

中文解釋：**這張表的欄位設計很值得學，因為每一欄回答一個不同的問題：**

| 欄位 | 回答什麼問題 |
| --- | --- |
| **規格參照** | **「根據是什麼？」**——這個要求從哪條規格來的 |
| **功能描述** | 「要驗什麼？」 |
| **所需激勵（stimulus）** | **「怎麼觸發它？」** |
| **檢查方法** | **「怎麼知道對不對？」** |
| **覆蓋率規格** | **「怎麼證明真的驗過了？」** |
| **覆蓋率參照** | 指向實際的 coverpoint |

**三個設計上的洞見：**

1. **「規格參照」在第一欄**——每個測試都要追溯到規格的某一條。
   **這防止「測了不該測的」和「規格有但沒測的」。**

2. **「所需激勵」和「檢查方法」分開**——
   這是驗證的兩半：**能觸發 ≠ 能發現錯誤**。
   （呼應 5.1.1 節的 Pentium FDIV：測到了，但測錯對象，所以沒發現。）

3. **最後兩欄關於覆蓋率，而且分成「規格」和「參照」兩欄**——
   **「宣稱要達成的覆蓋」和「實際的 coverpoint」要分開記錄**，
   這樣審查時才能檢查兩者是否對應。
   （這兩欄就是 5.9 節功能覆蓋率的來源。）

**整張表的邏輯鏈很清楚：規格 → 功能 → 怎麼觸發 → 怎麼檢查 → 怎麼證明測過了。**

Wally 的實際 DV plan 範例在第 5.11.1 節。

## 名詞表

| 名詞 | 意思 |
| --- | --- |
| DV plan / test plan | 設計驗證計畫。定義覆蓋需求的結構化文件 |
| Feature / subfeature | 功能 / 子功能。例如「每條 M 指令」是 feature，「所有暫存器組合」是 subfeature |
| Stimulus | 激勵。觸發某功能所需的輸入 |
| Coverage specification | 覆蓋率規格。指出「這個功能確實被驗證過」的依據 |

## 所以呢

**DV plan 的價值在於它把「測夠了嗎」這個模糊問題，
變成一張可以逐列勾選、可以被機器量測的表。**

兩件帶得走的事：
1. **五個欄位的邏輯鏈**：規格參照 → 功能描述 → 所需激勵 → **檢查方法** → 覆蓋率。
   **「能觸發」和「能發現錯誤」是兩件事，所以要分兩欄。**
2. **子功能的三種拆法**：所有暫存器、**來源與目的重疊的組合**、輸入 corner case。
   第二項最容易漏，也最容易出 bug。

下一節（5.3）講最便宜的除錯手段：lint。
