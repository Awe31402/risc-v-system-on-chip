## 關鍵點

### 特權單元的位置與時序

> "**The privileged unit adds architectural state: the CSRs and the 2-bit privilege mode.
>  Privileged instructions operate in the Memory stage and update the architectural state on the
>  rising edge of the clock at the start of the Writeback stage.**"
> — p.364

中文解釋：**兩件事要記住：**
1. **新增的架構狀態 = CSR + 2-bit 特權模式**
2. **特權指令在 Memory 級運作，在 Writeback 級開始時更新架構狀態**

（呼應 7.2 節：所有架構狀態的改動都延遲到 Writeback 級，這是 precise trap 的前提。）

**Fig. 8.12（p.368）是加上特權單元後的 Wally 方塊圖，
`privileged` 區塊含 `trap` 和 `CSR`，位於 Memory/Writeback 級。**

**（p.367 邊欄的閱讀慣例：**
「加到圖上的新東西用**亮藍色外框**標示。灰色的模組是還沒加入的。」**）

### 四個模組的分工

> "Fig. 8.13 shows a block diagram of the privileged unit, including major busses connecting components.
>  **The major components are the csr unit, which holds the CSRs; the trap unit that issues traps;
>  the privmode unit that tracks the privilege mode; and privdec, which decodes privileged instructions.
>  These blocks all operate in the Memory stage, and the csr and privmode blocks update state at the
>  start of the Writeback stage. The privileged pipeline registers (privpiperegs) delay faults that occur
>  in the Decode and Execute stages so that they are processed in the Memory stage instead.**"
> — p.365

中文解釋：**四個模組 + 一組 pipeline 暫存器：**

| 模組 | 職責 |
| --- | --- |
| **`csr`** | 持有所有 CSR |
| **`trap`** | **發出 trap**（決定 TrapM、CauseM、DelegateM） |
| **`privmode`** | **追蹤目前的特權模式** |
| **`privdec`** | **解碼特權指令** |
| **`privpiperegs`** | **把 Decode 和 Execute 級發生的 fault 延遲到 Memory 級處理** |

**`privpiperegs` 的存在理由很關鍵：
所有 trap 都要在同一個地方發生（Memory 級），
所以早期發生的 fault 要先存起來，等到 Memory 級再一起處理。**

### `csr` 模組的介面（很完整的清單）

> "The CSR unit (csr) contains all the CSRs and has the following functions:
>  - **Reads and writes the CSRs over the CSRReadValW and SrcAM signals**, respectively, connecting to
>    the IEU.
>  - During traps, it does the following:
>    o **Sends delegation and interrupt register values (mideleg/medeleg, and mip/mie) to the trap unit
>      and reads the trap cause from the trap unit**
>    o **Sends xstatus bits to trap and privmode**
>    o **May record InstrM (in xtval) and PCM (in xepc) from the IFU and IEUAdrM (in xtval) from the IEU**
>    o **Uses the CSRs (xtvect) to determine the trap destination, UnalignedPCNextF**
>  - Sends or receives the remaining signals (discussed in future chapters).
>    o **Sends pmp and satp CSRs to the LSU to control memory management (see Chapter 12)**
>    o **Sends the frm (floating-point rounding mode) CSR to control the FPU, which returns the
>      SetFFlagsM signals (see Chapter 16)**
>    o **The CLINT provides the MTIME_CLINT signal for the timer (see Section 20.2)**"
> — p.367–368

中文解釋：**這份清單顯示 `csr` 模組是整顆處理器的樞紐——它和 IFU、IEU、LSU、FPU、CLINT 都有連線。**

**注意三個資料來源對應 `xtval` 的不同內容**（呼應 Table 8.4）：
**`InstrM`（非法指令）、`IEUAdrM`（記憶體位址）、`PCM` 存進 `xepc`。**

### `trap` 與 `privmode`

> "**The trap module receives exceptions and interrupts; determines what to take, considering the
>  current privilege mode (PrivilegeModeW); and responds with TrapM, DelegateM, and CauseM.**"
> — p.368

> "**The privmode module changes the privilege in response to traps and mret/sret instructions.**"
> — p.368

中文解釋：**`trap` 負責「決定要不要 trap 和為什麼」，`privmode` 負責「改變特權模式」。**

### 組態旗標

> "**Privileged support is enabled by setting the ZICSR_SUPPORTED flag to 1 in config.vh.
>  When ZICSR_SUPPORTED = 0, all the privileged signals and architectural state are tied to 0 and
>  optimized away by logic synthesis.**"
> — p.368

中文解釋：呼應 4.2.5.1 節「綁 0 讓合成器最佳化掉」。

| `VECTORED_INTERRUPTS_SUPPORTED` | 向量中斷 |

| **`PMP_ENTRIES`** | **0、16 或 64** |

### 特權指令的解碼

> "**All these instructions have an op field of 1110011 and are further distinguished by the funct3
>  field and upper 12 bits of the instruction. The controller module in the IEU asserts PrivilegedM
>  based on the op field, and the privdec module looks at the other fields to determine the specific
>  privileged instruction.**"
> — p.370

中文解釋：**兩層解碼：IEU 的 controller 看 op（1110011）判斷「這是特權指令」，
`privdec` 再看其他欄位判斷「是哪一條」。**

**各指令的實作（p.370）：**

| 指令 | 實作 |
| --- | --- |
| `mret`/`sret` | 改變 PC、特權模式、status 暫存器 |
| `ecall`/`ebreak` | 產生對應的例外 |
| **`wfi`** | **在 Memory 級 stall Wally，直到中斷 pending 或逾時。逾時計數器也在特權單元裡** |
| CSR 讀寫 | **set 和 clear 涉及 read-modify-write 序列** |
| `sfence.vma` | 使 TLB 失效（第 11.2.4 節） |

**`privdec` 也負責在「指令未定義或不支援，或 `wfi` 逾時」時產生非法指令例外**（p.370）。

### `csr` 模組的六個子模組

> "The csr module contains the CSRs along with logic to read, write, set, and clear bits in the CSRs.
>  **It also contains logic to compute the next mtval (see Table 8.4) and PC (Fig. 8.17) during traps;
>  the logic is here rather than in the trap module to preserve locality because it depends on xtvec
>  (mtvec, stvec) and xepc (mepc, sepc).** The CSRs are partitioned into submodules:
>  - `csrsr` mstatus / sstatus — Status registers
>  - `csri` mip / sip / mie / sie — Interrupt pending and enable registers
>  - `csrc` — Performance counters
>  - `csrm` — Other M-mode CSRs
>  - `csrs` — Other S-mode CSRs
>  - `csru` — U-mode CSRs (floating-point)"
> — p.370

中文解釋：**六個子模組，按「功能」和「特權等級」混合分類。**

**「把 `mtval` 和 PC 的計算邏輯放在 `csr` 而非 `trap`，是為了保持局部性（locality），
因為它依賴 `xtvec` 和 `xepc`」**——這是一個很實際的模組劃分考量
（呼應 6.1 節：線長影響時序，把相關的東西放在一起）。

**非法存取的偵測（p.371）：**
> "**Each CSR submodule contains a register for each CSR, address decoders, write enables, and read
>  multiplexers. If none of the submodules detect a legal access, the csr module causes an
>  illegal-instruction exception.**"

**「沒有任何子模組認得這個存取」= 非法**——這是分散式解碼的自然結果。

### Trap 單元的邏輯（Fig. 8.14）

> "The trap module manages pending exceptions and interrupts, global and local interrupt enables, and
>  delegation registers. Key outputs include:
>  - **`TrapM`** Trap should occur
>  - **`CauseM`** Cause of highest-priority trap
>  - **`DelegateM`** Trap should be delegated to S-mode"
> — p.371

中文解釋：**Fig. 8.14（p.373）的資料流，值得跟一遍：**

```
mstatus.MIE ─┐
M_MODE ──────┼→ MIntGlobalEnM ─┐
U_MODE ──────┤                  ├→ (與 mideleg 一起選) ─┐
S_MODE ──────┼→ SIntGlobalEnM ─┘                        │
mstatus.SIE ─┘                                           │
                                                          ↓
mie, mip ────────→ PendingIntsM ────────────────→ ValidIntsM ─┐
                        ↓                                      │
                   IntPendingM（給 wfi 用）                    │
                                                               ↓
FaultsM ─────────→ ExceptionM ──────────────────→ Priority Encoder → CauseM
                        ↓                                      ↓
InstrValidM ───────────┴────────────→ InterruptM ────→ TrapM
                                                               ↓
medeleg/mideleg ──→ DelegateExM / DelegateIntM ──────→ DelegateM
```

**書上的說明（p.371–373）：**
> "**Precise interrupts are always associated with a specific PC so that the handler can return properly.
>  Therefore, when the instruction in the Memory stage is not valid, interrupts are disabled until the
>  next valid instruction arrives (InstrValidM = 1).** Meanwhile, the trap unit determines which
>  interrupts are pending (PendingIntsM) based on the mie and mip registers. The interrupts that are
>  both pending and enabled are valid (ValidIntsM). **A priority encoder considers all the valid traps to
>  determine a CauseM code for the highest priority trap. If any trap occurs, TrapM is asserted.**
>  Depending on the cause and type of the trap, the unit examines the corresponding bit of the mideleg or
>  medeleg register to assert DelegateM if the trap should be delegated to S-mode. **IntPendingM is also
>  raised when any interrupt is pending (to end a wfi), even if it is not enabled.**"

**三個關鍵設計：**
1. **`InstrValidM` 是 precise interrupt 的守門員**——
   **Memory 級沒有有效指令時不能接受中斷**（因為沒有 PC 可以存進 `mepc`）
2. **Priority encoder 實作 Table 8.4 的優先序**
3. **`IntPendingM` 和「中斷被接受」是兩回事**——
   **即使中斷沒被啟用，pending 也要結束 `wfi`**（呼應 8.2.2.4 節邊欄）

**Table 8.11（p.374）例外的來源：**

| 例外 | 來源模組 |
| --- | --- |
| Instruction page/access fault | **`mmu`**（第 11.4.3 節） |
| **Illegal instruction、Breakpoint、`ecall`** | **`privdec`**（8.4.2 節） |
| Instruction address misaligned | **`ifu`** |
| Load/Store 的 misaligned、page fault、access fault | **`mmu`** |

**大部分例外來自 MMU——這解釋了為什麼第 11 章那麼重要。**

### Precise trap 的實作（最重要的一段）

> "Recall that RISC-V traps are precise, so the instructions before the trap complete and the instructions
>  after the trap are flushed and do not affect architectural state. **The simplest way to ensure
>  consistency in the architectural state is to update all state at the same time. The register file is
>  written in the Writeback stage, so Wally updates all other state at this time. In particular,
>  instructions changing the privilege mode or CSRs write this state on the rising edge of the clock at
>  the start of the Writeback stage.**"
> — p.374

> "**Exceptions may occur as late as the Memory stage; load/store faults are not known until this time.
>  Again, it is simplest to have all traps take place at the same place in the pipeline and as late as
>  possible before architectural state is updated, meaning traps occur in the Memory stage and change
>  state at the rising edge of the clock at the start of the Writeback stage. When a trap occurs, the
>  instruction in the Memory stage and all subsequent instructions in earlier stages are flushed.
>  In Fig. 8.15, TrapM causes the full pipeline flush. On the rising edge of the clock at the start of
>  the Writeback stage, CSRs are updated (including epc, tval, cause, and status), and the privilege mode
>  and PC are changed to take the trap.**"
> — p.374

中文解釋：**兩個「最簡單」的設計原則，這是整節的核心：**

1. **「同時更新所有狀態最簡單」** → 全部在 Writeback 級開始時更新
2. **「所有 trap 都在 pipeline 的同一個地方、且盡可能晚」** → 全部在 Memory 級

**為什麼是 Memory 級？因為 load/store fault 要到那時才知道。**
**再晚就來不及了（Writeback 級已經在改狀態）。**

**Trap 的完整動作：**
- **`TrapM` 造成整條 pipeline flush**（Memory 級及更早的全部）
- **Writeback 級開始時：更新 `epc`、`tval`、`cause`、`status`，改變特權模式和 PC**

### 五種新的 pipeline 危障

**Fig. 8.15（p.375）是加上特權支援後的 hazard 單元，新訊號用藍色標出。
和 Fig. 7.19 相比多了五組：**

**（1）Trap → flush 全部**
```
FlushMCause ← TrapM | RetM | CSRWriteFenceM
FlushWCause ← TrapM & ~WFIInterruptedM
```

**（2）`mret`/`sret`（8.4.5.2，p.375）**
> "**Like traps, mret and sret change the PC and privilege mode on the rising edge of the clock at the
>  start of the Writeback stage. Hence, they must flush all subsequent instructions in the pipeline.
>  In Fig. 8.15, RetM causes a flush of all but the Writeback stage.**"

**`mret` 不 flush Writeback 級——因為 `mret` 自己就在那裡。**

**（3）CSR 讀 → stall（8.4.5.3，p.375–376）**
> "**CSR reads occur in the Memory stage so they obtain the latest CSR values, including any changes that
>  may have been triggered by the previous instruction, such as CSR writes or floating-point operations
>  that change flags. Therefore, like load and store structural hazards, CSR reads have a 2-cycle latency
>  from issue to use, so the pipeline must stall in the Decode stage when the next instruction source
>  register depends on the CSR read destination register. In Fig. 8.15, CSRRdStallD stalls the Decode
>  stage for a CSR read hazard.**"

**CSR 讀取和 load 一樣有 2 週期延遲**——因為它在 Memory 級才發生。
**所以下一條指令如果要用那個結果，就要 stall。**
（呼應 7.2.2.3 節的 `LoadStallD`。）

**（4）CSR 寫 → flush（8.4.5.4，p.376）**
> "**CSR writes also change architectural state and thus must occur on the rising edge of the clock at the
>  start of the Writeback stage. Writes to CSRs change the way a program behaves, such as turning on
>  virtual memory translation or changing the rounding mode of floating-point instructions. The simplest
>  way to ensure subsequent instructions reflect the new behavior is to flush and reissue the instructions
>  after a CSR write.**"

```
controller 發出 CSRWriteM → 提升 CSRWriteFenceM → hazard 單元 flush Decode、Execute、Memory 級
```

**「寫 CSR 會改變程式的行為方式」——
已經在 pipeline 裡的指令是用舊設定解碼的，所以必須重來。**
（呼應 2.8.1 節：「寫 CSR 會 flush pipeline 以確保一致性」。）

**（5）Fence（8.4.5.5，p.376）**
> "Fence instructions are synchronization events that ensure memory consistency. **fence.i and sfence.vma
>  ensure consistency of the instruction memory and virtual memory translations, respectively.**"

> "**In systems with no cache, all writes go to memory, which is inherently self-consistent. In systems
>  with instruction and data caches, a store may go to the data cache but not immediately to main memory,
>  so data may be inconsistent between the cache and main memory. An instruction read from that address
>  will obtain a stale value. fence.i makes sure that consistent instruction values are read.
>  The simplest way to implement fence.i is to flush the data cache (so all stores are written to main
>  memory) and invalidate the instruction cache.**"

**`fence.i` 的問題和解法：**
- **問題**：store 寫進資料 cache 但還沒到主記憶體，**從那個位址讀指令會拿到舊值**
- **解法**：**flush 資料 cache + invalidate 指令 cache**

（呼應 2.5、2.7 節：`fence.i` 是「寫程式進記憶體再跳過去執行」時需要的。）

**`sfence.vma` 同理：寫完頁表後 TLB 可能有舊項目 → 最簡單的做法是讓整個 TLB 失效。**

**「和 CSR 寫一樣，fence 也 assert `CSRWriteFenceM` 來 flush 並重抓後續指令。」**

**（p.376 邊欄：`fence.i` 定義在 Zifencei 擴充；
**在有 cache 的系統需要它來維持一致性，但在無 cache 系統可以當 NOP。**
`sfence.vma` 是特權規格的一部分，虛擬記憶體啟用時才支援。**）

**（6）`wfi`（8.4.5.6，p.376）**
> "**WFIStallM in the hazard unit (Fig. 8.15) is 1 while the wfi is active and no interrupts are pending.
>  In Fig. 8.15, WFIStallM drives StallM to keep wfi in the Memory stage until an interrupt is pending or
>  a timeout occurs. When an interrupt becomes pending, WFIStallM deasserts and WFIInterruptedM asserts,
>  to keep the wfi instruction from flushing as it advances to the Writeback stage and commits.
>  InterruptM and TrapM are asserted, flushing the instructions after wfi and jumping to the trap
>  handler. WFIStallM would preferably gate clocks to the unused parts of the core, but Wally does not
>  yet implement clock gating.**"

**`wfi` 的巧妙之處：它用 stall 實現「等待」，
而 `WFIInterruptedM` 確保它自己能順利退休**（不被自己造成的 trap flush 掉）。

**`wfi` 逾時邏輯（Fig. 8.16，p.377）：**
```
wfiM & (U_MODE | (S_MODE & status.TW)) & WFICount[msb] → WFITimeoutM → IllegalInstructionFaultM
```
**`WFICounter` 從 0 開始計數，最高位元設起時就逾時。**
**`WFI_TIMEOUT_BIT` 預設 16，所以 2^16 個週期後逾時。**

**（p.377 邊欄：「在不支援 S-mode 的系統，逾時只在 U-mode 且 `status.TW` 設起時發生。」**）

### PC 邏輯的擴充（Fig. 8.17）

> "Fig. 8.17 enhances the PC logic to support privileged operations: traps, mret/sret, and refetching
>  instructions after a pipeline flush."
> — p.377

中文解釋：**Fig. 8.17（p.378）的三層多工器，由內而外：**

**（1）`PCSrcE` mux（原本就有）**
```
PC1NextF = PCSrcE ? IEUAdrE : PCPlus4F
```
**注意輸出改名為 `PC1NextF`**（原本直接叫 `PCNextF`）。

**（2）`CSRWriteFenceM` mux（新增）**
```
PC2NextF = CSRWriteFenceM ? PCE : PC1NextF
```
> "**If fences or CSRs are supported, the CSRWriteFenceM signal flushes the pipeline... and reloads the
>  program counter with the instruction after the CSR write or fence. The flush is triggered in the
>  Memory stage, so the next instruction is in the Execute stage and its address is in PCE.
>  Thus, the PCWriteFenceM multiplexer chooses PC2NextF from either PC1NextF or PCE.**"

**關鍵：flush 在 Memory 級觸發，所以「下一條要重抓的指令」的位址在 `PCE`。**

**（3）Trap / return mux（新增，3 選 1）**
```
0 → PC2NextF（正常）
1 → EPCM（mret/sret：從 mepc 或 sepc）
2 → TrapVectorM（trap：從 mtvec 或 stvec）
```

**`TrapVectorM` 的產生（Fig. 8.17 左下）：**
```
TVecM = SelMTVEC ? MTVEC : STVEC
TrapVectorM = VectoredM ? {TVecM[XLEN-1:6], CauseM, 00} : TVecM
```
**向量中斷時，把 `CauseM` 串接到 `TVecM` 的高位元後面——不是加法，是串接。**
（呼應 8.2.5.5 節：對齊到 64 的倍數讓加法退化成串接。）

**（4）Reset mux（最外層）**
```
PCNextF = reset ? RESET_VECTOR : （上面的結果）
```

**最後一個細節（p.378）：**
> "**The least significant bit (lsb) of the PC is always zero, so any nonzero lsb of the trap vector or
>  EPC is discarded to form PCNextF.**"

**圖上寫成 `UnalignedPCNextF[XLEN-1:1]` 串接 `1'b0`——強制最低位元為 0。**

### Endian Swapper

> "**Wally processes all data internally as little-endian. When the RISC-V data endianness modes are
>  supported in configuration (BIGENDIAN_SUPPORTED = 1), Wally adds endian swappers to reverse big-endian
>  data being loaded and stored if the mstatus register enables big-endian.**"
> — p.378

中文解釋：**設計策略很清楚：內部一律 little-endian，只在 LSU 的邊界做轉換。**

**Example 8.1（p.378–379）的對照非常有教育意義：**
```asm
li  x1, 0xFEDCBA98_76543210
sd  x1, 1000(x0)
ld  x2, 1000(x0)
lwu x3, 1000(x0)
lwu x4, 1004(x0)
lbu x5, 1001(x0)
```

**記憶體內容（Fig. 8.18，p.379）：**

| 位址 | Little-Endian | Big-Endian |
| --- | --- | --- |
| 1007 | FE | 10 |
| 1006 | DC | 32 |
| 1005 | BA | 54 |
| 1004 | 98 | 76 |
| 1003 | 76 | 98 |
| 1002 | 54 | BA |
| 1001 | 32 | DC |
| **1000** | **10** | **FE** |

**暫存器內容（Table 8.12，p.379）：**

| Load | Reg | Little Endian | Big Endian |
| --- | --- | --- | --- |
| `ld x2, 1000(x0)` | x2 | **FEDCBA98_76543210** | **FEDCBA98_76543210** |
| `lwu x3, 1000(x0)` | x3 | 00000000_**76543210** | 00000000_**FEDCBA98** |
| `lwu x4, 1004(x0)` | x4 | 00000000_**FEDCBA98** | 00000000_**76543210** |
| `lbu x5, 1001(x0)` | x5 | 00000000_000000**32** | 00000000_000000**DC** |

**書上的觀察（p.379 邊欄）非常精闢：**
> "**Observe that a full-length write followed by a read in the same endianness returns the original
>  value. However, subword loads return different portions of the full word depending on the endianness.
>  A program can use this behavior to deduce the endianness of the machine.**"

**「全長度寫入後以同樣端序讀出，得到原值——
但 subword load 會依端序拿到不同的部分。
程式可以利用這個行為判斷機器的端序。」**

**這是一個經典的可攜性測試技巧。**

**實作（Fig. 8.19，p.380）：**
> "**It is similar to the LSU from Fig. 7.9 except that it swaps endianness before writing to memory and
>  after reading from memory. Big-endian subword reads must also swap the order of the subword by
>  inverting the address. The BigEndianM signal is asserted when the mstatus.MBE, SBE, or UBE bit is set
>  corresponding to the current privilege mode. The endianswap module exchanges byte 0 with byte 7, 1
>  with 6, and so forth. RV32 is the same except that endianswap only exchanges byte 0 with byte 3 and
>  byte 1 with byte 2 in a word.**"

**兩件事要做：**
1. **`endianswap` 模組交換 byte 順序**（RV64：0↔7、1↔6…；RV32：0↔3、1↔2）
2. **big-endian 的 subword 讀取還要反相位址**（因為 byte 在字內的位置也反了）

**代價（p.379）：**
> "**The endian logic adds a multiplexer delay to the Memory stage read and write paths, which might
>  impact cycle time.**"

**在 Memory 級的關鍵路徑上多一個多工器延遲**——這是支援 big-endian 的代價。

## 所以呢

**這節最有價值的是 8.4.5——它把「特權功能如何打亂 pipeline」講清楚了。**

**五種新危障整理成一張表（這是本節最該帶走的東西）：**

| 事件 | 處理 | 為什麼 |
| --- | --- | --- |
| **Trap** | **flush Memory 級及更早的全部** | precise trap 要求 |
| **`mret`/`sret`** | **flush 除 Writeback 外的全部** | 它們在 Writeback 級改 PC 和特權模式 |
| **CSR 讀** | **stall Decode 級**（2 週期延遲） | CSR 在 Memory 級才讀 |
| **CSR 寫 / fence** | **flush Decode/Execute/Memory 並重抓** | 已在 pipeline 裡的指令是用舊設定解碼的 |
| **`wfi`** | **stall Memory 級直到中斷 pending 或逾時** | 等待 |

另外三個值得記住的設計原則：

1. **「所有 trap 在同一個地方（Memory 級）、所有狀態在同一個時刻（Writeback 級開始）更新」**
   ——這是實現 precise trap 最簡單的方法。

2. **`InstrValidM` 是 precise interrupt 的關鍵**：
   Memory 級沒有有效指令時不能接受中斷，因為沒有 PC 可以存。

3. **向量中斷的目標位址用「串接」而非「加法」**——
   靠 `mtvec` 對齊到 64 的倍數換來。
