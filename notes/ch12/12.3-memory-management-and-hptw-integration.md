# 12.3 Memory Management and HPTW Integration

> 原書 p.526–532（Chapter 12: Load/Store Unit）
> 涵蓋 12.3.1 PMA Checker、12.3.2 PMP Checker、12.3.3 TLB and Cache Integration、
> 12.3.4 HPTW Integration

## 這節在講什麼

**整合的第二步：把 MMU 的三個元件和 HPTW 裝進 LSU。**

四個子節，依「加入難度」排序：
1. **PMA**（12.3.1）：**把「可不可以 cache」變成一個路徑選擇**——這是本節最實質的改動
2. **PMP**（12.3.2）：**不需要任何 LSU 修改**（三行就講完）
3. **TLB**（12.3.3）：**和 cache 平行存取**
4. **HPTW**（12.3.4）：**為什麼它一定要放在 LSU 裡**

**最該記住的是 Table 12.2（七種記憶體操作）
和 12.3.4 那三個「HPTW 必須走 D$」的理由。**

## 關鍵點

### PMA 帶來的核心改動：cached vs uncached 兩條路

> "**The PMA checker provides address decoding according to the memory map to select which memory device is
>  accessed for an address range and what attributes that device has, as described in Section 11.2.2.1.
>  Whereas main memory is cacheable, the peripherals are accessed directly over the bus.**"
> — p.527

中文解釋：**PMA 的加入把 LSU 從「只有一條路」變成「兩條路」：**

| 存取類型 | 走哪 |
| --- | --- |
| **Cacheable**（主記憶體） | **D$** |
| **Uncacheable**（周邊） | **直接走匯流排** |

**兩個新訊號（p.527）：**
```
CacheableOrFlushM = CacheableM | FlushDCacheM
```
> "**Cache flushes take priority and disregard the PMA by ORing FlushDCacheM with CacheableM to produce
>  CacheableOrFlushM.**"

**「cache flush 優先且不管 PMA」**——因為 flush 是對 cache 的操作，本來就要走 cache 路徑。

**Uncached 存取的路徑（p.527）：**
> "**Uncached accesses use AHB rather than the cache by driving LocalHADDR = IEUAdrM and
>  PreHWDATA = LSUWriteDataM (for stores) or ReadDataWordMuxM = FetchBuffer (for loads).**"

**控制訊號的分流（p.527–529）：**
> "**The read and write control signals should go to either the cache or bus depending on whether the access is
>  cacheable. Fig. 12.11 shows a demultiplexer added to the LSU to drive MemRWM from the IEU to either CacheRW or
>  BusRW.**"

**Fig. 12.11（p.528）的控制路徑：`MemRWM` 經一個 demux，
依 `CacheableM` 送到 `CacheRW`（→ `cachefsm`）或 `BusRW`（→ `buscachefsm`）。**

### Table 12.2：七種記憶體操作（本節最實用的表）

> "**With the PMA integration, the LSU supports a fully featured set of seven types of memory operations,
>  summarized in Table 12.2.**"
> — p.529

中文解釋：**Table 12.2（p.529）。這張表把 LSU 所有可能的行為一次列完：**

| Operation | Cacheable | Flush | Access Type | LSUHADDR | ReadDataWordMuxM | PreHWDATA | CacheWriteData |
| --- | --- | --- | --- | --- | --- | --- | --- |
| **Uncached load** | 0 | 0 | **`BusRW = 10`** | `IEUAdrM` | **`FetchBuffer[AHBW-1:0]`** | — | — |
| **Uncached store** | 0 | 0 | **`BusRW = 01`** | `IEUAdrM` | — | **`LSUWriteDataM`** | — |
| **Cached load hit** | 1 | 0 | **`CacheRW = 10`** | — | **`ReadDataWord`** | — | — |
| **Cached store hit** | 1 | 0 | **`CacheRW = 01`** | — | — | — | **`LSUWriteDataM`** |
| **Cache fetch** | 1 | 0 | **`CacheBusRW = 10`** | **`CacheBusAdr + BeatCount`** | — | — | **`FetchBuffer`** |
| **Cache writeback** | 1 | 0 | **`CacheBusRW = 01`** | `CacheBusAdr + BeatCount` | — | **`ReadDataWord`** | — |
| **Cache flush** | N/A | **1** | `CacheBusRW = 01` | `CacheBusAdr + BeatCount` | — | **`ReadDataWordM`** | — |

**讀表的三個重點：**
1. **三組 RW 訊號**：`BusRW`（uncached）、`CacheRW`（cache 命中）、`CacheBusRW`（cache 和匯流排之間）
2. **位址來源**：uncached 用 `IEUAdrM`，cache 的匯流排操作用 `CacheBusAdr + BeatCount`
3. **`ReadDataWordMuxM` 的兩個來源**：cache 命中時是 `ReadDataWord`，
   **uncached load 時是 `FetchBuffer` 的低位元**

### PMP：什麼都不用改

> "**The LSU's MMU contains an optional PMP checker described in Section 11.4.1.2. No LSU modifications are
>  required. Together, the PMA and PMP checkers generate load- and store-access faults and misaligned faults,
>  which are passed onto the privileged unit.**"
> — p.529

中文解釋：**整節只有三句話。**

**為什麼 PMP 不用改而 PMA 要改？**
- **PMA 決定「走哪條路」**（cache 還是匯流排）→ 影響資料通路
- **PMP 只決定「准不准」**（產生 fault）→ 不影響資料通路

**這個對比很有啟發：「產生 fault」比「改變路徑」容易整合得多。**

### TLB 與 Cache 的平行存取

> "**As mentioned in Section 11.1.1.7, accessing a cache with a virtual address leads to synonym problems when
>  multiple virtual addresses refer to the same physical address. These problems are avoided by indexing the cache
>  with the least significant bits, which are the same for virtual and physical addresses. After translation, the
>  tags (upper bits) are then checked against the physical tag. Therefore, the cache and TLB accesses occur in
>  parallel, and the tag output of the cache is compared against the physical address output of the TLB.
>  The size of a cache way is limited to the 4-KiB page size so that the cache set bits are in the physical page
>  offset, which are available immediately without waiting for address translation.**"
> — p.530

中文解釋：**這段是第 10、11、12 章的交會點，再確認一次完整的邏輯鏈：**
```
1. 用虛擬位址索引 cache 會有 synonym 問題
2. 但位址的低位元（page offset）在虛擬和實體位址中相同
3. 把 cache way 限制在 4 KiB → set 位元全在 page offset 裡
4. → cache 和 TLB 可以平行存取
5. → 轉譯完成後，用實體位址的上位元和 cache 的 tag 比對
```

**兩種情況的統一處理（p.530）：**
> "**When translation is off, the physical address PAdrM comes directly from IEUAdrM. When translation is on, the
>  TLB looks up PAdrM concurrently with the cache read. In either case, the cache hit logic compares the tags to
>  PAdrM.**"

**不管有沒有虛擬記憶體，cache 的命中邏輯都是「比對 `PAdrM`」——很乾淨的設計。**

**一個重要的邊界定義（p.531）：**
> "**Like the cache, the `ahbcacheinterface` uses the physical address PAdrM in place of IEUAdrM for uncached memory
>  operations. **The cache and TLB are the boundary between virtual and physical addressing, which ensures that the
>  bus always uses physical addresses.**"**

**「cache 和 TLB 是虛擬定址與實體定址的邊界」——
這一句把整個位址流的分界說清楚了。匯流排永遠只看到實體位址。**

### HPTW 為什麼一定要在 LSU 裡（三個理由）

> "**The HPTW is located in the LSU and routes its memory reads through the LSU's D$ because this:
>  - Ensures coherency (recently changed PTEs may be in the D$ but not yet in main memory).
>  - Enables updating (writing) a PTE's accessed and dirty bits because the D$, unlike the I$, is writeable.
>  - Improves performance for page table walks because PTEs may be in the D$ instead of main memory.**"
> — p.531

中文解釋：**三個理由，各自的份量不同：**

| 理由 | 為什麼重要 |
| --- | --- |
| **一致性** | **OS 剛改的 PTE 可能還在 D$ 裡沒寫回主記憶體**——不走 D$ 就會讀到舊的 |
| **可寫入** | **D$ 可寫而 I$ 不可寫**——更新 A/D 位元需要寫入（呼應 11.4.2.2 節的 Svadu） |
| **效能** | PTE 可能已經在 D$ 裡 |

**第一個理由是正確性問題，不只是效能問題**——這是最關鍵的。

**TLB miss 的成本（p.531）：**
> "**On a TLB miss, RISC-V may trigger a page-fault exception to ask the operating system to refill the TLB, but
>  this can add hundreds of cycles to a TLB miss. Most application processors, including Wally, provide a HPTW to
>  refill the TLB.**"

**「軟體處理 TLB miss 要多幾百個週期」——這就是硬體 HPTW 存在的理由。**

**一個 HPTW 服務兩個 TLB（p.531）：**
> "**TLB fill requests can come from either the ITLB (in the IFU) or DTLB (in the LSU), but the requests are all
>  serviced by the single HPTW located in the LSU.**"

### `IHAdrM`：一個名字揭示的設計

> "**During a page table walk, the HPTW outputs physical addresses as IHAdrM so the PMA and PMP checker can verify
>  the access is valid. The HPTW's IHAdrM mux (which is internal to the Datapath + FSM logic) chooses IEUAdrM
>  (for regular loads and stores) or HPTWAdr (for a TLB miss and subsequent page table walk).**"
> — p.531

中文解釋：**（p.531 邊欄的命名說明很有意思：**
「**`IHAdrM` 是 `IEUAdrM` 和 `HPTWAdr` 兩個名字的串接**」**
——I 來自 IEU、H 來自 HPTW，這個 mux 的名字直接說明了它的兩個輸入。）

**位址的組成（p.531）：**
> "**Because the HPTW handles both ITLB and DTLB misses, the HPTW cobbles together the page table address (HPTWAdr)
>  from either PCF or IEUAdrM (which are both virtual addresses), satp, and ReadDataM, which is the PTE read during
>  the page table walk.**"

**四個來源：`PCF`（指令 TLB miss）或 `IEUAdrM`（資料 TLB miss）提供 VPN、
`satp` 提供第一層的 PPN、`ReadDataM`（前一層的 PTE）提供後續層的 PPN。**

**完整流程（p.531–532）：**
> "**The MMU drives IHAdrM onto PAdrM, and the LSU makes an untranslated PTE read from this physical address.
>  It outputs the PTE via ReadDataM to the HPTW. If the PTE is a leaf node, the HPTW FSM writes the entry to the
>  TLB. Otherwise, it generates the next address of the page table walk and repeats the process.**"

**「untranslated PTE read」——頁表位址本身就是實體位址，不需要再轉譯。**
（呼應 11.4.1.3.5 節：走訪期間停用轉譯。）

### `ebufsmarb` 的完整版

中文解釋：**Fig. 12.9（p.527）是加上 burst 支援後的完整 `ebufsmarb`。
相對於 Fig. 9.26 的改動：**

**狀態機部分：**
```
IDLE ──(Both = LSUReq & IFUReq)──→ ARBITRATE
     ／IFUSave = 1, IFUSelect = 0, LSUSelect = 1, BeatCntEn = 1

ARBITRATE ──(HREADY & ~Both & FinalBeatD)──→ IDLE
          ／BeatCntRst = 1, IFUSelect = IFUReq, LSUSelect = LSUReq

ARBITRATE 自環（HREADY）／BeatCntEn = 1, IFUSelect = 0, LSUSelect = 1
                        輸出：IFURestore = 1, IFUDisable = 1, InArbitrate = 1
```

**新增的硬體（Fig. 12.9 下半部）：**
```
LUT: HBURST → 拍數（0:0000, 3:0011, 5:0111, 7:1111, else:0000）
BeatCount 計數器 + 比較器 → FinalBeat → （延遲一拍）FinalBeatD
IFUReqD（延遲的 IFUReq）
LSUDisable = InArbitrate & ~FinalBeatD & IFUReqD（大致）
```

**`LSUDisable` 就是 12.2.3 節那個 bug 的修正**——
**當 IFU 的 burst 還在進行中（`InArbitrate` 且還沒 `FinalBeatD`），
LSU 的新請求要被延遲。**

## 名詞表

| 名詞 | 意思 |
| --- | --- |
| **`CacheableOrFlushM`** | `CacheableM \| FlushDCacheM`；**cache flush 優先且不管 PMA** |
| **`BusRW` / `CacheRW` / `CacheBusRW`** | uncached 存取 / cache 命中 / cache 與匯流排之間 |
| `LocalHADDR` / `PreHWDATA` | 送往匯流排的位址 / 資料（uncached 時來自 `IEUAdrM` / `LSUWriteDataM`） |
| **`PAdrM`** | 實體位址。**轉譯關閉時 = `IEUAdrM`，開啟時來自 TLB** |
| **cache 與 TLB 是邊界** | **虛擬定址與實體定址的分界；匯流排永遠只看到實體位址** |
| **`IHAdrM`** | `IEUAdrM` 和 `HPTWAdr` 的名字串接；HPTW 的位址多工器輸出 |
| `HPTWAdr` | 由 `PCF` 或 `IEUAdrM`（VPN）、`satp`、`ReadDataM`（PTE）組成 |
| **`LSUDisable`** | **IFU burst 進行中時延遲 LSU 請求**（12.2.3 節那個 bug 的修正） |
| `InArbitrate` / `FinalBeatD` | 仲裁中 / burst 最後一拍（延遲版） |

## 所以呢

**這節把 MMU 和 HPTW 裝進 LSU。四件最該帶走的事：**

1. **PMA 的加入把 LSU 變成「兩條路」**：
   **cacheable 走 D$、uncacheable 直接走匯流排。**
   **Table 12.2 的七種操作就是這兩條路的所有組合。**

2. **PMP 不需要任何 LSU 修改**——
   因為它只產生 fault，不改變資料路徑。
   **「產生 fault」比「改變路徑」容易整合得多。**

3. **「cache 和 TLB 是虛擬定址與實體定址的邊界」**——
   匯流排永遠只看到實體位址。
   而 cache way ≤ 4 KiB 讓 cache 和 TLB 能平行存取。

4. **HPTW 必須走 D$ 的三個理由，第一個是正確性問題**：
   **OS 剛改的 PTE 可能還在 D$ 裡沒寫回主記憶體。**
   另兩個是「D$ 可寫（更新 A/D 位元）」和「效能」。
