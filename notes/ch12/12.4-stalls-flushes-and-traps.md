# 12.4 Stalls, Flushes, and Traps

> 原書 p.532–534（Chapter 12: Load/Store Unit）
> 涵蓋 12.4.1 LSU Stall Generation、12.4.2 LSU Trap Generation、
> 12.4.3 Disabling Interrupts、12.4.4 LSU Response to Stalls and Flushes

## 這節在講什麼

**整合後的 LSU 和 hazard 單元、特權單元怎麼互動。**

四個子節對應四個方向：
1. **LSU → hazard**（12.4.1）：**LSU 什麼時候 stall pipeline**
2. **LSU → privileged**（12.4.2）：**什麼時候產生 trap**
3. **LSU → privileged**（12.4.3）：**什麼時候延後中斷**
4. **hazard → LSU**（12.4.4）：**LSU 收到 stall/flush 時怎麼反應**

**最該記住的是那個貫穿全章的原則：
「匯流排交易一旦開始就必須完成」，以及 `GatedStallW` 這個技巧。**

## 關鍵點

### 核心原則

> "**The LSU stalls the pipeline during a bus access or hardware page table walk. It can generate traps due to
>  access, misaligned, or page faults. Bus transactions take multiple cycles and should be atomic (i.e., complete
>  once they start), so the LSU disables interrupts during bus transactions, including hardware page table walks.
>  The LSU receives writeback-stage stall and flush signals, but the cache fetch/writeback and HPTW continue their
>  operations even when the rest of the processor is stalled for the cache or TLB miss.**"
> — p.532

中文解釋：**四句話概括整節。最後一句是關鍵：**
**「即使處理器其餘部分因為 cache 或 TLB miss 而 stall，
cache 的抓取/寫回和 HPTW 仍然繼續運作。」**

**這是必要的——否則就死鎖了（stall 等 cache，cache 等 unstall）。**

### LSU 的三種 stall 來源

> "**The LSU asserts LSUStallM during multicycle cache operations (including cache line fetch, writeback, and
>  flush), during bus accesses, and when the HPTW is active. The hazard unit stalls all pipeline stages
>  (StallF, StallD, StallE, StallM, StallW) while LSUStallM is asserted. Specifically, LSUStallM asserts during a
>  D$, HPTW, or bus stall, indicated by:
>  - **DCacheStallM**: asserted by the `cachefsm` during a cache miss or flush
>  - **HPTWStall**: asserted when the HPTW is processing a TLB miss
>  - **BusStall**: asserted by `buscachefsm` or `busfsm` when the bus is in use**"
> — p.532–533

中文解釋：**三個來源，OR 起來就是 `LSUStallM`：**

| 訊號 | 來源 | 何時 |
| --- | --- | --- |
| **`DCacheStallM`** | `cachefsm` | **cache miss 或 flush** |
| **`HPTWStall`** | HPTW | **處理 TLB miss** |
| **`BusStall`** | `buscachefsm` 或 `busfsm` | **匯流排使用中** |

**最後一個週期的處理（p.533）：**
> "**On the last cycle of a memory operation, the respective stalls are lowered, which indicates that ReadDataM is
>  valid or that the store has committed to memory.**"

**stall 降下 = 「資料有效」或「store 已提交」的訊號。**

**另外兩個 stall（p.533）：**
> "**The hazard unit also stalls the Decode stage for data dependencies and structural hazards. The forwarding logic
>  in the controller raises LoadStallD when a load result is used by the next instruction and raises StoreStallD
>  when a load follows a store.**"

（呼應 7.2.2.3 和 10.4.2.3 節。）

### Trap 的產生時機

> "**The TLB, PMA, and PMP generate page, access, and misaligned faults by asserting TrapM at the beginning of a
>  memory access, before a cache miss could occur. Uncached memory operations are flushed if the access would
>  generate a fault.**"
> — p.533

中文解釋：**「在記憶體存取的開頭，在 cache miss 可能發生之前」——
這個時機很重要。**

**理由：如果先 cache miss 才發現要 fault，就已經浪費了幾十個週期，
而且 cache 的狀態已經改了。**
（呼應 11.4.1 節：PMP 檢查在關鍵路徑上，就是為了趕上這個時機。）

### 延後中斷的三個條件

> "**The LSU raises CommittedM to disable interrupts during a multicycle memory operation, as indicated by any of
>  the following signals:
>  - **BusCommittedM**: a memory operation is in flight on the bus
>  - **DcacheCommittedM**: the cache has partially updated its state
>  - **SelHPTW**: HPTW is walking the page table**"
> — p.533

中文解釋：**三個「不能被中斷」的情況：**

| 訊號 | 為什麼不能中斷 |
| --- | --- |
| **`BusCommittedM`** | **匯流排交易進行中**（放棄會讓裝置狀態不一致，呼應 9.5.5 節） |
| **`DcacheCommittedM`** | **cache 已經部分更新了狀態**（呼應 10.4.7 節） |
| **`SelHPTW`** | **HPTW 正在走訪頁表**（呼應 11.4.2.2 節：保證 PTE 寫入的原子性） |

**和 `LSUStall` 的關鍵差異（p.533）：**
> "**When CommittedM is asserted, the privileged unit suppresses pending interrupts.... Unlike LSUStall, CommittedM
>  remains high during the last cycle of a memory operation.**"

**`LSUStall` 在最後一個週期降下，但 `CommittedM` 保持高**——
**因為最後那個週期還在寫入狀態，仍然不能被中斷。**

### `GatedStallW`：讓 LSU 在 pipeline stall 時繼續跑

> "**The LSU's response to a stall depends on the current state of the D$, the bus, and the HPTW. Stalls are first
>  gated by the HPTW with GatedStallW = StallW & ~SelHPTW. This allows the HPTW to issue loads and stores through
>  the D$ while the rest of the pipeline is stalled. GatedStallW is renamed Stall in the cache. The `cachefsm` and
>  `buscachefsm` only check Stall at the end of a multicycle memory operation, which allows the cache or bus to
>  continue with the current operation while the pipeline is stalled.**"
> — p.533

中文解釋：**兩層 gating，這是本節最重要的機制：**

**（1）HPTW 走訪期間，LSU 不 stall：**
```
GatedStallW = StallW & ~SelHPTW
```
（呼應 11.4.2.1 節。）

**（2）cache 和匯流排只在「多週期操作結束時」才檢查 Stall：**
**這樣正在進行的操作可以繼續完成。**

### Stall 時各 FSM 停在哪

> "**On the last cycle of a memory operation, if Stall is high, the `cachefsm` remains in the final, AddressSetup,
>  state. This prevents the cache from executing the same memory operation over and over. Similarly, when Stall is
>  asserted, the `buscachefsm` waits in its last state (Mem3, see Fig. 12.5) for uncached operations. However,
>  `buscachefsm` does return to the Adr state after a cache line fetch or writeback so that the bus no longer
>  asserts BusStall. This lowers LSUStallM, which allows the hazard unit to unstall the pipeline.**"
> — p.534

中文解釋：**三種停留行為，各有理由：**

| FSM | 停在哪 | 為什麼 |
| --- | --- | --- |
| **`cachefsm`** | **AddressSetup 狀態** | **防止同一個記憶體操作被重複執行** |
| **`buscachefsm`（uncached）** | **Mem3 狀態** | 同上 |
| **`buscachefsm`（cache line fetch/writeback）** | **回到 Adr 狀態** | **讓 `BusStall` 降下 → `LSUStallM` 降下 → pipeline 能繼續** |

**第三個是例外，理由很關鍵：cache line 操作完成後，
匯流排就不該再 stall pipeline 了（cache 已經有資料了）。**

（呼應 9.5.5 節的 Mem3 自環和 10.4.3 節的 AddressSetup。）

### Memory 級被 flush 的三種情況

> "**The Memory stage may be flushed in three cases: on the first cycle of a cache miss, on an uncached bus access
>  due to a memory fault, or when another exception or interrupt flushes the pipeline.**"
> — p.534

中文解釋：**三種情況：**
1. **cache miss 的第一個週期**
2. **uncached 匯流排存取遇到 memory fault**
3. **其他例外或中斷 flush pipeline**

### 為什麼 in-flight 的 cache 操作不會 fault（很巧妙的論證）

> "**However, when a memory operation is in flight, Wally will not generate faults until that memory operation
>  completes. In-flight cache fetch and writeback addresses were already checked by the PMA and PMP checkers, so
>  they will not generate a fault when they are in flight. Specifically, cache fetches access PAdrM with the byte
>  offset bits zeroed and cache writeback addresses are always the Victim Way's tag + the set bits from PAdrM, with
>  zeros for the byte offset. These addresses were checked by the PMA and PMP when the cache line was first
>  fetched.**"
> — p.534

中文解釋：**這個論證很漂亮，值得拆解：**

**問題：cache fetch 和 writeback 用的位址（`CacheBusAdr`）
和原本被檢查的位址（`PAdrM`）不完全相同，那它們需要重新檢查嗎？**

**答案：不需要。理由是「它們在同一個 4 KiB page 內」：**

| 操作 | 位址組成 | 為什麼安全 |
| --- | --- | --- |
| **Cache fetch** | **`PAdrM` 但 byte offset 清零** | **同一條 cache line，PMA/PMP 已檢查過** |
| **Cache writeback** | **Victim Way 的 tag + `PAdrM` 的 set 位元 + 零** | **這條 line 第一次被抓進來時就檢查過了** |

**「這些位址在 cache line 第一次被抓取時就被 PMA 和 PMP 檢查過了」——
所以不需要重新檢查，也就不會在 in-flight 時產生 fault。**

**這個論證的價值：它證明了「in-flight 不 fault」這個簡化是安全的，
而不只是方便。**

## 名詞表

| 名詞 | 意思 |
| --- | --- |
| **`LSUStallM`** | `DCacheStallM \| HPTWStall \| BusStall`；stall 所有 pipeline 級 |
| `DCacheStallM` / `HPTWStall` / `BusStall` | cache miss 或 flush / 處理 TLB miss / 匯流排使用中 |
| `LoadStallD` / `StoreStallD` | load 後接使用 / store 後接 load 的結構危障 |
| **`CommittedM`** | `BusCommittedM \| DcacheCommittedM \| SelHPTW`；**延後中斷** |
| **`GatedStallW = StallW & ~SelHPTW`** | **讓 HPTW 能在 pipeline stall 時透過 D$ 發出 load/store** |
| AddressSetup / Mem3 | stall 時 `cachefsm` / `buscachefsm` 停留的狀態，**防止重複執行同一操作** |

## 所以呢

**這節講 LSU 和 hazard、privileged 單元的互動。四件最該帶走的事：**

1. **三種 stall 來源**：`DCacheStallM`、`HPTWStall`、`BusStall`。
   **stall 降下 = 「資料有效」或「store 已提交」。**

2. **`CommittedM` 和 `LSUStall` 的關鍵差異**：
   **`LSUStall` 在最後一個週期降下，但 `CommittedM` 保持高**——
   因為最後那個週期還在寫狀態。

3. **`GatedStallW = StallW & ~SelHPTW` 是核心技巧**：
   **整條 pipeline stall，但 LSU 繼續跑以服務 HPTW。**
   而 cache 和匯流排的 FSM **只在多週期操作結束時才檢查 Stall**，
   所以進行中的操作能完成。

4. **「in-flight 的 cache 操作不會 fault」有嚴謹的理由**：
   **fetch 和 writeback 的位址都在同一條 cache line 內，
   而那條 line 第一次被抓取時就已經通過 PMA 和 PMP 檢查了。**
