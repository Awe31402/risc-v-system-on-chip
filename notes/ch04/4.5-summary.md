## 關鍵點

### HDL 的定位

> "Hardware description languages (HDLs) are used to specify the design of an SoC in a form
>  that is both human and machine readable. The HDL code is simulated for logic verification
>  and synthesized onto a chip or FPGA. Wally is written in SystemVerilog, the most widely
>  used HDL."
> — p.191

中文解釋：**"both human and machine readable"（人和機器都讀得懂）是 HDL 的本質**——
所以它既要能被合成工具處理，也要能被同事看懂。這就是為什麼風格規範（4.3 節）重要。

**一份 HDL 有兩個去處：模擬（驗證，第 5 章）和合成（上晶片或 FPGA，第 6、23 章）。**

### 方法論再強調一次

> "SystemVerilog is a complex language, but **only a tiny subset is used to describe
>  synthesizable hardware.** A good designer visualizes the desired type of logic, then
>  writes SystemVerilog idioms that imply such logic. The designer should first determine
>  whether a component is combinational or sequential."
> — p.191

中文解釋：**"only a tiny subset"（只用一小部分）** 是本章最實際的訊息——
SystemVerilog 很龐大，但可合成的部分很小。**不需要學整個語言。**

**流程再重複一次：看見想要的邏輯 → 寫出對應的慣用寫法。
第一個要問的問題永遠是：組合還是時序？**

### 組合邏輯的慣用寫法

> "SystemVerilog has several idioms for combinational logic. assign statements define
>  Boolean or arithmetic equations. always_comb blocks can contain case statements or
>  if/else statements. case statements define combinational logic with truth tables.
>  if/else can be helpful for complex control logic. **Synthesis excels at optimizing logic
>  onto gates, so the designer can focus on writing a clear and concise description of what
>  the logic should do and let the tool perform the Boolean optimization.**"
> — p.191

中文解釋：**四種組合邏輯寫法的分工：**

| 寫法 | 適合 |
| --- | --- |
| `assign` | 布林或算術方程式 |
| `always_comb` + `case` | **真值表式的邏輯** |
| `always_comb` + `if/else` | **複雜的控制邏輯** |

**最後那句是重點：合成工具很擅長把邏輯最佳化成閘，
所以設計者的工作是「清楚簡潔地描述該做什麼」，布林最佳化交給工具。**
（呼應 4.1 節「工具會挑加法器架構」、4.2.5.4 節「工具會把優先權鏈轉成樹」。）

### 時序邏輯的慣用寫法

> "Synchronous sequential logic is built from edge-triggered flip-flops and combinational
>  logic. The always_ff @(posedge clk) idiom describes edge-triggered flip-flops. FSMs can
>  be described with a bank of flip-flops to hold the state, and combinational logic blocks
>  to compute the next state and output. The next state logic and output code may be merged
>  into the always_ff block for brevity. **Memories, such as RAMs, ROMs, and register files,
>  are a special case of sequential logic that contain an array of flip-flops or bit cells
>  indexed by an address.**"
> — p.191

中文解釋：**三層結構：**
1. **正反器**：`always_ff @(posedge clk)`
2. **FSM**：狀態暫存器（一排正反器）+ 次態邏輯 + 輸出邏輯（組合）
   （為求簡潔可合併進 `always_ff`——但 4.2.3.2 節警告：**熟練後再這樣寫**）
3. **記憶體**：時序邏輯的特例，**由位址索引的正反器或 bit cell 陣列**

### 階層、參數化與 generate

> "Larger modules are built from smaller modules, taking advantage of hierarchy and reuse.
>  Parameterized modules can adjust bus widths based on the parameter value. Conditional
>  generates, described by an if statement whose condition depends on a configuration
>  parameter, instantiate modules only under certain conditions (e.g., when a feature is
>  supported). Generate loops, described by a for statement, instantiate multiple pieces of
>  hardware. **SystemVerilog also has an array notation that is more succinct when the
>  hardware is identical.**"
> — p.191

中文解釋：**四個可組態工具的分工，這個對照很好用：**

| 工具 | 語法 | 用途 |
| --- | --- | --- |
| 參數化模組 | `#(parameter WIDTH=8)` | 調整匯流排寬度 |
| **條件產生** | `if (參數)` | **某功能支援時才實例化模組** |
| **產生迴圈** | `for (genvar)` | **產生多份硬體** |
| **實例陣列** | `mod m[N-1:0](...)` | **硬體完全相同時，比產生迴圈更簡潔** |

### SystemVerilog 的驗證能力（本章不深入）

> "Compared to Verilog, SystemVerilog has a much larger set of features for writing
>  testbenches to test hardware. These features include reading test vectors from files,
>  checking results against expectations, and reporting discrepancies. Indeed, SystemVerilog
>  has an entire object-oriented feature set for modeling and verification comparable to C++.
>  However, this book focuses on widely used constructs and the basic features needed for
>  testbenches."
> — p.191–192

中文解釋：**SystemVerilog 有一整套物件導向的驗證功能，複雜度可比 C++**——
（業界的 UVM 驗證方法學就建立在這上面。）

**但本書只教 testbench 需要的基本功能。** 這是第 5 章的範圍界定。

### Wally 風格摘要

> "Good style is important for readable and maintainable HDL code. Wally uses coding
>  guidelines similar to many other large SystemVerilog systems. It adopts UpperCamelCase
>  signal names, with single-letter suffixes to indicate the pipeline stage. Except in
>  generic or multiply instantiated modules, the same name is used for a signal throughout
>  the hierarchy of modules. Ports are connected by order for simple modules (flip-flops and
>  muxes), with the .sig notation for more complex modules, or with .sig(name) when a signal
>  must change names where it enters a generic module."
> — p.192

> "**We find that a dense coding style improves readability by letting the developer see more
>  of the code base on a screen.** Wally is heavily configurable, allowing it to scale from a
>  tiny rv32e core to a full-featured rv64gc application processor. **The configurations avoid
>  unnecessary hardware, keeping the size and critical path as tight as possible.**"
> — p.192

中文解釋：**風格規範的四點濃縮**（呼應 4.3 節）：
1. **UpperCamelCase 訊號名 + 單字母 pipeline 級後綴**
2. **同一個訊號在整個階層中用同一個名字**（通用或多次實例化的模組除外）
3. **埠連接：簡單模組按順序、複雜模組用 `.sig`、名稱必須改變時用 `.sig(name)`**
4. **偏好緊湊的編碼風格**——理由很實際：**一個螢幕能看到更多程式碼**

**最後一句點出可組態性的真正目的（p.192）：
「組態避免不必要的硬體，讓面積和關鍵路徑盡可能緊湊。」**
——**可組態性不只是方便，它直接影響 PPA**（呼應 2.8.2 節：
rv32e 是 2.99 GHz，rv64gc 只有 0.8 GHz）。

## 所以呢

**第 4 章的核心方法論只有一句：先看見硬體，再寫出隱含它的慣用寫法。**

四件帶得走的事：
1. **可合成的 SystemVerilog 只是整個語言的一小部分**——不用學整個語言。
2. **組合邏輯：`assign` / `always_comb`+`case`（真值表）/ `always_comb`+`if`（複雜控制）；
   時序邏輯：`always_ff @(posedge clk)` + `<=`。**
3. **合成工具會做布林最佳化和架構選擇**，所以設計者專注於「清楚描述要做什麼」。
4. **Wally 的可組態性直接服務 PPA**——不需要的功能不產生硬體。

下一章（第 5 章）把這些 HDL 拿去驗證：testbench、lint、覆蓋率、形式驗證。
