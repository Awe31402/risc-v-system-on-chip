# 20.3 PLIC

> 原書 p.784.e10–784.e13（Chapter 20: Peripherals）
> 涵蓋 20.3.1 Memory Map、20.3.2 Test Plan、20.3.3 Wally Implementation

## 這節在講什麼

CLINT 處理的是每個核心自己的兩個中斷。PLIC（Platform-Level Interrupt Controller，平台層級中斷控制器）處理的是**所有其他中斷**：UART、GPIO、SD 卡、網路卡……。它要做三件事——收集、排優先權、**路由到正確的 hart 與權限層級**。

PLIC 是這章唯一由 RISC-V 正式規格定義的周邊（其他都是 SiFive 的事實標準）。

## 關鍵點

### PLIC 的三個任務與規模

> "The Platform-Level Interrupt Controller (PLIC) takes interrupts from multiple peripherals, prioritizes them, and routes them to the appropriate hart's M- or S-mode external interrupt pin [PLIC22]. In general, the PLIC standard supports up to 1,024 interrupt sources and 15,872 hart context destinations, although a system normally has only a few of each."
> — p.784.e10

中文解釋：規格訂得很寬（1,024 個來源、15,872 個目的地），實際系統遠少於此。Wally 只有 2 個來源（UART、GPIO）和 2 個 context。

### hart context 是什麼

> "The hart context is a specific privilege mode on a specific hart to which an interrupt could be routed. The PLIC drives one external interrupt pin for each hart context. M-mode has a hart context, and S-mode, when implemented, has a second hart context."
> — p.784.e10

中文解釋：這是 PLIC 最重要的概念。**context = (hart, 權限模式)** 的組合。為什麼要分開？因為同一個中斷在不同情境下該由不同層級處理——例如 UART 中斷可能該交給 OS（S-mode），而某些硬體錯誤該交給 firmware（M-mode）。

邊欄的例子很清楚：「一個 4 核心、2-way 多執行緒的系統有 8 個 hart。每個 hart 有 M-mode 和 S-mode，所以系統有 16 個 hart context。Wally 有 1 個 hart、2 個 context。」

### 每個來源與每個 context 各有什麼

> "The PLIC has an interrupt pending bit and a programmable interrupt priority for each of the interrupt sources. Source 0 does not exist. A priority of 0 means never interrupt. ... The PLIC has a programmable priority threshold and claim/complete register for each context. It also has an interrupt enable bit for each source/context pair, so each context can receive interrupts from specific sources."
> — p.784.e10

中文解釋：整理成一張表比較清楚：

| 東西 | 每個什麼一份 |
| --- | --- |
| interrupt pending 位元 | 每個 source |
| interrupt priority | 每個 source |
| priority threshold | 每個 **context** |
| claim/complete 暫存器 | 每個 **context** |
| interrupt enable 位元 | 每個 **source × context** 組合 |

最後一項是二維的，這就是「路由」的實作方式——哪個 context 想收哪些 source，用一個位元矩陣表示。

注意兩個特例：**source 0 不存在**（所以 0 可以當成「沒有中斷」的回傳值），**priority 0 表示永不中斷**（等於一個額外的關閉開關）。

### 仲裁規則

> "The PLIC identifies the highest priority pending interrupt. If multiple interrupts with the same priority are pending, it selects the lowest source number. The PLIC broadcasts that interrupt to all hart contexts whose interrupts are enabled for that source and whose priority threshold is less than the interrupt priority."
> — p.784.e10–e11

中文解釋：兩層仲裁：
1. **優先權高的贏**；同優先權時**來源編號小的贏**（所以 source ID 本身就是次級優先權）
2. 只送給「有 enable 這個 source」**且**「threshold < 該中斷 priority」的 context

threshold 的用途是讓 context 能臨時只接收高優先權的中斷——例如在處理一個重要中斷時，把 threshold 調高擋掉雜訊。

### claim / complete 握手

> "A hart context claims an interrupt by reading its claim/complete register. The register returns the source number of the highest priority pending interrupt or 0 if no interrupt is pending. Reading the register also clears the pending bit within the PLIC. The hart context should respond to the claimed interrupt and cause the peripheral to stop issuing the interrupt. ... Then the hart context writes the interrupt source number back to the claim/complete register to indicate that the interrupt has been processed and that the PLIC can raise the pending bit again the next time that interrupt source is active."
> — p.784.e11

中文解釋：**同一個暫存器，讀是 claim、寫是 complete**，這是一個巧妙的設計。完整流程有三步，缺一不可：

1. **claim**（讀）：拿到來源編號，PLIC 清掉自己的 pending 位元
2. **處理**：**去周邊那邊把中斷源頭關掉**——例如 GPIO 的話要寫 1 清 `rise_ip`（呼應 20.1 的 W1C）。如果不做這步，周邊會一直拉著中斷線
3. **complete**（寫回同一個編號）：告訴 PLIC「處理完了，下次這個來源再有事可以再通知我」

第 2 步是初學者最常漏的——**PLIC 的 pending 清掉了不代表周邊不再發中斷**。中斷是 level-sensitive 的，源頭不關就會立刻再次 pending。

### 記憶體映射

> "Table 20.3 lists the memory-mapped PLIC registers and their address offsets, assuming 54 sources and 2 contexts. All PLIC registers are 32 bits wide."
> — p.784.e11

中文解釋：Table 20.3 的配置方式值得注意——**用位址空間換取簡單的解碼邏輯**：
- `0x000004`–`0x0000DB`：每個 source 一個 priority 暫存器（source i 在 offset `i*4`）
- `0x001000`、`0x001004`：pending 位元（一個 32 位元字管 32 個 source）
- `0x002000` + context × 0x80：每個 context 的 enable 位元
- `0x200000` + context × 0x1000：每個 context 的 threshold 和 claim/complete

context 之間的間距高達 0x1000（4 KiB），這是刻意的——**讓 OS 能用虛擬記憶體把不同 context 的暫存器映射到不同的頁**，這樣 S-mode 的軟體就只能存取自己那個 context 的暫存器，M-mode 的看不到。這是用位址佈局實現的權限隔離。

### Wally 的配置

> "Wally's PLIC receives interrupts from two sources (UART and GPIO) and two hart contexts (M- and S-mode). Like the SiFive FE310, Wally supports up to 54 interrupt sources with 3-bit priorities (1−7). ... GPIOIntr going to source PLIC_GPIO_ID = 3 and UARTIntr going to source PLIC_UART_ID = 10. Because GPIO has a lower source number than the UART, GPIO takes precedence when the intPriority values are equal."
> — p.784.e11–e12

中文解釋：優先權只有 3 位元（1–7），加上 0 表示關閉。這比規格允許的少很多，但夠用。

### 一個完整的中斷處理程式

> "Write a function to configure the PLIC to route UART and GPIO interrupts to Wally's M-mode external interrupt pin MExtInt, with the GPIO receiving higher priority. Write an external interrupt handler to determine which peripheral caused the interrupt and handle it accordingly."
> — p.784.e12（Example 20.3）

中文解釋：Example 20.3 的兩個函式示範完整流程：

```c
void plicInit(void) {
  *PLIC_INTPRIORITY3  = 5;                  // GPIO 優先權 5
  *PLIC_INTPRIORITY10 = 4;                  // UART 優先權 4
  *PLIC_INTEN00 = (1 << 3) | (1 << 10);     // 啟用兩個來源
  *PLIC_THRESHOLD0 = 2;                     // 優先權 > 2 才中斷
}

void mextIntHandler(void) {
  uint32_t *source = *PLIC_CLAIMCOMPLETE0;  // claim：讀出來源
  if      (source == 10) handleUARTInt();
  else if (source == 3)  handleGPIOInt();
  *PLIC_CLAIMCOMPLETE0 = source;            // complete：寫回
}
```

注意 `threshold = 2` 配上 priority 4 和 5——兩個都通過。如果把 threshold 設成 4，就只剩 GPIO（priority 5）能中斷。

### 測試方法

> "The general method of testing the PLIC is to go through various permutations of interrupts from the UART and GPIO that have different priorities and enables and that are routed to different contexts."
> — p.784.e12

中文解釋：三個維度的排列組合——優先權、enable、context。這是驗證仲裁邏輯的自然方法。

### 實作結構

> "For each context {machine, supervisor}: For each priority level [1…7]: Find which requests are pending and enabled at that context and priority; Determine whether that context and priority has at least one request. Find highest priority level with at least one pending enabled request. Find lowest-ID peripheral that has a pending enabled request at that priority level. Send interrupt to context if the priority is high enough for that context"
> — p.784.e13

中文解釋：這段虛擬碼把仲裁邏輯講得很清楚，注意它是**兩層巢狀的優先權編碼器**：
1. 外層：對每個 priority level（1–7），算出「這個 context 在這個優先權有沒有 pending 且 enabled 的請求」
2. 找出最高的有請求的優先權
3. 在那個優先權裡找 ID 最小的來源
4. 和 threshold 比較，夠高才送出

這是純組合邏輯，硬體上就是一堆 AND（pending & enable & priority match）加兩個優先權編碼器。程式碼在 `src/uncore/plic_apb.sv`。

## 名詞表

| 名詞 | 意思 |
| --- | --- |
| PLIC | Platform-Level Interrupt Controller，RISC-V 標準外部中斷控制器 |
| interrupt source | 中斷來源（source 0 不存在） |
| hart context | (hart, 權限模式) 的組合，中斷的目的地 |
| `intPriority` | 每個來源的優先權（Wally 為 1–7，0 表示關閉） |
| `intPending` | 每個來源的 pending 位元 |
| `intEn` | 每個 source × context 組合的 enable 位元 |
| `threshold` | 每個 context 的優先權門檻，低於它的中斷被擋掉 |
| `claimComplete` | 讀 = claim（取得來源編號並清 pending）、寫 = complete（告知處理完畢） |
| `MExtInt` / `SExtInt` | 送給核心 M/S 模式的外部中斷腳位 |
| `PLIC_NUM_SRC` | 設定實際的來源數量 |
| level-sensitive interrupt | 準位觸發中斷，源頭不關就會持續 |

## 所以呢

PLIC 把「很多周邊、很多核心、很多權限層級」的多對多中斷路由問題，用三張表（priority、threshold、enable 矩陣）加一個 claim/complete 握手解決。設計上值得學的兩點：**同一個暫存器讀寫語意不同**（省編碼空間又天然配對），以及**用 4 KiB 的位址間距讓虛擬記憶體能做權限隔離**。接下來兩節是真正的通訊周邊：UART（非同步）和 SPI（同步）。
