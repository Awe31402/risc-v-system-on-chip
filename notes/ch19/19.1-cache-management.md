# 19.1 Cache Management: Zicbom, Zicboz, Zicbop

> 原書 p.767–775（Chapter 19: Other Extensions）
> 涵蓋 19.1.1 RISC-V CMO Instructions（Zicbom、Zicboz、Zicbop、環境設定暫存器）、19.1.2 Test Plan、19.1.3 Wally Implementation（LSU、Cache、Uncached cbo.zero、Prefetch）

## 這節在講什麼

第 19 章是「雜項章」——把 RVA22S64 profile 要求、但不夠大到自成一章的擴充集中處理。19.1 講快取管理操作（CMO, cache management operation）：讓程式能主動控制個別快取線，而不是完全交給硬體。三個獨立的擴充：`Zicbom`（clean/inval/flush）、`Zicboz`（zero）、`Zicbop`（prefetch hint）。

為什麼需要這個？因為有些裝置（DMA 周邊）會繞過快取直接讀寫主記憶體，這時快取裡的資料就和記憶體不一致了。此外「把一塊記憶體清成 0」這件事常見到值得專用指令。

## 關鍵點

### 這章的定位

> "RISC-V is evolving rapidly. Table A.2 lists various extensions that had been ratified by the time of this writing, the profiles that use them, and the chapters that describe them. Most of the extensions are described in earlier chapters with their required hardware. This chapter describes extensions (particularly those needed for the RVA22S64 profile) that do not naturally fit elsewhere in the book"
> — p.767

中文解釋：**profile 是驅動力**。這些擴充不是因為技術上相關才放在一起，而是因為「RVA22S64 要求它們，而書裡沒有別的地方擺」。

### hint 是什麼

> "Some extensions define hints. Hints are encoded as ordinary instructions that have no effect on architectural state but that suggest the core change nonarchitectural state to improve performance or power. For example, the prefetch.r instruction suggests that the cache prefetch a cache line that the program anticipates will be needed soon."
> — p.767

中文解釋：hint 是一個很聰明的設計概念。**它編碼成一條既有的指令，在不支援的處理器上就是 nop，在支援的處理器上會改變非架構狀態（快取內容、發射速率）。** 因為不改架構狀態，所以忽略它永遠是安全的——這讓新舊處理器能執行同一份二進位檔。

### Zicbom：處理 incoherent agent

> "The Zicbom cache block management instructions, cbo.clean, cbo.inval, and cbo.flush, are used to maintain coherence between the data cache and main memory when an incoherent agent (e.g., a peripheral with direct memory access) might write data to the main memory without updating the cache."
> — p.768

中文解釋：三個指令對應三種需求：
- **`cbo.clean`**：把 dirty 的快取線寫回主記憶體。**在 DMA 裝置讀記憶體之前用**——確保它讀到最新的資料。
- **`cbo.inval`**：作廢快取線。**在 DMA 裝置寫記憶體之後用**——丟掉過時的快取內容。
- **`cbo.flush`**：clean 然後 inval，當成**一個 atomic 操作**。

三者都用 `rs1` 指定的**虛擬位址**。邊欄提到編碼細節：它們是 I-type，立即值欄位用來區分是哪個操作（**不加到 rs1 的基底位址上**）。prefetch hint 則編碼成 `ori x0, rs1, imm`，因為寫入 `x0` 什麼都不會發生，所以在不支援的機器上就是 nop。

### Zicboz：為什麼歸零值得一條指令

> "Programs sometimes need to initialize regions of memory to zero; for example, the operating system (OS) clears the .bss section of memory when starting a process. Using cbo.zero to clear one cache line at a time is faster than storing zeros one word at a time and also avoids the need to fetch a cache line from main memory that is about to be zeroed anyway."
> — p.768

中文解釋：**兩個好處，第二個更關鍵**。一般的 store 遇到 cache miss 會先把整條線從記憶體抓進來（write-allocate），但如果整條線馬上就要被寫成 0，那次抓取完全是浪費頻寬。`cbo.zero` 直接在快取裡建立一條全 0 的線，跳過抓取。

### Zicbop：prefetch 三種 hint

> "When a program knows it is likely to access a memory address soon, it can prefetch the corresponding cache line to hide the latency of waiting for the cache line. Zicbop defines three prefetch hint instructions (prefetch.i/r/w), which suggest that the processor prefetch instructions, read data, or write data, if beneficial. Prefetching for data reads and writes is often identical."
> — p.768

中文解釋：位址算法有個細節——「`imm` 的低 5 位元被當成 0」，所以位址是 `rs1 + {imm[11:5], 00000}`。這是因為 prefetch 的單位是快取線，不需要位元組精度。

### 環境設定暫存器控制誰能用

> "menvcfg and senvcfg registers enable the use of CMO instructions outside of M-mode. Each of these registers has CBZE, CBCFE, and CBIE enable fields. menvcfg's enable must be set to use a CMO instruction in S- or U-mode. If S-mode is supported, senvcfg's enable must also be set to use the instruction in U-mode."
> — p.768

中文解釋：兩層授權（M 允許 S/U，S 再允許 U），這是第 8 章 privileged 架構的標準模式。

> "CBIE = 00 disables cbo.inval and CBIE = 11 enables it. CBIE = 01 causes cbo.inval to operate as a flush, which invalidates the line but also ensures dirty data is first written back to the memory hierarchy, making the instruction safer to use."
> — p.769

中文解釋：**`CBIE = 01` 這個中間狀態設計得很好。** `cbo.inval` 是危險的——如果快取線是 dirty 的，作廢它就會**遺失資料**。把它悄悄升級成 flush，就讓不信任的 U-mode 程式也能安全使用：語意上仍然是「這條線之後不在快取裡」，但不會弄丟資料。

### 測試方法

> "The WALLY-cbom-01 test copies a reference region of memory to another region aligned to the size of a cache way. It then invalidates, cleans, or flushes the copied region and checks main memory for the correct data. The WALLY-cboz-01 test copies a region of memory with known data, then overwrites it with cbo.zero, and then verifies that the region contains zeros."
> — p.769

中文解釋：測試的關鍵是「**對齊到 cache way 的大小**」——這樣才能精確控制哪些線在快取裡。測試假設 64 位元組的快取線。

### Wally 的 CMO 改動範圍

> "The Wally ZICBOM_SUPPORTED and ZICBOZ_SUPPORTED configuration parameters indicate whether Wally should add hardware support for CBO instructions. The CBO extension modifies the controller, privileged, lsu, pmachecker, and cache units. The IEU controller detects CBO instructions, and gates them with the appropriate environment configuration registers, envcfg. It sends CBOpM[3:0], which specifies {zero, clean, flush, inval}, to the LSU."
> — p.769

中文解釋：五個模組要改。核心訊號是 4 位元的 one-hot `CBOpM`。流程是：controller 解碼並用 `envcfg` 過濾 → MMU 檢查例外 → LSU 依情況送給 cache 或 AHB 匯流排。

### CMO 仍然要走完整的位址轉換與權限檢查

> "As with a regular load or store, during a cbo.* operation, the LSU receives the virtual address for the CMO instruction. If virtual memory is enabled, the TLB translates it to a physical address, throws a store page fault if the page is not accessible, and sets the access/dirty bits if necessary. The PMA and PMP check that the physical address is accessible and throw a store access fault if not."
> — p.770

中文解釋：**CMO 被當成 store 來檢查權限**（和第 17 章 AMO 一樣）。這很合理——`cbo.inval` 可能弄丟資料、`cbo.zero` 會改資料，都是寫入級別的行為。Fig. 19.2 的 PMA checker 加了 CMO 這個存取類型。

### cache FSM 的改動

> "CMOp is sent to the cache FSM, which controls the various operations. The FSM produces a new ClearValid output to clear the valid bit for CMO invalidate and flush operations. For cbo.zero, the cache always selects LineWriteData = 0."
> — p.770

中文解釋：Fig. 19.4 與 Table 19.1 顯示 `cachefsm` 的改動。四個指令各自的路徑：

> "cbo.inval remains in the Access state. It asserts ClearValid to invalidate the line if there is a hit. cbo.clean and cbo.flush both transition to the Writeback state if the line hits and is dirty. ... However, for cbo.* instructions, it continues directly to AddressSetup rather than Fetch because it does not need to fetch a missing line."
> — p.774

中文解釋：
- **`cbo.inval`**：完全不離開 Access 狀態，一個 cycle 搞定（只是清 valid 位元）。
- **`cbo.clean` / `cbo.flush`**：命中且 dirty 才進 Writeback，寫回後清 dirty 位元（flush 另外還清 valid）。關鍵差異是寫回完成後**直接回到 AddressSetup 而不是 Fetch**——因為不需要抓新的線進來。
- **`cbo.zero`**：命中或（未命中但 victim 乾淨）時，一個 cycle 內寫滿 0 並設好 valid/dirty/tag。如果 victim 是 dirty 的，先進 Writeback 把它趕出去。

邊欄提到一個設計取捨：也可以從 Writeback 直接回 Access，但那樣就得在轉態時降低 `CacheStall`，會**拉長關鍵路徑**。先繞到 AddressSetup 的話，`CacheStall` 只取決於當前狀態。

### cbo.inval 也要更新 LRU

> "cbo.inval clears the valid bit for the matching line and updates the LRU (least recently used) bits, such that the invalidated way becomes the next victim."
> — p.770–772

中文解釋：這是一個容易漏掉的細節。作廢一條線之後，那個 way 是空的，理應優先被拿來用。不更新 LRU 的話，下次 miss 可能會踢掉一條有效的線，而讓空的 way 閒著。

### 新的 HitDirtyWay 輸出

> "Unlike other cache operations, cbo.clean and cbo.flush need to know if the hit cache line is dirty, indicated by the new HitDirtyWay output."
> — p.774

中文解釋：平常的 load/store 只在乎「命中了嗎」和「victim 髒不髒」；clean/flush 卻要知道「**命中的那條線**髒不髒」，因為只有髒的才需要寫回。這是一個新的訊號（Fig. 19.5）。

### 不可快取記憶體上的 cbo.zero

> "The MMU can mark certain main memory pages as uncacheable using page-based memory types (PBMT). cbo.zero must still write a cache line worth of zeros to such memory, but it must directly do so through the AHB bus. The BusCMOZero = CMOp[3] & ~Cacheable signal indicates this situation."
> — p.774

中文解釋：這是一個 corner case。`cbo.zero` 的語意是「把這條線的範圍寫成 0」，就算那塊記憶體不可快取也一樣要做，只是必須直接發到匯流排。實作上複用 `ahbcacheinterface` 既有的 CacheWriteback 狀態（因為它本來就會逐個 beat 送出一個 burst），只改兩處：進入條件加上 `BusCMOZero`，以及**這種情況下不發 `CacheBusAck`**（因為 `cachefsm` 根本沒發出這個請求，不該收到確認）。

### Wally 忽略 prefetch

> "Wally is an in-order processor that stalls during cache fills. Therefore, prefetch would stall the processor and not improve performance. Hence, the prefetch.* hints are ignored."
> — p.774

中文解釋：這是 hint 設計價值的完美示範。Wally 的管線在快取填充時會停住，所以「提前抓」不但沒好處，還會**提前把處理器停住**——比不做還糟。因為它是 hint，直接忽略就好，程式照樣正確執行。

## 名詞表

| 名詞 | 意思 |
| --- | --- |
| CMO (cache management operation) | 快取管理操作 |
| Zicbom / Zicboz / Zicbop | 快取線管理／歸零／預取的三個擴充 |
| hint | 不改架構狀態、可安全忽略的建議型指令 |
| incoherent agent | 繞過快取直接存取主記憶體的裝置（如 DMA 周邊） |
| `cbo.clean` / `cbo.inval` / `cbo.flush` / `cbo.zero` | 寫回／作廢／寫回並作廢／歸零一條快取線 |
| `prefetch.i/r/w` | 預取指令／讀取資料／寫入資料的 hint |
| `menvcfg` / `senvcfg` | M/S 模式的環境設定暫存器 |
| CBZE / CBCFE / CBIE | 分別啟用 zero／clean+flush／inval 的欄位 |
| `CBOpM[3:0]` | one-hot 的 CMO 操作訊號 {zero, clean, flush, inval} |
| `ClearValid` | 清除快取線 valid 位元的新 FSM 輸出 |
| `HitDirtyWay` | 命中的那條線是否為 dirty |
| `BusCMOZero` | 不可快取的 cbo.zero，需直接走 AHB |
| PBMT (page-based memory types) | 用頁表項標記記憶體型態（如不可快取） |
| write-allocate | 寫入未命中時先把整條線抓進快取 |

## 所以呢

CMO 的核心價值是「把快取從純粹的硬體自動機制，變成軟體可以介入的資源」。這在有 DMA 的系統上是必需的，在做大量記憶體初始化時是效能優化。Wally 的實作示範了一件事：即使是「只加四條指令」，也要動到 controller、privileged、LSU、PMA checker、cache 五個模組——因為它們必須走完整的位址轉換與權限檢查路徑。下一節換一個同樣「看似小、實則牽動很多」的主題：非對齊存取。
