## 關鍵點

### 三種虛擬記憶體模式

> "**In RISC-V, machine-level processes exclusively use physical addressing. Virtual memory is an optional
>  RISC-V feature. If supported, supervisor- and user-level processes can enable virtual addressing through
>  the *supervisor address translation and protection* (satp) register. RV32 supports 32-bit virtual
>  addresses and 34-bit physical addresses with a 2-level page table.... RV64 supports 39-, 48-, and 57-bit
>  virtual addresses with 3-, 4-, and 5-level page tables, respectively, and 56-bit physical addresses.**"
> — p.478

中文解釋：**四種模式的對照，這張表要記熟：**

| 模式 | 虛擬位址 | 實體位址 | 頁表層數 | 虛擬位址空間 |
| --- | --- | --- | --- | --- |
| **Sv32**（RV32） | **32 bits** | **34 bits** | **2** | **4 GiB** |
| **Sv39**（RV64） | **39 bits** | 56 bits | **3** | **512 GiB** |
| **Sv48**（RV64） | **48 bits** | 56 bits | **4** | **256 TiB** |
| Sv57（RV64） | 57 bits | 56 bits | 5 | — |
| **Sv bare** | （關閉虛擬記憶體） | | | |

**RV32 可用最多 16 GiB 實體記憶體（2^34）。**
**未來預留 64 位元虛擬位址加 6 層頁表，等 128 PiB 不夠用時。**

**（p.478 邊欄：**「Sv 前綴指的是 supervisor mode 中和 *v*irtual memory 相關的功能。」**）

**（p.479 邊欄的實務建議：**
「本章和 Wally 的實作聚焦到 Sv48。**2021 年 12 月的規格版本加了 Sv57**，
實作是直接的擴充，但只和有特殊記憶體需求的系統相關。」**）

**Sv39 為什麼受偏好（p.481）：**
> "**Sv39 is sufficient for many contemporary systems, uses less page table storage, and has faster page table
>  walking, so it is preferred unless the larger address space is required.**"

**三個理由：夠用、省頁表空間、走訪快（少一層）。**

### `satp` 暫存器

> "**The satp register enables the various virtual addressing modes and points to the root (level 1) page
>  table for a process. It also contains the *address space identifier* (ASID), which acts as a short process
>  ID (PID) assigned by the OS to differentiate multiple processes' virtual address spaces that might coexist
>  in a TLB.**"
> — p.478

中文解釋：**Fig. 11.6（p.479）的欄位配置：**

| | MODE | ASID | PPN |
| --- | --- | --- | --- |
| **RV32 satp** | bit 31（1 bit） | bits 30:22（**9 bits**） | bits 21:0（22 bits） |
| **RV64 satp** | bits 63:60（**4 bits**） | bits 59:44（**16 bits**） | bits 43:0（44 bits） |

**MODE 的編碼（p.478–479）：**

| MODE | RV32 | RV64 |
| --- | --- | --- |
| 0 / 0000 | **Sv bare（停用）** | **Sv bare** |
| 1 | **Sv32** | — |
| **1000** | — | **Sv39** |
| **1001** | — | **Sv48** |
| 1010 | — | Sv57 |

**PPN 的用法（p.478）：**
> "**PPN defines the PPN of the root page table. Shift it left by 12 to get the physical address (base
>  address) of the root page table, which is always aligned to a page boundary.**"

**Context switch（p.479）：**
> "**Each user or supervisor-mode process has its own virtual memory space and ASID. When the OS performs a
>  context switch, it reloads satp with the page table address and ASID of the new process.**"

**（p.479 邊欄：**「較舊的 x86 處理器沒有 ASID，context switch 時要 flush TLB。」**
——呼應 11.1.1.7 節。）

### 完整的位址轉譯追蹤（Example 11.4）

中文解釋：**Example 11.4（p.479）是理解多層頁表最好的練習。
Sv32、2 層頁表、`satp = 0x80012345`、虛擬位址 `0x013FF124`：**

```
1. satp 的 msb（MODE）= 1 → 虛擬記憶體啟用
2. 接下來 9 bits 是 0 → ASID = 0
3. satp 剩下 22 bits = root（level 1）頁表的 PPN = 0x012345
   → 補 12 個 0 得到 level 1 頁表的實體位址 = 0x012345000
4. 從虛擬位址取 VPN1 = 4 → level 1 PTE 的位址
   = 0x012345000 + 4 words (16 bytes) = 0x012345010
5. level 1 PTE 給出 level 0 頁表的 PPN = 0x1AABBC
   → level 0 頁表的實體位址 = 0x1AABBC000
6. VPN0 = 0x3FF（1023）→ level 0 PTE 的位址
   = 0x1AABBC000 + (0x3FF << 2) = 0x1AABBCFFC
7. 該項給出實體記憶體的 PPN = 0x377889
8. 附上虛擬位址的 page offset 0x124
   → 最終 34-bit 實體位址 = 0x377889124
```

**每一層的公式都一樣：`PPN << 12 + VPN × PTE大小`。**
**（Sv32 的 PTE 是 4 bytes，所以 `VPN << 2`；RV64 是 8 bytes，`VPN << 3`。）**

### 虛擬位址格式

中文解釋：**Fig. 11.8（p.480）：**

| 模式 | 欄位配置 |
| --- | --- |
| **Sv32** | `VPN1(10) \| VPN0(10) \| Page Offset(12)` |
| **Sv39** | `符號延伸自[38] (25) \| VPN2(9) \| VPN1(9) \| VPN0(9) \| Offset(12)` |
| **Sv48** | `符號延伸自[47] (16) \| VPN3(9) \| VPN2(9) \| VPN1(9) \| VPN0(9) \| Offset(12)` |

**為什麼 Sv32 是 10 bits 而 RV64 是 9 bits（p.479）：**
> "**Each page table fits on one page, so RV32 has 2^12/4 = 2^10 entries in a page table, and RV64 has
>  2^12/8 = 2^9 entries.**"

**一個頁表剛好一頁（4 KiB）；Sv32 的 PTE 是 4 bytes、RV64 是 8 bytes。**

**RV64 的符號延伸要求（p.481）——這是個容易踩的坑：**
> "**For RV64 (Sv39 and Sv48), the upper bits of the virtual address must all be the same (either all 1s or
>  all 0s) so that the address space includes the bottom and top of the range but leaves nonexistent
>  addresses in the middle; if the bits are not the same, a page fault occurs. This matches conventional
>  practices, where user-mode programs occupy low addresses, while supervisor-mode OS occupies high
>  addresses, and the OS can easily distinguish between the two by looking at the most significant bit of the
>  virtual address.**"

**高位元必須全 0 或全 1，否則 page fault。**
**好處：使用者程式在低位址、OS 在高位址，看最高位元就能分辨。**

### PTE 格式與旗標

中文解釋：**Fig. 11.9（p.481）的 PTE 格式：**

| | Reserved | PPN | RSW | D | A | G | U | X | W | R | V |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| **RV32** | — | bits 31:10（**22**） | 2 | 1 | 1 | 1 | 1 | 1 | 1 | 1 | 1 |
| **RV64** | bits 63:54（10） | bits 53:10（**44**） | 2 | 1 | 1 | 1 | 1 | 1 | 1 | 1 | 1 |

**兩種格式的低 10 個旗標位元完全相同。**
**RV32 支援 2^(22+12) = 16 GiB 實體記憶體，RV64 支援 2^(44+12) = 64 PiB。**

**Table 11.1（p.482）旗標的意義，這張表要記熟：**

| Flag | 意義 |
| --- | --- |
| **V** | **Valid：1 表示該 page 在主記憶體中** |
| **X, W, R** | **執行、寫入、讀取權限**（見下面的編碼表） |
| **U** | **User mode 可存取** |
| **G** | **Global：對所有位址空間都存在；TLB 比對時忽略 ASID** |
| **A** | **Accessed：自上次清除以來至少被存取過一次** |
| **D** | **Dirty：page 中至少一個 byte 被寫過** |
| **RSW** | 保留給 OS 使用 |

**`XWR` 的編碼（Table 11.1，p.482）——注意 000 的特殊用法：**

| XWR | 意義 |
| --- | --- |
| **000** | **指向下一層頁表的指標**（不是 leaf！） |
| 001 | Read only |
| **010** | **\<illegal\>** |
| 011 | Read-write |
| 100 | Execute only |
| 101 | Read-execute |
| 111 | Read-write-execute |

**`XWR = 000` 表示「這是個指標，不是最終的 PTE」——這是多層頁表的關鍵編碼。**
**`XWR = 010`（只能寫不能讀）是非法的。**

**保護規則（p.481）：**
> "**A page fault occurs if the privilege or permissions for the access attempted are incorrect. In user mode,
>  a fault occurs for any access if U = 0. In supervisor mode, if U = 1, a fault always occurs when trying to
>  execute code; reads and writes succeed only when sstatus.SUM (supervisor user memory) = 1.
>  This protects the system from certain security vulnerabilities.**"

| 模式 | U = 0 | U = 1 |
| --- | --- | --- |
| **User** | **永遠 fault** | 依 XWR |
| **Supervisor** | 依 XWR | **執行永遠 fault；讀寫要 `sstatus.SUM = 1`** |

**「S-mode 永遠不能執行 user page」——防止把控制權交給 user 程式的程式碼。**

**（p.481 邊欄：**「OS 設 `sstatus.SUM` 來讀寫 user-mode page。
**但它通常保持 SUM 為低，避免意外踩到 user page。**」**）

**G 位元（p.481）：**
> "**The G bit indicates that a page is global and applies to all processes; the ASID is ignored for global
>  pages. OS pages are typically global because the OS is called from many different user-mode processes.**"

### Swap space、thrashing、共享記憶體

> "**The OS reserves part of the disk for *swap space* to hold pages that don't fit in physical memory.
>  The OS uses the PPN field of the PTE to locate the page on disk. Paging from disk is slow, so if a computer
>  doesn't have enough RAM to hold the working set, it will begin *thrashing*, frequently page faulting and
>  reducing the system to a crawl. Mobile devices generally terminate an entire app that hasn't been used
>  recently to reclaim its memory rather than enduring the delay and wear and tear of paging to flash memory.**"
> — p.482

中文解釋：**兩個實務觀察：**
- **`V = 0` 時 PPN 欄位被 OS 拿來存「這個 page 在磁碟的哪裡」**——一個欄位兩種用途
- **行動裝置寧可直接砍掉整個 app，也不要換頁到 flash**（延遲 + 磨損）

**共享記憶體（p.482）：**
> "**When two processes wish to communicate through shared memory, they allocate a shared page through a system
>  call such as `shmget()`. Each process has its own virtual addresses mapping to the shared physical
>  addresses. Thus, each process also has its own PTE pointing to the shared PPN. The PTE flags could differ
>  between processes; a producer-consumer buffer might be read-only for the consumer but read/write for the
>  producer.**"

**同一個實體 page，兩個 process 各有自己的 PTE，權限可以不同——很優雅的設計。**

### 可變 Page 大小

> "**Usually, the level 0 page table is the leaf page table and points to normal 4-KiB pages (also called
>  *kilopages*). The nonleaf PTEs use {X, W, R} = 000 to indicate that they point to the next level page
>  table.... However, if XWR are nonzero for a higher-level PTE, then that entry points to a superpage.
>  The superpage must be aligned to its natural (page) boundary (with all the low-order bits being 0).
>  The low-order untranslated bits of the virtual address form an offset into the superpage.**"
> — p.483

中文解釋：**機制很簡單：`XWR ≠ 000` 的高層 PTE 就是 leaf，指向一個 superpage。**

**Table 11.2（p.483）的 page 大小：**

| Format | Leaf Level | Page Offset Bits | **Page Size** | Page Type |
| --- | --- | --- | --- | --- |
| Sv32 | 0 | 12 | **4 KiB** | Kilopage |
| **Sv32** | **1** | 12 + 10 = 22 | **4 MiB** | **Megapage** |
| Sv39/48 | 0 | 12 | **4 KiB** | Kilopage |
| **Sv39/48** | **1** | 12 + 9 = 21 | **2 MiB** | **Megapage** |
| **Sv39/48** | **2** | 12 + 9×2 = 30 | **1 GiB** | **Gigapage** |
| **Sv48** | **3** | 12 + 9×3 = 39 | **512 GiB** | **Terapage** |

**（p.483 邊欄解釋了為什麼 Sv32 的 megapage 比較大：**
**「Sv32 的 PTE 是 32 bit 而非 64 bit，所以固定大小的頁表裡能放兩倍的 PTE」**——
索引 10 bits vs 9 bits。）

**對齊要求：superpage 必須對齊到它自己的大小邊界（低位元全 0）。**

**Example 11.5（p.484）示範四種情況的轉譯，值得跟一遍：**

| 虛擬位址 | VPN3/2/1/0 | 結果 |
| --- | --- | --- |
| `0000_0000_8020_1340` | 0, 2, 1, 1 | **kilopage**（leaf 在 level 0），PA = `00_0000_8020_0340` |
| `FFFF_FFFF_FFFF_F238` | 511, 511, 511, 511 | kilopage，PA = `00_0000_8020_1238` |
| `0000_0000_8000_FFF8` | 0, 2, 0, — | **megapage**（level 1 的 XWR ≠ 0），**PPN 低 9 bits 被丟棄**，PA = `00_0000_9000_FFF8` |
| `0000_0100_C0A0_7BC0` | 2, —, —, — | **terapage**（level 3 就是 leaf），**PPN 低 27 bits 被丟棄**，PA = `00_0000_C0A0_7BC0` |

**規則：leaf 在越高層，被丟棄的 PPN 位元越多，page offset 越長。**

**（p.484 邊欄的圖例說明：**
「頁表範例中，**白底項目是有效的（V = 0 是無效）**，
**灰底項目是無效的**，**藍色項目是畸形的、使用時應該造成 page fault**。」**）

### Huge Pages（Svnapot）

> "**Many important programs use tens to hundreds of kilobytes of code and data. They are too small to make
>  efficient use of a megapage yet clutter the TLB with large numbers of 4-KiB pages. Competing architectures
>  such as ARMv8 have observed that 64-KiB *huge pages* are valuable, and Linux takes advantage of such pages
>  when they are supported.**"
> — p.486

中文解釋：**問題：4 KiB 太小（塞爆 TLB），2 MiB 太大（浪費）。中間需要 64 KiB。**

**Svnapot 的機制（p.486）：**
> "**The optional RV64 Svnapot extension combines sixteen contiguous 4-KiB pages to create 64-KiB huge pages
>  naturally aligned to 64-KiB address boundaries. In general, the extension anticipates any *naturally
>  aligned power of two* (NAPOT) page size (i.e., 8, 16, 32, 64 KiB), but only 64-KiB pages are standardized
>  in Version 1.0 of the extension.**"

> "**When the Svnapot extension is supported, bit 63 of the PTE is the N bit. If a PTE has N = 1 and
>  PPN[3:0] = 1000, the entry is considered NAPOT. The four least significant bits of the VPN are ignored when
>  accessing the page table, so the 16 contiguous 4-KiB virtual pages all can share the same PTE.
>  After translation, the four bottom bits of the PPN are replaced by these bits of the VPN.
>  If PPN[3:0] has any value other than 1000 in the PTE when PTE bit N = 1, a page fault occurs.**"

**機制：`N = 1` 且 `PPN[3:0] = 1000` → **16 個連續的 4-KiB page 共用一個 PTE**。
轉譯時把 PPN 的低 4 bits 換成 VPN 的低 4 bits。**

**Example 11.7（p.488）：**
> "Consider a PTE for VPN 0x80020 with N = 1 and PPN = 0x80308. Translate virtual address 0x80025678....
>  **This PPN's four least significant bits are 1000, so this is a NAPOT entry for a huge page.
>  The address 0x80025678 has a VPN of 0x80025. The TLB matches against the VPN entry of 0x80020 (by ignoring
>  the bottom four bits) and returns the PPN of 0x80308. It replaces the bottom 4 bits of the PPN (0x8) with
>  those from the VPN (0x5), giving 0x80305, and then appends the page offset 0x678 to obtain a PA of
>  0x80305678. Observe that the bottom 16 bits of the virtual and PA are identical, as expected for a
>  2^16 = 64-KiB huge page.**"

**驗證方式很漂亮：64-KiB page 表示低 16 bits 不轉譯，所以 VA 和 PA 的低 16 bits 應該相同。**

### Aliasing：不同大小的 page 可以指向同一處

**Table 11.3（p.487）示範三個不同的虛擬位址 alias 到同一個實體位址：**

| 虛擬位址 | page 類型 | 實體位址 |
| --- | --- | --- |
| `0x0100_9531_A00C` | **terapage** | `0x0000_9531_A00C` |
| `0x0080_5531_A00C` | **gigapage** | `0x0000_9531_A00C` |

（這就是 11.1.1.7 節說的 synonym problem 的具體樣貌。）

### A/D 位元的管理

> "**The OS uses A/D (accessed/dirty) bits to manage pages. The A bit indicates that the virtual page has been
>  accessed since that bit was last cleared. The D bit indicates that the virtual page has been written since
>  that bit was last cleared. The OS writes dirty pages (with D = 1) back to the disk when they are evicted
>  and could use the A bit in a pseudo least recently used (pLRU) page replacement scheme.**"
> — p.488

中文解釋：**OS 的 pLRU 策略（p.488）：**
> "**For example, one strategy is for the OS to periodically mark all pages as unused (A = 0). Accessed pages
>  subsequently raise their accessed bits to A = 1. When a page needs to be evicted, the OS picks a page that
>  is still marked as unused.**"

**很簡單的近似：週期性清 A 位元，evict 時挑 A = 0 的。**

**硬體 vs 軟體更新（p.488）——兩個擴充：**

| 擴充 | 意義 |
| --- | --- |
| **Svade** | Supervisor virtual memory A/D exception。**存取 A = 0 的 page 或寫入 D = 0 的 page 時會 page fault**（軟體更新） |
| **Svadu** | Supervisor virtual memory A/D update。**HPTW 在硬體中更新 A/D 位元，不 fault** |

**`menvcfg.ADUE`（bit 61）控制：`ADUE = 0` 時停用 Svadu，改用軟體更新。**

**「Linux 支援 A/D 位元的軟體管理，所以許多核心缺少硬體支援」**（p.488）。

### `status` 暫存器的三個相關位元

> "**The mstatus/sstatus register... has three bits that affect address translation: MPRV, MXR, and SUM.
>  These bits manage accesses across privilege levels.**"
> — p.488

中文解釋：**三個位元各解決一個問題：**

**（1）`MPRV`（Modify PRIvilege）（p.489）**
> "**Some RISC-V implementations perform misaligned loads and stores with a trap to a machine-mode handler
>  rather than in hardware because the hardware is costly and rarely used. The handler needs to do address
>  translation even though it is running in machine mode, which usually uses physical addressing only.
>  When set, the mstatus.MPRV bit causes the system to do address translation and protection according to the
>  privilege level specified in MPP (normally the user or supervisor mode that caused the trap).**"

**用途：讓 M-mode 的 trap handler 能用「造成 trap 的那個模式」的位址轉譯。**

**（2）`MXR`（Make eXecutable Readable）（p.489）**
> "**When set, mstatus.MXR... allows loads from executable nonreadable pages (with X = 1 but R = 0) so that
>  the trap handler can read instructions.**"

**用途：讓 handler 能讀取「只能執行不能讀」的 page 裡的指令。**

**（3）`SUM`（permit Supervisor User Memory access）（p.489）**
> "**Supervisor code normally should not access information from user-mode pages, to reduce the risk of
>  malicious user-mode programs affecting privileged operations. However, the supervisor occasionally needs
>  to control user-mode data. The mstatus/sstatus.SUM bit allows these accesses when set; otherwise,
>  supervisor-mode access to user memory causes a load or store page fault. The OS typically sets SUM only
>  when necessary and then clears it for safety.**"

**用途：讓 S-mode 能存取 user page；平常關閉以策安全。**

### 三個記憶體保護機制

> "**RISC-V provides three, often-overlapping, memory protection mechanisms:
>  - The PMA checker defines the addresses and access limitations for memory ranges and memory-mapped I/O
>    devices.
>  - The PMP checker restricts types and privilege of access to certain memory ranges.
>  - Virtual memory provides the X, W, R, and U access-permission flags and limits user-mode processes to only
>    access pages explicitly allocated to them by the OS.**"
> — p.489

中文解釋：**三者的分工：**

| 機制 | 管什麼 | 特性 |
| --- | --- | --- |
| **PMA** | **記憶體範圍和 I/O 裝置的位址與存取限制** | **設計時就硬接（可部分組態）** |
| **PMP** | **特定記憶體範圍的存取類型與特權** | **軟體可組態** |
| **虛擬記憶體** | X/W/R/U 權限旗標，以及 user process 只能存取 OS 配置給它的 page | 每個 process 各自的頁表 |

### PMA Checker

> "**RISC-V specifies that a core must contain a platform-dependent PMA that generates select signals for each
>  memory bank or I/O peripheral and produces access faults if the memory access is unsuccessful.
>  An unsuccessful access may be caused by a physical address located in a *vacant* portion of the memory map
>  or an unsupported operation (e.g., a byte access to a peripheral that only supports word accesses).**"
> — p.489–490

中文解釋：**PMA 檢查的六類屬性（p.490），這份清單很有價值：**

| 屬性 | 說明 |
| --- | --- |
| **Reads, writes, executes** | 允許哪些操作 |
| **Access width** | **從 byte 到多字 burst** |
| **Hardware page table accesses** | 是否允許 HPTW 存取 |
| **Cacheability** | **主記憶體通常可以，memory-mapped I/O 通常不行** |
| **Idempotency** | **同一操作多次執行結果是否相同**（見下） |
| **Atomic memory operations (AMOs)** | 是否支援（第 17 章） |

**Idempotency 的說明（p.490）很重要：**
> "**- Normally yes for main memory: reading or writing the same value twice is harmless
>  - Normally no for peripherals that could have side effects
>  - Instruction fetches and speculative or redundant accesses must be avoided for non-idempotent devices**"

**「非冪等裝置必須避免推測性或重複的存取」**——
呼應 9.5.5 節的 UART 接收緩衝器例子。

**Table 11.4（p.491）rv64gc 的 PMA 設定，這張表很實用：**

| Region | Base Address | Range | Access Width | XRW | Cacheable | Idempotent | Atomic |
| --- | --- | --- | --- | --- | --- | --- | --- |
| **RAM** | 80000000 | 7FFFFFF | **Any** | **XWR** | **Yes** | **Yes** | **Yes** |
| GPIO | 10060000 | FF | **32-bit** | RW | No | No | No |
| SPI | 10040000 | FFF | **8-bit** | RW | No | No | No |
| **UART** | 10000000 | 07 | **8-bit** | RW | No | No | No |
| PLIC | 0C000000 | 3FF0000 | 32-bit | RW | No | No | No |
| CLINT | 02000000 | FFFF | Any | RW | No | No | No |
| SDC | 00013000 | FFF | {32/64}-bit | RW | No | No | No |
| **Boot ROM** | 00001000 | FFF | Any | **XR** | **Yes** | **Yes** | No |

**三個觀察：**
1. **只有 RAM 和 Boot ROM 可以 cache 且是冪等的**
2. **只有 RAM 支援原子操作**
3. **Boot ROM 是 XR（不可寫）**

**（p.490 的設計提醒：**
「**在位址 0 不放記憶體是明智的，這樣解參照 NULL 指標會造成 access fault。**」**）

### Svpbmt：讓 PTE 覆寫 PMA

> "**Some peripherals perform *direct memory access* to read or write from main memory.... If the peripherals
>  aren't specially designed to interact with the cache, they may face a coherence problem where the data
>  cache contains valid data and the main memory contains different data. It is useful to mark certain portions
>  of main memory as uncacheable to avoid this coherence problem.**"
> — p.490

中文解釋：**問題：DMA 造成 cache 不一致**（呼應 9.1.4 節）。
**解法：把某些主記憶體區域標記為不可 cache。**

**Svpbmt 的機制（p.491）：**
> "**The optional RV64 RISC-V Svpbmt... extension allows a PTE to override the PMA for certain pages.
>  The menvcfg.PBMTE bit must be set to enable page-based memory types.... When enabled, bits 62:61 of the PTE
>  are the PBMT field. If these bits are 00, the system uses the standard PMA checker. If the bits are 01 or 10,
>  the system overrides the PMA checker to indicate uncacheable main memory and I/O, respectively.
>  Whereas main memory is idempotent, I/O space is non-idempotent.**"

| PBMT | 意義 |
| --- | --- |
| **00** | 用標準 PMA |
| **01** | **不可 cache 的主記憶體**（冪等） |
| **10** | **I/O**（不可 cache，**非冪等**） |

**「Linux 自動偵測並使用 Svpbmt」**（p.491）。

### PMP Checker

> "**By default, the PMP grants machine-mode access to all parts of physical memory and denies supervisor- and
>  user-mode access to all of physical memory. It may then be configured in software to grant access to certain
>  portions in S- or U-mode or to revoke access to certain portions in M-mode. For example, the OpenSBI M-mode
>  firmware configures the PMP so that S- and U-mode software can access all memory except a region used by the
>  firmware. Even if malicious software compromises the OS, the PMP prevents it from corrupting the firmware.**"
> — p.491

中文解釋：**預設值很重要：M-mode 全部可存取、S/U-mode 全部禁止。**
**典型用法：開放 S/U 存取大部分記憶體，但保留韌體自己的區域。**

**（p.491 邊欄的安全應用很有啟發：**
「通常 M-mode 程式碼可存取整個記憶體。**但在安全系統中，
M-mode boot loader 可能只在啟動時需要讀取加密金鑰。
boot loader 之後可以撤銷對含金鑰的 ROM 位址的存取，
這樣即使攻擊者危害了其他 M-mode 韌體也拿不到它們。**」**）

**PMP 暫存器（p.491–492）：**
- **`pmpaddr0`–`pmpaddr63`**（0、16 或 64 個）：**位址必須對齊 4-byte 邊界，
  所以最低 2 bits 是 0 且不儲存**
  - RV32：`pmpaddr` 指定 34-bit 實體位址的 bits [33:2]
  - RV64：指定 56-bit 實體位址的 bits [55:2]
- **`pmpcfg`**：每個區域一個 8-bit 欄位（Fig. 11.13，p.492）

**`pmpcfg` 的欄位（Fig. 11.13）：**
```
bit 7: L（locked）
bits 6:5: 0（保留）
bits 4:3: A（區域類型）
bit 2: X
bit 1: W
bit 0: R
```

**`L` 位元的兩個作用（p.492）：**
> "**The L field indicates if the region is locked. In a locked region (L = 1), the corresponding pmpaddr and
>  pmpcfg registers cannot be written except when the system is reset. The XWR permissions always apply to S-
>  and U-mode programs. When L is set, they also apply to M-mode programs.**"

**鎖定 = 不能改 + 權限也套用到 M-mode。**

**Table 11.5（p.492）區域類型：**

| A[1:0] | Name | Region Type |
| --- | --- | --- |
| **00** | **OFF** | 停用 |
| **01** | **TOR** | **Top of range**：從前一個 `pmpaddr` 開始，到目前這個結束 |
| **10** | **NA4** | Naturally aligned 4-byte region |
| **11** | **NAPOT** | **Naturally aligned power of two region（≥ 8 bytes）** |

**NAPOT 的編碼很巧妙（p.492）：**
> "**When the type is NAPOT, the region is a power of 2 long, whose base address and size are encoded in
>  pmpaddr. Specifically, the string of 1s at the bottom of pmpaddr determines the size. If the least
>  significant k bits of pmpaddr are 1s, the region size is 2^(k+3). The base address is determined by treating
>  these k bits as 0 and shifting the address left by 2.**"

**「低位連續 1 的個數 k」編碼了大小 2^(k+3)。**

**Example 11.8（p.493）：**
> "**The A field of pmpcfg is 3 (11₂), so this is a NAPOT region. The region's pmpaddr = 0x2004013F has k = 6
>  trailing 1s, so its size is 2^9 = 512 bytes. Discarding these ones gives 0x20040100 and shifting left by 2
>  gives 0x80100400. Hence, this region spans 512 bytes from 0x80100400 to 0x801005FF.**"

**優先序（p.492）：**
> "**The PMP checker examines each of the regions in sequential order to find the first region that matches the
>  physical address. It applies the protection specified by the X, W, R, and L bits for that region.**"

**「循序找第一個匹配的」——所以編號小的優先。**
（Example 11.9，p.494 的說明：「region 15 讓 80000000-FFFFFFFF 全部可存取，
**但權限是循序評估的，所以編號較小的 region 2、4、5、6 優先且更嚴格。**」）

**重置行為與必要設定（p.493–494）：**
> "**At reset, all PMP regions are OFF; so all accesses are granted to M-mode and denied to S- and U-mode
>  (if PMP is supported).**"
> "**If physical memory protection (PMP) is implemented, at least one region must be configured before entering
>  supervisor or user mode; otherwise, all instruction fetches and data accesses will trap. A simple
>  configuration is to make all memory accessible by setting pmpcfg0 = 0F and pmpaddr0 = all 1s.**"

**這是個實務陷阱：有 PMP 卻沒設定就進 S/U mode → 所有存取都 trap。**

### 九種記憶體例外

> "**RISC-V has nine types of memory exceptions: three flavors (access, page, misaligned) for each of three
>  types of accesses (instruction, load, store/AMO).**"
> — p.494

中文解釋：**3 × 3 = 9 種，很整齊的分類。**

**三種 flavor 的成因與處理：**

| Flavor | 成因 | Handler 通常怎麼做 |
| --- | --- | --- |
| **Access fault** | **非法存取：不存在的記憶體、寫唯讀記憶體、違反 PMP** | **印錯誤訊息並殺掉 process** |
| **Page fault** | **虛擬記憶體系統偵測到硬體無法處理的問題** | **通常委派給 S-mode handler**：PTE 無效就配置實體 page 並從磁碟抓；也可能設 A/D 位元；**權限不對就殺掉 process** |
| **Misaligned** | 見下 | 見下 |

**Misaligned 的兩種情況（p.494）：**
> "**Instruction-misaligned exceptions only occur when the address is an odd multiple of 2 and compressed
>  instructions are not supported. The handler should kill the process. Load-misaligned and Store/AMO-misaligned
>  exceptions occur when the data address is not a multiple of the access size and the core does not have
>  hardware support for misaligned accesses.... When a misaligned access is not handled in hardware, the
>  processor throws an exception, and the handler may issue a sequence of accesses to emulate the misaligned
>  access. If the PMA Aligned attribute is 1, then a misaligned access can throw an access-fault instead.
>  For example, peripherals may only support aligned accesses even though main memory supports misaligned
>  accesses.**"

**注意最後一句：同一個未對齊存取，對主記憶體可能是 misaligned exception，
對周邊可能是 access fault。**

### Fences

> "**The `sfence.vma` instruction invalidates all TLB entries. The OS should use `sfence.vma` after modifying
>  the page tables to ensure that programs see the new page tables rather than stale entries in the TLB.**"
> — p.495

> "**If both PMP and virtual memory are implemented, the TLB may cache PMP permissions, even in M-mode, when
>  virtual memory is not active. In this situation, the firmware must also issue a `sfence.vma` after updating
>  PMP CSRs.**"
> — p.495

中文解釋：**兩個使用時機：改頁表後、以及改 PMP CSR 後。**

**第二個容易忘記：TLB 可能 cache 了 PMP 權限，即使在 M-mode。**

### HPTW

> "**An OS expects a hardware page table walker (HPTW) to handle TLB misses. The RISC-V Ssccptr
>  (*supervisor cacheable coherent page table read*) extension indicates that the HPTW can access any main
>  memory region. Wally's HPTW supports this feature. The HPTW is located in the LSU, but it handles misses
>  from both the data and instruction TLBs (DTLB and ITLB).**"
> — p.495

中文解釋：**一個 HPTW 服務兩個 TLB**（放在 LSU 裡）。
**理由在 11.4 節（p.496）：「只需要一個 HPTW，
因為透過匯流排介面一次只能服務一個 miss。」**

## 所以呢

**這節是 RISC-V 虛擬記憶體與保護的完整規格。五件最該帶走的事：**

1. **三種模式的選擇**：**Sv39 最常用**（夠用、省空間、走訪快）；
   **RV64 的虛擬位址高位元必須全 0 或全 1**（user 在低位、OS 在高位）。

2. **PTE 的 `XWR = 000` 表示「這是指標不是 leaf」**——
   這一個編碼撐起了整個多層頁表機制，**而 `XWR ≠ 000` 的高層 PTE 就是 superpage。**

3. **三個保護機制的分工**：
   **PMA（設計時硬接，管裝置屬性）、PMP（軟體組態，管特權存取）、
   虛擬記憶體（每 process 的頁表權限）。**
   **PMP 的陷阱：有 PMP 卻沒設定就進 S/U mode → 全部 trap。**

4. **Idempotency 是個容易忽略但重要的屬性**——
   非冪等的周邊（如 UART 接收緩衝器）不能被推測性存取。

5. **`sfence.vma` 有兩個使用時機**：改頁表後、**以及改 PMP CSR 後**
   （因為 TLB 可能 cache 了 PMP 權限）。
