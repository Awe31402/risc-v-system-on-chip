## 關鍵點

### MMU 的職責

> "**The *memory management unit* (MMU) is responsible for handling virtual memory and memory protection.
>  This allows the programmer to write a program as if it has a large amount of memory that cannot conflict
>  with memory from other programs and makes it more difficult for malicious programs to steal information
>  from other programs.**"
> — p.469

中文解釋：**兩個目標：容量的幻覺 + 隔離保護。**

**Wally 的三個元件（p.469）：**
> "**Wally implements these features using two MMUs, one in the instruction fetch unit (IFU) and one in the
>  load/store unit (LSU). Wally also includes a single hardware page table walker (HPTW) to efficiently
>  fetch page table entries (PTEs).**"

**兩個 MMU（IFU 和 LSU 各一）+ 一個共用的 HPTW。**

**兩個記憶體檢查器（p.469）：
physical memory attributes（PMA）checker 和 physical memory protection（PMP）checker。**

### 物理定址的四個問題

> "In a simple computer system without virtual memory, a process (i.e., a running program) directly
>  specifies the address of main memory that it wishes to access; this is called *physical addressing*."
> — p.469

中文解釋：**四個問題（p.469–470），每一個都被虛擬記憶體解決：**

| 問題 | 說明 |
| --- | --- |
| **Relocation（重定位）** | **每個 process 必須載入到記憶體中的空位，所有位址參照都要跟著改** |
| **Fragmentation（碎片化）** | 一個 process 結束後留下的空間可能太小，別的 process 放不下 |
| **Overlays（覆蓋）** | **process 可能太大放不進記憶體 → 早期要程式設計師手動在記憶體和磁碟間搬運** |
| **缺乏 protection** | **一個 process 可能意外寫到另一個的記憶體造成兩者當掉，
或惡意程式從另一個 process 的記憶體空間偷密碼** |

### 虛擬記憶體：一個優雅的解法

> "***Virtual memory* is an elegant solution to all these problems. With virtual memory, each process is
>  given its own *virtual address (VA) space*, so the process has an illusion of a large, private,
>  contiguous memory. Therefore, the process can be loaded at an address determined at compile/link time and
>  does not require relocation. Because virtual addresses are private to the process, memory is protected
>  from interference by other processes.**"
> — p.470

中文解釋：**一個機制解決四個問題：**

| 問題 | 怎麼被解決 |
| --- | --- |
| Relocation | **每個 process 有自己的虛擬位址空間，編譯時決定的位址永遠有效** |
| **Fragmentation** | **page 大小固定，所以不會有碎片** |
| **Overlays** | **OS 自動在虛擬（硬碟）和主記憶體間搬 page，程式設計師不用管** |
| Protection | **虛擬位址是 process 私有的** |

**Physical memory 是 virtual memory 的 cache（p.470）：**
> "**The virtual memory used by each process can be kept on the hard drive. Hard drives provide vast amounts
>  of inexpensive storage, but are painfully slow, so computers use main memory (usually DRAM) to cache the
>  commonly accessed virtual memory. This cache is called *physical memory*.**"

**這個類比很重要：主記憶體之於虛擬記憶體，就像 cache 之於主記憶體。
page 就是 cache line。**

**額外的好處（p.470）：**
> "**A process may have multiple threads that all share the same virtual address space, so communication
>  between threads within a process is easier than communication between processes.**"

**（p.470 的歷史：**虛擬記憶體由 **Tom Kilburn 和團隊為曼徹斯特大學的 Atlas 電腦發明**
[Kilburn62]。Atlas 有 16,000 個 50-bit 字的快速磁芯記憶體（0.4 μs 存取）、
96,000 字的較便宜磁鼓記憶體（4 μs）、以及大量磁帶儲存（平均 88 μs/字）。**）

**（p.470–471 的軟體落後史，和第 8.1.1 節呼應：**
Intel 80286 在 **1982** 年就加了 x86 的虛擬記憶體硬體支援，
**但 PC 作業系統落後了將近二十年**。
Windows 3.11（1992）和 Mac MultiFinder（1987）用**沒有保護的協同多工**，
所有程式共用同一個位址空間——**一個程式的 bug 可以讓整台電腦當掉，而且這不罕見**。
Windows NT 自 1993 年支援虛擬記憶體但和許多熱門程式不相容。
**Windows 2000 和 Mac OS X 才把記憶體保護和先佔式多工帶給主流 PC。**）

### Pages：固定大小的區塊

> "**Let the *page size* be P = 2^p bytes. Let a virtual address consist of n bits and a physical address
>  consist of m bits, corresponding to N = 2^n and M = 2^m bytes of virtual and physical address space,
>  respectively.**"
> — p.471

中文解釋：**符號定義要記住，後面的計算都用它：**

| 符號 | 意義 | 典型值 |
| --- | --- | --- |
| **p** | page size 的位元數 | **12（4 KiB）** |
| **n** | 虛擬位址位元數 | 32 或 64 |
| **m** | 實體位址位元數 | 34（RV32）或 56（RV64） |

**每個 process 有 2^(n−p) 個虛擬 page，系統有 2^(m−p) 個實體 page。**

**Page size 的取捨（p.471）：**
> "**Like a larger cache line size, a larger page size takes advantage of spatial locality and has less
>  overhead on a miss but greater penalties on a miss. Because disks have long latency but decent bandwidth,
>  the page size should be large for highest performance. Most processors and operating systems have
>  standardized on P = 4-KiB page sizes (p = 12 bits).**"

**書上的計算例（p.471）：M = 16 GiB 主記憶體 → m = 34 → 2^(34−12) = 2^22 個實體 page。**

**三種 page 狀態（p.471）：**

| 狀態 | 意義 |
| --- | --- |
| **Unallocated** | **沒有資料，不佔磁碟空間** |
| **Cached** | 已配置且目前在實體記憶體裡 |
| **Uncached** | 已配置但目前在磁碟上 |

**（p.471 邊欄：**「有些系統用 *resident* 和 *nonresident* 取代 cached/uncached。」
以及：**「硬碟上保留給 uncached 虛擬 page 的區域叫 *swap space*。」**）

### 頁表與位址轉譯

> "**The MMU uses a *page table* to perform address translation between virtual and physical pages, which are
>  uniquely identified by virtual and physical page numbers (VPNs and PPNs), respectively. The page table has
>  one *page table entry* (PTE) for each virtual page.**"
> — p.471–472

中文解釋：**位址的兩段（Fig. 11.3，p.473）：**
```
虛擬位址：┌── VPN (n−p bits) ──┬── Page Offset (p bits) ──┐
                    ↓ Translation        ↓ （不用轉譯）
實體位址：┌── PPN (m−p bits) ──┴── Page Offset (p bits) ──┘
```

**關鍵：page offset 在虛擬和實體位址中完全相同，不需要轉譯。**
（**這個性質是 11.1.1.7 節那個最佳化的基礎。**）

**Example 11.1（p.472）：**
> "Suppose a program accesses virtual address 0x00005028.... **the VPN is the upper 32 − 12 = 20 bits of the
>  virtual address: 0x00005. The page offset is the bottom 12 bits, 0x028. According to the page table,
>  virtual page 5 maps to physical page 1. Hence, the 34-bit physical address is 0x000001028.**"

### Page Fault

> "**If a process accesses a virtual page that is in the uncached or unallocated state, then a *page fault*
>  occurs, and the system must fetch the page from disk. The processor takes a *page fault exception*.
>  The OS handles the exception by reading the desired virtual page from disk, placing it into an empty
>  physical page in main memory, and updating the PTE to the cached state with the proper PPN.
>  The exception then returns to the interrupted instruction, which executes again and gets a page hit on the
>  second try.**"
> — p.472–473

中文解釋：**流程：trap → OS 從磁碟讀 page → 放進空的實體 page → 更新 PTE →
返回並重跑那條指令。**

**「重跑那條指令」正是 8.1.2 節說的 precise trap 的用途。**

**替換策略（p.473）：**
> "**If the physical memory is completely full, the OS must choose a physical page to replace. If this
>  *victim* page is *dirty*, the OS must write it back to disk. As in a regular cache, one might choose the
>  least recently used (LRU) page. But determining true LRU is expensive, so the system may use a heuristic
>  that approximates LRU. The PTEs typically contain additional state to keep track of whether the page is
>  dirty or has been accessed recently.**"

**和 cache 完全平行：victim、dirty、LRU 近似。
PTE 裡的 A（accessed）和 D（dirty）位元就是給 OS 做這件事的。**

### Protection

> "**Page table entries usually have additional bits to indicate whether a page is writable or executable and
>  what privilege level(s) can access it. For example, code pages should not be writable, and data pages
>  should not be executable so that a virus can't use a buffer overflow attack to inject bad instructions.
>  The page tables must not be writable in user mode, lest the program rewrite its own page table to change
>  this protection or to access another program's physical memory.**"
> — p.473

中文解釋：**三條保護規則，每一條都對應一種攻擊：**

| 規則 | 防什麼 |
| --- | --- |
| **程式碼 page 不可寫** | 防止程式被竄改 |
| **資料 page 不可執行** | **防止 buffer overflow 注入指令**（這是最經典的攻擊手法） |
| **頁表在 user mode 不可寫** | **防止程式改自己的頁表來繞過保護或存取別人的記憶體** |

### 多層頁表：解決頁表太大

> "**The full page table described above can be unreasonably large. Because most processes use only a tiny
>  fraction of the virtual address space, most PTEs contain unallocated pages and are unnecessary.**"
> — p.473

**Example 11.2（p.474）的計算很有說服力：**
> "Determine the size of the page table for n = 32-bit and n = 64-bit virtual addresses with 4-KiB pages.
>
> **Solution:** The page table has 2^(n−p) entries, with p = 12. So, the number of entries is
> **2^(32−12) = 2^20 for n = 32 and 2^(64−12) = 2^52 for n = 64.**
> Each PTE must be large enough to hold the PPN and some status bits and, as a practical matter, should be
> word aligned. Thus, each PTE is typically one word, 4 bytes in a 32-bit system and 8 bytes in a 64-bit
> system. Hence, the page table size is **4 bytes × 2^20 = 4 MiB in the 32-bit system and
> 8 bytes × 2^52 = 32 PiB in the 64-bit system.**"

**32-bit 系統的頁表要 4 MiB（勉強可接受），64-bit 要 32 PiB（完全不可能）。**

**多層頁表的原理（p.474）：**
> "**In a 2-level page table, the upper bits of the virtual address are used to choose an entry from a level
>  1 page table, which points to a level 0 page table. The lower bits of the virtual address are used to
>  index into the level 0 page table and choose a PTE, which contains the PPN and status bits.
>  If only a small part of virtual memory is used, most of the level 0 page tables contain only unallocated
>  pages. In such a case, the level 1 PTE is marked NULL (not valid), and the level 0 page table does not
>  even exist.**"

**關鍵：用不到的 level 0 頁表根本不存在。**

**（p.474 邊欄的命名提醒：**「**root（最頂層）頁表有最大的層級編號，
而最低層的頁表（含 PPN）是 level 0。**」——**編號方向和直覺相反。**）

**設計慣例（p.474）：**
> "**Each page table is typically chosen to fill one page. Only the top-level page table need be in main
>  memory at all times. Some pages of the lower levels could themselves be uncached and loaded from secondary
>  storage only upon demand.**"

**Example 11.3（p.474）的計算展示了多層頁表的威力：**
> "Consider the 2-level page table in Fig. 11.4 for n = 32 with 4-KiB pages.... Suppose the virtual memory has
>  2,048 (2^11) pages allocated at the bottom of the address space for code and an upward-growing heap, then a
>  large gap, then one page for a downward-growing stack, and nothing above. Determine the size of the page
>  table.
>
> **Solution:** The level 1 page table occupies 1 page (4 KiB) because it contains 2^10 4-byte entries.
> Similarly, each level 0 page table occupies 1 page. **With only 3 active level 0 page tables (2 for the 2^11
> virtual pages of code and heap and 1 for the single page allocated to the stack), the overall page table
> size is 4 pages = 4 × 4 KiB = 16 KiB.**"

**從 4 MiB 降到 16 KiB——縮小 256 倍。**

### TLB：解決存取太慢

> "**A virtual memory system with a k-level page table adds k page table accesses to every memory access,
>  which reduces performance dramatically. The MMU mostly avoids this penalty by using a small cache of
>  recent virtual-to-physical page number translations, called a *translation lookaside buffer* (TLB).
>  A small (e.g., 128-entry) fully associative TLB can achieve a hit rate of better than 99% on many
>  applications, and a larger TLB may achieve 99.99%.**"
> — p.474–475

中文解釋：**問題：k 層頁表 = 每次記憶體存取多 k 次存取。**
**解法：TLB，一個轉譯結果的小 cache。**

**命中率驚人：128 項的 fully associative TLB 就能超過 99%。**

**兩層 TLB（p.475）：**
> "**Some systems use a smaller first-level TLB with single-cycle access and a larger second-level TLB with
>  high hit rate. For example, the AMD Opteron processor uses a 2-level TLB with 40 entries in the fast first
>  level and 512 entries in the second level with 7-cycle latency.**"

**TLB miss 的處理（p.475）：**
> "**Historically, processors would take an exception on a TLB miss. The exception handler would then issue a
>  sequence of page table reads to traverse the multilevel page table to reach the PTE and then put this
>  entry in the TLB and return to the program. This is slow to do in software, so most modern processors have
>  *hardware page table walkers* (HPTWs), which are state machines that issue the page table reads.**"

**從軟體處理演進到硬體 HPTW。**

### 可變 Page 大小

> "**A program that accesses widely separated portions of a large data structure may touch many different
>  pages, causing the TLB to quickly run out of capacity and frequently miss. Thus, most architectures support
>  more than one page size. For example, x86-64 supports 4-KiB, 2-MiB, and 1-GiB pages.
>  Pages bigger than 4 KiB are called *large pages*, *huge pages*, or *superpages*.**"
> — p.475

中文解釋：**動機：大資料結構會用掉太多 TLB 項目。**

**取捨（p.476）：**
> "**These larger pages save space in the TLB and in the page tables. They make efficient use of disks or
>  networks that achieve peak bandwidth when transferring large contiguous chunks. However, the latency of
>  paging these superpages in and out is high. Also, the OS must make a more complex decision of whether to
>  allocate one superpage or many smaller pages.**"

| 好處 | 壞處 |
| --- | --- |
| **省 TLB 和頁表空間** | **換頁的延遲高** |
| 大塊連續傳輸對磁碟/網路效率好 | **OS 要做更複雜的配置決策** |

### Process、虛擬記憶體、Cache 的交互作用

**（1）Context switch 與 PID（p.476）**
> "**The TLB must adjust translations for different processes as well. One solution is to flush the TLB on
>  each context switch, but this incurs a performance penalty reloading the TLB. A higher-performance design
>  adds a *process ID* (PID) field to each TLB entry so that translations for multiple processes can coexist.
>  Some parts of memory, such as the OS or I/O peripherals, may belong to a *global address space* and thus be
>  accessible by any process at the same virtual address. The TLB may include a global bit to indicate that
>  these PTEs apply to all PIDs.**"

**兩個機制：PID 欄位（讓多個 process 的轉譯共存）和 global 位元（OS 的 page 對所有 PID 都適用）。**

**（2）共享記憶體（p.476）**
> "**More than one process can access shared variables by configuring their page tables to point to a shared
>  physical page. Thus, different virtual addresses can translate to the same physical address.**"

**（3）Synonym problem（同義問題）——這段是本節最重要的技術內容**
> "**Programs use virtual addresses, so, ideally, cache accesses also use virtual addresses before they are
>  translated to physical addresses. However, this is complicated because the same virtual address in
>  different processes could correspond to different physical addresses, and different virtual addresses in
>  different processes could *alias* to the same physical address. This is known as the *synonym problem*.**"

**兩個方向的問題：**
- **同一個虛擬位址在不同 process 對應不同實體位址**
- **不同虛擬位址可能 alias 到同一個實體位址**

**解法：virtually indexed, physically tagged cache（p.476）——這段要完全理解：**
> "**most systems avoid the problem entirely by using *virtually indexed, physically tagged* caches with a way
>  size less than or equal to the page size (usually both 4 KiB). A processor accesses the L1 cache using the
>  set bits from the page offset, which are not translated. The TLB is accessed concurrently with the L1
>  cache. After they are both read, the physical address from the TLB is checked against the physical address
>  tag from the cache line.**"

**機制的核心：**
```
1. page offset 不需要轉譯（虛擬和實體相同）
2. 如果 way size ≤ page size，那 set 位元就全部落在 page offset 裡
3. → 可以用虛擬位址直接索引 cache，不必等 TLB
4. TLB 和 cache 同時存取
5. 兩者都讀出後，用 TLB 給的實體位址和 cache 的 tag 比對
```

**這就是「虛擬索引、實體標記」——索引快（不用等轉譯），標記正確（用實體位址比對）。**

**（Fig. 11.5（p.477）畫出這個平行存取：
虛擬位址的 VPN 加 PID 送進 TLB，page offset 送進 L1$；
TLB 輸出 PPN，cache 輸出 Tag，兩者比較得到 Cache Hit；
TLB miss 則送給 HPTW。）**

**為什麼 L1 cache 的 way 不能超過 page size（p.476）：**
> "**Page offsets are normally 12 bits, which limits each L1 cache way to 4 KiB. Larger L1 caches use
>  associativity; for example, the Intel Haswell 32 KiB cache with 4-KiB ways is 8-way set associative.
>  This limitation doesn't apply to higher-level caches because the physical address is available by the time
>  an L1 cache miss is discovered.**"

**這就是第 10 章那條規則的完整理由。而且注意最後一句：
高層 cache 沒有這個限制，因為 L1 miss 時實體位址已經算出來了。**

**Associativity 的成本上限（p.476–477）：**
> "**Increasing associativity costs power (more RAMs to access concurrently) and time (a larger way mux).
>  Some designs find 4-way associativity is a practical limit, restricting physically tagged virtually indexed
>  L1 caches to 16 KiB.**"

**4-way × 4 KiB = 16 KiB 是實務上的 L1 上限。**

**兩個替代解法（p.477）：**
| 方法 | 做法 | 用例 |
| --- | --- | --- |
| **Hardware anti-aliasing** | **cache miss 時檢查所有可能位置有沒有 alias，有就 invalidate** | AMD Opteron 64 KiB 2-way cache（32-KiB page） |
| **Page coloring** | **OS 把 alias 的 page 配置到「低位元相同」的實體位址** | 例如 2^16-byte cache 中相同的低 16 位元 |

### 實體記憶體檢查

> "**A processor with memory-mapped I/O needs to route physical memory accesses to the appropriate device.
>  For example, a range of physical memory addresses correspond to main memory (DRAM), but other ranges could
>  correspond to a UART..., GPIO..., CLINT..., PLIC.... Reserved addresses outside of mapped ranges should
>  cause an illegal address exception. Moreover, the processor may need to know attributes about each of the
>  devices, such as whether the values are cacheable (yes for memory, no for most peripherals) or whether only
>  certain-sized memory accesses are supported.**"
> — p.477

中文解釋：**PMA 要回答三個問題：**
1. **這個位址對應哪個裝置？**（保留位址要拋例外）
2. **可以 cache 嗎？**（記憶體可以，多數周邊不行——呼應 10.2 節）
3. **支援哪些存取大小？**

**額外的需求（p.478）：**
> "**Some of these addresses or attributes may change when new devices are plugged into the system. Moreover,
>  certain physical addresses may only be accessed in a privileged mode for added security. Hence, most systems
>  require some configurable checking of physical memory addresses in hardware; the details vary significantly
>  between architectures.**"

**兩個理由需要「可組態」的檢查：裝置可能熱插拔、某些位址只能在特權模式存取。**

**（p.478 邊欄的經典引言，呼應 1.4 節和 2.5 節：**
> "**There is only one mistake that can be made in computer design that is difficult to recover from —
>  not having enough address bits for memory addressing and memory management. The PDP-11 followed the unbroken
>  tradition of nearly every known computer**" [Bell76].

**「電腦設計唯一難以挽回的錯誤，就是位址位元給得不夠。」**
邊欄也說明了 PDP-11 的下場：**記憶體很快就大到 16 位元裝不下，
PDP-11 架構無法優雅地演進到更寬的位址，所以快速過時，被更成功的 VAX-11 取代。**）

## 名詞表

| 名詞 | 意思 |
| --- | --- |
| **MMU** | 記憶體管理單元。處理虛擬記憶體與記憶體保護 |
| Relocation / fragmentation / overlays | 重定位 / 碎片化 / 覆蓋——物理定址的三個問題 |
| **Virtual address (VA) space** | 每個 process 私有的位址空間 |
| **Physical memory** | 主記憶體，**作為虛擬記憶體（磁碟）的 cache** |
| **Page** | 固定大小的區塊（通常 4 KiB），類比於 cache line |
| Swap space | 硬碟上保留給 uncached 虛擬 page 的區域 |
| Unallocated / cached / uncached | 未配置 / 在實體記憶體中 / 在磁碟上（也叫 resident / nonresident） |
| **VPN / PPN / page offset** | 虛擬頁號 / 實體頁號 / **頁內偏移（虛擬與實體相同，不需轉譯）** |
| **PTE** | Page table entry。含狀態位元和 PPN |
| **Page fault** | 存取 uncached 或 unallocated 的 page；OS 從磁碟載入後重跑該指令 |
| **多層頁表** | **用不到的低層頁表根本不存在**；root 是最高層級編號，**level 0 含 PPN** |
| **TLB** | Translation lookaside buffer。轉譯結果的小 cache；**128 項 fully associative 可達 99% 命中率** |
| **HPTW** | Hardware page table walker。硬體走訪頁表的狀態機 |
| Superpage / large page / huge page | 大於 4 KiB 的 page；省 TLB 空間但換頁延遲高 |
| **PID / global bit** | Process ID 讓多 process 的轉譯共存 / 標記對所有 PID 適用的 page |
| **Synonym problem** | 同義問題：同 VA 對應不同 PA，或不同 VA alias 到同 PA |
| **Virtually indexed, physically tagged** | **用未轉譯的 page offset 索引 cache、用 TLB 的 PA 比對 tag；TLB 與 cache 平行存取** |
| Anti-aliasing / page coloring | 硬體檢查並 invalidate alias / OS 把 alias page 配置到低位元相同的 PA |
| **PMA / PMP** | Physical memory attributes（**位址對應哪個裝置、可否 cache、支援哪些大小**）/ physical memory protection |

## 所以呢

**這節建立了虛擬記憶體的完整理論。四件最該帶走的事：**

1. **虛擬記憶體用一個機制解決四個問題**：
   relocation（私有位址空間）、fragmentation（固定 page 大小）、
   overlays（OS 自動換頁）、protection（位址私有 + PTE 權限位元）。

2. **兩個「太大/太慢」問題和它們的解法**：
   **頁表太大 → 多層頁表**（64-bit 從 32 PiB 降到 16 KiB）；
   **存取太慢 → TLB**（128 項就有 99% 命中率）。

3. **`virtually indexed, physically tagged` cache 是第 10 章那條規則的完整理由**：
   **page offset 不需轉譯 → way size ≤ page size 時 set 位元全在 offset 裡
   → cache 和 TLB 可以平行存取。**
   **這也限制了 L1 way size ≤ 4 KiB，實務上 L1 上限約 16 KiB（4-way）。**

4. **PMA 檢查器回答三個問題**：位址對應哪個裝置、可不可以 cache、支援哪些存取大小。
   **周邊不可 cache——因為它們的值會因外部事件改變。**
