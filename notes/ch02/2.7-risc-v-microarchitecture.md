# 2.7 RISC-V Microarchitecture

> 原書 p.56–70（Chapter 2: Introduction to RISC-V）
> 涵蓋 2.7.1 Single-Cycle、2.7.2 Pipelined、2.7.3 Verification

## 這節在講什麼

**第一次動手做處理器。** 這節是整本書的縮影——
用一個極簡的 RV32I 子集（只支援 13 條指令），把整個設計流程走一遍：
**單週期微架構 → pipeline 微架構 → SystemVerilog 實作 → 驗證。**

三個階段各自的重點：
- **單週期**：建立資料通路（datapath）和控制器（controller）的基本結構。CPI = 1，但時脈很慢。
- **Pipeline**：插入暫存器切成五級，時脈快 5 倍，但引入 **hazard**（危障）問題。
- **驗證**：寫測試程式和 testbench 驗證正確性。

**這節的內容在第 7 章會完整重做一次**，所以現在的目標是建立整體圖像，不是記住細節。

## 關鍵點

### 微架構規格書：從 ISA 到 HDL 的中間文件

> "Recall that microarchitecture is the interconnection of gates and registers that
>  implement an architecture. Many microarchitectures may exist for a given
>  architecture. Design teams write a *microarchitecture specification* describing
>  the microarchitecture in enough detail that a logic designer can write hardware
>  description language (HDL) code based on the spec."
> — p.56

中文解釋：呼應 1.2 節的 architecture / microarchitecture 分離。
**這裡多了一個實務環節：microarchitecture specification（微架構規格書）。**

流程是：**ISA 規格 → 微架構規格書 → HDL 程式碼**。
中間這份文件的功能是「詳細到讓邏輯設計師能照著寫 HDL」。
**Fig. 2.9 那張方塊圖就是微架構規格書的核心內容。**

### 這次要做的 13 條指令

> "This section and the next explore microarchitectures for a simplified RV32I core
>  that supports the following instructions:
>  - ALU Instructions: add, sub, and, or, slt, addi, andi, ori, slti
>  - Memory Instructions: lw, sw
>  - Branch Instructions: beq, jal"
> — p.56

中文解釋：**13 條指令，但涵蓋了全部六種格式中的五種**（R、I、S、B、J），
所以資料通路的結構是完整的。這是很聰明的教學設計——
**用最少的指令涵蓋最多的結構種類。**

（少的是 U-type（`lui`/`auipc`）和乘除、浮點等擴充。）

### 架構狀態 vs 非架構狀態

> "All microarchitectures must include the architectural state (memory, PC, and
>  registers). Some microarchitectures may include other *nonarchitectural state*,
>  such as pipeline registers, caches, or branch history, to make the processor run
>  faster. However, this information could be flushed, and the processor will still
>  restart correctly based on the architectural state."
> — p.56

中文解釋：**這是理解整本書的關鍵區分，而且判準非常清楚：**

| | 內容 | 判準 |
| --- | --- | --- |
| **架構狀態** | 記憶體、PC、暫存器（+ CSR） | **丟掉就錯了** |
| **非架構狀態** | pipeline 暫存器、cache、分支歷史 | **丟掉還是對的，只是變慢** |

**「能不能 flush 掉還正確」就是判準。**

這個區分在後面極度重要：
- **第 7 章 pipeline**：hazard 發生時可以 flush pipeline 暫存器
- **第 10 章 cache**：cache 可以清空，因為資料在記憶體裡還有
- **第 14 章亂序執行**：推測執行猜錯了整批丟掉

**所有「加速用的東西」都必須是非架構狀態**——否則出錯就無法恢復。

（2.3 節提過 context switch 要存的就是架構狀態。）

### 效能公式與兩種微架構的取捨

> "T_CPU = #instructions × CPI × T_c"
> — Eq. (2.1), p.56

> "The single-cycle microarchitecture executes one instruction in each clock cycle;
>  that is, CPI = 1. It is simple but slow because the clock period is long.
>  The pipelined microarchitecture uses a 5-stage pipeline so that five instructions
>  can overlap their execution and the clock period T_c can be much shorter.
>  This comes at the expense of pipeline registers and hardware to detect for
>  dependencies and resolve them through forwarding and stalls; the stalls increase
>  the CPI somewhat."
> — p.56

中文解釋：**這就是 1.6 節那個「執行時間 = 指令數 × CPI × 週期時間」公式的實際應用。**
注意**指令數由 ISA 和編譯器決定，微架構只能動後兩項**。

兩種設計的取捨：

| | CPI | T_c | 代價 |
| --- | --- | --- | --- |
| **單週期** | **1**（最理想） | **很長**（一條指令要跑完整條路徑） | 簡單但慢 |
| **5 級 pipeline** | 略大於 1（stall 造成） | **短很多**（理想是 1/5） | pipeline 暫存器 + hazard 偵測硬體 |

**pipeline 的本質是「犧牲一點 CPI 去換大幅縮短 T_c」。**
淨效果是贏的，但不是免費的 5 倍。

### 三大單元：IFU、IEU、LSU

> "The core is partitioned into an *instruction fetch unit* (IFU), *integer execution
>  unit* (IEU), and *load/store unit* (LSU). The IFU contains the PC, IROM, and the
>  logic to increment the PC or handle branches and jumps. The IEU contains the
>  *integer register file* (IRF), the datapath with an ALU, the branch comparator,
>  and multiplexers to handle arithmetic instructions and memory/branch address
>  generation, and a controller to decode instructions. The LSU contains the
>  *data tightly-integrated memory* (DTIM) used for loads and stores."
> — p.56–57

中文解釋：**這三個單元的劃分會貫穿整本書**，先記熟：

| 單元 | 全名 | 裡面有什麼 | 負責 |
| --- | --- | --- | --- |
| **IFU** | Instruction Fetch Unit | PC、IROM、PC 遞增與分支跳躍邏輯 | **抓指令、決定下一條在哪** |
| **IEU** | Integer Execution Unit | 暫存器檔案（IRF）、ALU、比較器、多工器、控制器 | **解碼、運算** |
| **LSU** | Load/Store Unit | DTIM | **存取資料記憶體** |

Fig. 2.9（p.58）是單週期處理器的方塊圖，三個單元用不同色塊框起來。
書上也說明了圖的畫法慣例（p.57）：
**粗線 = XLEN 寬的匯流排（32 或 64 bit），中線 = 較窄的多位元訊號，細線 = 1-bit 訊號。**
——看這本書所有電路圖都適用這個慣例。

### Harvard vs von Neumann：為什麼有兩個記憶體

> "A processor with a unified memory containing instructions and data is called a
>  *von Neumann architecture*... A processor with separate instruction and data
>  memories is called a *Harvard architecture*... von Neumann architectures are more
>  flexible because they allow for not only loading but also modifying programs, but
>  they are slower because separate cycles are needed to access an instruction and
>  then the data."
> — p.57 邊欄

> "Modern computers generally gain the advantages of both architectures by using a
>  single unified main memory but separate instruction and data caches."
> — p.57 邊欄

中文解釋：**這個單週期處理器有兩個記憶體（IROM 和 DTIM），是 Harvard 架構。**
原因很實際：**單週期要在同一個週期內抓指令又存取資料，
一個記憶體做不到（只有一個 port）。**

但 Harvard 有缺點：**程式不能修改自己**（因為指令記憶體是唯讀的），
這讓載入程式、動態連結、JIT 編譯都不可能。

**現代的解法是兩全其美**：主記憶體統一（von Neumann，靈活），
但**指令和資料各有自己的 cache**（Harvard 的速度）。
代價是需要同步機制——**這正是 2.5 節 `fence.i` 指令存在的理由**
（邊欄直接點名："RISC-V uses the fence.i instruction to force this
synchronization, as described in Section 10.4.2.6"）。

另一個邊欄解釋了 DTIM 名字的由來（p.57 邊欄）：
**"tightly integrated"** 是因為它**直接接到 IEU 的位址和資料匯流排，
不經過外部匯流排協定的開銷**——所以快且延遲固定。

### 暫存器檔案的三個埠

> "The register file has three ports: read ports 1 and 2 and write port 3. It
>  receives a 5-bit address for each port (A1, A2, and A3) specifying one of the
>  2^5 = 32 registers. The read ports read the specified registers onto the read data
>  ports (RD1 and RD2). The write port needs to know where to write (A3), what to
>  write (WD3), whether to write (WE3, write enable), and when to write (on the
>  rising edge of clock)."
> — p.57

中文解釋：**三個埠：兩讀一寫。** 這直接對應 2.1 節「最多兩個來源、一個目的」的 ISA 設計。
（呼應 2.6 節：ARM 需要三個讀取埠，所以暫存器檔案更貴。）

**寫入埠需要四樣資訊**，這個清單很值得記：
**寫哪裡（A3）、寫什麼（WD3）、要不要寫（WE3）、什麼時候寫（時脈上升緣）。**
任何同步寫入的元件都是這四樣。

另外：**IROM 只讀，所以只有一個埠；DTIM 由 WE 訊號決定讀或寫。**

### 資料通路的關鍵元件

> "The comparator (comp) asserts Eq if R1 == R2, for beq tests. The sign extender
>  unit (extend) forms the 32-bit ImmExt from the immediate fields of the
>  instruction."
> — p.57

> "The ALU has an adder and various other logic operators. The adder directly drives
>  IEUAdr = PC + ImmExt to the LSU and IFU for fast memory address calculation.
>  ALUResult is selected from the various possible operations according to Table 2.3.
>  The ALUControl signal comprises the {Sub, ALUOp} bits that indicate whether to
>  subtract and whether to consider the funct3 field to determine the operation."
> — p.57

中文解釋：注意 `extend` 模組就是 2.2 節 Fig. 2.4 那張規格的實作。

**ALUControl 只有 2 bit**，Table 2.3（p.58）的真值表：

| Sub | ALUOp | Funct3 | ALUResult |
| --- | --- | --- | --- |
| 0 | 0 | X | **ADD**（強制加法，給 load/store 算位址） |
| 0 | 1 | 000 | ADD |
| 0 | 1 | 110 | OR |
| 0 | 1 | 111 | AND |
| 1 | 1 | 000 | SUB |
| 1 | 1 | 010 | SLT |

**讀法**：`ALUOp = 0` 表示「不管 funct3，就是加法」——
這是給 `lw`/`sw`/`beq` 算位址用的。
`ALUOp = 1` 才看 funct3 決定真正的運算。

**這是一個很典型的控制訊號分層設計**：主解碼器只說「要不要看 funct3」，
細節交給 ALU decoder。這樣主解碼器可以只看 op 欄位，變得很小。

### 逐週期追蹤範例程式

> "Consider running the program from Code Example 2.14 on the RISC-V single-cycle
>  computer starting at address 0x1000."
> — p.57

中文解釋：Code Example 2.14（p.57）的三行程式（x1 初值 0x2000，x2 = 7，位址 0x2004 的內容是 0x2A）：

```asm
start: lw  x3, 4(x1)      # 0x1000    0x0040A183
       sub x5, x3, x2      # 0x1004    0x402182B3
       beq x0, x0, 0x1000  # 0x1008    0xFE000CE3
```

書上逐週期追蹤（p.58–59），**摘出每個週期的關鍵動作**：

**Cycle 1（`lw x3, 4(x1)`）**
- IROM 從 0x1000 讀出指令
- 指令 bit 19:15 = rs1 = 1 → 暫存器檔案的 A1 讀出 x1 = 0x2000 到 R1
- extend 把立即值 4 延伸成 ImmExt = 0x00000004
- 控制器設 `ALUSrc = 10` 選 SrcB = ImmExt、SrcA = R1
- **ALU 算 IEUAdr = 0x2000 + 4 = 0x2004**
- DTIM 從這個位址讀出 ReadData = 0x2A
- 控制器設 `ResultSrc = 1` 選 Result = ReadData，`RegWrite = 1`
  → 時脈上升緣把 0x2A 寫進 x3
- 同時 PCPlus4 = 0x1004，`PCSrc = 0`，所以 PCNext = PCPlus4

**Cycle 2（`sub x5, x3, x2`）**
- 讀 A1 = 3、A2 = 2 → SrcA = 0x2A，SrcB = 7
- ALU 減法：**ALUResult = 0x2A − 7 = 0x23**
- Result mux 選 IEUResult（不是 ReadData）
- 書上有個值得注意的細節：
  **"Note that the data memory reads from this address, too, but the read data is
  not used."** ——**DTIM 還是讀了，只是結果沒被選用。**
  這是單週期設計的常態：所有單元每個週期都在動，只是選擇性使用輸出。

**Cycle 3（`beq x0, x0, 0x1000`）**
- A1 = 0、A2 = 0，**暫存器 0 硬接為 0**，所以比較器 assert `Eq`
- 控制器根據 `beq` + `Eq` 設 `PCSrc = 1`
- extend 產生 ImmExt = 0xFFFFFFF8 = **−8**
- **ALU 算 IEUAdr = PC + ImmExt = 0x1008 − 8 = 0x1000**
- PC mux 選 PCNext = IEUAdr，`RegWrite = 0`（不寫暫存器）
- PC 更新為 0x1000，**無限迴圈**

**這個追蹤最值得學的是「控制訊號怎麼指揮資料流」**——
資料通路是固定的，不同指令只是設不同的多工器選擇訊號。

### 控制器：主解碼器 + ALU 解碼器

> "As we saw in the sample program, the controller must produce appropriate control
>  signals to drive the multiplexers and write enable signals in the datapath to
>  execute the current instruction."
> — p.59

> "PC normally increments by 4, but it skips to the IEUAdr computed by the ALU for
>  jumps and taken branches. The PCSrc logic determines whether this skip should occur."
> — p.60

中文解釋：Fig. 2.10（p.60）顯示控制器分兩塊：
**Main Decoder**（只看 op 欄位）+ **ALU Decoder**（看 funct3、funct7、ALUOp）。

Table 2.4（p.60）主解碼器真值表——**這張表就是控制器的完整規格**：

| Instruction | Op | RegWrite | ImmSrc | ALUSrc | ALUOp | ALUResultSrc | MemWrite | ResultSrc | Branch | Jump |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| `lw` | 0000011 | 1 | 00 | 01 | 0 | 0 | 0 | **1** | 0 | 0 |
| `sw` | 0100011 | **0** | 01 | 01 | 0 | 0 | **1** | 0 | 0 | 0 |
| R-type ALU | 0110011 | 1 | xx | 00 | **1** | 0 | 0 | 0 | 0 | 0 |
| I-type ALU | 0010011 | 1 | 00 | 01 | **1** | 0 | 0 | 0 | 0 | 0 |
| `beq` | 1100011 | **0** | 10 | 11 | 0 | 0 | 0 | 0 | **1** | 0 |
| `jal` | 1101111 | 1 | 11 | 11 | 0 | **1** | 0 | 0 | 0 | **1** |

**讀表的重點**：
- `sw` 和 `beq` 的 `RegWrite = 0`（不寫暫存器，呼應 2.1 節「S 和 B 沒有 rd」）
- `sw` 的 `MemWrite = 1`（唯一一條寫記憶體的）
- `lw` 的 `ResultSrc = 1`（唯一一條結果來自記憶體的）
- **`ImmSrc` 剛好對應 2.2 節 Fig. 2.4 的四種立即值格式**（00=I、01=S、10=B、11=J）

PCSrc 的邏輯很簡單（p.63 的 SystemVerilog）：
```
PCSrc = Branch & Eq | Jump
```
**「是分支而且條件成立，或者是跳躍」** —— 一行就講完了控制流。

ALUControl 的邏輯（p.60）：
```
ALUControl[1] = Sub = ALUOp & ((Funct3 == 3'b000) & Funct7b5 & Op[5] | (Funct3 == 3'b010))
ALUControl[0] = ALUOp
```
其中 `Funct3 == 000 & Funct7b5 & Op[5]` 是 `sub`（要 R-type 才看 funct7，所以要 & Op[5]），
`Funct3 == 010` 是 `slt`。

### Lazy decoder：教學版和正式版的差別

> "Distinguishing subtraction from add, addi, and other ALU instructions requires
>  checking bits from funct3, funct7, and the opcode. This chapter uses a *lazy
>  decoder* that only examines enough bits to distinguish the supported instructions;
>  it produces unpredictable results for illegal instructions. The full Wally decoder
>  uses a precise decoder that raises an illegal-instruction exception for any illegal
>  instruction when exceptions (Zicsr) are supported."
> — p.60 邊欄

中文解釋：**這個區分很重要，避免誤會後面 Wally 的程式碼。**

- **lazy decoder（懶惰解碼器）**：只看「足以分辨支援的指令」的那幾個 bit。
  非法指令的結果無法預測。**教學用，簡單。**
- **precise decoder（精確解碼器）**：完整檢查，非法指令會觸發 illegal-instruction exception。
  **正式的 Wally 用這個**（呼應 2.5 節 profile 建議未實作 opcode 要拋例外）。

### SystemVerilog 實作的模組結構

中文解釋：Code Example 2.15（p.61–65）是完整的單週期處理器 SystemVerilog 程式碼。
**不用細讀，但要看懂模組階層**——它跟方塊圖一一對應：

```
riscvsingle
├── ifu          （PC 暫存器、加法器、PC 多工器、irom）
├── ieu
│   ├── controller  （main decoder + ALU decoder + PCSrc 邏輯）
│   └── datapath
│       ├── regfile
│       ├── extend
│       ├── cmp
│       ├── alu
│       └── 各種 mux2
└── lsu          （DTIM）
```

**"even if you are unfamiliar with the details, you should be able to relate the
modules and their inputs and outputs to the objects in the block diagrams."**（p.61）
——**方塊圖和 HDL 是一對一的。** 這就是第 4 章要教的設計方法。

幾個值得看的片段：

**暫存器檔案（p.64）**——三個要點都在註解裡：
```systemverilog
// Read 2 ports combinationally (A1/RD1, A2/RD2)
// Write port 3 on rising edge of clock (A3/WD3/WE3)
// Register 0 hardwired to 0
always_ff @(posedge clk)
  if (WE3) rf[A3] <= WD3;
assign RD1 = (A1 != 0) ? rf[A1] : 0;
assign RD2 = (A2 != 0) ? rf[A2] : 0;
```
**「讀是組合邏輯、寫是時序邏輯」**，以及 **x0 用一個三元運算子就硬接成 0**。

**extend 模組（p.64）**——直接是 2.2 節 Fig. 2.4 的程式碼版：
```systemverilog
2'b00: ImmExt = {{20{Instr[31]}}, Instr[31:20]};                        // I-type
2'b01: ImmExt = {{20{Instr[31]}}, Instr[31:25], Instr[11:7]};           // S-type
2'b10: ImmExt = {{20{Instr[31]}}, Instr[7], Instr[30:25], Instr[11:8], 1'b0};  // B-type
2'b11: ImmExt = {{12{Instr[31]}}, Instr[19:12], Instr[20], Instr[30:21], 1'b0}; // J-type
```
**注意 B 和 J 結尾都硬接 `1'b0`**——就是 2.1 節那個「最低位元恆為 0」。
而 `{20{Instr[31]}}` 就是「把 bit 31 複製 20 次」的符號延伸。

### Pipeline：切成五級

> "Fig. 2.11 shows how to convert the single-cycle processor into a classic
>  five-stage pipeline by adding registers between stages. The processor executes an
>  instruction across these stages as follows:
>  - Fetch: Reads the instruction from the instruction memory (IROM)
>  - Decode: Decodes the control signals and reads the source registers from the register file
>  - Execute: Performs the ALU operation
>  - Memory: Accesses the data memory to read or write data
>  - Writeback: Writes the result to the register file"
> — p.65

中文解釋：**經典五級 pipeline，縮寫是 F、D、E、M、W。**

| 級 | 做什麼 | 用到哪個單元 |
| --- | --- | --- |
| **F**etch | 從 IROM 讀指令 | IFU |
| **D**ecode | 解碼控制訊號、讀來源暫存器 | IEU |
| **E**xecute | ALU 運算 | IEU |
| **M**emory | 存取資料記憶體 | LSU |
| **W**riteback | 寫回暫存器檔案 | IEU |

**做法非常簡單：在單週期的資料通路中間插入暫存器。**
Fig. 2.11（p.66）就是 Fig. 2.9 加上四排 pipeline 暫存器，
底下多了一個貫穿全圖的 **hazard** 單元。

書上邊欄補充（p.67 邊欄）：**IEU 負責 Decode、Execute、Writeback 三級**——
所以 IEU 在 Fig. 2.11 裡被切成兩塊（圖的左邊和右下角都標了 IEU）。

### 訊號命名慣例：後綴表示所在級

> "Each signal is now annotated with a suffix corresponding to its pipeline stage.
>  Notice how the control signals are also pipelined so they advance along with the
>  instructions they control. Also note how the destination register rd must be
>  pipelined so that the result is written to the proper register in the Writeback
>  stage."
> — p.65–67

中文解釋：**這個命名慣例整本書都在用，一定要習慣：**
`InstrD`（Decode 級的指令）、`ALUResultE`（Execute 級的 ALU 結果）、
`RegWriteW`（Writeback 級的寫入致能）……

**兩個容易忽略但關鍵的點：**
1. **控制訊號也要 pipeline**——`RegWrite` 在 Decode 級產生，
   但要到 Writeback 級才用，所以必須一級一級傳下去（圖上最上面那幾條長線）。
2. **rd 也要 pipeline**（`RdD → RdE → RdM → RdW`）——
   否則寫回時不知道要寫哪個暫存器。

**「指令走到哪，它的控制訊號和目的暫存器編號就要跟到哪」**——
這是 pipeline 設計最容易出錯的地方。

### 暫存器檔案的分半時序技巧

> "The register file writes in the first half of a cycle and reads in the second half,
>  so a value can be written and read back out in the same cycle."
> — p.67

中文解釋：**這是一個很巧妙的技巧。**
Writeback 級（第 5 級）寫暫存器，Decode 級（第 2 級）讀暫存器。
如果一條指令在 W 級寫 x3，同時另一條在 D 級要讀 x3，會讀到舊值。

解法：**前半週期寫、後半週期讀**（用時脈的負緣寫入）。
這樣同一個週期內寫進去的值馬上讀得到。

**這等於免費解掉了「相隔 3 條指令」的資料相依**，
剩下的才需要 forwarding 處理。

### 理想 5 倍，實際達不到

> "Only one major operation (ALU, memory, or register file access) occurs in each
>  stage, so the cycle time is substantially faster—ideally, 5x if not for the
>  sequencing overhead of the extra registers and the inability to perfectly balance
>  each stage of the pipeline."
> — p.67

中文解釋：**兩個讓 5 倍達不到的原因要記住：**
1. **sequencing overhead**：pipeline 暫存器本身有 setup time 和 clk-to-Q 延遲，
   每一級都要付一次。切越細，這個固定開銷佔比越高。
2. **無法完美平衡**：時脈由**最慢的那一級**決定。
   如果記憶體存取比 ALU 慢，其他級再快也沒用。

**這解釋了 1.6 節為什麼 Pentium 4 做到 31 級卻沒有變快 31 倍**——
第 1 點的開銷會吃掉一切，第 2 點也有極限。

### Hazard：pipeline 的代價

> "The pipelined processor design is complicated by *pipeline hazards* that arise
>  when one instruction depends on another that is still in the pipeline. The two
>  main types of hazards are data hazards and control hazards."
> — p.67

> "*Data hazards* are caused by pipeline delays in reading and writing registers.
>  Some data hazards can be solved by *forwarding* results from a previous instruction,
>  and others require *stalling* the pipeline."
> — p.67

> "*Control hazards* occur when the decision of what instruction to fetch next has
>  not been made by the time the fetch takes place. A branch predictor addresses
>  control hazards by guessing which instruction should be fetched next; if the guess
>  is wrong, the processor must *flush* the incorrect instructions and restart with
>  the correct one."
> — p.67

中文解釋：**兩種 hazard 和三種解法，整理成一張表：**

| Hazard 類型 | 原因 | 解法 |
| --- | --- | --- |
| **Data hazard**（資料危障） | 前一條指令的結果還沒寫回，後一條就要讀 | **forwarding**（把結果直接從中途接過去）；不夠的話 **stall**（暫停） |
| **Control hazard**（控制危障） | 還不知道分支結果，就得抓下一條指令了 | **branch predictor**（猜）；猜錯就 **flush**（把錯的指令清掉） |

**三種手段的成本不同**：
- **forwarding**：加多工器和接線，**不損失效能**（最好的解法）
- **stall**：插入氣泡，**CPI 上升**
- **flush**：丟掉已做的工作，**CPI 上升更多**（pipeline 越深損失越大——呼應 1.6 節）

Fig. 2.11（p.66）上可以看到這些機制的硬體：
Execute 級前面的 `ForwardAE` / `ForwardBE` 多工器，
以及底部橫貫全圖的 **hazard 單元**，輸出 `StallF`、`StallD`、`FlushD`、
`StallE`、`FlushE`、`StallM`、`FlushM`、`StallW`、`FlushW`。
**每一級都可以被個別 stall 或 flush。**

（`flush` 掉的都是非架構狀態——呼應前面那個區分。）

細節在第 7.2.2 節。

### 驗證：先寫測試程式

> "All hardware requires logic verification to catch the bugs and gain some
>  confidence that the design is correct."
> — p.67

> "This section uses a simple ad-hoc test program listed in Code Example 2.16 that
>  exercises all types of instructions, including taken and not-taken branches.
>  If the program runs correctly, it should store the value 7 into address 96 and
>  then 25 into address 100. A store with any other address or value indicates failure."
> — p.67

中文解釋：**測試程式的設計思路值得學：**
1. **涵蓋所有指令型別**（exercises all types of instructions）
2. **包含成立和不成立的分支**（taken and not-taken branches）——
   這是分支測試的最低要求，只測一種等於沒測
3. **用「寫到特定位址的特定值」當成功訊號**（存 7 到位址 96，再存 25 到位址 100）
4. **任何其他的寫入都算失敗**——**注意這個嚴格性**：
   不是「有寫對就好」，而是「不能寫錯」

Code Example 2.16（p.68）的程式裡有幾行寫著 `# Shouldn't be taken` 和
`# Shouldn't happen`——**這些是負面測試**，如果處理器錯誤地執行了它們，
就會寫出錯誤的值而被抓到。**這是很聰明的設計：讓錯誤自己暴露。**

書上邊欄有句很誠實的話（p.67 邊欄）：

> "A mark of an inexperienced engineer is to expect one's code is correct on the
>  first try."

**「期待自己的程式第一次就對，是新手的特徵。」**

### Testbench：自我檢查的測試平台

中文解釋：Code Example 2.17（p.69）的 SystemVerilog testbench，結構值得記住：

```systemverilog
// 1. 產生時脈
always begin clk <= 1; #5; clk <= 0; #5; end   // 10 ns 週期

// 2. 初始化：前兩個週期 assert reset
initial begin reset <= 1; #22; reset <= 0; end

// 3. 自我檢查
always @(negedge clk)
  if (MemWrite) begin
    if (DataAdr === 100 & WriteData === 25) $display("Simulation succeeded");
    else if (DataAdr !== 96) $display("Simulation failed");
  end
```

**三個部分：時脈產生、重置、結果檢查。** 這是所有 testbench 的基本骨架（第 5 章詳述）。

檢查邏輯剛好對應測試程式的設計：
**寫到 100 且值是 25 → 成功；寫到 96 以外的任何地方 → 失敗。**
（寫到 96 是預期中的中間步驟，所以放過。）

**"The testbench will hang if no writes occur."**（p.68）——
如果處理器完全沒動作，測試會卡住而不是誤報成功。**這也是刻意的。**

### 波形觀察

中文解釋：Fig. 2.12（p.70）是模擬波形（原書此處為波形圖）。
書上指出幾個觀察點（p.69），這是讀波形的示範：

- **110 ns 時 PC 從 0x20 跳到 0x28**——因為 `beq around` 成立
- **45 ns 時 PC = 8**，程式算 12 + (−9) = 3：
  `SrcA` = 0x0000000C = 12，`SrcB` = 0xFFFFFFF7（−9 的二補數），`Result` = 3
- **195 ns 時 `MemWrite` 拉高**，寫入 0x00000019 = 25 到位址 0x00000064 = 100
  → 印出 "Simulation succeeded"

**讀波形的方法就是「拿程式對照訊號」**——
知道第幾 ns 該執行哪條指令，然後檢查訊號值對不對。

實際跑法（p.69 邊欄）：
```
$ cd cvw/examples/verilog/riscvsingle
$ vsim -do riscvsingle.do
```

## 所以呢

**這節是整本書的縮小模型：方塊圖 → 控制真值表 → SystemVerilog → testbench，
四個步驟就是之後每一章的固定流程。**
最該帶走的三件事：
1. **架構狀態 vs 非架構狀態**——「flush 掉還正確嗎」是判準，後面所有加速機制都靠這個區分成立。
2. **T_CPU = 指令數 × CPI × T_c**——pipeline 是拿一點 CPI 換大幅縮短 T_c。
3. **兩種 hazard、三種解法**（forward / stall / flush），第 7 章要親手實作。
