## 這節在講什麼

**Wally 怎麼接上 AHB 匯流排。**

五個子節，主線是三個新東西：
1. **`ahbinterface` + `busfsm`**（9.5.1）：**三狀態 FSM 驅動 AHB 的階段**
2. **EBU**（9.5.2）：**在 IFU 和 LSU 之間仲裁**
3. **Bus hazard**（9.5.5）：**匯流排的多週期操作怎麼和 hazard 單元、特權單元互鎖——本節最難也最重要**

**最該精讀的是 9.5.5 的 `BusCommitted` 機制：
它解決了「bus transaction 進行到一半時來了中斷怎麼辦」這個問題。**

## 關鍵點

### 加上匯流排後的系統架構

> "The basic pipelined processor core from Fig. 7.13 has no bus interface because its memories (DTIM and
>  IROM) are inside the core and it does not access peripherals. **This section adds an uncore module with
>  memory and peripherals that communicate with the core over an AHB bus. The memory and peripherals are
>  collectively called AHB *devices*. When the BUS_SUPPORTED configuration variable in config.vh is 1,
>  Wally adds an AHB interface to the load/store unit (LSU) and instruction fetch unit (IFU) to access
>  peripherals or memory other than the DTIM or IROM. Wally also adds an *external bus unit* (EBU) that
>  arbitrates between requests from the LSU and IFU and passes the selected request onto the uncore's AHB
>  bus.**"
> — p.411

中文解釋：**Fig. 9.20（p.411）的兩層結構：**

```
┌─ wallypipelinedsoc ───────────────────────────────────────────┐
│ ┌─ uncore ────────────────────────────────────────────────┐   │
│ │  RAM(ram_ahb)  Boot ROM(rom_ahb)   ┌ahbapbbridge┐        │   │
│ │  External Memory Interface          │ uart_apb  │        │   │
│ │                                     │ clint_apb │  APB   │   │
│ │              AHB ───────────────────┤ spi_apb   │        │   │
│ │                                     │ plic_apb  │        │   │
│ │                                     └ gpio_apb ─┘        │   │
│ └────────────────────────┬────────────────────────────────┘   │
│ ┌─ wallypipelinedcore ───┴────────────────────────────────┐   │
│ │              ┌─── EBU ───┐                               │   │
│ │         AHB ─┤           ├─ AHB                          │   │
│ │   ┌ DTIM ┐ LSU        IFU ┌ IROM ┐                       │   │
│ └────────────────────────────────────────────────────────┘   │
└───────────────────────────────────────────────────────────────┘
```

**三層模組：`wallypipelinedsoc`（頂層）= `wallypipelinedcore` + `uncore`。**

**Table 9.8（p.412）三個記憶體組態參數：**

| 參數 | 意義 | 位址 |
| --- | --- | --- |
| **`UNCORE_RAM_SUPPORTED`** | AHB 上的 uncore RAM | **0x80000000** |
| **`BOOTROM_SUPPORTED`** | AHB 上給 bootloader 的 ROM | **0x1000** |
| **`EXT_MEM_SUPPORTED`** | 接 uncore 外 RAM 的 AHB 介面（例如 FPGA 上的 DDR 控制器） | 0x80000000 |

（呼應 2.4 節的 memory map 和 4.4 節的組態。）

**（p.412 邊欄：**「rv32imc 組態有 DTIM 和 IROM，**也有**接 uncore 周邊的匯流排。
它不含外部（uncore）記憶體。」**——所以兩者可以並存，見 9.5.4 節。）

### LSU 加上匯流排介面後的變化

> "**Compared to Figs. 7.13 and 8.19 where the LSU had a DTIM, this updated LSU keeps the subword and
>  bendian support but removes the DTIM and adds the AHB signal pins and an `ahbinterface` module that has
>  fetch and write buffers and a `busfsm` control state machine. The fetch buffer holds the HRDATA read
>  from the bus, and the write buffer holds the values driving HWDATA and HWSTRB onto the bus.
>  The `busfsm` walks through the phases of the AHB transaction and generates AHB control signals and the
>  fetch buffer enable at appropriate times.**"
> — p.412

中文解釋：**`ahbinterface` 模組的三個部件：**

| 部件 | 作用 |
| --- | --- |
| **Fetch buffer** | 接住從匯流排讀回的 `HRDATA` |
| **Write buffer** | 驅動 `HWDATA` 和 `HWSTRB` 到匯流排 |
| **`busfsm`** | **走過 AHB 的各階段，在適當時機產生控制訊號和 fetch buffer enable** |

**一個簡化（p.412）：**
> "**There is no need for the DTIM A (address) multiplexer of Fig. 7.13 because the bus transaction starts
>  in the Memory stage for both loads and stores; so IEUAdrM ties directly to LSUHADDR.**"

**因為匯流排交易對 load 和 store 都在 Memory 級開始，
所以不需要 7.2.1 節那個「讀用 IEUAdrE、寫用 IEUAdrM」的多工器。**

**（p.412 邊欄的簡化清單：Fig. 9.21 省略了幾個 AHB 控制訊號。
**`HBURST` 目前硬接為 0**（第 12.2 節才引入 burst 模式的 cache line 抓取和寫回）；
**`HPROT` 硬接 4'b0011、`HMASTLOCK` 硬接 0**（不支援保護和匯流排鎖定）；
**`HRESP` 被忽略**（記憶體系統不產生錯誤條件）。）

### 匯流排存取要多花至少兩個週期

> "Recall from Table 7.8 that an LSU DTIM access involves work in the Execute, Memory, and Writeback stages
>  but only stalls for hazards. **In contrast, an access to bus-based memory always takes at least two extra
>  cycles, as shown in Fig. 9.22 for ld followed by additional instructions (i1, i2, ...). The LSU stalls
>  the CPU during these extra cycles by setting BusStall = 1, so the LSU with an AHB interface behaves as a
>  multicycle (nonpipelined) system.**"
> — p.413

中文解釋：**Fig. 9.22（p.413）的時序表很清楚：**

| Cycle | F | D | E | M | W | State/AHB | BusStall |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 0 | ld | | | | | | 0 |
| 1 | i1 | ld | | | | | 0 |
| 2 | i2 | i1 | ld | | | | 0 |
| **3** | i3 | i2 | i1 | **ld** | | **Adr** | **1** |
| **4** | i3 | i2 | i1 | ld | | **Data** | **1** |
| **5** | i3 | i2 | i1 | ld | | **Mem3** | **0** |
| 6 | i4 | i3 | i2 | i1 | ld | | 0 |

**`ld` 在 Memory 級停了三個週期（Adr、Data、Mem3），其中前兩個 `BusStall = 1`。**

**Table 9.9（p.414）LSU 的五級 AHB 存取步驟：**

| Stage | Read | Write |
| --- | --- | --- |
| **Execute** | 計算記憶體位址 `IEUAdrE` = 基底 + 偏移 | 同左 |
| **Mem1/AHB Adr** | **驅動 `HADDR = IEUAdrM`；產生其他 AHB 控制訊號** | 同左，**並做 subword 寫入多工** |
| **Mem2/AHB Data** | **從 AHB 裝置同步讀出 `HRDATA`** | **驅動 `HWDATA` 到 AHB** |
| **Mem3** | **在週期開始時把 `HRDATA` 捕捉進 `ReadDataM`，然後做 subword 讀取和端序多工** | 寫入裝置 |
| **Writeback** | 把 `ReadDataW` 寫進暫存器檔案 | （無） |

**三個階段的職責（p.414）：**
1. **Adr 階段（Mem1）**：`HREADY`（這裡叫 `LSUHREADY`）可能為低，表示匯流排不能接受請求。
   **LSU 保持 Adr 階段訊號穩定直到 `LSUHREADY` 為高。**
2. **Data 階段（Mem2）**：裝置讀或寫。**慢的裝置可以讓 `LSUHREADY` 保持低來拉長這個階段。**
3. **Mem3 階段**：**把 `HRDATA` 捕捉進 `FetchBuffer` 暫存器，
   為 subword 存取做多工，必要時重排 byte 做端序轉換，產生 `ReadDataM`。**

**（p.413 邊欄的重要設計取捨：**
> "**The Mem2 and Mem3 phases could be merged, but this might increase the cycle time of the processor.
>  In a processor with a DTIM/IROM or cache, bus accesses are infrequent, so it is better to have a fast
>  cycle time than a lower bus latency.**"

**「有 cache 的話匯流排存取不頻繁，所以寧可要快的時脈而非低的匯流排延遲。」**
——這是典型的 Amdahl's Law 思維。）

**（p.414 邊欄有一段更長的分析，說明為什麼不利用 AHB 的 pipeline 特性來消掉那兩個 stall 週期：
**「位址要提前一週期算好（會增加 LSU 的 `IEUAdrE` 關鍵路徑），
或資料要晚一週期讀寫（會給 LSU 的 Load Delay Hazard 加一個週期）。
可以改，但匯流排交易不頻繁（多數存取被 cache 過濾掉），
而 Amdahl's Law 說要讓常見情況變快。所以維持較低的時脈週期比降低匯流排延遲好。」**）

### `busfsm`：三狀態機

> "**The LSU's AHB bus interface has a three-state FSM controller (`busfsm`) shown in Fig. 9.23 that
>  sequences the steps from Table 9.9 for both stores and loads. State names match the AHB specification's
>  Adr and Data phases with the added third state, Mem3. All memory requests start in the Adr phase.
>  If read or write is requested, `busfsm` asserts BusStall to stall the pipeline while the bus services the
>  request. When the bus is ready, `busfsm` asserts HTRANS = 2 (NONSEQ) to initiate a single AHB read or
>  write and advances to the Data state. While in the Data state, the FSM asserts BusCommitted to prevent
>  the privileged unit from taking interrupts until the bus transaction completes. When the bus raises
>  HREADY to complete the Data phase, `busfsm` advances to Mem3 and raises CaptureEn on reads to enable the
>  fetch buffer to sample HRDATA. While in Mem3, BusStall is lowered, so the pipeline can advance.**"
> — p.414

中文解釋：**Fig. 9.23（p.415）的狀態機：**

```
        ┌─ else ─┐                    ┌─ HREADY ─┐        ┌─ Stall ─┐
        ↓        │                    ↓          │        ↓         │
      ┌─────┐    │  HREADY & |RW    ┌──────┐     │     ┌──────┐     │
reset→│ Adr │────┴─ /HTRANS=2 ─────→│ Data │─────┴────→│ Mem3 │─────┘
      └─────┘      BusStall=1       └──────┘  HREADY   └──────┘
         ↑                        BusCommited=1 /CaptureEn=1  BusCommited=1
         └──────────────────────────────────────────────────┘
                              ~Stall
```

**三個狀態的輸出（從 Fig. 9.23 讀出）：**

| 狀態 | 輸出 | 轉移條件 |
| --- | --- | --- |
| **Adr** | `BusStall = 1`（有請求時），`HTRANS = 2` | `HREADY & |RW` → Data |
| **Data** | **`BusCommited = 1`**，`BusStall = 1` | `HREADY` → Mem3（並 `CaptureEn = 1`） |
| **Mem3** | **`BusCommited = 1`**，`BusStall = 0` | `~Stall` → Adr |

**`Stall` 對 LSU 是 `StallW`，對 IFU 是 `StallD`。**

**`BusCommitted` 是關鍵：它在 Data 和 Mem3 狀態為 1，
阻止特權單元在匯流排交易進行中接受中斷。**（9.5.5 節詳述。）

### IFU 的匯流排介面：更簡單

> "**The IFU bus interface is similar to the LSU interface, but it is 32-bit little-endian read-only.
>  Thus, it drops HWDATA, HWRITE, HWSTRB, and the subword and endian logic, as shown in Fig. 9.24, and
>  HSIZE is 010 to always fetch 4-byte instructions. The IFU `busfsm` receives StallD instead of StallW.
>  In the Mem3 stage, the IFU outputs InstrRawF from the fetch buffer.**"
> — p.414–415

中文解釋：**IFU 比 LSU 少了四樣：`HWDATA`、`HWRITE`、`HWSTRB`、subword/endian 邏輯。**
**`HSIZE` 永遠是 010（4 bytes）。**

**（p.415 邊欄的重要提醒：**
> "**Without some sort of local memory, the processor runs slowly because each instruction or data access
>  takes at least 3 cycles over the bus. Chapter 12 describes the full LSU with a cache and bus.
>  The cache services most accesses, while the bus fetches cache misses from RAM and accesses peripherals
>  in the uncore.**"

**沒有本地記憶體的話處理器會很慢（每次存取至少 3 週期）——
所以 cache 很重要。**）

**AHB 訊號的命名慣例（p.415）：**
> "**The AHB signals from each unit have corresponding IFU or LSU prefixes, and the EBU must arbitrate
>  between requests from the two units.**"

**`IFUHADDR`、`LSUHADDR`、`IFUHREADY`、`LSUHREADY`…**

### EBU：LSU 優先的仲裁器

> "**The external bus unit (EBU) implements a subset of the multilayer AHB protocol to arbitrate between the
>  IFU and LSU AHB interfaces (also called controllers). LSU requests get priority. The selected
>  controller's request is placed on the bus to the uncore. As shown in Fig. 9.25, the EBU consists of an
>  FSM arbiter (`ebufsmarb`), muxes to choose the selected controller, and registers to retain the other
>  controller's request.**"
> — p.415

中文解釋：**EBU 的三個部件：FSM 仲裁器 + 多工器 + 暫存其他控制器請求的暫存器。**

**多工邏輯（p.415）：**
```
LSUSelect = 1 → 送 LSU 的訊號
IFUSelect = 1 → 送 IFU 的訊號
都沒選中   → 匯流排收到 0，保持 idle
```
**`HRDATA` 同時送給 IFU 和 LSU。
只有 LSU 會寫外部記憶體，所以 `HWDATA` 只接 LSU，
而 IFU 從不 assert `IFUHWRITE`，所以那個訊號硬接為 0。**

**為什麼 LSU 優先（p.416）：**
> "**It always gives priority to the LSU to prevent deadlocking the pipeline.**"

**這是關鍵的正確性考量，不只是效能考量：**
**LSU 在 Memory 級、IFU 在 Fetch 級。如果讓 IFU 優先，
LSU 就可能永遠等不到匯流排，而 pipeline 前面已經卡住了 → deadlock。**

### `ebufsmarb`：兩狀態 Mealy 機

> "**The `ebufsmarb`, shown in Fig. 9.26, arbitrates when both the LSU and IFU make requests at the same
>  time.... Only two states are required, an Idle state to indicate either 1 or 0 requests are active and
>  an Arbitrate state, which selects the LSU. It is a Mealy machine with outputs that are a function of the
>  current state and inputs. When two requests occur in the Idle state, the FSM transitions to Arbitrate and
>  selects the LSU. Because the IFU detects HREADY = 1, it assumes the Adr phase of the request was taken
>  and moves on to the Data phase. So, the ControllerInput module must save the IFU's Adr phase HADDR and
>  control signals for later. Data phase signals are inherently delayed, so they need not be stored and
>  replayed. When the device completes the memory request, HREADY asserts, and the FSM returns to Idle.
>  Upon returning to Idle, the IFU Adr phase is replayed by driving the stored IFU request onto the bus.**"
> — p.416–417

中文解釋：**這是本節最巧妙的設計，關鍵問題是：**

**IFU 看到 `HREADY = 1` 就以為自己的 Adr 階段被接受了，於是前進到 Data 階段。
但實際上匯流排給了 LSU。怎麼辦？**

**解法：`ControllerInput` 模組把 IFU 的 Adr 階段訊號存起來，之後重播。**

**Fig. 9.26（p.417）的狀態機：**

| 狀態 | 條件 | 輸出 |
| --- | --- | --- |
| **Idle** | `IFUHTRANS[1]` | `IFUSelect = 1` |
| | `LSUHTRANS[1]` | `LSUSelect = 1`，`CntlRest = 1` |
| | **`LSUHTRANS[1] & IFUHTRANS[1]`**（兩者都請求） | **`IFUSave = 1`、`IFUSelect = 0`、`LSUSelect = 1`** → 進入 Arbitrate |
| | else | `CntlRest = 1` |
| **Arbitrate** | else | `IFUSelect = 0`、`LSUSelect = 1` |
| | **`HREADY & ~(LSUHTRANS[1] & IFUHTRANS[1])`** | 回到 Idle，**`IFURestore = 1`、`IFUDisable = 1`** |

**三個關鍵訊號：`IFUSave`（存起來）、`IFURestore`（取回）、`IFUDisable`。**

**「Data 階段訊號本質上就是延遲的，所以不需要儲存和重播」**——
只有 Adr 階段訊號需要（呼應 9.2.2 節：AHB 的 pipeline 讓 Adr 和 Data 階段分離）。

### 仲裁的實際時序

中文解釋：**Fig. 9.27（p.418）示範「IFU 和 LSU 同時讀取，接著兩次 IFU 讀取」（p.417）：**

| Cycle | 發生什麼 |
| --- | --- |
| **0** | **IFU 和 LSU 同時請求**（兩者 `HTRANS` = NONSEQ = 2）。**FSM 選 LSU**，`LSUSelect = 1`，`HADDR = LA1`。**IFU 的請求被存進 `controllerinput`（`IFUSave = 1`）** |
| **1** | FSM 進入 Arbitrate。`HREADY = 1` 表示裝置回傳了 `HRDATA`。`LSUHREADY` assert 讓 LSU 捕捉資料。**同時 EBU 選出存起來的 IFU 請求 Adr 訊號（IA1）驅動上匯流排。`IFUHREADY = 0` 繼續 stall IFU** |
| **2** | FSM 回到 IDLE。**裝置用 IA1 的 `HRDATA` 和 `HREADY = 1` 回應 IFU 的請求** |
| **3, 4** | **又有兩個 IFU 請求，但 LSU 不再請求，所以不需要仲裁** |

**（p.417 邊欄預告：**「加上資料 cache 後，cache miss 會產生 AHB burst 請求。
Burst 操作要求 EBU 計數每個字，**確保較低優先權的 IFU 在 burst 期間不被中斷**。」**）

**（p.418 邊欄的位址寬度說明：**
`HRDATA` 和 `HWDATA` 寬度是 `AHBW`（設為 Wally 組態的自然字長 XLEN）。
**`HADDR` 是實體位址，寬度 `PA_BITS`（RV32 為 34、RV64 為 56）。**
**程式用 32 或 64 位元位址。無 MMU 的系統：RV32 前面補兩個 0 變成 34 位元，
RV64 去掉最高 8 個位元變成 56 位元。**）

### Uncore 的位址解碼與裝置多工

> "**The decoder uses the configuration parameters \<DEVICE\>_SUPPORTED, \<DEVICE\>_BASE, and \<DEVICE\>_RANGE
>  to determine which devices (e.g., Boot ROM, uncore RAM, GPIO) are supported and where they appear in the
>  memory map.**"
> — p.418–419

中文解釋：**Fig. 9.28（p.419）的 uncore 結構：
`adrdecs` 模組接收 Adr 階段的 `HADDR`，產生 one-hot 的 `HSEL`（每個裝置一位元）。**

**運作流程（p.419）：**
> "**HSEL[0] is asserted when HADDR doesn't match any device address. When the previous transaction's Data
>  phase completes, as indicated by that device asserting HREADY, the current transaction enters the Data
>  phase and latches HSEL to HSELD. The currently selected device reads or writes during the Data phase and
>  raises its HREADYOUT when complete. The HREADY multiplexer picks HREADYOUT from the selected device
>  (based on HSELD) and drives HREADY back to the EBU and to all the devices. If no device is selected, the
>  bus is idle and immediately asserts HREADY to avoid locking up.**"

**`HSEL[0]` 是「沒有裝置匹配」的特殊位元**（呼應 9.2.2 節的 default subordinate）。

**（p.420 邊欄的重要初始化要求：**
> "**Upon reset, both HSEL[0] and HSELD[0] must be set to 1 to assert HREADY and, thus, prevent the bus from
>  locking up.**"

**重置時兩者都要設為 1，否則匯流排一開始就掛住。**）

### 範例：連續讀取不同裝置且有 wait state

中文解釋：**Example 9.2（p.419–420）。ROM 有 2 個額外 wait state，RAM 有 1 個。
ROM 是裝置 1，RAM 是裝置 2。Fig. 9.29（p.420）的逐週期分析：**

| Cycle | 發生什麼 |
| --- | --- |
| **0** | 匯流排閒置：**`HSEL[0] = 1`** 表示無請求 |
| **1** | ROM 交易的 Adr 階段開始，控制器 assert **`HSEL[1]`**。**`HREADY = 1` 因為匯流排原本閒置** |
| **2** | **ROM 的 Data 階段開始但沒完成。同時 RAM 的 Adr 階段開始並 assert `HSEL[2]`，但存取要等 `HREADY` 升起才能開始** |
| **2–4** | **慢的 ROM 完成它的 Data 階段。多工器用 `HSELD`（延遲版的 `HSEL`）選 ROM 的 `HREADYOUT` 當 `HREADY`** |
| **4** | **ROM 終於 assert `HREADYOUT`（因而 `HREADY`）** |
| **5** | **RAM 的 Data 階段開始，但慢的 RAM 直到第 6 週期才 assert `HREADYOUT`。同時匯流排變閒置並 assert `HSEL[0]`** |
| **5–6** | 多工器選 RAM 的 `HREADYOUT` 當 `HREADY`。**RAM 終於在第 6 週期 assert `HREADYOUT`** |

**這個例子完整展示了 AHB pipeline 的重疊：
ROM 的 Data 階段和 RAM 的 Adr 階段在第 2 週期同時發生。**

### 匯流排與 TIM 並存

> "**An embedded processor typically doesn't have caches but instead has a small IROM and DTIM in the core
>  as well as a bus to peripherals or external memories. For example, the Wally rv32imc configuration is
>  organized this way. The address decoder must distinguish between accesses to these TIMs versus bus
>  accesses and use a mux to access them accordingly.**"
> — p.420

> "**Wally handles this decoding using a PMA checker in the MMU.... The PMA checker's address decoder
>  outputs SelDTIM, which controls a multiplexer to select between the DTIM's read data (DTIMReadDataM) or
>  the AHB's fetch buffer (FetchBuffer). SelDTIM also demuxes the read/write signal RWM to either the DTIM
>  or busfsm.**"
> — p.421

中文解釋：**`SelDTIM` 做兩件事：選讀取資料來源、以及把 `RWM` 分流到 DTIM 或 `busfsm`。**
（PMA checker 在第 11.4.1.1 和 12.3.1 節。）

**IFU 同理（p.421）：**
> "**The IFU uses the same approach to select between the IROM and the Bus, as shown in Fig. 9.32.
>  A separate PMA checker in the IFU's MMU outputs SelIROM to select the IROM or the Bus. Unlike the LSU's
>  DTIM, the IROM only reads instructions. PCNextF directly drives the IROM read address port.**"

**Fig. 9.31（p.422）是抽象化的 LSU 圖，用縮寫表示模組：
SWW = subwordwrite、SWR = subwordread、ES = endianswap。
`busfsm` 藏在 `ahbinterface` 裡。**

### Bus Hazards：互鎖機制（本節最難的部分）

> "**Each AHB interface in the IFU and LSU takes multiple cycles to complete a bus transaction. The `busfsm`
>  from Fig. 9.23 must *interlock* with the hazard unit to correctly stall the pipeline and delay
>  interrupts occurring in the middle of a bus transaction.**"
> — p.423

中文解釋：**（p.423 邊欄定義 interlock：**
「互鎖禁止某些會衝突的狀態發生。例如，**在匯流排交易期間發生的中斷必須延遲到交易完成後**。」**）

**Stall 的產生（p.423）：**
> "**Because each bus transaction takes multiple cycles, the LSU or IFU `busfsm` generates BusStall while in
>  the midst of a transaction. Specifically, BusStall asserts when the bus transitions from the Adr phase
>  into the Data phase and remains high until the Data phase completes. When BusStall is lowered, the hazard
>  unit unstalls the pipeline, and the IFU or LSU enters its Mem3 stage, producing a valid instruction
>  InstrRawF or capturing the load result in ReadDataM.**"

```
LSUStallM = BusStall（來自 LSU 的 busfsm）
IFUStallF = BusStall（來自 IFU 的 busfsm）
```
**hazard 單元用 `StallW` 來 stall 整條 pipeline。**

**（p.423 邊欄：`LSUStallM` 也在 cache 和硬體頁表走訪器 stall 時 assert（第 12.4.1 節）；
`IFUStallF` 也在 cache stall 和 spill 時 assert（第 13.4.3 節）。
**「某一級的 stall 會 stall 前面所有級。所以 Writeback 級的 stall 會 stall 整條 pipeline。」**）

**Bus stall 的完整邏輯（p.423 邊欄）：**
```
StallWCause = (IFUStallF & ~FlushDCause | LSUStallM) & ~FlushWCause
```
> "**A Fetch flush (FlushFCause) has priority over an IFU stall (IFUStallF), and a Writeback flush
>  (FlushWCause) has priority over an LSU stall. FlushFCause is not explicitly defined but is equivalent to
>  FlushDCause because a flush in one stage also flushes all previous pipeline stages. Similarly, FlushDCause
>  always asserts whenever FlushWCause asserts.**"

**「flush 優先於 stall」的原則再次出現**（呼應 7.2.2.4 節）。

### Trap 與 bus transaction 的優先權

> "**Traps take priority and should flush the pipeline rather than processing the LSU/IFU stall. However,
>  traps are only allowed at the start (i.e., in the Adr phase) of a bus transaction. The CommittedM/F
>  signals... postpone interrupts arriving in the middle (in the Data phase) of a bus transaction.**"
> — p.423

中文解釋：**核心規則：**
**「trap 只能在 bus transaction 的開頭（Adr 階段）發生。」**

**理由（p.423）：**
> "**`BusCommitted` must remain high while waiting in Mem3 so that the interrupt does not occur until the
>  next instruction. BusCommitted is zero only during the Adr phase, which allows interrupts to occur before
>  either the LSU or IFU starts a bus access. If a trap occurs while the IFU or LSU is in the Adr phase, the
>  bus transaction is canceled by driving HTRANS to 0.**"

**兩種情況的處理完全不同：**

| 階段 | `BusCommitted` | trap 發生時 |
| --- | --- | --- |
| **Adr** | **0** | **允許 trap，並把 `HTRANS` 驅動為 0 取消交易** |
| **Data / Mem3** | **1** | **延後中斷到下一條指令** |

**這很合理：Adr 階段還沒真的送出請求，可以取消；
Data 階段已經在跟裝置溝通了，中途放棄會讓裝置狀態不一致。**

### EBU 與 hazard 的互動

> "**Recall that when both the IFU and LSU need to access the bus, the EBU prioritizes the LSU. In that case,
>  when the LSU completes its request and lowers LSUStallM, the pipeline remains stalled until the IFU's
>  request is finished. Because StallW is still asserted, the LSU's `busfsm` remains in Mem3 to prevent
>  reissuing the bus request. After the IFU's `busfsm` transitions to Mem3, both units lower their BusStall
>  signals and the pipeline resumes. Other hazards such as CSR writes may also stall the pipeline, keeping
>  the `busfsm` in Mem3 to prevent reissuing the bus request.**"
> — p.423

中文解釋：**Mem3 狀態的第二個作用：「停在這裡，不要重發請求」。**

**Fig. 9.23 的 Mem3 狀態有一個 `Stall` 自環——就是為了這個。**
**只要 pipeline 還被別的原因 stall 著，`busfsm` 就留在 Mem3。**

### 完整的中斷延遲範例

中文解釋：**Fig. 9.34（p.425）配 Code Example 9.1（p.426）：**
```asm
80001000:    ori  x4, x0, 10
80001004:    addi x5, x4, 10
. . .
TrapHandler:
80002000:    auipc x6, 24
```

**逐週期分析（p.425）：**

| Cycle | 發生什麼 |
| --- | --- |
| **1** | CPU 開始從 0x80001000 抓 `ori`，進入匯流排的 Adr 階段 |
| **2** | **`busfsm` 進入 Data 階段時 assert `BusCommittedF`** |
| **3** | **中斷變成 pending（`InterruptPending = 1`），但因為 `BusCommittedF = 1`，中斷被延遲** |
| **5** | 匯流排完成抓取 `ori`（進入 Mem3 階段） |
| **6** | **CPU 開始從 0x80001004 抓 `addi`，進入 Adr 階段。`BusCommittedF = 0`，所以 pending 的中斷可以被處理。`TrapM` flush pipeline，包括正在 Adr 階段的 `addi` 抓取** |
| **7** | trap handler 開始從 0x80002000 抓 `auipc`，進入 Adr 階段 |

**這個例子完整展示了「中斷等到交易邊界」的機制。**

**（p.425 邊欄有一段很有洞見的補充：**
> "**The IFU could allow TrapM in cycle 5 to flush the completed fetch because the IFU only reads
>  instructions. In contrast, when an instruction begins to write to memory, it must commit.
>  Section 11.2.2.1 defines *nonidempotent* reads that have side effects and also must commit.
>  For example, reading the Receive Buffer Register (RBR) in a 16550 UART also empties the buffer.
>  Therefore, the RBR is nonidempotent because consecutive reads to the same address return different
>  values.**"

**`nonidempotent`（非冪等）讀取是個重要概念：
讀取本身有副作用（例如讀 UART 的接收緩衝器會清空它），
所以這種讀取一旦開始就必須完成。**）

### `Committed` 邏輯進入 trap 單元

> "**In this chapter, CommittedF = BusCommittedF. Later chapters will add other cases when CommittedF
>  asserts. Similar to the IFU, the LSU asserts CommitedM when its BusCommitedM asserts. The `trap` module in
>  the privileged unit asserts Committed when either the LSU's CommitedM or the IFU's CommitedF assert.
>  Committed delays interrupts until the instruction completes.**"
> — p.426

中文解釋：**Fig. 9.35（p.426）是 Fig. 8.14 的 trap 單元加上 `Committed` 邏輯：**
```
Committed = CommittedM | CommittedF
EnabledIntsM & ~Committed → ValidIntsM
```
**`Committed` 直接擋住 `ValidIntsM`——所以中斷不會被接受。**

**（p.426 邊欄的設計取捨很值得看：**
> "**The hazard unit could choose to stall just the Decode stage when IFUStallF asserts. However, this would
>  mean that an exception could occur in the Memory stage while an instruction is being fetched. To ensure
>  the exception is taken, the hazard unit would have to stall the Memory stage until the IFU lowers
>  BusStall. Caches complicate this issue further. Thus, Wally instead stalls the entire pipeline during
>  both IFU and LSU bus accesses.**"

**「Wally 選擇在 IFU 和 LSU 的匯流排存取期間 stall 整條 pipeline」——
這是為了簡化而犧牲一點效能。**）

## 所以呢

**這節把 Wally 接上了 AHB 匯流排，三個新機制最重要：**

1. **`busfsm` 的三個狀態（Adr → Data → Mem3）**：
   **匯流排存取至少多花兩個週期**，而 **Mem3 有雙重作用**——
   捕捉資料，以及「pipeline 還被 stall 時停住不重發請求」。

2. **EBU 的 LSU 優先仲裁**：這不只是效能考量，**是防止 deadlock 的正確性要求**。
   而 **`ControllerInput` 存下 IFU 的 Adr 訊號稍後重播**，
   解決了「IFU 誤以為請求被接受」的問題。

3. **`BusCommitted` 的互鎖**：
   **trap 只能在 Adr 階段發生（可以用 `HTRANS = 0` 取消交易）；
   進入 Data 階段後就要延後中斷到下一條指令。**

還有一個實務上的設計哲學（來自兩處邊欄）：
**「匯流排存取不頻繁（多數被 cache 過濾），
所以寧可維持快的時脈週期，而非降低匯流排延遲」**——
這是 Amdahl's Law 在微架構設計上的直接應用。
