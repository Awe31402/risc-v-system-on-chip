# 17.3 Test Plan

> 原書 p.706–707（Chapter 17: Extensions: A (Atomic)）

## 這節在講什麼

非常短的一節。A 擴充的測試現況是「AMO 有官方測試、lr-sc 沒有」，所以 Wally 自己補了兩個簡單的測試程式。這節也順帶揭露了一個測試基礎建設的限制。

## 關鍵點

### 官方測試涵蓋 AMO 但缺 lr-sc

> "At the time of this writing, riscv-arch-test has AMO tests listed in Table 17.4, but lacks lr-sc tests."
> — p.706

中文解釋：Table 17.4 的數量：RV32IA 每個 `.w` 指令 69 個測試（共 552 個），RV64IA 每個指令 133 個測試（含 `.d` 版本，共 2,394 個）。這個數字和第 16 章浮點的千萬級測試相比小得可憐——因為 AMO 的狀態空間本來就小（幾個算術運算 + 位址對齊 + 權限），沒有浮點那種 corner case 爆炸。

lr-sc 缺測試是可以理解的：要測「預約被作廢」需要製造出干擾的寫入，這在單執行緒的架構測試框架裡很難自然表達。

### Wally 自己補的測試

> "The tests/wally-riscv-arch-test directory contains simple WALLY-lrsc-01 tests. They are located in the privileged subdirectory because the test infrastructure does not yet look for an A subdirectory. WALLY-lrsc performs a successful LoadReserved and StoreConditional word and double-word operation followed by an unsuccessful operation to check basic functionality."
> — p.706

中文解釋：測試內容很基本——成功的 lr-sc（字與雙字），然後製造一次失敗。放在 `privileged` 子目錄純粹是因為測試框架還沒有 `A` 這個分類，這是一個誠實揭露的工程 workaround，不是設計。

## 名詞表

| 名詞 | 意思 |
| --- | --- |
| RV32IA / RV64IA | 基礎整數 + 原子擴充的測試組態 |
| `WALLY-lrsc-01` | Wally 自製的 lr-sc 基本功能測試 |

## 所以呢

測試這一層很薄，某種程度上反映了 A 擴充在單核心上的簡單性——沒有其他核心來搶，大部分行為是直接的。真正困難的並行驗證要到多核心系統才出現。下一節看 Wally 實際怎麼把 AMO 和 lr-sc 塞進既有的 LSU。
