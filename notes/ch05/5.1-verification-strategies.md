## 這節在講什麼

驗證方法論的全景。核心問題是：**怎麼知道測夠了？**

六個子節分別回答不同層面：
1. **測試向量從哪來**（5.1.1）：窮舉 → ad-hoc → directed → **coverage-driven** → **constrained random**
2. **標準答案從哪來**（5.1.2）：參考模型
3. **測單元還是測系統**（5.1.3）
4. **模擬太慢怎麼辦**（5.1.4）：硬體模擬（emulation）
5. **成熟度怎麼衡量**（5.1.5）：TRL
6. **設計和驗證怎麼協作**（5.1.6）：**always-broken vs always-working**

**最該帶走的是 5.1.1 的測試向量光譜，和 5.1.6 的 always-working 策略。**

## 關鍵點

### 驗證的地位：佔開發團隊一半

> "Logic verification is the process of checking that logic conforms to the specification.
>  Verification is generally more time-consuming and expensive than design. **Verification
>  engineers make up about half of an SoC development team.** Verification engineers need a
>  broad understanding of the system to define tests that exercise the full range of
>  features and because errors they discover might come from anywhere. **The mantra of SoC
>  design is "If it is not verified, it will not work."**"
> — p.193

中文解釋：呼應 1.2 節「驗證比設計貴」。這裡給了具體數字：**驗證工程師約佔 SoC 團隊一半。**

章首兩句引言值得記（p.193）：
> "Everyone knows debugging is twice as hard as writing a program in the first place."
> — Brian Kernighan（C 語言發明人，1974）

> "If you didn't test it, it doesn't work."
> — Bob Colwell（Pentium Pro 到 Pentium 4 的首席架構師）

**「沒測過就是不能用」**——注意用的是斷言語氣，不是「可能有問題」。

**驗證的五大挑戰（p.193）：**
1. **定義哪些功能需要測**
2. **決定用什麼測試向量**
3. **建立可靠的參考模型**
4. **偵測到 bug 時定位並修好**
5. **應付大型模擬的巨大執行時間**

### SystemVerilog 的五個語言子集

中文解釋：**Table 5.1（p.194）把整個語言切成五塊，各有用途：**

| 子集 | 節 | 用途 |
| --- | --- | --- |
| **Synthesizable** | 4.2 | RTL 設計 |
| **Testbench** | 5.4 | 初始化記憶體、從檔案讀測試、檢查結果、記錄差異 |
| **Assertions (SVA)** | 5.7 | 指定設計必須滿足的性質 |
| **Functional coverage (FC)** | 5.9 | coverpoint 與 covergroup，量測 RTL 被驗證得多徹底 |
| **Object-oriented** | n/a | 通用可重用 testbench，特別是 UVM；也用於功能覆蓋率 |

**這張表解釋了為什麼 SystemVerilog 這麼龐大：它其實是五種語言縫在一起。**

**UVM 的定位（p.194 邊欄）：**
> "The Universal Verification Methodology (UVM) [IEEE 1800.2-2017] is a standardized method
>  of logic verification with SystemVerilog that is widely accepted in industry. It takes an
>  object-oriented approach involving drivers, monitors, stimulus generators, and
>  scoreboards. **The methodology is sufficiently complex that it is primarily used by
>  verification specialists and is beyond what can be covered in this chapter.**"
> 入門書推薦：*Getting Started with UVM: A Beginner's Guide* [Cooper13]。

### 測試向量的五個層次（最重要的一段）

中文解釋：**5.1.1 節給出一個由淺到深的光譜，這是本節的核心。**

**（1）窮舉測試（exhaustive）**
> "A full adder has three inputs and two outputs, so it could be fully tested with 2³ = 8
>  vectors. Unfortunately, such *exhaustive testing* becomes intractable even for moderately
>  interesting blocks such as an adder with two 64-bit inputs, which requires 2¹²⁸ test
>  vectors."
> — p.196

**只對極小的模組可行。** 64-bit 加法器要 2¹²⁸ 個向量——不可能。

**（2）Ad-hoc / exploratory 測試**
> "The next level of sophistication is ad-hoc testing using a modest set of test vectors
>  informed by an understanding of the design. The RISC-V test program from Code Example
>  2.16 is another example of *ad-hoc* or *exploratory* test vectors.... **Ad-hoc testing is
>  a good way to quickly get basic confidence that a system performs its key functions.
>  However, it does not give high confidence that the system works for the complete range
>  of inputs.**"
> — p.196

**用途明確：快速建立基本信心，但不保證完整。**
（呼應 2.7.3 節那個手工測試程式。）

**開 Linux 也算 ad-hoc 測試（p.196）：**
> "Booting Linux is another readily available ad-hoc test that exercises some of the
>  complicated interactions between instructions, exceptions, caches, and virtual memory.
>  **However, booting Linux is no substitute for rigorously testing each feature
>  individually.**"

**（3）Directed 測試：系統性覆蓋 corner case**
> "*Directed* testing attempts to systematically cover *corner cases*. In this context,
>  corner cases are inputs that would be most likely to trigger unusual behavior. For
>  example, for a 64-bit adder, corner cases for each input could include
>  {0, 1, 2, 3, 2³², 2⁶³−1, 2⁶³, 2⁶³+1, 2⁶⁴−2, 2⁶⁴−1, and two random values in the middle
>  of the range}. The adder can be tested with the *cross-product* of these 12 corner cases,
>  that is, where every combination of the corners is used as the two inputs."
> — p.196

**12 × 12 = 144 個 corner case。** 那組數字本身值得記：
**0、1、2、3、2³²（字邊界）、有號最大值附近（2⁶³−1, 2⁶³, 2⁶³+1）、
無號最大值附近（2⁶⁴−2, 2⁶⁴−1）、加兩個隨機值。**

**但 directed 測試有盲點（p.196 邊欄）——這個警告很精彩：**
> "Corner cases are not always enough. Imagine a carry lookahead adder coded by hand. It
>  would be easy to introduce a typo in one of the columns that works for these corner cases
>  but does not work for all cases. Similarly, a manufacturing defect in one of the
>  transistors that caused column 12 of the adder to depend only on input A but not input B
>  would go undetected by these cases."

**corner case 測的是「邊界」，測不到「中間某一位元壞掉」。**

**Pentium FDIV bug 是最著名的案例（p.196–197）：**
> "Intel's infamous Pentium floating-point divide bug (FDIV) in 1994 was caused by a bad
>  tool that optimized out 5 of 1,066 minterms from a quotient digit selection programmable
>  logic array (PLA), resulting in an error that occurred around the 9th or 10th decimal
>  digit in about 1 division of every 9 billion for randomly selected inputs [Halfhill95].
>  **Directed tests would be unlikely to catch such a subtle error.** Moreover, testing was
>  performed on the quotient selection equations, which were actually correct, rather than
>  the transistor-level output of the PLA tool, which had the missing minterms."

**這個案例有三個教訓：**
1. **90 億次除法才錯一次的 bug，directed 測試抓不到**
2. **測錯了對象**——測的是（正確的）方程式，不是（有缺陷的）PLA 工具輸出
3. **後果**：Intel 一開始說不重要（一般試算表使用者 27000 年才遇到一次），
   但 IBM 算出在高負載試算表上是**每 24 天一次** → IBM 停止出貨 →
   **Intel 召回，花費 4.75 億美元**

**（4）Coverage-driven 測試**
> "Directed tests work well for some modules, but the cross-product can still be too large
>  for modules with many inputs, and determining sensible corners can be difficult for other
>  modules. *Coverage-driven testing* is a technique that defines *coverage points* (also
>  called *coverpoints*) that need to be tested. For example, a processor might define basic
>  coverage points to be every source and destination register, every instruction opcode,
>  and extreme values (0, 1, −1, max positive, max negative, and so on). The riscv-arch-test
>  suite satisfies coverage points for each instruction. It writes a signature to show that
>  the test worked."
> — p.197

**關鍵轉變：從「我測了什麼」變成「我要求哪些點必須被碰到」。**
（呼應 3.7 節的 riscv-arch-test。）

**（5）Constrained random 測試：本節最有洞見的部分**
> "A *constrained random test generator* produces test vectors, consisting of random
>  instructions. Constrained random test generation is particularly good at hitting
>  hard-to-find cases, which are also called *corner cases* in a somewhat different usage of
>  the term. For example, **it is difficult to write a directed test that causes an interrupt
>  while the instruction fetch unit is stalled waiting for the load/store unit to service a
>  translation lookaside buffer miss. But a constrained random test generator that produces
>  millions or billions of code sequences exercising interrupts and virtual memory may
>  stumble across an instruction sequence that hits this corner case.**"
> — p.197

**這是隨機測試的真正價值：抓那些「你寫不出來的」測試案例。**

書上舉的例子非常具體：**「IFU 因為 LSU 正在處理 TLB miss 而 stall 時，剛好來了中斷」**
——這種多單元交互的狀態組合，人根本設計不出對應的 directed 測試。

> "Moreover, experience shows that the constrained random test generator often unearths bugs
>  in areas unforeseen by the DV plan. **How do we know if we have generated enough code
>  sequences? The DV plan specifies code and functional coverage requirements, and we
>  generate random tests until coverage reaches 100% or it becomes easier to write some
>  directed tests for coverpoints that the random generator is not reaching.**"
> — p.197

**停止準則很清楚：跑隨機測試直到覆蓋率達 100%，
或直到「為漏掉的 coverpoint 手寫 directed 測試」比較划算為止。**
——**隨機和 directed 是互補的，不是二選一。**

**實務上混用（p.197）**：Wally 早期用簡單的 ad-hoc 程式確認基本功能，
之後用 riscv-arch-test（含 constrained random 測試覆蓋一組 coverage point）。
**因為 riscv-arch-test 目前不太涵蓋特權規格，所以也為這些功能寫 ad-hoc 和 directed 測試。**
（呼應 3.7.3 節的缺口。）

### 參考模型：兩個關鍵原則

> "Creating a reference model for a new system can be an enormous task. Although it does not
>  need to be cycle accurate and handle pipelining or out-of-order execution, it still must
>  faithfully implement every feature of the architecture. Moreover, an architecture
>  sometimes has unspecified behavior; for example, **RISC-V highly recommends but does not
>  require an illegal-instruction fault on an undefined opcode. The reference model and the
>  DUT must produce the same results in these situations.**"
> — p.198

> "**The reference model and RTL should be written by different teams to reduce the chance
>  that both models contain the same conceptual or implementation errors.**"
> — p.198

中文解釋：**兩個原則：**
1. **參考模型不需要週期精確，但必須忠實實作架構的每個功能**
   （呼應 3.1 節：ISS 不算週期）
2. **參考模型和 RTL 要由不同團隊寫**——
   **避免兩者犯同樣的概念或實作錯誤。**
   （呼應 3.7.3 節的缺口：wally 的周邊測試預期值是自己寫的，所以沒有這個保護。）

**「未指定行為」是個微妙的問題**：RISC-V 只是「強烈建議」非法 opcode 要拋例外，
沒有強制。**這種情況下參考模型和 DUT 必須表現一致**——
所以要先協調好選哪一種行為。

**三個 RISC-V 參考模型的定位（p.198）：**

| 模型 | 定位 |
| --- | --- |
| **Sail** | **官方可執行參考模型，有爭議時優先於書面規格**。但**對中斷和相關周邊的支援還不足**，某些特權行為不適合當參考 |
| **Spike** | **較成熟**，有中斷支援，是部分 OpenHW Group 核心的參考 |
| **ImperasDV** | **商用參考模型，業界廣泛使用** |

（其他 RISC-V 模擬器還有 QEMU、Whisper、IDL，p.198 邊欄。）

### 單元測試 vs 系統測試：一個現實的取捨

> "In a hierarchical development approach, different teams could develop different units,
>  such as the integer execution unit (IEU), floating-point unit (FPU), instruction fetch
>  unit (IFU), and load/store unit (LSU). Each unit could be verified in isolation with
>  unit-level testing.... Ideally, the individual units would already be correct, so
>  system-level testing would only catch integration bugs. Moreover, testing a unit is faster
>  than testing the system because it involves fewer lines of code and fewer tests irrelevant
>  to the unit."
> — p.198

> "**Unfortunately, testbench development is quite time-consuming. Creating test vectors
>  tailored to unit interfaces can also be difficult. For example, it is much easier to load
>  a program into memory and run a system-level test on an entire processor than to determine
>  all of the control, data, and stall signals going into and coming out of an LSU.**"
> — p.198

> "Consequently, teams tend to emphasize testing relatively large blocks with simple
>  interfaces. In an SoC, tests may focus on each different core or accelerator and on
>  overall SoC integration, rather than on units within a core."
> — p.198

中文解釋：**理論上單元測試比較好，實務上常常不做。理由很誠實：**

**做單元測試的成本是「要自己造出所有輸入訊號」。**
要測 LSU，你得搞清楚所有控制、資料、stall 訊號該長什麼樣——
**這比「把程式載進記憶體跑整顆處理器」難得多。**

**結論：測「介面簡單的大區塊」。**
SoC 層級就是測各個 core 和加速器，以及整體整合，而不是 core 內部的單元。

**這是一個「理想 vs 成本」的真實取捨，值得記住。**

### Emulation：模擬太慢的解法

> "An SoC with thousands to millions of lines of RTL generally simulates with a system clock
>  of **several kilohertz or even single hertz**. Running large simulations is painful,
>  especially if these simulations are repeated after each design change. Simulations are
>  accelerated by running many jobs in parallel on different cores, but this takes an
>  expensive compute farm and even more expensive simulator licenses. In contrast, if the RTL
>  is synthesized onto one or more FPGAs, it can run at **megahertz rates**. Such *hardware
>  emulation* can accelerate verification by orders of magnitude."
> — p.198–199

中文解釋：**數字對比很震撼：軟體模擬「幾 kHz 甚至 1 Hz」，FPGA 模擬「MHz」。**
差了三到六個數量級。

**FPGA emulation 的實際狀況（p.199）：**
- **中等複雜的系統可以裝進一顆大 FPGA**，成本數千到數萬美元
- 需要中等程度的基礎建設開發（透過晶片介面施加和檢查測試向量）
- **合成、place and route、下載到 FPGA 要幾分鐘到幾小時**
- **模擬要跑幾天的測試，在 FPGA 上可能幾秒就跑完**
- **但代價：如果輸出不符預期，用笨拙的晶片內邏輯分析器介面隔離 bug 可能要花幾小時**

**這就是 5.1 節開頭那句「模擬慢但可見度完整；硬體模擬快好幾個數量級但可見度受限」**（p.196）
的具體展開。**取捨是「速度 vs 可見度」。**

**商用 SoC 太大裝不下單一 FPGA（p.199）：**
用 **Cadence Palladium 或 Synopsys ZeBu** 這類商用模擬系統，
裡面是整櫃的 FPGA、RAM 和 I/O，處理數千億個邏輯閘。
**這些系統要價數百萬美元，是大型驗證的珍貴資源。**

### TRL：成熟度的共通語言

> "NASA developed a TRL scale in the 1970s to discuss the level of technical maturity for
>  space systems.... Whereas academia usually develops prototypes in TRL 1−4, industry
>  commercializes products in TRL 7−9. **TRLs 4−7 are sometimes called the *Valley of Death*,
>  where neither academia nor industry prioritizes funding.**"
> — p.199

中文解釋：**"Valley of Death"（死亡之谷）這個概念很重要**：
學界做到 TRL 1–4，業界從 TRL 7–9 接手，**中間的 4–7 沒人願意出錢。**

**OpenHW Group 的定位就是搭這座橋**（p.199）：
"The OpenHW Group aims for collaborations between industry and academia to bridge the
Valley of Death." **多數核心以 TRL5 為目標，相當於新的商業授權處理器 IP。**

**Table 5.2（p.200）的 OpenHW TRL 定義，摘要：**

| TRL | 名稱 | OpenHW 的對應 |
| --- | --- | --- |
| 1 | Basic Principles Observed | 研究專案產出 |
| 2 | Concept Formulation | Core IP 開發專案的起點 |
| **3** | **Proof of Concept** | **RTL 設計完成；核心能編譯、能開 Linux、有 CoreMark 結果** |
| **4** | **Component Prototype** | **產出初步 PPA 結果（FPGA 或 ASIC 合成）** |
| **5** | **Subsystem Designed and Tested** | **完成完整驗證；通過 OpenHW RTL Freeze 檢查清單，可供業界採用** |
| 6 | Functional (Alpha) Prototype | 整合進 MCU 系統，原型矽片製造並在開發板上展示 |
| 7 | Field Demonstration Prototype | 原型矽片製造、部署並在實地展示 |

**Wally 的實際進度（p.199）：**
- **TRL3**：通過 riscv-arch-tests 並在模擬中開 Linux ✓
- **TRL4**：有合成結果，且 FPGA 實作能在實驗室開 Linux ✓
- **TRL5（尚未達成）**需要：
  - **所有待測功能都有設計驗證計畫**
  - **DV 計畫中所有項目達 100% 功能覆蓋率**
  - **100% 程式碼覆蓋率（line、condition、branch、FSM）**
  - **所有測試在回歸中通過**
  - **沒有未解決的問題**

**這五條就是「完整驗證」的操作型定義**，也是第 5 章後面各節的目標。

### always-broken vs always-working（本節第二重要的觀念）

> "Back in the bad old days of the 1990s, design and verification were often rigidly
>  separated. Designers wrote RTL, perhaps ran basic unit testing, and then threw the code
>  "over the wall" to a verification team, often in a different country. The verification
>  team would locate bugs and throw them back to the designer to fix. **This process was slow
>  because of the loose coupling between teams and tended to increase verification cost
>  because the designer made decisions without awareness of how they would affect the
>  verification effort.**"
> — p.200

> "As verification cost came to exceed design cost, teams adopted more collaborative
>  approaches. **Successful SoC projects now begin with the goal of verification in mind.**"
> — p.201

中文解釋：**「丟過牆」的模式失敗了，因為設計者做決定時不知道會怎麼影響驗證成本。**
（呼應 2.10 節：「每個功能都從 test plan 開始」。）

**兩種策略的對比（p.201）——這是本節最有價值的一段：**

| | **always-broken** | **always-working** |
| --- | --- | --- |
| 做法 | 各自開發單元並除錯 → **最後才整合整個系統** → 跑系統回歸 | **一次就完成困難的整合**（用盡可能小的功能集）→ **每加一個功能就先跑系統層級回歸再簽入** |
| 整合 | 整合時必然浮現大量互相依賴的困難 bug，**除錯很久** | **只做一次痛苦的整合** |
| 期間狀況 | **系統壞著，別人無法繼續開發**（沒有可用的原型可以改進）；單元擁有者只能各自加功能做單元測試 | **回歸永遠是通過的** |
| 除錯難度 | 難（不知道是誰造成的） | **容易——設計者確切知道是哪個改動造成的** |
| 結果 | **整體回歸永遠是壞的**，只在成功整合後有短暫的正常期，然後痛苦的整合過程重演 | 新功能和測試在系統除錯後逐步加入 |

**always-working 的關鍵洞見：「每次只加一點、加之前先確認不會破壞現有功能」，
讓除錯範圍永遠很小。**

**書上也承認現實（p.201）：**
> "In the real world, this is sometimes impractical, due to adding a very large new feature,
>  restructuring the design or test cases, or because of license, hardware, or software
>  problems that temporarily stall regression. **However, when these problems arise, the team
>  should prioritize getting back to a working code base as quickly as possible.**"

### Test-driven development

> "*Test-driven development* [Beck03] is a development process in which the test cases are
>  written before the code. It can be viewed as a disciplined form of always-working
>  verification. The general process is:
>  1. Add a new test for added capability.
>  2. Run all the tests and confirm the new one fails.
>  3. Make a code change to implement the added capability.
>  4. Run all the tests and confirm the new one succeeds.
>  5. Refactor the code to remove duplication."
> — p.202

中文解釋：**TDD 是 always-working 的紀律化版本。**

**第 2 步（確認新測試會失敗）常被忽略但很重要**——
如果新測試一開始就通過，表示它根本沒測到你想測的東西。

**Wally 的實際做法（p.202）：**
> "Tracking down a complex bug in a large RTL system through simulation is so time consuming
>  and painful that developers strive to minimize doing this. **Wally has gravitated toward
>  an always-working test-driven methodology. Whenever possible, small changes are made and
>  immediately tested to confirm that they work and don't break other features. If a change
>  introduces a bug, it may be faster to discard the change and re-create it carefully in
>  smaller steps than to diagnose the bug in a waveform viewer.**"

**最後那句很實在：出了 bug 時，「丟掉改動、用更小的步驟重做」可能比
「在波形檢視器裡查 bug」還快。**

工作流程（p.202）：
**在自己 fork 的 dev 分支上改 → 功能完成並測試後發 pull request 進 main 分支。**
（呼應 4.1.2 節的版本控制。）

## 名詞表

| 名詞 | 意思 |
| --- | --- |
| DUT | Device under test，待測物 |
| UVM | Universal Verification Methodology。業界標準的物件導向驗證方法學 |
| Exhaustive testing | 窮舉測試。只對極小模組可行 |
| Ad-hoc / exploratory testing | 依對設計的理解，用少量測試向量快速建立基本信心 |
| **Directed testing** | **系統性覆蓋 corner case**（如 12 個邊界值的 cross-product） |
| Cross-product | 交叉乘積。所有 corner case 組合 |
| **Coverage-driven testing** | **先定義必須測到的 coverage point，再想辦法覆蓋** |
| **Constrained random test generator** | **產生大量隨機指令序列，專門抓「人寫不出來的」難尋案例** |
| Reference model | 參考模型。**應由不同團隊撰寫**，避免和 RTL 犯同樣錯誤 |
| Unspecified behavior | 架構未強制規定的行為；參考模型與 DUT 必須表現一致 |
| **Hardware emulation** | **把 RTL 合成到 FPGA 上跑**。kHz → MHz，快好幾個數量級，但可見度受限 |
| TRL | Technology Readiness Level。NASA 起源的成熟度量表 |
| **Valley of Death** | **TRL 4–7，學界與業界都不優先投資的區間** |
| **always-broken / always-working** | **最後才整合（回歸長期壞掉）/ 一次整合後持續小步驗證（回歸永遠通過）** |
| Test-driven development | 先寫測試再寫程式碼；always-working 的紀律化形式 |
| Regression | 回歸測試。確認新改動沒有破壞既有功能 |

## 所以呢

**兩個觀念決定了整章的走向：**

1. **測試向量的光譜**：窮舉（不可行）→ ad-hoc（快速信心）→ directed（覆蓋邊界）
   → coverage-driven（定義必須測到的點）→ **constrained random（抓人想不到的組合）**。
   **實務上全部混用，停止準則是「覆蓋率達 100%」。**

2. **always-working 策略**：一次完成整合，之後每加一個功能都先跑系統回歸。
   **這讓除錯範圍永遠很小**——出問題時你知道就是剛才那個改動。

還有兩個值得記住的具體事實：
- **Pentium FDIV bug 花了 Intel 4.75 億美元**，而 directed 測試抓不到它。
- **Wally 目前在 TRL4，要到 TRL5 需要 100% 程式碼與功能覆蓋率**——
  這就是 5.8 和 5.9 節的目標。

下一節（5.2）講怎麼把這些要求寫成一份 DV 計畫。
