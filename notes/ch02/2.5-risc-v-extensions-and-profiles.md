# 2.5 RISC-V Extensions and Profiles

> 原書 p.52–54（Chapter 2: Introduction to RISC-V）
> 涵蓋 2.5.1 RISC-V Profiles

## 這節在講什麼

RISC-V 最重要的結構性設計：**模組化擴充機制**。

核心觀念是：**基礎指令集（RV32I / RV64I）刻意做到最小，其他全部是選配擴充。**
要乘法就加 M，要浮點就加 F/D，要壓縮就加 C。
一個微控制器可以只實作 RV32I，一顆伺服器晶片可以疊十幾個擴充。

但這帶來一個新問題：**選配太多會碎片化**——軟體不知道能假設什麼。
解法是 **profile（規格組合）**：預先定義好幾套標準組合，
軟體開發者就針對 profile 寫程式，不用管每顆晶片的細節。

**「擴充 + profile」這組機制，是 RISC-V 能同時服務微控制器和伺服器的原因。**

## 關鍵點

### 基礎指令集：RV32I 和 RV64I

> "The base instruction sets are known as RV32I or RV64I. These operate on 32- or
>  64-bit registers, respectively. The RISC-V Unprivileged Specification defines
>  several other ratified extensions (see Table 2.2)."
> — p.52

中文解釋：**「base」這個字要抓住**——RV32I / RV64I 是地基，**任何 RISC-V 處理器都必須有**。
上面疊什麼是自由的。這跟 x86/ARM 完全不同：那些架構的指令集是一整包，沒得選。

### 主要擴充一覽

> "The M extension supports multiply, divide, and remainder instructions. The F, D,
>  and Q extensions support single-, double-, and quad-precision floating-point math,
>  respectively. All of these could be emulated in software but are much faster with
>  hardware support. The A extension introduces atomic instructions used for
>  synchronization between multiple RISC-V harts."
> — p.52

中文解釋：Table 2.2（p.52）的完整清單，**這張表值得記熟**：

| 擴充 | 內容 |
| --- | --- |
| **A** | Atomic read-modify-write，用於同步 |
| **B** | Bit manipulation（B = Zba + Zbb + Zbs） |
| **C** | **Compressed（16-bit 指令）** |
| **E** | Embedded（暫存器縮減為 x0–x15） |
| **F, D, Q** | 單 / 雙 / 四倍精度浮點 |
| **M** | **乘、除、取餘** |
| **Zicsr** | **CSR 與特權指令** |
| **Zifencei** | `fence.i` 指令 / 指令記憶體同步 |
| **V** | Vectors（資料平行） |
| **U** | User mode |
| **S** | Supervisor mode（給 OS 和虛擬記憶體） |
| **H** | Hypervisor（多個並行作業系統） |
| **G** | **= I, M, F, D, A, Zicsr, Zifencei**（常用組合的縮寫） |

**注意 M 是選配的**——連乘法都不是基礎指令！
這就是「base 做到最小」的極致。（所以 2.1 節的階乘範例用了 `mul`，
書上特別註明那來自 M 擴充。）

書上也點出一個關鍵取捨：**"All of these could be emulated in software but are
much faster with hardware support."**——
擴充不是「有或沒有」的功能差別，而是**速度差別**。
沒有 FPU 也能算浮點（軟體模擬，見 2.3.6 節的例外處理範例），只是慢。

### G = 常見的應用處理器組合

> "Most application processors support the M, F, D, and A extensions and CSRs and
>  instruction fences, which is written as RV64IMAFD_Zicsr_Zifencei. A processor
>  with all these extensions is abbreviated as RV32G or RV64G."
> — p.52

中文解釋：**`G` 是 "general purpose" 的縮寫**，
等於 `IMAFD_Zicsr_Zifencei` 這一長串。所以 **RV64G = RV64IMAFD_Zicsr_Zifencei**。
看到 RV64G 就知道「這是一顆該有的都有的通用處理器」。

### C 擴充：壓縮指令，省 25–30% 程式碼

> "Nonvolatile program memory can be the most expensive component in an embedded
>  processor, so these processors usually support a compressed instruction set
>  (similar to the ARM Thumb instructions) that packs most frequently used
>  instructions into only 16 bits. The RISC-V C extension provides these compressed
>  instructions, reducing instruction bits fetched by up to 25% or 30%.
>  RV64GC = RV64IMAFDC_Zicsr_Zifencei contains all of the standard extensions."
> — p.53

中文解釋：**壓縮指令的動機是成本，不是效能**——
嵌入式處理器裡，**非揮發性程式記憶體（flash/ROM）往往是最貴的元件**。
把常用指令壓成 16-bit，程式碼小 25–30%，直接省錢。

（順帶：這也是 2.1 節那個「分支偏移最低位元恆為 0」技巧的前提——
因為有 16-bit 指令，所以指令在 **2-byte 邊界**而非 4-byte 邊界。）

**RV64GC 是最完整的標準組合**，這也是 Wally 支援的等級。

### E 擴充：砍掉一半暫存器，省 1/4 面積

> "RV32E targets tiny embedded cores. The RV32I register file comprises about half
>  the area of a minimal core, so RV32E eliminates registers x16-x31 to save a
>  quarter of the core area."
> — p.53

中文解釋：**這個數字很震撼：暫存器檔案佔了一個極簡核心約一半的面積。**
（呼應 1.6 節 RISC-I die photo——暫存器檔案確實佔了大半張晶片。）

砍掉一半暫存器 → 省下**四分之一的核心面積**。
對極小的嵌入式核心來說這是巨大的節省。

**這也解釋了 2.1 節那個「暫存器命名順序很怪」的邊欄**：
命名刻意安排成「只用 x0–x15 時，每一類用途（ra、sp、s、t、a）都還有得用」——
就是為了讓 E 擴充可用。**設計時就預留了這條路。**

### Zicsr 和 Zifencei

> "The Zicsr extension introduces CSRs and instructions to read and write these
>  registers; this is necessary to support traps, multiple privilege modes, and
>  other configuration options. The Zifencei standard extension adds the fence.i
>  instruction to synchronize writes and fetches for instruction memory. This is
>  needed by operating systems that load programs into memory."
> — p.53

中文解釋：**連 CSR 都是選配的**（Zicsr）——這代表最小的 RISC-V 處理器
連 trap 機制都可以沒有。（呼應 2.1 節說「沒有 mtvec 的話 `ecall` 什麼都不做」。）

`fence.i` 的用途值得理解：**當你把程式寫進記憶體（當資料寫），
然後要跳過去執行它（當指令讀）**，中間需要同步——
因為指令 cache 可能還存著舊的內容。
**這正是 OS 載入程式時必須做的事。**

### RV128I：預留給未來

> "RISC-V also defines an unratified base instruction set RV128I supporting 128-bit
>  memory addresses by using 128-bit registers, anticipating that the 64-bit addresses
>  of RV64I (which support 16 exabytes of memory) will eventually become insufficient
>  for large computers."
> — p.53

中文解釋：64-bit 位址能定址 **16 exabyte**，看似用不完，但 RISC-V 已經預留了 RV128I。
書上很坦白：**"No commercial need yet exists for 128-bit addresses, and the
standard may evolve when these large systems are developed."**（p.53）

旁邊那句引言是本節最好的一句話（p.53 邊欄，出自 Bell75）：

> "There is only one mistake that can be made in computer design that is difficult
>  to recover from—not providing enough address bits for memory addressing and memory
>  management. The PDP-11 followed the unbroken tradition of nearly every computer."
> — p.53 邊欄

**「電腦設計唯一難以挽回的錯誤，就是位址位元給得不夠。」**
呼應 1.4 節 PDP-11 因為 18-bit 位址不夠而被 VAX 取代。
**RV128I 的存在就是為了不重蹈覆轍。**

### 廠商自訂擴充：自由，但有反向誘因

> "RISC-V vendors are free to develop their own proprietary nonstandard extensions.
>  Such extensions can provide a competitive advantage. However, vendors also have
>  an incentive to publish and standardize their extensions to increase software
>  adoption."
> — p.53

中文解釋：**這是 RISC-V 生態系治理的關鍵張力，說得很精準：**
- **自訂的誘因**：差異化、競爭優勢
- **標準化的誘因**：**只有標準化，編譯器和軟體才會支援你**

第二個誘因是自我修正機制——你可以自己搞，但沒人幫你寫軟體。
這比純粹禁止有效。（呼應 1.7 節說 RISC-V International 的治理是關鍵。）

書上邊欄還提到偵測機制（p.53 邊欄）：
程式可以讀 **`misa` CSR（machine instruction set architecture）**
來查詢有哪些字母擴充可用，然後決定用擴充指令還是呼叫函式庫。
**"RISC-V International is in the process of defining a standard way to determine
whether other named extensions (e.g., Zifencei) are supported."**
——字母擴充查得到，具名擴充（Z 開頭那些）的查詢機制還在制定中。

### 加速器也算 RISC-V 系統的一部分

> "Some RISC-V systems provide *accelerators* for specialized tasks. An accelerator
>  might be a fixed-function unit such as an H.265 video decompressor or a
>  programmable unit such as a graphics processor. An accelerator typically
>  communicates with the cores through shared memory."
> — p.53

中文解釋：呼應 1.2 節的 SoC 和 dark silicon。
**加速器不是擴充指令，是獨立的硬體單元，透過共享記憶體跟核心溝通。**
這是兩種不同的加速途徑：
- **擴充指令**（如 V 向量擴充）：在核心裡加功能單元
- **加速器**：在核心外加獨立單元

### Profile：對抗碎片化的機制

> "RISC-V has a great deal of configurability and extensibility. Initially, it used
>  ISA strings such as RV64IMAC to define the supported extensions, but these are
>  becoming unwieldy as more extensions are added with longer names, resulting in
>  strings such as RV64IMAFDC_Zicsr_Zifencei_Zicclsm_Zba_Zkt_Svnapot. RISC-V defines
>  *profiles* to capture standard collections of extensions. Software developers can
>  specify a profile with a minimum feature set needed to run the software."
> — p.53

中文解釋：**問題很具體**：ISA 字串已經長到人類無法閱讀，
而且軟體開發者不可能針對每一種組合測試。

**Profile 是解法**：把「合理的組合」預先命名。
軟體說「我需要 RVA22S64」，晶片說「我符合 RVA22S64」，就搭上了。

已批准的 profile 清單（p.54）：

| Profile | 內容 |
| --- | --- |
| RVI20U32 | Basic unprivileged RV32I |
| RVI20U64 | Basic unprivileged RV64I |
| RVA20U64 | Application processor RV64GCU |
| RVA20S64 | Application processor RV64GCUS |
| RVA22U64 | Application processor RV64GCBU |
| **RVA22S64** | **Application processor RV64GCBUS with rich OS** |
| RVA23U64 | Application processor RV64GCBVU with rich OS |
| RVA23S64 | Application processor RV64GCBVUSH with rich OS |
| RVB23U64 | Customized processor RV64GCBU |
| RVB23S64 | Customized processor RV64GCBUS |

**命名規則讀得出來**：`RV` + 類別（I=基本 / A=application / B=customized）
+ 年份（20/22/23）+ 模式（U=只有 user / S=含 supervisor）+ 位元寬。

**RVA22S64 要記住**——第 2 章開頭（p.32）就說了 **Wally 支援 RVA22S64 profile**。

### Profile 的三個規定

> "All profiles are little-endian. The profiles strongly recommend raising an illegal
>  instruction exception on unimplemented opcodes."
> — p.54

> "Notice that the profiles standardize U- and S-mode features. Only a small amount
>  of portable firmware runs in machine mode, so M-mode features are not standardized."
> — p.54

中文解釋：三個重點：
1. **所有 profile 都是 little-endian**（呼應 2.1 節）
2. **強烈建議未實作的 opcode 要觸發 illegal instruction exception**——
   這樣軟體才能靠 exception handler 做軟體模擬（呼應 2.3.6 節的 FPU 例子）
3. **profile 只標準化 U-mode 和 S-mode，不管 M-mode**

第三點的理由很實際：**只有很少量的可攜韌體跑在 M-mode**，
M-mode 的東西本來就跟平台綁死（呼應 2.3.6 節說 SBI 讓同一份 OS 跑在不同晶片上——
**變的就是 M-mode 那層韌體**）。

書上邊欄還提到 profile 也統一了一些細微行為（p.54 邊欄）：
有沒有硬體效能監視器（Zihpm）、虛擬記憶體的 dirty bit 是硬體設定還是軟體例外（Svadei）、
cache block 是不是 64 bytes（Zic64b）。
**"The RISC-V profiles gave these behaviors names in March 2023 so that platforms
can rely on consistent behavior."** ——連這種小地方都要命名，就是為了防碎片化。

## 名詞表

| 名詞 | 意思 |
| --- | --- |
| Base instruction set | 基礎指令集 RV32I / RV64I。所有 RISC-V 處理器必備 |
| M / A / F, D, Q / C / E / V / B | 乘除 / 原子 / 浮點 / 壓縮 / 嵌入式 / 向量 / 位元操作 擴充 |
| Zicsr / Zifencei | CSR 與特權指令 / `fence.i` 指令記憶體同步 |
| G | = I, M, F, D, A, Zicsr, Zifencei（通用組合縮寫） |
| RV64GC | 含所有標準擴充的 64 位元組態 |
| RV32E | 嵌入式版本，砍掉 x16–x31，省約 1/4 核心面積 |
| RV128I | 未批准的 128 位元基礎指令集，預留給未來 |
| `misa` CSR | 可讀取以查詢支援哪些字母擴充 |
| Accelerator | 加速器。獨立硬體單元，透過共享記憶體與核心溝通 |
| Profile | 規格組合。預先定義的標準擴充集合，如 RVA22S64 |

## 所以呢

**RISC-V 的模組化（最小 base + 選配擴充）讓同一套 ISA 能從微控制器涵蓋到伺服器，
但代價是碎片化風險——profile 就是治理這個風險的機制。**
兩件實務上要記住的事：**RV64GC 是完整的標準組合**，
**RVA22S64 是 Wally 目標的 profile**。
下一節（2.6）拿 RISC-V 跟 ARM、MIPS、SPARC、x86 直接比較，
把 1.7 節那張「設計陷阱清單」講完整。
