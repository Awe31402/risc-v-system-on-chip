# 11.3 Test Plan

> 原書 p.495（Chapter 11: Memory Management Unit）

## 這節在講什麼

**MMU 的測試計畫，一頁不到。**

三件事：
1. **官方測試完全沒有 MMU 測試**——全靠 Wally 手寫
2. **測試檔的命名規則**（依組態不同要用不同的檔案）
3. **一個明確的缺口：`sfence.vma` 沒有測試**

## 關鍵點

### 官方測試的空白

> "**At the time of this writing, riscv-arch-test does not yet have MMU tests. Handwritten Wally MMU tests that
>  exercise each feature at least once are in `tests/wally-riscv-arch-test/riscv_test_suite/rv{32/64}i_m/
>  privilege`. More comprehensive functional verification tests are under development at the time of this
>  writing.**"
> — p.495

中文解釋：**"does not yet have MMU tests"——官方測試套件對 MMU 是完全空白的。**

**「每個功能至少測一次」（exercise each feature at least once）
是很低的標準**——它只能抓到「完全沒實作」的錯誤，
抓不到 corner case 和功能間的交互作用。

（呼應 3.7.3 節、8.3 節：特權和 MMU 的測試一直是 RISC-V 生態系的弱點。）

**測試放在特權測試的目錄下**（`rv{32/64}i_m/privilege`），
和第 8 章的特權測試在一起。

### 測試檔清單

> "**The `WALLY-pma.S` and `WALLY-pmp.S` test files check basic operation of the PMA and PMP, including each type
>  of normal and exceptional access. The virtual memory tests are in `WALLY-mmu-sv32` for RV32 and
>  `WALLY-mmu-sv{39/48}` for RV64. If Svadu, Svnapot, and Svpbmt are supported, use
>  `WALLY-mmu-sv*-svadu-svnapot-svpbmt` instead.**"
> — p.495

中文解釋：**測試檔的對應關係：**

| 測試檔 | 測什麼 |
| --- | --- |
| **`WALLY-pma.S`** | **PMA 的基本操作**（每種正常與例外存取） |
| **`WALLY-pmp.S`** | **PMP 的基本操作** |
| **`WALLY-mmu-sv32`** | RV32 的虛擬記憶體 |
| **`WALLY-mmu-sv39` / `WALLY-mmu-sv48`** | RV64 的虛擬記憶體 |
| **`WALLY-mmu-sv*-svadu-svnapot-svpbmt`** | **支援那三個擴充時改用這個** |

**注意最後一項：擴充支援與否會改變預期行為，所以要用不同的測試檔。**
（例如 Svadu 支援時 HPTW 會硬體更新 A/D 位元而不 fault——
**同一個測試在兩種組態下的正確答案不同。**）

### 測試的設計

> "**These tests require a page table rich enough to exercise all the virtual memory features and exception
>  conditions. SV48 uses the 4-level table from Fig. 11.10(a), and the other flavors use similar tables.**"
> — p.495

中文解釋：**測試的核心是那張「刻意設計得很豐富的頁表」。**

**回顧 Fig. 11.10(a)（11.2 節，p.485）裡刻意放進去的問題項目：**
- **Misaligned Terapage**（對齊錯誤）
- **Misaligned Megapage**
- **Aligned Gigapage / Megapage**（正確的對照組）
- **`Writes fault for D = 0`**
- **`Reads fault for A = 0`**
- **`Illegal to have W but not R`**（`XWR = 010`）
- **`Can't point to Level -1`**（level 0 的 PTE 卻是 `XWR = 000`）

**這張頁表本身就是測試計畫**——每一個畸形項目對應一種例外條件。
**這是一個很值得學的測試設計手法：把所有錯誤情況編碼進一個資料結構裡。**

### 明確的缺口

> "**No tests are yet written for `sfence.vma`.**"
> — p.495

中文解釋：**一句話承認缺口。**

**`sfence.vma` 沒測的後果值得想一下：**
- 它負責 invalidate TLB（11.2.4 節）
- **改完頁表沒有正確 invalidate → 程式會用到過期的轉譯**
- **這種 bug 在一般測試中幾乎不可能被發現**，
  因為它只在「改頁表 + 剛好有舊項目在 TLB 裡」時才出現

（呼應 8.3 節 Table 8.5：`sfence.vma` 在特權指令測試裡也是標記為 "Not explicitly tested yet"。
**同一個缺口被提到兩次。**）

**詳細的 MMU 測試計畫在 `docs/testplans`**（p.495）。

## 所以呢

**這節很短，但透露了三件事：**

1. **官方測試套件完全沒有 MMU 測試**——全部靠 Wally 手寫，
   而且標準只是「每個功能至少測一次」。

2. **那張「刻意畸形」的頁表（Fig. 11.10a）本身就是測試計畫**——
   把 misaligned superpage、`A = 0`、`D = 0`、`XWR = 010`、
   「level 0 卻是指標」等錯誤條件全部編碼進一個資料結構。
   **這是很值得學的測試設計手法。**

3. **`sfence.vma` 完全沒有測試**——
   這個缺口在第 8 章也被提過一次。
   它的 bug 很難被一般測試抓到，因為只在特定時序下才出現。
