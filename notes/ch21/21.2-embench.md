# 21.2 Embench

> 原書 p.784.e27–784.e39（Chapter 21: Benchmarking）
> 涵蓋 21.2.1 Porting Embench、21.2.2 Embench Flags、21.2.3 Instruction Set Impact、21.2.4 Troubleshooting

## 這節在講什麼

Embench 是為了修正 CoreMark 那些問題而設計的新 benchmark：**用真實程式而不是合成程式、用 19 個程式的幾何平均而不是單一分數、同時測速度與程式大小**。

這節也是全書少數會**公開承認自己的 benchmark 結果有問題**的地方——書上發現 `nbody` 的分數 1,480 是假的，並且追查出原因，然後把它從平均裡剔除。這個 debug 過程比分數本身更有價值。

## 關鍵點

### Embench 的四個設計原則

> "Embench is: Free and easy to use. Based on a suite of actual programs that are really used. Supported by both academics and industry. Summarized by a single score based on the geometric mean of the program performances."
> — p.784.e29

中文解釋：第二點是對 synthetic benchmark 的直接回應。第四點的**幾何平均**很重要——算術平均會被單一極端值主宰，幾何平均對「各程式的相對比值」比較公平（這也是為什麼後面 `nbody` 的 1,480 能把平均從 1.67 拉到 2.39）。

### 19 個程式與它們的多樣性

> "Table 21.3 summarizes the programs included in Embench Version 1.0. The programs span a range of common embedded applications, from sorting to data compression to mathematics. All are less than 3,000 lines of C code and require less than 16 KiB of program memory and 4 KiB of data memory, so they fit on the smallest of processors. Different programs stress the branch predictor, memory system, and ALU in different ways."
> — p.784.e29–e30

中文解釋：Table 21.3 列出 19 個程式（`aha-mont64` 蒙哥馬利乘法、`crc32`、`cubic` 三次方根、`edn` 濾波器、`huffbench` 壓縮、`matmult`、`minver` 矩陣反轉、`nbody`、`nettle-aes`、`nettle-sha256`、`nsichneu` Petri 網、`picojpeg`、`qrduino` QR 碼、`sglib`、`slre` 正規表示式、`st` 統計、`statemate` 狀態機、`ud` 矩陣分解、`wikisort` 合併排序），並且標註每個程式對 branch / memory / compute 的壓力等級（low/med/high）。

**這個多樣性是 Embench 相對 CoreMark 的核心優勢**——單一程式只能反映一種工作型態。

> "Each program is tuned to take about 4 seconds to run on a Cortex-M4 reference processor, so the entire benchmark can run in a few minutes on physical hardware."
> — p.784.e30

中文解釋：**所有分數都是相對於 ARM Cortex-M4 的正規化值**。邊欄說明為什麼選它：「Cortex-M4 是 3 級管線的嵌入式處理器，有 Thumb 壓縮指令集、乘法指令、以及 AHB 介面接指令與資料記憶體。對 RV32IMC 的管線實作而言是一個合理的競爭對手。」

### 四種測量：速度與大小各兩種最佳化

> "Embench measures both the speed and code size. Moreover, it is compiled in flavors that optimize for speed and for size. Hence, Embench makes four measurements. The overall Embench results are the geometric mean of the size or speed of all the Embench benchmarks."
> — p.784.e31

中文解釋：`sizeopt`（用 `-Os`）和 `speedopt`（用 `-O2`）兩種編譯，各自量速度與大小——總共四個數字。這比 CoreMark 的單一分數資訊量大得多，而且**逼你面對取捨**。

### 暖機：一個常被忽略的方法學細節

> "The Embench main() function in embench-iot/support/main.c warms up the caches and branch predictor by running a benchmark once using the warm_caches() function. Warmup removes compulsory cache misses and initializes the branch history table, giving a more realistic estimate of long-term program behavior."
> — p.784.e32

中文解釋：**先跑一次不計時，第二次才量**。理由是：真實程式跑很久，開頭那些 compulsory miss（強制失誤，第一次碰到資料一定會失誤）佔比極小；但 benchmark 只跑幾秒，不暖機的話這些一次性成本會嚴重扭曲結果。

### 結果：速度與大小的取捨

> "The sizeopt size is 1.05, indicating that the RV32IMC ISA uses 5% more code storage than ARMv7-M (primarily because it lacks bit manipulation instructions). The speedopt speed is 1.04, which indicates that the Wally rv32gc configuration takes a mean 4% fewer cycles to execute the benchmarks than the Cortex-M4."
> — p.784.e33

中文解釋：Table 21.4 的總結（記住：**大小越小越好、速度越大越好**）：

| | Size | Speed | CPI |
| --- | --- | --- | --- |
| sizeopt (`-Os`) | 1.05 | 0.98 | 1.20 |
| speedopt (`-O2`) | 1.22 | 1.04 | 1.18 |

> "Compared to the mean sizeopt results, the mean speedopt results show a 6% speed increase (from 0.98 to 1.04) at a 17% increase in code size (from 1.05 to 1.22)."
> — p.784.e33

中文解釋：**6% 的速度要用 17% 的程式大小去換**——這個比率對嵌入式系統來說通常不划算（記憶體就是成本）。這正是 Embench 同時報告四個數字的價值：一個數字看不出這種取捨。

CPI 比 CoreMark（1.14）高：

> "The mean CPI is 1.20 for sizeopt and 1.18 for speedopt. These are somewhat higher than for CoreMark because the Embench benchmarks push the pipeline and branch predictor harder. nsichneu has an unusually high CPI because of the large number of use-after-load stalls as well as a substantial number of branches and branch mispredictions."
> — p.784.e34

中文解釋：這證明 Embench 是更嚴苛（也更真實）的測試。

### 為什麼某些程式在 RISC-V 上特別慢

> "notable slow RISC-V programs include cubic, minver, nbody, and st. cubic uses long double variables, which GCC treats as 64-bit on ARM but 128-bit on RISC-V, so RISC-V is naturally much slower [Gallmann21]. The other three also use floating-point arithmetic, which is less efficient in the RISC-V libraries."
> — p.784.e34

中文解釋：**`cubic` 慢不是因為處理器慢，是因為 `long double` 在 RISC-V 上是 128 位元而 ARM 上只有 64 位元**——同樣的 C 程式在做不同精度的運算。這是跨架構 benchmark 的典型陷阱：你以為在比硬體，其實在比 ABI 和函式庫。

> "nettle-sha256 is much larger on rv32imc because of the lack of bit manipulation instructions such as rotate and reverse used for hashing."
> — p.784.e34

中文解釋：呼應第 18 章——SHA-2 的 sigma 函數沒有 `ror` 就要好幾條指令。

### Embench 1.0 的一個已知瑕疵

> "Embench 1.0 discards the libraries in the size calculations. Unfortunately, it is not perfectly consistent; in particular, start_trigger and stop_trigger comprise 36 bytes on ARM and 4 bytes on RISC-V. This causes short benchmarks to have a size score greater than 1 on RISC-V even though the density of the main code is comparable to ARM."
> — p.784.e34

中文解釋：**測量工具本身的偏差**。這種細節（36 bytes vs 4 bytes 的量測用程式碼被算進去）會系統性地讓短程式的 RISC-V 分數偏高。書上點出這點，值得學習的是「看 benchmark 結果要先理解它怎麼量的」。

### ISA 的影響：比 CoreMark 更細緻的結論

> "The base instruction set greatly underperforms the reference Cortex-M4 with only about half the speed. However, with just the addition of the M extension, Wally outperforms Cortex M4 by 4% on average, clearly showing how important multiply is to the workloads in the Embench benchmark."
> — p.784.e36–e37

中文解釋：Table 21.7 的幾何平均速度：rv32i = 0.52 → rv32im = 1.04。**單靠 M 擴充就從「只有一半速度」變成「快 4%」**，和 CoreMark 的結論一致。

**C 擴充的完整分析**（這是全章最好的微架構討論）：

> "The C extension reduces code size by 28% for Embench. It improves the performance of some applications but reduces the performance of others. This highlights the inherent microarchitectural tradeoff Wally made when implementing the IFU spill logic. Because compressed instructions are smaller, more will fit within a single cache line and on average should improve the instruction cache hit rate as this is equivalent to increasing the cache line length. However, the cache SRAM implementation has one read/write port, so if a 4-byte instruction spills across cache line boundaries, the spill logic breaks the request into two sequential reads, thus slowing down instruction fetch. The net speed is approximately equal with and without the C extension."
> — p.784.e37–e39

中文解釋：C 擴充有**兩個方向相反的效應**：
- **好處**：指令變小 → 一條快取線裝得下更多指令 → 等同於加長快取線 → I$ 命中率上升
- **壞處**：4 位元組指令可能跨快取線 → spill 邏輯要拆成兩次循序讀取（因為 SRAM 只有一個讀寫埠）→ 取指變慢

**兩者幾乎抵消**，所以淨速度持平。但程式大小減少 28%——所以 C 擴充是「免費」拿到程式密度。這個分析把第 7 章（spill 邏輯）、第 10 章（快取）、第 14 章（壓縮指令）串起來了。

> "The bit manipulation extensions (Zba, Zbb, Zbc, Zbs) have a profound impact on nettle-sha256, which uses rotations extensively, and a small improvement on a few others ... The mean benefits are 4% decreased size and 5% increased speed."
> — p.784.e39

中文解釋：這正是第 18 章開頭引用的數字來源。

### 一個假的 3000 倍加速

> "nbody in particular executes only 1,025 instructions with the D extension but more than 3.1 million without it. It is not credible that floating-point should bring a 3000x reduction in instructions. On close examination, we see that the rv32imc version calls bodies_energy 100 times in a loop. The rv32gc version detects that the call to bodies_energy produces an invariant result and then adds that result up 100 times. Discarding this bad benchmark brings the geometric mean for speedopt_speed down to a more plausible 1.67."
> — p.784.e39

中文解釋：**這是全章最有教育意義的一段。** Table 21.7 裡 `nbody` 在 rv32gcb 的速度是 **1,480**（其他程式都在 1 左右），`st` 是 23.7、`minver` 是 7.24——這些數字顯然不對。

追查結果：**編譯器發現 `bodies_energy()` 的回傳值是常數（loop-invariant），於是把 100 次呼叫優化成「算一次，加 100 次」**。程式沒跑錯，只是被最佳化掉了——benchmark 測不到它想測的東西。

書上的處理方式值得學：**不是接受 2.39 這個好看的數字，而是判斷它不可信、找出原因、剔除壞資料，報告較低但真實的 1.67。**

這個發現也回扣本章開頭 Patterson & Hennessy 的批評——即使是「用真實程式」的 Embench，還是會被編譯器最佳化扭曲。

### 移植與除錯

> "If Embench is not compiling successfully, check the build logs in addins/embench-iot/logs/build-<version>.log. ... If you need to debug a new version of the benchmarks, it is faster to simulate in Spike first: $ make clean / $ make spike. Spike gives a speed of 1.23 (again, normalized to the Cortex-M4 speed). Recall that Spike executes one instruction per cycle (IPC)."
> — p.784.e39

中文解釋：Spike 的 1.23 是一個有用的參考點——**它代表「CPI = 1 的理想處理器」能拿到的分數**。Wally 的 1.04 與它的差距（約 15%）就是管線冒險造成的損失。用 Spike 先跑也快很多，適合除錯。

（邊欄：Embench 2.0 在本書製作期間推出，移除了 `cubic`、`minver`、`nbody`、`st`，新增 `depthconv`、`md5sum`、`targfind`、`xgboost`。**注意被移除的正好就是書上點名有問題的那四個。**）

## 名詞表

| 名詞 | 意思 |
| --- | --- |
| Embench | FOSSi 主辦的嵌入式處理器基準，用真實程式 |
| FOSSi | Free and Open Source Silicon Foundation |
| geometric mean | 幾何平均，比算術平均更適合綜合相對比值 |
| `sizeopt` / `speedopt` | 用 `-Os` ／ `-O2` 編譯的兩種版本 |
| Cortex-M4 | 參考處理器，所有分數都相對於它正規化 |
| warm up | 暖機，先跑一次載入快取與分支預測器再計時 |
| compulsory miss | 強制失誤，第一次存取必然發生的快取失誤 |
| `warm_caches()` / `start_trigger()` / `stop_trigger()` | Embench 的暖機與計時函式 |
| IFU spill logic | 指令跨快取線時拆成兩次讀取的邏輯 |
| loop-invariant | 迴圈不變量，編譯器可以提到迴圈外只算一次 |
| `long double` | RISC-V 上是 128 位元、ARM 上是 64 位元 |
| Spike | RISC-V 官方 ISA 模擬器，CPI = 1 |
| `lief` | 解析 ELF 檔的 Python 函式庫，Embench 需要 |
| `embench_arch_sweep.py` | 自動跑五種 ISA 變體的腳本 |

## 所以呢

Embench 修正了 CoreMark 的幾個主要問題（真實程式、多樣性、同時看大小與速度、幾何平均），結論也更細緻——最重要的是 C 擴充那段分析：**程式密度省 28%，速度持平，因為 I$ 命中率的好處被 spill 的壞處抵消**。但這節最大的收穫是方法學上的：即使是設計良好的 benchmark，也會被編譯器最佳化扭曲到產生 1,480 這種荒謬的數字。**看到好得不像話的結果時，第一反應應該是懷疑而不是慶祝。** 下一節換一個角度——不是比效能，而是驗證「快取和分支預測器有沒有照設計運作」。
