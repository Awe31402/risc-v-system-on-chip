# 17.2 RISC-V Practices

> 原書 p.698–706（Chapter 17: Extensions: A (Atomic)）
> 涵蓋 17.2.1 Consistency Models、17.2.2 Fences、17.2.3 Atomic Instructions（AMO、lr-sc）、17.2.4 Atomic Subsets、17.2.5 Profile Extensions

## 這節在講什麼

17.1 建立了概念地圖，這節把 RISC-V 填進去。RISC-V 選了 release consistency（叫 RVWMO），提供三樣工具：`fence` 指令（基礎 I 指令集就有）、AMO 原子指令、以及 lr-sc 對（後兩者屬於 A 擴充）。另外還有一堆聽起來很像密碼的小擴充名稱（Zaamo、Zalrsc、Ziccif、Ziccrse、Ziccamoa、Za128rs、Za64rs、Ztso），這節會解釋它們各自在保證什麼。

## 關鍵點

### RVWMO：RISC-V 的記憶體模型

> "RISC-V uses a release consistency model called RISC-V Weak Memory Ordering (RVWMO) [RISCV-Unprivileged]. ... The thread appears to execute in order from the perspective of other memory instructions in the same hart, but memory instructions from another hart may observe the memory instructions from the first hart being executed in a different order."
> — p.698

中文解釋：這句話定義了「弱」在哪裡——**自己看自己是照順序的，別人看你可以是亂的**。原因就是 17.1 講的 store buffer 與亂序執行。想讓別人看到順序，就得明確同步。

### 為什麼還要 A 擴充（單核心也要）

> "The atomic (A) extension provides atomic instructions to support synchronization across threads; this extension is necessary for single-core processors with multiple threads as well as for multicore processors."
> — p.698

中文解釋：呼應 17.1.4 的重點——單核心多執行緒一樣有 race condition，因為 context switch 可以插在任何地方。Wally 是單核心，但還是需要 A 擴充。

### memory 與 I/O 的順序可以分開管

> "Recall from Section 11.2.2.1 that a RISC-V core can use physical memory attributes (PMAs) to designate certain address ranges as main memory and others as peripheral I/O. Peripheral reads are called input, and peripheral writes are called output. The RVWMO can enforce consistency separately for memory and I/O accesses; for example, using a lock to control access to a shared data structure in main memory does not have to wait for an access to a peripheral to complete."
> — p.699

中文解釋：這是 RISC-V `fence` 指令有四種存取類型（r/w/i/o）而不是兩種的原因。周邊存取通常慢很多，不該把記憶體同步卡在它後面。

### Ztso：給 x86 程式移植用的後路

> "RISC-V optionally supports the RISC-V Total Store Ordering (RVTSO) consistency model, which is called the Ztso extension. RVTSO makes it easier to port programs written for other TSO architectures such as x86 or SPARC. It may come for free on simple in-order processors because they never access memory out of program order."
> — p.699

中文解釋：從 x86 移植過來的程式可能隱含依賴 TSO 的保證（因為在 x86 上「剛好會動」）。Ztso 讓這些程式不用改寫。ELF 檔會在 `e_flags` 欄位的 bit 4 標記「這個程式需要 Ztso」。簡單的循序處理器實作 Ztso 是**免費的**——因為它本來就不亂序。

### fence 的四種存取類型與八個位元

> "Fences can enforce ordering for memory reads (r), memory writes (w), peripheral input (i), and peripheral output (o). A fence takes two arguments that specify which types of accesses before the fence must complete before which types of accesses after the fence may occur."
> — p.699

中文解釋：Fig. 17.3 的立即值格式：bit 31:28 是 `fm`（通常 0000），bit 27:24 是 **predecessor set**（PI、PO、PR、PW），bit 23:20 是 **successor set**（SI、SO、SR、SW）。語意是：其他 hart 在看到 successor set 裡的任何存取之前，一定先看到 predecessor set 裡的所有存取。

Table 17.3 的常用組合值得記：
- `fence iorw, iorw`（0xFF）：記憶體與 I/O 都有 sequential consistency。偽指令 `fence` 就是這個。
- `fence rw, rw`（0x33）：記憶體的 sequential consistency。
- `fence r, rw`（0x23）：**acquire** 操作
- `fence rw, w`（0x31）：**release** 操作
- `fence r, r`（0x22）：Linux 的 `smp_rmb()`（read memory barrier）
- `fence w, w`（0x11）：Linux 的 `smp_wmb()`（write memory barrier）
- `fence.tso`（0x833）：等同 `fence rw, rw` 但 `fm = 1000`，語意較弱（給 total store order）

### Wally 的 fence 是 nop

> "Simple in-order pipelined cores with no store buffers, such as Wally, are inherently sequentially consistent and thus don't require fences between memory accesses. fence can be treated as a nop on these cores."
> — p.700（邊欄）

中文解釋：這是一個很實用的觀察。**沒有 store buffer 的單核心循序管線本來就是 sequentially consistent**，fence 什麼都不用做。這也說明 fence 的成本完全來自硬體最佳化——你不做那些最佳化就不用付這個錢。

### 三種特殊 fence

> "Recall that RISC-V also supports fence.i (synchronize instruction memory) and sfence.vma (synchronize page table). fence.i requires the Zifencei extension. It synchronizes the instruction and data caches... sfence.vma requires virtual memory support and synchronizes the TLB"
> — p.700

中文解釋：三種 fence 各管一件事：
- `fence`：記憶體/IO 存取順序
- `fence.i`（Zifencei）：I$ 與 D$ 的一致性，自我修改程式碼用
- `sfence.vma`：TLB 與頁表的一致性

另外 `menvcfg.FIOM`（Fence of I/O implies Memory）位元設起來後，低於 M-mode 的權限層級下，I/O 的 fence 位元會自動連帶記憶體的 fence 位元。`senvcfg.FIOM` 對 U-mode 做同樣的事。這是給 OS 用軟體模擬虛擬 I/O 裝置用的。

### A 擴充的兩種形式

> "The RISC-V atomic (A) extension defines two forms of atomic instructions: atomic memory operations (AMOs) and LoadReserved-StoreConditional (lr-sc), as listed in Table I.24 in the last pages of the book. AMO instructions fetch data, operate on it, and store it back into the same memory address from which it was fetched."
> — p.700

中文解釋：AMO 是「單一指令完成讀-改-寫」，lr-sc 是「兩個指令 + 一個預約」。

### aq 和 rl 位元

> "Both forms of atomic instructions, AMOs and lr-sc, have acquire and release bits (aq and rl) that can optionally be set to order the atomic operations relative to other memory accesses within the same hart, without the need for an additional fence. When aq is set, no later memory operation in the hart can be observed to take place before this atomic access. When rl is set, all previous memory operations in the hart will be observed to take place before this atomic access. When both aq and rl are set, the atomic access will be sequentially consistent"
> — p.700–701

中文解釋：這就是 17.1.3.4 講的 acquire/release 約束在 RISC-V 的具體實現——**不用額外指令，只是指令裡的兩個位元**。注意最後一句限制：`aq`/`rl` 不管 I/O 操作的順序，需要的話還是得用 `fence`。

### AMO 的形式與九種運算

> "AMOs are of the form amo<op>.w rd, rs2, (rs1). The operation <op> is one of swap, add, and, or, xor, max, maxu, min, or minu. These instructions read a value from memory address rs1 into rd. They also compute (rs1) op rs2 and put the value back into the same address."
> — p.701–702

中文解釋：例子：`a0 = 1000`、`t0 = 2`、記憶體 1000 存 5，則 `amoadd.w s0, t0, (a0)` 讀出 5 放進 s0，把 2+5=7 寫回位址 1000。RV64 另有 `.d` 雙字版本。

用 AMO 實作 17.1.4.1 的三個經典原子操作（假設 `t1 = 1`、`a0 = adr`、`a1 = swap`、`val` 在 `s0`）：
- `TestAndSet(adr)` → `amoswap.w s0, t1, 0(a0)`
- `Swap(adr, swap)` → `amoswap.w s0, a1, 0(a0)`
- `FetchAndIncrement(adr)` → `amoadd.w s0, t1, 0(a0)`

`amoor`/`amoand`/`amoxor` 則用來原子地設定、清除、切換 memory-mapped 裝置暫存器裡的位元——這是驅動程式常見的需求。

### AMO 相對 lr-sc 的優勢

> "They are not as flexible as lr-sc but are simpler, do not livelock, and perform better on highly parallel systems because they involve a single instruction and always succeed."
> — p.701

中文解釋：三個好處，其中「不會 livelock」和「一定成功」最重要。這是 17.1.5.2 那個 lr-sc 風險的直接對照。

### TestAndTestAndSet：先用普通 load 探路

> "Spinning on lw before amoswap, called TestAndTestAndSet, is more efficient than spinning on amoswap because lw doesn't stress the shared memory system as much as an atomic operation."
> — p.702

中文解釋：這是一個很實用的最佳化。Code Example 17.16 的 spin lock 先用普通的 `lw` 迴圈檢查鎖是否為 0，只有看起來有機會才發 `amoswap`。原因是原子操作會佔用/失效共享快取線，一大堆核心同時自旋原子操作會把記憶體系統打爆（cache line ping-pong）；普通 load 可以在本地快取的 Shared 狀態讀，不干擾別人。

程式的關鍵兩行：
- 取鎖：`amoswap.w.aq t1, t0, (a0)` —— **aq** 確保臨界區內的存取不會被提前到取鎖之前
- 放鎖：`amoswap.w.rl x0, x0, (a0)` —— **rl** 確保臨界區內的存取都在放鎖之前完成

> "If the aq and rl were not specified, accesses to shared variables in the critical section might appear to happen when the lock is not held, resulting in improper synchronization."
> — p.702

中文解釋：這句話精確說明了 aq/rl 不是裝飾——少了它們，臨界區就不是臨界區了。

### AMO 的例外歸類為 store

> "When an AMO instruction causes an exception, it is reported as a store instead of a load. Thus, the exceptions are formally called store/AMO. The possible exceptions are store/AMO access fault, store/AMO address misaligned, and store/AMO page fault."
> — p.703

中文解釋：這解釋了為什麼第 8 章 `mcause` 的表裡寫的是「Store/AMO」而不是「Store」。AMO 既讀又寫，規格選擇用較嚴格的（store）權限來檢查。

### reservation set 不是一個字，而是一塊

> "Strictly speaking, lr reserves a block of contiguous addresses rather than a single word. This block is called the reservation set. A write to any address within the reservation set cancels the reservation. The reservation set is often one full cache line, so the reservation is tracked with an extra status bit on the cache line. Cache lines are often 512 bits (64 bytes), so this is a common reservation set size."
> — p.703

中文解釋：這是實作現實造成的規格鬆綁。用快取線的一個狀態位元追蹤預約很便宜；如果要精確到單一字就得存位址，貴得多。代價是**假失敗（false sharing）**——別人寫同一條快取線的其他位置也會作廢你的預約。

### context switch 要清掉預約

> "During a context switch or change of relevant page table entries, the OS invalidates any pending reservations by performing a StoreConditional to a scratch address."
> — p.703（邊欄）

中文解釋：很實用的小技巧。`sc` 到任何位址都會清掉預約，所以隨便寫一個暫存位址就當作「清除預約」用。不清的話，換回來的執行緒可能繼承了前一個執行緒的預約狀態。

### constrained lr-sc loops 的保證

> "As described in Section 17.1.5.2, lr-sc is at risk of livelock if two concurrent threads constantly cancel each other's reservations. RISC-V prevents livelock with an eventual success guarantee for constrained lr-sc loops [RISCV-Unprivileged]. In simple terms, the execution environment guarantees that one of the threads will eventually successfully store."
> — p.703

中文解釋：這是規格層級的承諾，但實作方式因系統而異：
- **單核心**：自然成立，因為 OS 切換執行緒的頻率遠低於一個 lr-sc 迴圈的長度，就算某個執行緒剛好被切走，另一個也會成功。
- **多核心**：需要一個 **monitor** 硬體偵測 livelock，強制讓其中一個成功。

「constrained」的意思是：迴圈必須符合規格規定的形式（指令數有限、不含可能引發例外的操作等），才享有這個保證。

### 為什麼 spin lock 偏好 amoswap 而非 lr-sc

> "This example is more complex than the preferred amoswap lock method of Code Example 17.16, but illustrates lr-sc and a fence."
> — p.704

中文解釋：Code Example 17.18 用 lr-sc 做 spin lock，比 17.16 的 amoswap 版長也複雜。放鎖時用 `fence rw, w` + `sw x0, 0(a0)`——因為 RISC-V 的 acquire/release 註記**只存在於原子指令上，普通的 load/store 沒有**，所以普通 store 要放鎖就得自己加 fence。

### Zaamo / Zalrsc：A 擴充的兩半

> "Although the RISC-V atomic (A) extension supports both AMOs and lr-sc instructions, AMOs may be preferred because they scale better to highly parallel systems and also are easy to implement on cacheless microcontrollers. The Zaamo extension supports only the AMO instructions of the A extension. The Zalrsc extension supports only the lr-sc instructions of the A extension. The A extension implies Zaamo + Zalrsc."
> — p.705

中文解釋：拆開的理由很實際——**lr-sc 需要追蹤預約，在沒有快取的微控制器上不好做**；AMO 就容易得多。所以小型系統可以只實作 Zaamo。

### 四個 profile 擴充在保證什麼

> "An OS normally expects that main memory is suitable for holding programs and that interrupts cannot occur midway through fetching an instruction. The RVA20U64 and later profiles formalize this understanding with the Ziccif extension"
> — p.705

中文解釋：這四個擴充都是在把「OS 本來就假設成立」的事情寫成正式保證。這是 profile（見附錄 A）的典型作用——不是加新功能，而是把隱含假設明文化，讓 OS 敢依賴它。

- **Ziccif**（instruction fetch）：主記憶體必須支援取指，而且取指是原子的（中斷不會插在一條指令只取了一半的時候）。Wally 的 IFU 遇到 spill（指令跨快取線）會停住管線直到取完，所以天生支援。
- **Ziccrse**（RsrvEventual）：所有主記憶體都必須有 RsrvEventual 性質，也就是 lr-sc 最終一定會成功。Wally 單核心 + 合理的 OS scheduler 就滿足。
- **Ziccamoa**（AMOArith）：所有主記憶體都必須支援全部的 AMO 指令。Wally 的 PMA checker 預設在主記憶體允許所有原子操作，所以支援。
- **Za128rs / Za64rs**：告訴 OS 預約集合不超過 128 / 64 位元組。

### 為什麼 OS 需要知道 reservation set 的大小

> "When the OS allocates memory for a lock, it prefers to have no other variables within the same reservation set so other accesses do not interfere with acquiring the lock. If the reservation set is large, this wastes memory, and if the OS doesn't know the size of the reservation set, it cannot allocate memory effectively."
> — p.706

中文解釋：這是 false sharing 的預防。OS 想把鎖變數單獨放在一個 reservation set 裡，但它得先知道這個 set 有多大。RVA22 profile 要求 Za64rs（≤ 64 bytes）就是為了限制浪費——64 bytes 剛好是典型的快取線大小。

## 名詞表

| 名詞 | 意思 |
| --- | --- |
| RVWMO | RISC-V Weak Memory Ordering，RISC-V 的 release consistency 模型 |
| RVTSO / Ztso | RISC-V 的 TSO 模型，方便從 x86/SPARC 移植 |
| predecessor set / successor set | fence 立即值的前半/後半，指定要排序哪些存取類型 |
| r / w / i / o | 記憶體讀／記憶體寫／周邊輸入／周邊輸出 |
| `fence.tso` | 立即值 0x833，提供 total store order 的較弱 fence |
| `smp_rmb()` / `smp_wmb()` | Linux 的讀／寫記憶體屏障，對應 `fence r,r` / `fence w,w` |
| `menvcfg.FIOM` | Fence of I/O implies Memory，讓 I/O fence 連帶記憶體 fence |
| AMO | atomic memory operation，單指令完成讀-改-寫 |
| `aq` / `rl` | AMO 與 lr-sc 指令上的 acquire / release 位元 |
| TestAndTestAndSet | 先用普通 load 自旋、看起來有機會才發原子指令 |
| store/AMO exception | AMO 的例外歸類為 store 類 |
| reservation set | lr 預約的一整塊連續位址，通常一條快取線 |
| constrained lr-sc loop | 符合規格形式、享有「最終必成功」保證的 lr-sc 迴圈 |
| eventual success guarantee | 執行環境保證某個執行緒的 sc 終將成功 |
| monitor | 多核心用來偵測並打破 lr-sc livelock 的硬體 |
| Zaamo / Zalrsc | A 擴充的兩半：只有 AMO ／只有 lr-sc |
| Ziccif / Ziccrse / Ziccamoa | profile 擴充：取指原子性／lr-sc 必成功／全 AMO 支援 |
| Za128rs / Za64rs | 宣告 reservation set 不超過 128 / 64 位元組 |
| false sharing | 同一條快取線上無關的變數互相干擾 |

## 所以呢

RISC-V 的並行工具箱到齊了：RVWMO 定義基準行為、`fence` 提供粗粒度排序、`aq`/`rl` 提供細粒度排序、AMO 提供簡單可靠的原子操作、lr-sc 提供靈活但要小心 livelock 的組合原語。接下來 17.3 看怎麼測這些指令，17.4 看 Wally 怎麼在 LSU 裡實作它們。
