# 5.8 Code Coverage

> 原書 p.217–221（Chapter 5: Design Verification）

## 這節在講什麼

**從「有沒有抓到錯」轉向「測得夠不夠」。**

程式碼覆蓋率量的是：**測試向量有沒有把 RTL 的每一行、每一個運算式、
每一個條件分支都跑過。**

內容四塊：
1. **六種覆蓋率的定義**（line、statement、expression、condition、FSM、branch）
2. **怎麼在 Questa 裡收集**（UCDB、`vcover`）
3. **一個完整的實例**：全加器從 100% 掉到 91.66% 的過程——**這段最值得讀**
4. **coverage exclusion**（覆蓋率排除）和它的風險

**核心限制要先記住（5 章導論 p.195 就說了）：
「程式碼覆蓋率是必要但不充分的——它偵測不到某個功能根本沒被寫出來。」**

## 關鍵點

### 六種覆蓋率

> "A logic simulator can collect and report coverage metrics for HDL code. **A minimum level
>  of coverage is that the test vectors should activate every line of code, called *line
>  coverage*.** A next level of coverage is to ensure every expression in a logic equation and
>  every condition in a case or branch has been exercised, called *statement*, *expression*,
>  *condition*, *FSM*, and *branch coverage*."
> — p.217

中文解釋：**六種覆蓋率，由粗到細（p.218 的定義整理）：**

| 覆蓋率 | 檢查什麼 |
| --- | --- |
| **Line** | 每一行程式碼都被執行過。**最低標準** |
| **Statement** | **每個敘述**都被執行過。比 line 更精確——**因為一個敘述可能跨多行，一行也可能有多個敘述** |
| **Branch** | 控制結構（`if`、`case`）中的布林運算式**同時評估出 TRUE 和 FALSE** |
| **Condition** | `if` 敘述中，**每個輸入都被測到 TRUE 和 FALSE**，且其他輸入處於「會讓輸出取決於該輸入」的狀態 |
| **Expression** | 同 condition，但適用於**賦值敘述的右側** |
| **FSM** | **所有狀態都被到達，所有狀態轉換都被執行過** |

**Statement vs line 的差別值得注意**：
書上明說 statement coverage「比 line coverage 更具體」，
理由是「一個敘述可能跨越多行，而多個敘述可能放在同一行」。

### Condition/expression coverage 的細膩之處

> "Condition and expression coverage check that each input of a Boolean expression is
>  exercised TRUE and FALSE **while the other inputs are in a state that make the output
>  depend on the input being exercised.**"
> — p.218

中文解釋：**畫線那句是關鍵，它讓 condition coverage 遠比 branch coverage 嚴格。**

**書上的例子非常清楚（p.218）：**
```systemverilog
y = a & b | c;
```
**`y` 只有在 `b == 1` 且 `c == 0` 時才取決於 `a`。**
（因為 `c == 1` 時 y 恆為 1，`b == 0` 時 `a & b` 恆為 0。）

**所以完整的 expression coverage 需要六個案例：**
- `a = 0 / 1` **when b = 1, c = 0**
- `b = 0 / 1` **when a = 1, c = 0**
- `c = 0 / 1` **when a and b are not both 1**

**為什麼這個條件重要？** 因為只有在這種狀態下，
**「如果這個輸入接錯了，輸出才會不同」**——測試才有意義。
（呼應 5.1.1 節那個邊欄：「某一欄只依賴 A 不依賴 B 的製造缺陷會躲過 corner case 測試」。）

### 怎麼收集：Questa 的 UCDB

中文解釋：Code Example 5.7（p.218）是加上覆蓋率的 do file：
```tcl
vlog fulladder.sv
vopt +acc work.testbench -o workopt +cover=sbecf      # ← 加這個
vsim workopt -coverage                                 # ← 和這個
run -all
coverage save -instance /testbench/dut fulladder.ucdb  # ← 存檔
quit
```

**三個改動（對比 5.5 節的 Code Example 5.4）：**
1. **`vopt` 加 `+cover=sbecf`**——
   **`s`tatement、`b`ranch、`e`xpression、`c`ondition、`f`sm**，五個字母各對應一種覆蓋率
2. **`vsim` 加 `-coverage`**
3. **`coverage save -instance /testbench/dut` 存進 `.ucdb`**
   （**UCDB = Unified Coverage Database，統一覆蓋率資料庫**）

**產生人類可讀的報告（p.218）：**
```bash
$ vsim -c -do fulladder-batch-coverage.do
$ vcover report -details fulladder.ucdb > fulladder_coverage_details.rpt
```

**合併多個測試的覆蓋率（p.221）——大型設計必用：**
```bash
$ vcover merge -out combined.ucdb test1.ucdb test2.ucdb
```

### 實例：從 100% 到 91.66%（最值得讀的部分）

中文解釋：**書上用全加器做了一個完整的對照實驗，非常有教學價值。**

**被測的程式碼（Code Example 5.8，p.218）：**
```systemverilog
50:  assign s = a ^ b ^ c;
51:  assign cout = (a & b) | (a & c) | (b & c);
```

**情況一：用完整的 8 個向量（窮舉）**

報告（Code Example 5.9，p.219）：
```
Expression Coverage:
    Expressions          Bins 6   Covered 6   Misses 0   Coverage 100.00%
Line 50 Item 1  ((a ^ b) ^ c)         3 of 3 input terms covered = 100.00%
Line 51 Item 1  (((a & b) | (a & c)) | (b & c))   3 of 3 input terms covered = 100.00%
Statement Coverage:
    Statements           Bins 2   Hits 2   Misses 0   Coverage 100.00%
    Line 50: 9 hits,  Line 51: 9 hits
Total Coverage By Instance (filtered view): 100.00%
```
**6 個 expression bin（兩個式子各 3 個輸入項）、2 個 statement，全部覆蓋。**

**情況二：拿掉兩個向量（Code Example 5.10，p.220）**
```
// abc_cout s
000_00
001_01
010_01
011_10
100_01
//101_10     ← 註解掉
//110_10     ← 註解掉
111_11
```

**結果（Code Example 5.11，p.220）：**
```
Expressions          Bins 6   Covered 5   Misses 1   Coverage 83.33%
Line 51 Item 1  (((a & b) | (a & c)) | (b & c))
Expression totals: 2 of 3 input terms covered = 66.66%

Input Term  Covered  Reason for no coverage  Hint
  a            N     '_1' not hit            Hit '_1'
  b            Y
  c            Y
Total Coverage By Instance (filtered view): 91.66%
```

**書上的解釋（p.219–220）值得逐句理解：**
> "Now the tests no longer contain a vector that makes cout = 1 due to a being 1 (the last row
>  has cout = 1, but b and c are both 1 so cout doesn't depend on a).... **the vectors no
>  longer are sufficient to show that setting input a = 1 affects cout.** Row 2 of the Focused
>  Expression View indicates that a is never 1 when b and c are in a state that affects the
>  output. The *nonmasking condition* is tricky to interpret in this report but essentially
>  means **when b ^ c is 1 such that cout is influenced by a.**"

**關鍵推理鏈：**
1. 剩下的向量中，**`a = 1` 且 `cout` 真的取決於 `a`** 的情況不存在了
2. 最後一列 `111` 雖然有 `a = 1` 且 `cout = 1`，
   **但 `b` 和 `c` 都是 1，所以 `cout` 本來就是 1，和 `a` 無關**
3. **「非遮蔽條件（nonmasking condition）」就是 `b ^ c == 1`**——
   只有 b 和 c 不同時，`cout` 才取決於 `a`

**這個例子完美示範了 5.8 節那句「其他輸入要處於讓輸出取決於該輸入的狀態」。**

**注意 statement coverage 仍然是 100%**（兩行都執行了 6 次）——
**只有 expression coverage 掉到 66.66%。**
**這就是為什麼需要多種覆蓋率指標：粗的指標會給你虛假的安全感。**

（整體 91.66% 是各項的加權結果。）

### TRL5 要求 100% 覆蓋率，以及怎麼達成

> "As discussed in Section 5.1.5, Technology Readiness Level 5 (TRL5) requires 100% code
>  coverage to ensure the entire code has been exercised. **This typically involves writing a
>  set of directed tests that cover the obvious cases (e.g., tests each instruction), using a
>  random test generator to stress unobvious cases, and then writing more custom directed
>  tests to check stranger cases (e.g., illegal instructions).**"
> — p.221

中文解釋：**達成 100% 覆蓋率的三段式策略，呼應 5.1.1 節：**

| 階段 | 手段 | 目標 |
| --- | --- | --- |
| 1 | **Directed 測試** | 明顯的案例（每條指令） |
| 2 | **隨機測試產生器** | **不明顯的案例** |
| 3 | **更多客製 directed 測試** | **更奇怪的案例**（如非法指令） |

**注意第 3 階段的存在**：隨機測試打不到的地方，最後還是要手寫。
（呼應 5.1.1 節的停止準則：「直到覆蓋率 100%，或直到手寫比較划算」。）

### Coverage exclusion：必要但危險

> "Nevertheless, **it is often impossible to actually exercise all of the statements because
>  certain parts of the code may be unreachable, particularly if the code is configurable.**
>  For example, a 32-bit configuration cannot exercise 64-bit instructions. The designer adds
>  *coverage exclusions* to tell the coverage tool to ignore certain uncovered cases that the
>  designer is satisfied are unreachable.... **Adding exclusions requires caution because
>  poorly written or outdated exclusions can hide legitimate bugs.**"
> — p.221

中文解釋：**問題很實際：可組態的程式碼必然有無法到達的部分。**
32-bit 組態下，64-bit 指令的程式碼永遠不會執行——**但它還在原始碼裡。**
（呼應 4.2.5 節：Wally 把可組態性推到極致，所以這個問題更嚴重。）

**解法是 coverage exclusion：告訴工具「這幾行不算」。**

**但書上的警告很重要：**
> "**poorly written or outdated exclusions can hide legitimate bugs**"

**「寫得不好或過時的排除，會藏住真正的 bug。」**

**兩個風險：**
1. **寫得太寬**——順便排除了本該測到的程式碼
2. **過時**——當初無法到達，後來程式碼改了變成可到達，但排除還在

**這和 5.3 節 lint 的 `lint_off` 是同一類風險：
豁免機制必要，但每次豁免都是一次「我確定這裡沒問題」的承諾。**

Wally 的覆蓋率排除範例在第 5.11.11.2 節。

## 名詞表

| 名詞 | 意思 |
| --- | --- |
| **Line coverage** | 每行程式碼都被執行。最低標準 |
| **Statement coverage** | 每個敘述都被執行。比 line 更精確（敘述可跨行，一行可多敘述） |
| **Branch coverage** | 控制結構的布林運算式同時評估出 TRUE 和 FALSE |
| **Condition / expression coverage** | 每個輸入都測到 TRUE/FALSE，**且其他輸入處於讓輸出取決於該輸入的狀態**（`if` 的條件 / 賦值右側） |
| **FSM coverage** | 所有狀態都到達、所有轉換都執行過 |
| Nonmasking condition | 非遮蔽條件。讓輸出真正取決於某輸入的其他輸入狀態 |
| **UCDB** | Unified Coverage Database。Questa 的覆蓋率資料庫 |
| `+cover=sbecf` | 啟用 statement / branch / expression / condition / fsm 覆蓋率 |
| `vcover report` / `vcover merge` | 產生報告 / 合併多個 UCDB |
| **Coverage exclusion** | 覆蓋率排除。告訴工具忽略無法到達的程式碼；**過時或過寬的排除會藏住真 bug** |

## 所以呢

**程式碼覆蓋率是「必要但不充分」——它證明程式碼被跑過了，
但證明不了「該寫的功能有寫」。**

三件帶得走的事：
1. **那個全加器實驗是本節精華**：拿掉兩個向量，
   **statement coverage 還是 100%，但 expression coverage 掉到 66.66%。**
   **粗的指標會給你虛假的安全感。**
2. **Condition/expression coverage 的嚴格之處在於「其他輸入必須讓輸出取決於該輸入」**——
   這才是真正能抓到「接錯線」的測試。
3. **Coverage exclusion 是必要之惡**（可組態程式碼必然有不可到達的部分），
   但**過時的排除會藏住真正的 bug**——和 lint 的 `lint_off` 同一類風險。

**TRL5 要求 100% 程式碼覆蓋率**，達成路徑是
**directed（明顯案例）→ random（不明顯）→ 客製 directed（奇怪案例）。**
