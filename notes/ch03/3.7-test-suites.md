# 3.7 Test Suites

> 原書 p.133–140（Chapter 3: RISC-V Software Tool Flow）
> 涵蓋 3.7.1 riscv-arch-test、3.7.2 RISCOF、3.7.3 wally-riscv-arch-test

## 這節在講什麼

把前面所有工具組織成**自動化測試流程**。

核心機制其實很單純，就是 3.3.8 節的 signature 放大版：
**同一支測試程式，在參考模型（Sail）和待測物（Spike 或 Wally）上各跑一次，
比對 signature 是否相同。**

三個子節：
- **3.7.1** `riscv-arch-test`：**官方**測試套件（合規認證用）
- **3.7.2** `RISCOF`：**跑測試的框架**（編譯、執行、比對）
- **3.7.3** `wally-riscv-arch-test`：官方沒測到的部分，**本書自己寫的**

**最該注意的一句話：通過官方測試是用 RISC-V 商標的必要條件，
但不足以證明實作完全正確。**

## 關鍵點

### 官方測試的地位：必要但不充分

> "RISC-V International's Architecture Test Special Interest Group (SIG) provides the
>  RISCOF RISC-V Compatibility Framework, which includes the riscv-arch-test suite of
>  tests that exercise every unprivileged RISC-V instruction. Passing these tests is a
>  requirement to use the RISC-V trademark, but the tests are not sufficient to prove
>  an implementation is completely correct."
> — p.133

中文解釋：**兩句話要分開記：**
1. **通過測試 = 能用 RISC-V 商標**（商業上的門檻）
2. **但不等於實作正確**（技術上不充分）

邊欄講得更明確（p.133 邊欄）：
**"Passing the RISCOF tests and having the results approved by RISC-V International
is a prerequisite to licensing the RISC-V trademarks in connection with the design."**

**這是「合規」和「正確」的區別**——
合規測試測的是「有沒有做到規格要求的基本行為」，
不是「在所有情況下都對」。
（呼應 2.8 節邊欄：「沒測過的功能通常有 bug，我們確信 bug 還在」。）

### 整體流程

> "RISCOF compiles the riscv-arch-test tests and simulates them with Sail to produce
>  signatures for each test. Section 5.6 describes verifying the SystemVerilog model by
>  running the same tests and comparing the signatures."
> — p.133

中文解釋：**兩階段流程，這是本節的骨架：**

```
階段一（本章）：RISCOF 編譯測試 → 在 Sail 上跑 → 產生「標準答案」signature
                                 → 在 Spike 上跑 → 比對（Spike 當 DUT）

階段二（第 5.6 節）：同樣的測試在 Wally 的 SystemVerilog 模型上跑
                     → 跟階段一的 signature 比對
```

**Sail 產生標準答案，因為它是權威**（呼應 3.5 節）。

### Wally 用到的測試層次

> "At the time of this writing, further test suites and formal verification methods are
>  rapidly evolving. In the interim, we have created the wally-riscv-arch-test suite
>  with additional tests, especially of privileged instructions, the memory management
>  unit, and peripherals, described in Chapters 8, 11, and 20."
> — p.133

> "Other more specialized Wally tests include floating-point tests, benchmarks, and
>  booting Linux, described in Chapters 16, 21, and 22 and Appendix F."
> — p.133

中文解釋：呼應 2.8 節 Table 2.7。**五層測試各自負責不同範圍：**

| 測試 | 涵蓋 | 對應章節 |
| --- | --- | --- |
| `riscv-arch-test` | 官方：所有非特權指令 | 本節 |
| `wally-riscv-arch-test` | **特權指令、MMU、周邊** | 第 8、11、20 章 |
| TestFloat | 浮點 | 第 16 章、Appendix F |
| Benchmarks | 效能 | 第 21 章 |
| Linux boot | **最終整合測試** | 第 22 章 |

編譯所有測試（p.133）：
```bash
$ cd $WALLY   # top-level cvw directory
$ make --jobs
```
**`--jobs` 讓 make 在多核機器上平行執行，快很多**（p.133 邊欄）。

### riscv-arch-test 的組織（3.7.1）

> "riscv-arch-test provides test cases for the RV32I and RV64I instruction sets and
>  various ratified extensions including C, M, F, D, Zb*, and Zk*, along with some basic
>  privileged instruction tests. Each instruction has an assembly language test file
>  that exercises the instruction and generates a signature containing the expected
>  results."
> — p.133–134

> "riscv-arch-test is incorporated into the cvw repository as a git submodule so that
>  improvements in the suite can easily be pulled into cvw."
> — p.134

中文解釋：**一條指令一個測試檔**，每個檔案產生一個 signature。

**用 git submodule 引入**——這樣上游改進可以直接 pull 進來，
不必手動同步。（Git submodule 見 Appendix C。）

**目錄結構（Fig. 3.6，p.134）**：
在 `$WALLY/addins/riscv-arch-test/riscv-test-suite`，
是所謂的 **architectural test pool（架構測試池）**：

```
riscv-test-suite/
├── env/                    ← 共用標頭檔
│   ├── arch_test.h
│   ├── encoding.h
│   └── test_macros.h
├── Makefile.include
├── README.md
├── rv32e_m/                ← 頂層按架構分
├── rv32i_m/
│   ├── I/                  ← 再按擴充分
│   │   └── src/
│   │       ├── add-01.S    ← 一條指令一個檔
│   │       ├── addi-01.S
│   │       └── ...
│   ├── C/
│   ├── M/
│   ├── F/
│   ├── privilege/          ← 測 ebreak、ecall、非對齊存取與分支跳躍
│   └── ...
└── rv64i_m/
```

**三層結構：架構（rv32i_m）→ 擴充（I、C、M、F、privilege）→ src/ 下的個別測試檔。**

**注意「目前的測試設計為在 machine mode 執行」**（p.134）——
所以頂層目錄名字結尾是 `_m`。

（想看目錄樹可以用 Linux 的 `tree` 指令，p.134 邊欄。）

### 測試檔的結構（3.7.1.2）

中文解釋：Code Example 3.20（p.135–136）是 `add-01.S` 的節錄。
**結構全靠巨集，骨架是固定的：**

```asm
#include "model_test.h"
#include "arch_test.h"
RVTEST_ISA("RV32I")               ← 宣告需要的 ISA

.section .text.init
.globl rvtest_entry_point
rvtest_entry_point:
    （把暫存器初始化成可預測的值，如 0xfeedbead）

RVMODEL_BOOT                      ← 這裡什麼都不做
RVTEST_CODE_BEGIN
RVTEST_CASE(0,"//check ISA:=regex(.*32.*);...",add)

RVTEST_SIGBASE(x3,signature_x3_1) ← 設 x3(gp) 指向 signature 記憶體

inst_0: # Test add x24, x4, x24 with x4 = 0x7fffffff, x24 = 0x00000001
TEST_RR_OP(add, x24, x4, x24, 0x80000000, 0x7fffffff, 0x1, x3, 0, x18)

inst_1: # Test add x28, x10, x10 with x10 = 0x00020000
TEST_RR_OP(add, x28, x10, x10, 0x40000, 0x20000, 0x20000, x3, 4, x18)
...
RVTEST_CODE_END
RVMODEL_HALT                      ← 寫成功訊號到 HTIF

RVTEST_DATA_BEGIN                 ← 給 load/store 用的初始化資料
.align 4
rvtest_data:
.word 0xbabecafe
RVTEST_DATA_END

RVMODEL_DATA_BEGIN                ← signature 開始
signature_x3_1:
    .fill 17*(XLEN/32),4,0xdeadbeef   ← 17 個 32-bit 結果的空間
RVMODEL_DATA_END                  ← signature 結束
```

**幾個要點：**
1. **`TEST_RR_OP` 巨集**展開成實際的測試指令序列，
   從註解看得出來它測 `add x24, x4, x24`，其中 x4 = 0x7fffffff、x24 = 1，
   **預期結果 0x80000000（正溢位）**——**刻意挑邊界值**。
2. **`RVTEST_SIGBASE(x3, ...)` 把 gp 指向 signature 記憶體**，
   之後每個結果用 `sw s8, 0(gp)`、`sw t3, 4(gp)`… 依序寫入。
3. **signature 預填 `0xdeadbeef`**（呼應 3.3.10 節：沒被寫到一眼看得出來）。
4. **`RVMODEL_HALT` 寫成功訊號到 HTIF** 結束模擬。

**要改測試的話**（p.136）：
**改 `RVTEST_CODE_BEGIN` 和 `RVTEST_CODE_END` 之間的程式碼，
並視需要增加 `.fill` 的 signature 空間。**

參考 signature（Code Example 3.21，p.136）只是純數字清單：
```
80000000
00040000
```
**對應前兩個測試的預期結果。**

（巨集的完整說明在 github.com/riscv-non-isa/riscv-arch-test 的 TestFormatSpec.adoc，p.135 邊欄。）

### RISCOF：跑測試的框架（3.7.2）

> "RISCOF (github.com/riscv-software-src/riscof) is a set of scripts that compile test
>  cases and run them on Sail and Spike to generate signatures, which can then be used
>  to compare signatures produced by an HDL processor model. RISCOF was developed by
>  the Indian Institute of Technology (IIT) Madras and Incore and has become part of
>  the RISC-V International riscv-arch-test flow."
> — p.137

中文解釋：**RISCOF 是「跑測試的腳本集合」**，用 Python 寫的（p.133 邊欄）。

**重要路徑（p.137）：**

| 路徑 | 內容 |
| --- | --- |
| `$WALLY/tests/riscof/spike` | 組態檔 |
| `$WALLY/tests/riscof/work` | 編譯後的測試與 signature |

**執行方式**：在 `$WALLY/tests/riscof` 執行 `make`。
**也會被 `$WALLY` 或 `$WALLY/sim` 的 `make` 間接呼叫。**

### YAML 組態

> "Each reference configures a configuration in the riscof directory, which in turn
>  points to a YAML file in the riscof/spike subdirectory containing the instruction set
>  architecture (RV{32/64}), extensions, and so on.... The YAML file configures the value
>  of the machine instruction set architecture register (misa) to indicate standard
>  extensions supported: A, C, D, F, I, M, and XLEN = 32."
> — p.137

中文解釋：組態用 **YAML**（p.137 邊欄：YAML Ain't Markup Language，
類似 JSON 但**用縮排表示層級而非大括號**。RISC-V 工具普遍用 YAML）。

Code Example 3.22（p.137）的片段：
```yaml
hart_ids: [0]
hart0:
  ISA: RV32IMAFDCZicsr_Zicond_Zifencei_Zfa_Zfh_Zca_Zcb_Zba_Zbb_Zbc_Zbkb_Zbkc_Zbkx_Zbs_Zknd_Zkne_Zknh
  physical_addr_sz: 32
  User_Spec_Version: '2.3'
  supported_xlen: [32]
  misa:
    reset-val: 0x4000112D
```

**RISCOF 的篩選機制（p.137）：**
> "RISCOF examines all the tests in the specified directory, making a list in
>  `riscof/riscof_work/{CONFIG}/test_list.yaml` of those with an RVTEST_ISA macro
>  compatible with the ISA configuration."

**測試檔開頭的 `RVTEST_ISA("RV32I")` 就是用在這裡**——
RISCOF 據此決定哪些測試適用於當前組態。

### RISCOF 的輸出結構

> "RISCOF compiles and runs the tests on both a "Device under test" (Spike) and a
>  reference model (Sail_CSim) and checks that their signatures (DUT-spike.signature and
>  Reference-sail_c_simulator.signature) match. It also invokes elf2hex to convert the
>  ELF files into memfiles suitable to load into a Verilog testbench."
> — p.138

中文解釋：**"DUT"（device under test，待測物）這個詞很重要**，
整本書驗證章節都會用。
**在這一階段 DUT 是 Spike，參考模型是 Sail。**
（到第 5.6 節，DUT 換成 Wally 的 SystemVerilog 模型。）

**Fig. 3.8（p.139）的輸出目錄結構**，每個指令一組：
```
cvw/tests/riscof/work/riscv-arch-test/rv32i_m/
└── I/src/add-01.S/
    ├── dut/                                 ← 待測物（Spike）的檔案
    │   ├── DUT-spike.signature              ← Spike 產生的 signature
    │   └── my.elf                           ← 給 Spike 的 ELF
    └── ref/                                 ← 參考模型（Sail）的檔案
        ├── add-01.log                       ← Sail 模擬的 log
        ├── ref.elf                          ← 給 Sail 的 ELF
        ├── ref.elf.memfile                  ← 給 Verilog 模擬用的機器碼
        ├── ref.elf.objdump                  ← 反組譯（除錯方便）
        ├── ref.elf.objdump.addr             ← 標籤位址（給 Verilog testbench）
        ├── ref.elf.objdump.lab              ← 標籤名稱（給 Verilog testbench）
        └── Reference-sail_c_simulator.signature   ← Sail 產生的 signature
```

**注意 `ref` 目錄多出來的三個檔案是給第 5 章用的**：
`memfile`（載入 Verilog 記憶體）、`.addr` 和 `.lab`（讓 testbench 能顯示標籤名稱）。
**這就是「本章的工具輸出，餵給第 5 章的硬體驗證」的接點。**

RISCOF 的 log（Fig. 3.7，p.139）會逐項報告，最後印出：
```
TEST NAME : .../I/src/add-01.S : STATUS : Passed
```
並產生 `report.html`。

**實務警告**（p.138 邊欄）：
> "Running RISCOF can take more than an hour on a slow machine. The largest part of
>  the time comes from the slow Sail simulator producing signatures. Unfortunately,
>  RISCOF is not yet smart enough to only process test cases that have changed."

**跑一次可能超過一小時，瓶頸是 Sail，而且沒有增量編譯。**
（呼應 3.5 節：Sail 只有 30 萬指令/秒。）

### wally-riscv-arch-test 的限制（3.7.3）

> "The $WALLY/tests/wally-riscv-arch-test directory is derived from riscv-arch-test but
>  contains test cases written for this book that are not part of the riscv-arch-test
>  suite. They include:
>  - Privileged tests, including traps, CSRs, and the MMU
>  - Peripheral tests"
> — p.138

> "Sail does not presently model the peripherals used to generate interrupts, so it
>  cannot be used to generate the expected values. Instead, scripts copy a
>  reference_output file from wally-riscv-arch-test to the corresponding riscof/work
>  directory. This means that the developer must predict the expected values and that
>  there is no reference model to catch errors in these predictions."
> — p.138

中文解釋：**第二段是本節最重要的警告，一定要理解。**

**問題**：Sail **不模擬周邊**（呼應 3.1 節：Sail 是 ISS，不是 emulator）。
所以牽涉中斷和周邊的測試，**Sail 產生不出標準答案**。

**折衷做法**：開發者**手寫預期輸出**（`reference_output` 檔），腳本直接複製過去。

**後果（書上說得很直白）**：
**"the developer must predict the expected values and that there is no reference model
to catch errors in these predictions."**
——**沒有參考模型可以抓出「預期值本身寫錯」的錯誤。**

**這是驗證方法論上的一個真實缺口**：
如果你對規格的理解錯了，測試和實作會「一起錯」而測試還是過。
讀第 8、20 章的特權和周邊測試時，要記得這個限制。

### 怎麼加新測試（實用清單）

中文解釋：書上給的完整步驟（p.140），**要自己加測試時照這個做：**

1. **照其他測試的格式建 `.S` 測試檔**
   - **保留既有的 riscv-arch-test 巨集**
   - **改 `RVTEST_ISA` 和 `RVTEST_CASE` 行**以符合所需擴充（例如 `RV64I_Zicsr`）
2. 把測試加進 `tests.vh` 裡的某個測試套件
3. 如果是新套件，加到 testbench
4. 把測試套件加到回歸測試
5. **分兩種情況：**
   - **Sail 能正確模擬**（不依賴中斷或周邊）：
     在 `sim` 目錄執行 `make`，叫 RISCOF 編譯並產生
     `Reference-sail_c_simulator.signature`
   - **Sail 不能模擬**：
     - **在 `RV_TEST_CASE` 裡加上 `"NO_SAIL=True"`**
     - 把預期值寫在
       `riscv-test-suite/rv{32/64}i_m/<testtype>/references/testname.reference_output`
     - 在 `sim` 執行 `make`，讓 RISCOF 編譯但不跑 Sail
6. 執行 `regression-wally` 跑測試
7. 到 `tests/riscof/work/wally-riscv-arch-test` 檢查 object dump 和 signature

**`NO_SAIL=True` 這個旗標就是上面那個限制的實作方式。**

## 名詞表

| 名詞 | 意思 |
| --- | --- |
| riscv-arch-test | RISC-V 官方架構測試套件。**通過是用商標的必要條件，但不足以證明正確** |
| RISCOF | RISC-V Compatibility Framework。編譯並執行測試、比對 signature 的 Python 腳本集 |

| **DUT** | Device under test，待測物。本章是 Spike，第 5 章換成 Wally |
| Reference model | 參考模型，產生標準答案。本章是 Sail |
| Git submodule | 把外部 repo 嵌入本 repo，方便同步上游改進 |

## 所以呢

**測試的核心機制始終是同一個：在參考模型和待測物上跑同一支程式，比對 signature。**
三個實務要點：
1. **官方測試是「合規」門檻，不是「正確」保證**——這是讀第 5 章驗證方法的前提。
2. **RISCOF 跑一次可能超過一小時，瓶頸是 Sail**，而且沒有增量編譯。
3. **周邊和中斷的測試沒有參考模型**——預期值是人寫的，寫錯了沒人抓得到。
   這是 Wally 驗證流程上一個真實的缺口。

RISCOF 產生的 `memfile`、`.addr`、`.lab` 就是交給第 5 章硬體驗證的接口。
