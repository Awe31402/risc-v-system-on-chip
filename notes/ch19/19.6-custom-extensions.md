# 19.6 Custom Extensions

> 原書 p.783–784（Chapter 19: Other Extensions）

## 這節在講什麼

RISC-V 最大的賣點之一就是「你可以自己加指令」。但「可以加」和「加了能用」是兩回事。這節講兩件事：做一個自訂擴充要動到哪些東西（不只是硬體），以及為什麼即使做出來了，最好還是把它標準化。

## 關鍵點

### 做一個自訂擴充要做什麼

> "The general process of creating a custom extension is to start with a precisely written specification, critically reviewed by an experienced team. In a test-driven design methodology, create a test plan and a set of tests to fully exercise the custom extension. Then update the HDL implementation. If the extension adds new instructions, the controller must decode the instructions and send appropriate commands to functional units. If the extension adds new CSRs, the privileged unit must add support. A custom extension usually requires a simulator and patches to the compiler and possibly the OS to run the extension."
> — p.783

中文解釋：順序值得注意——**規格 → 測試 → 實作**，這是 test-driven design。RTL 是第三步，不是第一步。

而且工作量的大頭不在硬體：
- **硬體**：controller 解碼、functional unit、（如果有新 CSR）privileged unit
- **軟體**：**模擬器、編譯器修補、可能還有 OS**

這就是 RISC-V 的現實——加一條指令到 RTL 可能只要一天，但讓工具鏈認得它、讓編譯器會用它、讓除錯器看得懂它，可能要幾個月。這也呼應第 18 章說的「編譯器無法自動推導出密碼學指令，所以密碼函式庫都是專家手寫組語」。

### 為什麼要把自訂擴充標準化

> "Some companies create proprietary extensions to differentiate their products in the market. However, when a custom extension proves useful, there are many incentives to publish and standardize it: More software and hardware developers will use the extension. The extension become accessible on the main branch of the compiler, simulator, and OS. The ecosystem support burden is shared among many developers. The extension will not conflict with subsequent standard extension encodings and CSRs. The inventor gains credibility in the open-source RISC-V community and in the marketplace."
> — p.783

中文解釋：五個理由裡有兩個是**避免痛苦**而非追求好處：

- 「**生態系的支援負擔由眾人分攤**」——自己維護一套編譯器 fork 是永無止境的工作，每次上游更新都要重新合併。
- 「**不會和後續的標準擴充編碼與 CSR 衝突**」——這是最實際的風險。你今天佔用的那塊編碼空間，RISC-V International 明天可能拿去定義標準擴充。到時候你的晶片就和標準不相容了。

換句話說，專有擴充的差異化優勢是有期限的，而維護成本是永久的。

### fast track 流程

> "Relatively simple or noncontroversial extensions are standardized through a RISC-V International fast track process: A proposer documents the extension's name, motivation, use cases, and high-level description. The proposer requests that the RISC-V Architecture Review Committee open a fast-track review. Appropriate tech chairs review the plan milestones. The proposer provides a draft specification for internal review by an appropriate RISC-V committee. The proposer provides a final draft specification and checklist of deliverables. The final draft specification goes for a 2-week public review period. If no objections are raised, the RISC-V Technical Steering Committee votes to approve the extension."
> — p.783

中文解釋：七個步驟，但重點是「**relatively simple or noncontroversial**」。這條快速通道是給 Zicond、Zihintpause 這種小而明確的東西用的。

> "More complex extensions, such as vector, matrix, CHERI, and crypto, are usually developed by a task group over a longer period of time with collaboration from many stakeholders."
> — p.784

中文解釋：大擴充（向量、矩陣、CHERI 記憶體安全、密碼學）走的是 task group 路線，時間以年計。第 18 章的 Zk* 就是這樣來的。

## 名詞表

| 名詞 | 意思 |
| --- | --- |
| custom extension | 自訂擴充，非標準的指令或 CSR |
| proprietary extension | 專有擴充，用來做產品差異化 |
| test-driven design | 先寫規格與測試，再做實作 |
| fast track process | RISC-V International 給簡單擴充的快速標準化流程 |
| Architecture Review Committee | 架構審查委員會 |
| Technical Steering Committee | 技術指導委員會，最終投票批准 |
| task group | 為複雜擴充成立的長期工作小組 |
| CHERI | 一種硬體記憶體安全架構，正在發展中的複雜擴充 |

## 所以呢

這節的實用結論是：**加指令的硬體成本遠低於軟體生態成本**，而且不標準化的長期代價（維護 fork、編碼衝突）通常超過短期的差異化好處。下一節 19.7 做總結，然後第 20 章換到完全不同的主題——周邊裝置。
