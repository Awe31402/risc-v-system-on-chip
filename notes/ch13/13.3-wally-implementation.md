# 13.3 Wally Implementation

> 原書 p.559–576（Chapter 13: Instruction Fetch Unit）
> 涵蓋 13.3.1 Instruction Cache、13.3.2 PC Logic、13.3.3 Branch Predictor、
> 13.3.4 ITLB Misses、13.3.5 Reset, Stalls, Flushes, and Traps

## 這節在講什麼

**Wally 的 IFU 實作。結構和 LSU 很像，但有三個關鍵差異。**

五個子節：
1. **I$**（13.3.1）：**就是第 10 章的 cache 但 `READ_ONLY_CACHE = 1`**
2. **PC 邏輯**（13.3.2）：多了分支預測器的多工器
3. **分支預測器**（13.3.3）：**本節的主體，五個子子節**
4. **ITLB miss**（13.3.4）：借用 LSU 的 HPTW
5. **Reset / stall / flush / trap**（13.3.5）

**最該精讀的是 13.3.3.1 的 GHR forwarding（把 RAW hazard 的概念用到分支歷史上）
和 13.3.3.3 的 IC prediction（一個「猜錯了也常常沒關係」的有趣設計）。**

## 關鍵點

### IFU 相對於 LSU 的四個差異

> "**The IFU and LSU serve similar functions and thus have similar structure. Compared to the LSU in Fig. 12.2,
>  the IFU drops the subword and endian swapping logic because instructions are always 32 bits and little-endian.
>  The read-only I$ omits write circuitry. The IFU adds PC logic, including an optional branch predictor.
>  The IMMU relies on the LSU's HPTW to service ITLB misses. Exceptions generated during the Fetch stage are
>  pipelined to generate TrapM during the Memory stage.**"
> — p.559

中文解釋：**四個差異，各有理由：**

| 差異 | 理由 |
| --- | --- |
| **少了 subword 和端序邏輯** | **指令永遠是 32-bit 且 little-endian**（呼應 2.1、8.4.7 節） |
| **I$ 沒有寫入電路** | 唯讀 |
| **多了 PC 邏輯（含分支預測器）** | IFU 獨有 |
| **ITLB miss 靠 LSU 的 HPTW** | 只需要一個 HPTW（呼應 11.4、12.3.4 節） |

**Fetch 級產生的例外要 pipeline 到 Memory 級才變成 `TrapM`**
（呼應 8.4.1 節的 `privpiperegs`、11.4.3 節的 `privilegepiperegs`）。

**四種組態的 IFU 記憶體（p.560）：**

| 組態 | IFU 記憶體 |
| --- | --- |
| **rv32e**（嵌入式） | **只有外部記憶體** |
| **rv{32/64}i**（簡單） | **只有 IROM** |
| **rv32imc**（微控制器） | **IROM + 外部記憶體** |
| **rv{32/64}gc**（應用處理器） | **I$ + 外部記憶體** |

### I$：拿掉三樣東西

> "**Chapter 10 described the generic level 1 cache used by both the LSU and IFU. The IFU has a cache when
>  ICACHE_SUPPORTED = 1, and it instantiates the `cache` module with the parameter READ_ONLY_CACHE = 1.
>  Fig. 13.13 shows a block diagram of the I$. Compared to the generic cache of Fig. 10.24, it omits the write
>  logic, dirty bits, and writeback and flush operations. Eliminating the writeback and flush logic also simplifies
>  the bus and address selection logic. The cache FSM (`cachefsm`) also eliminates the Writeback, Flush, and
>  FlushWriteback states.**"
> — p.560

中文解釋：**`READ_ONLY_CACHE = 1` 一個參數就拿掉四樣：**
**寫入邏輯、dirty 位元、writeback、flush。**

**連帶簡化：`cachefsm` 從七個狀態減到四個（少了 Writeback、Flush、FlushWriteback）。**

（呼應 4.2.5 節的參數化設計和 10.4.1 節。）

**Invalidation（p.560）：**
> "**During a `fence.i` instruction, the IFU invalidates the I$ to synchronize the instruction and data caches.
>  To do so, it asserts InvalidateICacheM, which drives InvalidateCache in the I$ to clear the valid bits in all
>  cache lines.**"

**I$ 保留 invalidate（清 valid 位元），只是不需要 flush（寫回 dirty）。**

### PC 邏輯

> "**Fig. 13.14 shows the PC logic. Compared to Fig. 8.17, the new branch predictor muxes are highlighted in darker
>  blue. When the branch predictor guesses a taken branch, BPPCSrcF = 1 and PC takes its value from the BTA BPPCF,
>  which is generated by the BTB or RAS (Fig. 13.15). Otherwise, the PC is incremented by 4.**"
> — p.560

中文解釋：**Fig. 13.14（p.562）的多工器鏈，由內而外：**

```
BPReturnF：  BTAF（BTB）或 RASPCF（RAS）  → BPPCF
BPPCSrcF：   PCPlus4F 或 BPPCF            → PC0NextF
BPWrongE：   PC0NextF 或 PCCorrectE       → PC1NextF
CSRWriteFenceM： PC1NextF 或 NextValidPCE → PC2NextF
trap/ret：   PC2NextF、EPCM、TrapVectorM   → UnalignedPCNextF
reset：      UnalignedPCNextF 或 RESET_VECTOR → PCNextF
```

**注意 `PCCorrectE` 的來源（p.560）：**
```
PCSrcE = 1（分支成立）→ PCCorrectE = IEUAdrE（計算出的 BTA）
PCSrcE = 0           → PCCorrectE = PCE + 4（PCLinkE）
```

**Fence 和 CSR 寫入的特殊處理（p.560）——這段很重要：**
> "**Fences and CSR writes change the architectural state, so when these instructions reach the Memory stage, they
>  flush and reissue the subsequent instructions. The PC must be reloaded with the address of the first instruction
>  to reissue, PCM + 4. This next PC is normally PCE. However, the instructions in the Execute and Decode stages may
>  be flushed from a previous branch misprediction. When BPWrongM = 1, the PC logic selects PCF because it is the
>  address of the next valid instruction.**"

**這是個微妙的 corner case：**
**「PCM + 4」正常來說就是 `PCE`，
但如果先前的分支誤預測把 Execute 和 Decode 級的指令 flush 掉了，
`PCE` 就不是有效的下一條指令——這時要用 `PCF`。**

**（p.560 邊欄的例子：**「Fence 和 CSR 寫入會改變後續指令的行為，
所以任何在飛的指令都必須重新啟動。例如，**當 `satp` 或頁表改變並發生 `sfence.vma` 時，
後續指令必須用新的定址重新發出。**」**）

### 分支預測器的組態

> "**Wally can be configured with static or dynamic branch prediction. For dynamic prediction, Wally supports
>  Gshare, by default, or the 2-bit predictor. When BPRED_SUPPORTED = 0, it uses a static predictor that guesses
>  *not taken*. When BPRED_SUPPORTED = 1, it uses a dynamic predictor `bpred` with a branch direction predictor
>  (2-bit saturating counter or Gshare), BTB, and RAS.**"
> — p.562

中文解釋：**三個組態參數：**

| 參數 | 意義 |
| --- | --- |
| `BPRED_SUPPORTED` | 0 = 靜態（永遠預測不成立）、1 = 動態 |
| **`BPRED_TYPE`** | **`BP_GSHARE`（預設）或 `BP_TWOBIT`** |
| `BPRED_SIZE` / `BTB_SIZE` | 方向預測器有 2^BPRED_SIZE 項、BTB 有 2^BTB_SIZE 項 |

### `bpred` 的整體結構

中文解釋：**Fig. 13.15（p.563）的 `bpred` 有五個子模組：**

| 子模組 | 職責 | 圖 |
| --- | --- | --- |
| **BHT/PHT**（`twobit` 或 `gshare`） | 方向預測 | Fig. 13.17 |
| **BTB** | 目標位址 + 指令類別 | Fig. 13.18 |
| **`icpred`** | **指令類別（IC）預測** | Fig. 13.19 |
| **RAS** | 函式返回位址 | Fig. 13.20 |
| **Misprediction Recovery** | 偵測誤預測並 flush | — |

**Fetch 級的動作（p.564）：**
> "**At the beginning of the Fetch stage, the BTB outputs the predicted target address BPBTAF and the IC:
>  BPReturnF, BPCallF, BPJumpF, and BPBranchF. None of these being high indicates a non-CFI. If a return instruction
>  is predicted (BPReturnF = 1), the PC logic chooses RASPCF as the predicted PC (BPPCF). Otherwise,
>  BPPCF = BPBTAF, the predicted BTA. If the Branch Decision logic determines that the predicted IC is a jump or a
>  taken branch, PCNextF = BPPCF.**"

**（CFI = control flow instruction，控制流指令。）**

**更新時機（p.564）：**
> "**`bpred` updates the predictors (RAS, BTB, and direction predictor: BHT/PHT) at the end of the Memory stage
>  rather than Execute.**"

**在 Memory 級末更新而非 Execute 級——理由見下面的 Gshare 實作。**

### 指令類別預測（IC prediction）：一個有趣的設計

> "**In addition to predicting the BTA, the BTB now also predicts the IC with the aid of the IC prediction module,
>  `icpred`, which determines the type of instruction: branch, jump, return, call, or noncontrol flow instruction
>  (non-CFI). By predicting IC, the next PC (PCNextF) can be calculated (PCF + 4 for non-CFI instructions) or
>  predicted (for branch/jump instructions) before the instruction is actually decoded in the Decode stage.**"
> — p.564

中文解釋：**為什麼需要預測指令類別？**
**因為在 Fetch 級還沒解碼，不知道這是不是分支——但又必須立刻決定下一個 PC。**

**誤預測的後果很有趣（p.564）：**
> "**The IC prediction module (`icpred`) keeps track of the actual and predicted IC and, in the Decode stage, detects
>  if they don't match (ICWrongD). Mispredicted IC typically causes `bpred` to predict the wrong PCNextF, which
>  leads to the same 2-cycle penalty as other branch mispredictions. However, even if the IC was predicted
>  incorrectly, the behavior could be the same, for example an `addi` and a nontaken branch both fetch the next
>  instruction from PC + 4. So, there is no need to flush the pipeline. The only side effect is that the performance
>  counters tracking IC and branch direction mispredictions increment.**"

**關鍵洞見：IC 猜錯不一定要 flush**——
**只要「抓到的下一條指令」是對的就好。**
例如 `addi`（非 CFI）和「不成立的分支」都是抓 PC + 4，
**所以把 `addi` 誤判成分支完全沒關係。**

**這呼應 13.1.5 節的統一恢復邏輯：
只檢查 `PCD == PCCorrectE`，不管誤預測的來源是什麼。**

**一個很重要的設計原則（p.564）：**
> "**Branch predictors are tricky because many types of bugs only result in lower prediction accuracy rather than
>  incorrect processor behavior. In particular, a good predictor must take care to only update its predictions when
>  valid branches commit. For example, flushed branches should not update predictions.**"

**「分支預測器很棘手，因為很多種 bug 只會降低準確度而非造成錯誤行為」**
——這就是 13.2 節說需要獨立效能驗證的理由。

**而那條規則「只在有效的分支 commit 時才更新」是所有預測器的共同紀律。**

### Gshare 實作：把 RAW forwarding 用到分支歷史上

> "**Section 13.1.3 introduced the principles of Gshare. The ideal Gshare algorithm predicts, executes, and updates
>  the predictor one instruction at a time. However, a pipelined implementation may have multiple branches in-flight
>  between prediction, execution, and when the predictor updates. Additionally, pipeline flushes should roll back
>  updates to the GHR. Wally handles these complications in a similar manner as *read after write* (RAW) IEU hazards;
>  it delays GHR and PHT updates until the Memory stage and uses forwarding to send GHR updates (from later stages)
>  back to the Fetch stage.**"
> — p.564–565

中文解釋：**這是本節最漂亮的類比：**

| IEU 的 RAW hazard | Gshare 的 GHR 問題 |
| --- | --- |
| 前一條指令的結果還沒寫回暫存器 | **前面的分支結果還沒更新進 GHR** |
| **解法：forwarding** | **解法：forwarding** |

**（p.566 邊欄明說：「這個 forwarding 邏輯類比於 7.2.2.3 節的 RAW 資料 forwarding，
當一條指令的來源運算元依賴另一條的目的地，但目的地還沒寫進暫存器檔案時。」）**

**兩種實作（p.565）：**

| `BPRED_TYPE` | 做法 |
| --- | --- |
| **`BP_GSHARE_BASIC`** | **在 Memory 級更新，避免 flush 問題，但沒有 forwarding** |
| **`BP_GSHARE`** | **加上 forwarding 邏輯，把 GHR 從較晚的級傳回 Fetch 級** |

**為什麼延遲到 Memory 級（p.565）：**
> "**Flushed branch instructions should not update the GHR and PHT. Consider a CSR write followed by a branch.
>  When the CSR write gets to the Memory stage, the branch will be in the Execute stage. The CSR write flushes the
>  branch so it should not modify the GHR or PHT. By delaying GHR shifts until the Memory stage, the GHR does not
>  require any repair.**"

**「延遲到 Memory 級就不需要修復 GHR」——用延遲換掉修復邏輯。**

**GHR 的更新條件（p.566）：**
```
只在有效的分支上更新：BranchM = 1、FlushW = 0、StallW = 0
更新方式：把 PCSrcM（當前分支的結果）移入
```

**延遲的代價（p.566）：**
> "**A consequence of updating the GHR at the end of the Memory stage is that that the GHR lags four cycles behind
>  the PC. So, the GHR fails to account for in-flight branches, thus degrading prediction accuracy.**"

**GHR 落後 PC 四個週期**——這就是需要 forwarding 的理由。

### GHR Forwarding 的機制

> "**The chain of GHR{E/D/F/NextF} muxes at the top of the forwarding logic incorporates each stage's branch outcomes
>  into the GHR seen by the Fetch stage. If a stage has a branch instruction in it, the GHR is shifted right by 1,
>  and that stage's branch direction is shifted in. All stages except Fetch use the calculated branch
>  (Branch{D/E/M}) to determine whether to shift the GHR. Fetch must use the predicted value (BPBranchF).
>  Execute and Memory use calculated branch directions (PCSrc{E/M}) to shift into the GHR; Fetch and Decode have to
>  use the predicted values (BPDir{F/D}[1]). As a result of forwarding, GHRNextF includes the outcomes of all recent
>  branches, including in-flight branches. Gshare XORs PCNextF with GHRNextF, instead of the stale GHRM, to form
>  PHTIndexNextF for reading the PHT in the Fetch stage.**"
> — p.566

中文解釋：**Fig. 13.17（p.567）的 forwarding 鏈，由後往前建構：**

```
GHRM（已提交的歷史）
  ↓ 若 BranchM，移入 PCSrcM
GHRE
  ↓ 若 BranchE，移入 PCSrcE
GHRD
  ↓ 若 BranchD，移入 BPDirD[1]（預測值）
GHRF
  ↓ 若 BPBranchF，移入 BPDirF[1]（預測值）
GHRNextF ──XOR── PCNextF ──→ PHTIndexNextF
```

**注意「用計算值還是預測值」的分界：**

| 級 | 用什麼判斷是不是分支 | 移入什麼方向 |
| --- | --- | --- |
| **Fetch** | **`BPBranchF`（預測）** | **`BPDirF[1]`（預測）** |
| **Decode** | `BranchD`（計算） | **`BPDirD[1]`（預測）** |
| **Execute** | `BranchE`（計算） | **`PCSrcE`（計算）** |
| **Memory** | `BranchM`（計算） | **`PCSrcM`（計算）** |

**Decode 級的不對稱很有意思：已經知道「是不是分支」（解碼完了），
但還不知道「會不會成立」（要到 Execute 級）——所以方向只能用預測值。**

**Example 13.3（p.568）的計算：**
> "State the value of GHRNextF in terms of GHRM for the following three cases: when no stages contain branches, when
>  only the Memory stage holds a branch and it is taken, and when all stages hold branches and only Execute isn't
>  taken.
>  **Solution:** If no stages hold branches, **GHRNextF = GHRM**, the same as without forwarding.
>  For the other two cases, **GHRNextF = {1, GHRM[k-1:1]}** and **GHRNextF = {1, 1, 0, 1, GHRM[k-4:4]}**."

**第三個案例：四個級都有分支，只有 Execute 不成立，
所以移入 1（Memory）、1（Execute 前的…）——
實際上是由後往前串接成 `{BPDirF, BPDirD, PCSrcE, PCSrcM, GHRM[k-4:4]}`
= `{1, 1, 0, 1, ...}`。**

### 方向預測的 Forwarding

> "**The remaining Gshare forwarding logic passes along the predicted direction of a branch in a later stage to the
>  Fetch stage if their indexes match. If an index match occurs with an in-flight branch, the BPDirF mux chooses the
>  forwarded predicted direction (FwdNewBPDirF) instead of the stale prediction read from the PHT. The muxes forward
>  the predicted direction from the earliest stage that matches because it has the most up-to-date prediction.**"
> — p.566

中文解釋：**第二層 forwarding：不只 GHR，連「預測方向」本身也要 forward。**

**條件：`MatchX = (IndexX == IndexF) & BranchX`**
**（索引相同 + 那一級確實是分支）**

**Example 13.4（p.568）：**
> "What is the predicted direction (BPDirF) in the Fetch stage if a branch is in the Execute stage (BranchF = 1) and
>  matches the Fetch stage index (IndexE == IndexF), with no other stage's index matching?
>  **Solution:** MatchE = (IndexE == IndexF) & BranchE = 1. So, MatchX = 1 and the predicted direction from the
>  Execute stage is forwarded to the Fetch stage: **BPDirF = FwdNewBPDirF = NewBPDirE.**"

**「選最早的匹配級，因為它有最新的預測」**（和 IEU 的 forwarding 原則一致，
呼應 7.2.2.2 節）。

**總結（p.566）：**
> "**In summary, the forwarding logic ensures that the Fetch stage sees all uncommitted branch outcomes not yet
>  reflected in the GHR and PHT.**"

### BTB 實作

> "**The Wally BTB uses the same 2-port memory as in Fig. 13.7. Like the PHT and GHR, the BTB is updated in the
>  Memory stage to avoid writing flushed branches to it, so it also uses forwarding to account for in-flight branches
>  and jumps.**"
> — p.568

中文解釋：**BTB 的結構（p.568）：**
```
2^b 項，每項 = XLEN-bit BTA + 4-bit IC
→ 2^b × (XLEN + 4)-bit 的 dual-port RAM
讀位址來自 PCNextF 的低位元，寫位址來自 PCM 的低位元
```

**Forwarding 的細節（p.568）——這裡有個不對稱：**
> "**When an in-flight instruction's address matches PCF, the address of the fetched instruction, the BTB forwards the
>  in-flight instruction's class and BTA to the Fetch stage. In any later stage, the true IC can be forwarded
>  (IClass{D/E/M/W}) because it is determined in the Decode stage by the `icpred` module. However, the BTA is not
>  computed until the Execute stage; therefore, the Decode stage must forward BPBTAD, its predicted BTA.
>  Forwards from the Execute, Memory, and Writeback stages use the true BTA, IEUAdr{E/M/W}.
>  When multiple instructions' PCs match PCF, the earliest pipeline stage has priority as it contains the most recent
>  BTA.**"

| 級 | IC | BTA |
| --- | --- | --- |
| **Decode** | **真值**（`icpred` 在此決定） | **預測值 `BPBTAD`**（還沒算出來） |
| **Execute / Memory / Writeback** | 真值 | **真值 `IEUAdr{E/M/W}`** |

**（p.568 邊欄的索引選擇很有意思：**
「不支援壓縮指令時，指令是字對齊的（PC[1:0] = 00），所以 BTB 用 PC[b+1:2] 索引。
**支援壓縮指令時 PC 可能是 2 的倍數，所以 BTB 可以用 PC[b:1] 索引。
但這樣會用一個常常無用的位元（bit 1 常常是 0）換掉一個有用的位元（bit b+1）。
用 `{PC[b+1] ⊕ PC[1], PC[b:2]}` 來索引 BTB 在實證上表現稍好**，
因為 PC[1] 不成比例地是 0（也就是未壓縮指令較多），這讓 PC[b+1] 能當作有意義的位元。」**）

**（p.568 邊欄：**「BTB 同時包含 BTA 和 IC，**因為單一大記憶體比兩個小記憶體密度更高。**」**）

### `icpred`：怎麼判斷指令類別

> "**Fig. 13.19 shows the IC prediction module, `icpred`, which tracks the predicted and actual IC and, in the Decode
>  stage, determines if they match. Because the actual IC is not available until the Decode stage, the BTB provides
>  an IC prediction BTBIClassF in addition to the predicted BTA. BTBIClassF is separated into individual signals and
>  becomes BPBranchF, BPJumpF, BPCallF, and BPReturnF. In the Decode stage, `icpred` decodes the actual IC and asserts
>  IClassWrongD if it doesn't match the predicted class.**"
> — p.569

中文解釋：**怎麼辨認 call 和 return（p.570）——這段很實用：**
> "**`icpred` uses BranchD and JumpD from the IEU. It recognizes certain `jal` instructions as function calls (CallD)
>  and certain `jalr` instructions as function returns (ReturnD). Most function calls and returns are recognized
>  because they use x1 (ra) as the destination (for `jal`) or source (for `jalr`). However, `icpred` also recognizes
>  calls and returns that use x5 (t0). `icpred` checks the rd and rs1 fields in the Decode stage to detect function
>  calls and returns. CallD asserts for `jal {ra/t0}`. ReturnD asserts for `jalr x0, {ra/t0}`.**"

**判斷規則：**

| 類別 | 條件 |
| --- | --- |
| **Call** | **`jal` 且 rd = x1(ra) 或 x5(t0)** |
| **Return** | **`jalr` 且 rd = x0 且 rs1 = x1(ra) 或 x5(t0)** |

**（Fig. 13.19 的 Decoder 就是在檢查 `Rs1 == 1 or 5` 和 `Rd == 1 or 5`。）**

**（p.570 邊欄解釋了為什麼也要認 t0：**
「多數函式會在堆疊上存還原暫存器。**Waterman 設想用共用的存還原程式碼來縮減程式碼大小，
他稱之為 *millicode*，跨函式呼叫共用。他建議用 `jal t0, <save/restore>` 來呼叫這段共用的 millicode，
以避免覆寫 `ra`。因此 `jal ra` 和 `jal t0` 都是 CallD。**」**）

**BTB 的更新策略（p.570）：**
> "**The BTB only updates when IClassWrongM is asserted or the BTA was wrong, saving power when the prediction is
>  correct.**"

**預測對了就不寫——省電。**

### RAS 實作：需要修復邏輯

> "**Wally's RAS implementation consists of two main parts: a small asynchronous flip-flop memory to record return
>  addresses and a `Ptr` register that indicates the top of stack. The memory is organized as a circular buffer with
>  RAS_SIZE entries.**"
> — p.570–571

中文解釋：**Fig. 13.20（p.571）的 RAS 比 Fig. 13.9 複雜很多，多了「修復」邏輯。**

**基本操作（p.571）：**
```
Call 執行（CallE）且未被 flush 或 stall → Push：寫 PCLinkE，Ptr++
Fetch 級預測 return（BPReturnF）        → Pop：讀 RASPCF，Ptr--
```

**三種需要修復的情況（p.571）——這是本段的重點：**

| 情況 | 條件 | 修復 |
| --- | --- | --- |
| **Decode 或 Execute 級的 return 被 flush** | `FlushedRetDE = 1` | **`Ptr++`（撤銷 pop）** |
| **類別預測器錯誤地預測了 return** | `WrongPredRetD & ~ReturnD` | **`Ptr++`（撤銷錯誤的 pop）** |
| **類別預測器漏掉了 return** | `BPReturnWrongD & ReturnD` | **`Ptr--`（補上）** |

**這三種修復反映了一個事實：RAS 的 pop 發生在 Fetch 級（很早），
但「那真的是 return 嗎」要到 Decode 級才知道。**

**（p.572 邊欄：**「因為 RAS 用非同步 flip-flop 記憶體，**讀取是組合式的，
不需要位址在時脈邊緣前 setup。記憶體有分開的讀寫埠，所以 RAS 可以同時 push（寫）和 pop（讀）。**」**）

**（p.571 邊欄很誠實：**「`bpred` 模組在 `INSTR_CLASS_PRED = 0` 時停用 IC 預測。
這個組態下，IC 由 Fetch 級部分解碼 `Instr` 來決定。**雖然這會拉長 Fetch 級，
但目前不影響週期時間，因為 Fetch 級不在關鍵路徑上。
測試顯示啟用和停用類別預測時，類別預測器對分支預測準確度的影響可忽略，
所以沒有重大的效能 bug。**」**）

### 誤預測恢復

> "**`bpred` can mispredict direction, target address, and IC, which leads to a pipeline flush if the PC of the
>  predicted instruction is wrong, regardless of the type of misprediction. The branch predictor reports the
>  misprediction to the hazard unit, which flushes the Decode and Execute stages. If the predicted PC is correct but
>  the other predictors are wrong, the branch predictor still updates its state with the correct target and IC and
>  records the misprediction in the optional performance counters.**"
> — p.572

中文解釋：**Table 13.1（p.573）是恢復邏輯的完整真值表：**

| `PCD == PCCorrectE`？ | `PCSrcE`（分支方向） | Flush Pipeline？ | `PCNextF` |
| --- | --- | --- | --- |
| **Yes** | either | **No** | **PCF + 4** |
| **No** | **0（不成立）** | **Yes** | **PCCorrectE = PCE + 4** |
| **No** | **1（成立）** | **Yes** | **PCCorrectE = IEUAdrE** |

**「只看 PC 對不對」——這張表把所有誤預測類型統一了。**

**Fig. 13.21（p.573）的逐週期範例（p.572），分支在 0x100 被錯誤預測為成立、BTA = 0x200：**

| Cycle | 發生什麼 |
| --- | --- |
| **1** | **BTB 預測這是分支（`BPBranchF = 1`）、`BTAF = 0x200`；gshare 預測成立（`BPPCSrcF = 1`）→ `PCNextF = 0x200`** |
| **2** | IEU 解碼並偵測到分支（`BranchD = 1`） |
| **3** | **IEU 執行比較，發現不成立（`PCSrcE = 0`）→ 正確的下一條應該是 `PCLinkE = PCE + 4 = 0x104`。
`bpred` 比較 `PCD = 0x200` 和 `PCCorrectE`，不符 → **`BPPCWrongE` 和 `BPWrongE` assert**；
hazard 單元 assert `FlushD` 和 `FlushE` 沖掉 0x200 和 0x204 兩條指令；
`bpred` 更新 `PCNextF = PCCorrectE = 0x104`** |
| **4** | **分支 commit：寫 BTB（`PCM = 0x100`、`IEUAdrM = 0x200`、`BranchM = 1`）；
gshare 移到 Weakly Taken 狀態；**GHR 移入一個 0**（未成立的分支）** |

**注意第 4 步：即使誤預測，BTB 仍然要更新（記下正確的 BTA 0x200）——
因為下次這條分支可能真的成立。**

**（從 Fig. 13.21 可以看到 `GHRNextM` 從 `3D7 (0011 1101 0111)` 變成
`1EB (000 1110 1011)`——右移一位並移入 0。）**

### ITLB Miss

> "**As introduced in Section 12.3.4, the LSU HPTW services both LSU and IFU TLB misses. When the IFU's ITLB misses,
>  it asks the LSU's HPTW to find the missing PTE. Fig. 13.22 shows the interface between these modules, with optional
>  signals in gray. Specifically, the ITLB asserts ITLBMissF and sends PCF to the HPTW. The page table walker handles
>  the ITLB miss, returns PTE and PageType, and pulses ITLBWriteF to write PTE into the ITLB.
>  If SVADU_SUPPORTED = 1, the HPTW atomically updates access and dirty bits in memory and the ITLB.**"
> — p.574

中文解釋：**Fig. 13.22（p.574）的介面只有五條線：**
```
IFU → LSU：ITLBMissF、PCF、（InstrUpdateDAF）
LSU → IFU：ITLBWriteF、PTE、PageType
```

**（p.574 邊欄的優先序：**
「**如果 ITLB 和 DTLB 在同一週期都 miss，HPTW 給 DTLB 優先權，先處理 DTLB miss 再處理 ITLB miss。**」
——呼應 9.5.2 節「LSU 優先」的原則。）

### Reset 的一個有趣問題

> "**On reset, the cache clears the cache line valid bits. When a line is invalid, the other bits don't matter.
>  The valid bits are implemented with flip-flops, so they are easy to reset.**"
> — p.574

> "**Resetting the BTB and BHT/PHT is more problematic because these prediction memories are large and, hence, far
>  more efficient to implement with SRAM, yet SRAM lacks a reset input. Thus, the branch memories are normally not
>  reset but power up with unknown values. As a consequence, branch prediction is nondeterministic and may vary from
>  one hardware boot to another depending on the random values in the prediction memories. In simulation, these
>  memories begin with 0 values because they are implemented with the System Verilog `bit` type rather than `logic`.**"
> — p.574

中文解釋：**這是一個很有意思的實務問題：**

| | Cache valid 位元 | BTB / BHT |
| --- | --- | --- |
| 實作 | **flip-flop** | **SRAM**（大，密度重要） |
| 能否 reset | **可以** | **不行（SRAM 沒有 reset 輸入）** |
| 開機時的值 | 0 | **未知的隨機值** |

**後果：分支預測是不確定性的（nondeterministic），
每次硬體開機可能不一樣。**

**但這沒關係——因為分支預測器是非架構狀態，猜錯只是慢。**

**模擬時的差異值得注意：模擬中用 `bit` 型別所以從 0 開始，
但真實硬體是隨機的**（呼應 4.2.2.3 節：`bit` 只有 0/1，`logic` 有四態）。

### Stall、Flush、Trap

> "**The IFU's stalls, flushes, and traps closely resemble those of the LSU, as described in Section 12.4.
>  The IFU asserts IFUStallF to stall the pipeline during multicycle cache operations (ICacheStallF), bus accesses,
>  or ITLB misses. The IFU generates page, access, and misaligned instruction address faults during the Fetch stage
>  as described in Sections 8.2.5.2 and 11.4.3. These faults are pipelined as shown in Fig. 11.28 to generate traps in
>  the Memory stage. During a multicycle operation, such as a bus access, the IFU disables interrupts by asserting
>  CommittedF to ensure bus operations complete once in flight.**"
> — p.575

中文解釋：**和 LSU 完全平行的三組機制：**

| IFU | LSU（對照） |
| --- | --- |
| `IFUStallF` | `LSUStallM` |
| `CommittedF` | `CommittedM` |
| Fetch 級的 fault pipeline 到 Memory 級 | 同 |

**Flush 的行為（p.576）：**
> "**Flushes clear the instruction in the Decode stage to be a nop. They also cancel cache or bus operations before
>  they begin but do not interfere with in-flight multicycle bus or cache operations.**"

**Hazard 單元的變化（p.576）——一個很簡潔的改動：**
> "**Fig. 13.23 shows the updated hazard unit with changes to support branch prediction in blue. **BPWrongE replaces
>  PCSrcE from Fig. 9.33.** In Chapter 9, the processor assumed not taken on a branch and simply fetched PC + 4.
>  If the branch was actually taken (PCSrcE = 1), the processor flushed the Decode and Execute stages.
>  Now those stages are only flushed when the branch predictor fetched the wrong instruction (BPWrongE = 1).**"

**`BPWrongE` 取代 `PCSrcE`——一個訊號的替換就完成了整個改動。**
**因為「分支成立」不再等於「要 flush」，只有「預測錯」才要 flush。**

## 所以呢

**這節是 IFU 的完整實作。五件最該帶走的事：**

1. **GHR 的 forwarding 是 RAW hazard 的直接類比**：
   **分支結果延遲到 Memory 級才更新 GHR（避免 flush 造成的修復），
   然後用 forwarding 把在飛分支的結果傳回 Fetch 級。**
   **Fetch 和 Decode 級只能用預測值，Execute 和 Memory 級用計算值。**

2. **IC 猜錯不一定要 flush**——
   只要「抓到的下一條指令」是對的就好（`addi` 和不成立的分支都是 PC + 4）。
   **Table 13.1 把所有誤預測統一成「`PCD == PCCorrectE` 嗎」。**

3. **RAS 需要三種修復**，因為 pop 發生在 Fetch 級但「那真的是 return 嗎」
   要到 Decode 級才知道。

4. **BTB 和 BHT 用 SRAM 所以無法 reset**——
   分支預測在真實硬體上是不確定性的，每次開機可能不一樣。
   **這沒關係，因為它們是非架構狀態。**

5. **hazard 單元的改動只有一個訊號替換**：
   **`BPWrongE` 取代 `PCSrcE`**——
   「分支成立」不再等於「要 flush」，只有「預測錯」才要。

**還有一個貫穿的紀律：「只在有效的分支 commit 時才更新預測器」——
被 flush 的分支絕對不能更新 GHR、PHT、BTB 或 RAS。**
