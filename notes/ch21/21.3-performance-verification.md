# 21.3 Performance Verification

> 原書 p.784.e39–784.e47（Chapter 21: Benchmarking）
> 涵蓋 21.3.1 Cache Performance Verification、21.3.2 Branch Predictor Performance Verification

## 這節在講什麼

這節提出一個很重要但容易被忽略的概念：**functional verification（功能驗證）不夠**。

第 13 章那套驗證流程證明的是「程式跑出正確的答案」。但一個永遠失誤的快取、一個永遠預測錯的分支預測器，**答案還是對的**——只是慢得多。這類 bug 功能測試抓不到。

**Performance verification（效能驗證）**就是拿處理器和一個參考模型比對「快取命中率」「預測準確率」這些非功能性指標。書上說這個過程「揭露了大量的 Wally 實作錯誤」。

## 關鍵點

### 為什麼需要效能驗證

> "The Wally tests described in earlier chapters focus on functional verification, to show that Wally runs programs correctly. Caches and branch predictors can have subtle errors that produce correct results but are slower than they should be. Consider a defective cache that always misses or a branch predictor that always predicts wrong. The processor recovers and eventually produces the correct result, but runs more slowly than intended. Performance verification is used to compare the processor against a reference model and detect performance bugs. ... The branch predictor's performance verification unearthed numerous Wally implementation errors."
> — p.784.e39–e40

中文解釋：關鍵洞察是——**快取和分支預測器是「純粹的最佳化」，它們壞掉不會讓答案錯，只會讓速度慢**。這正是它們難驗證的原因，也是為什麼需要一套獨立的方法。

最後一句話很有份量：**分支預測器的效能驗證揪出了大量 bug**。這不是理論上的顧慮，是實際的經驗。

### 暖機與量測時機

> "Recall that caches and branch predictors initially have compulsory misses when they are empty, then see a lower miss rate when they have loaded the working set. Performance validation typically runs a test once to warm up the system, then a second time to take measurements. Each benchmark executes a function to indicate the end of the warmup and another function to indicate the end of the benchmark. The performance counters are sampled at both events, and the difference is recorded into the transcript."
> — p.784.e40

中文解釋：和 21.2 的暖機同樣的道理。CoreMark 用 `start_time()`/`stop_time()`，Embench 用 `start_trigger()`/`end_trigger()`。

### 快取驗證：對照一個 Python 模型

> "Wally's instruction and data caches are tested against a Python reference model in $WALLY/bin/CacheSim.py. The Verilog testbench optionally records a trace of cache accesses. ... The log contains one line for each memory access that indicates the address, the type of access (Write, Read, Flush, or Invalidate) and the outcome (Hit, Miss, or Evict)."
> — p.784.e40

中文解釋：方法很直接——**硬體吐出存取軌跡，Python 模型獨立算出每次該命中還是失誤，然後逐筆比對**。這和第 16 章用 SoftFloat 當浮點的參考模型是同一個思路：**獨立實作，交叉驗證**。

```
$ regression-wally --cache
```

> "CacheSim.py has a simple model of an associative cache with a configurable number of lines and ways and address size. It predicts whether each access from the logs should be hit, miss, or evict (evict also implies miss) and compares against the Wally behavior. It should report no mismatches on any test case."
> — p.784.e40

中文解釋：注意這裡的**誠實揭露**：

> "Run the cache simulation on the various regression test cases. It is expedient to use the existing tests but is not a particularly thorough way of exercising the caches. arch64i is the most useful of the test cases because it exercises loads, stores, and branches."
> — p.784.e40

中文解釋：「expedient but not particularly thorough（方便但不特別徹底）」——**重用既有的功能測試來做效能驗證是權宜之計**，因為那些測試不是為了壓測快取而設計的。這是一個誠實的限制說明。

### 分支預測器的四個部分

> "Wally's branch predictor, bpred, consists of four major modules: a branch direction predictor (branch/pattern history table: BHT or PHT), branch target buffer (BTB), return address stack (RAS), and instruction class (IC) predictor. The accuracy of the first two are verified against a C reference model running Embench. The RAS and IC predictor trend reasonably as a function of size but have not been checked against a reference model."
> — p.784.e41

中文解釋：四個部分（第 13 章講過），但**只有前兩個有參考模型**。RAS 和 IC 預測器只確認「準確率隨大小合理地上升」——這是較弱的檢驗，書上也直說了。

### sim_bp：分支預測器的參考模型

> "sim_bp takes a text file containing one line for each branch instruction encountered during program execution. Each line contains the branch instruction address and direction, T for taken or N for not taken. sim_bp also receives parameters that specify the size of the direction and target predictors. It simulates the behavior of a 2-bit or Gshare branch predictor that encounters this instruction trace and reports the direction and target prediction accuracies."
> — p.784.e41

中文解釋：和快取驗證一樣的模式——**硬體記錄軌跡（`BPRED_LOGGER=1` 產生 `branch.log`），C 模型獨立重跑，比對準確率**。

邊欄有一個重要註記：

> "sim_bp is forked from github.com/synxlin/branch-predictor-simulator, which appears not to be presently accepting pull requests. It modifies the Gshare hashing function to use PC[1], as described in Section 13.3.3.2, which is necessary for good performance with compressed instructions."
> — p.784.e41（邊欄）

中文解釋：**參考模型也必須跟著設計走**。因為有壓縮指令，PC 的 bit 1 是有意義的（指令可以在 2 位元組邊界），所以 Gshare 的雜湊函數要納入它——參考模型如果沒改，比對就會全錯。這是使用第三方參考模型時的典型陷阱。

### 兩種軌跡：branch.log 與 cfi.log

> "sim_bp reports the BTB accuracy using the instruction trace; however, branch.log does not contain jumps or jump registers, so it does not accurately reflect Wally's BTB implementation. The testbench's logger records all branches, jumps, and jump registers in cfi.log. To simulate true BTB performance, replace branch.log with cfi.log in the above commands."
> — p.784.e42

中文解釋：這個區分很重要。**方向預測器只管條件分支**（跳或不跳），但 **BTB 要管所有的控制流指令**（branch、jump、jump register）——因為它們都需要預測目標位址。所以兩種驗證要用不同的軌跡檔（CFI = control flow instruction）。

### 掃描結果：預測器大小的影響

> "the CModelBranchAccuracy.sh script sweeps sim_bp for k = b = 6 to 16 in steps of 2 for both 2-bit and Gshare branch predictors on each Embench benchmark."
> — p.784.e42

中文解釋：輸出的數字（誤預測率，越低越好）：

| 大小 | 2-bit (bimodal) | Gshare |
| --- | --- | --- |
| 6 | 9.99% | 11.46% |
| 8 | 8.40% | 8.53% |
| 10 | 7.30% | 6.32% |
| 12 | 6.85% | 4.56% |
| 14 | 5.68% | 3.54% |
| 16 | 5.68% | **1.90%** |

**兩個關鍵觀察**：
1. **小的時候 Gshare 比 bimodal 差**（6 bit：11.46% vs 9.99%）——因為 Gshare 用 GHR 和 PC 做 XOR 雜湊，表小的時候別名（aliasing）衝突嚴重。
2. **大的時候 Gshare 大勝**（16 bit：1.90% vs 5.68%）——它能捕捉分支之間的相關性。而 bimodal 從 14 到 16 完全沒改善（5.68% → 5.68%），已經飽和。

這正是為什麼現代處理器都用有全域歷史的預測器。

### 真實硬體的準確率掃描

> "The regression-wally --branch script runs a sweep of Embench benchmarks across branch predictor types and sizes and logs the performance counters. It uses the wsim parameter flag to set PrintHPMCounters = 1, so that the testbench records the HPM counters in the simulation transcript. Embench is a long simulation, so regression-wally launches multiple simulations in parallel, each running a copy of Embench with a different branch predictor type and size."
> — p.784.e43

中文解釋：「Run performance verification (which may take half a day to run all simulations)」——**半天**。這是效能驗證的實際成本：要掃描很多組態 × 19 個 benchmark × 每個都要暖機跑兩次。

### 效能驗證抓到的真實 bug

> "The performance verification effort initially detected discrepancies from theory, helping uncover numerous performance bugs in early Wally implementations. For example, we found that the Gshare implementation worked for basic loops and spaghetti code but did not recover well from pipeline flushes. Ultimately, we settled on an implementation that only updated the global history register (GHR) in the Writeback stage but forwards in-flight branch results"
> — p.784.e43（邊欄）

中文解釋：**這是整節最有價值的一段**——一個具體的 performance bug 案例。

問題是：GHR 要在什麼時候更新？太早（在 Fetch 或 Decode 就用預測值更新）的話，管線被 flush 時 GHR 裡就留下了錯誤的歷史，之後一段時間的預測都會歪掉。解法是**只在 Writeback 級（指令確定要完成時）更新 GHR，但同時把還在管線裡的分支結果轉送（forward）給預測器用**——兩全其美。

**這種 bug 功能測試絕對抓不到**，因為程式照樣跑出正確答案。只有把誤預測率和理論值比對，才會發現「怎麼比模型差這麼多」。

### RAS 與 IC 預測器的結果

> "Figs. 21.2 and 21.3 show Wally's RAS and class prediction accuracies. Although we have no reference model for comparison, the predictor accuracies increase with size as expected and are better than 99% for reasonable sizes, indicating no major performance bugs."
> — p.784.e43

中文解釋：
- **RAS**（Fig. 21.2）：3 個項目就有 99.09%，16 個項目達 99.55%。**很小就夠用**——因為函式呼叫的巢狀深度通常不深。
- **IC 預測器**（Fig. 21.3）：64 項只有 96.9%，1024 項達 99.9%，4096 項以上接近 100%。

注意書上的謹慎用詞：「indicating no major performance bugs」——**沒有參考模型時只能說「看起來合理」，不能說「驗證通過」**。

### 個別 benchmark 的差異

> "Fig. 21.4 shows detailed branch predictor results for the different types and sizes of predictors for different Embench benchmarks compiled with speedopt. Some benchmarks such as crc32 are highly predictable and have almost no mispredictions. The Gshare accuracy generally improves with the GHR length. Many applications such as minver and ud have correlated branches and benefit strongly from longer GHRs. For most benchmarks, the 2-bit predictor captures all branches with b = 6 (number of BHT entries = 2^b), so increasing predictor size only marginally improves accuracy. Larger applications benefit from a bigger predictor."
> — p.784.e45

中文解釋：Fig. 21.4 的五張圖顯示巨大的差異：
- **`crc32` 幾乎零誤預測**——迴圈次數固定，完全可預測
- **`cubic`、`nbody` 的誤預測率高達 35–38%**（小的 Gshare）
- **`minver`、`ud` 從長 GHR 獲益極大**——它們的分支彼此相關

這印證了 21.1 開頭的話：**「不同程式在不同電腦上跑得不一樣好」**——連同一個預測器面對不同程式的表現都天差地別。

### CoreMark 的分支統計

> "CoreMark running on Wally rv64gc reports a branch misprediction rate of 66,966/591,846 = 11% for Gshare k = b = 10, as described in Section 21.1. The 16-entry RAS has a misprediction rate of 75/15,096 = 0.5%. The 1,024-entry BTB has a target misprediction rate of 4,525/(635,493 + 31,423) = 0.7% and an instruction class misprediction rate of 14,604/3,448,364 = 0.4%"
> — p.784.e45

中文解釋：四個數字放在一起看很有意思——**方向預測錯 11%，但目標、RAS、指令類別的錯誤率都低於 1%**。也就是說分支預測的瓶頸完全在「跳不跳」這個判斷上，不在「跳去哪裡」。這對設計者是明確的指引：要改善就投資在方向預測器（更大的表、TAGE 之類的進階演算法），BTB 和 RAS 已經夠好了。

## 名詞表

| 名詞 | 意思 |
| --- | --- |
| functional verification | 功能驗證，證明程式跑出正確答案 |
| performance verification | 效能驗證，證明快取/預測器達到應有的效率 |
| performance bug | 答案正確但速度不如預期的錯誤 |
| `CacheSim.py` | 快取的 Python 參考模型 |

| CFI | control flow instruction，控制流指令 |
| BHT / PHT | branch/pattern history table，方向預測表 |
| BTB / RAS / IC predictor | 分支目標緩衝／返回位址堆疊／指令類別預測器 |
| GHR | global history register，全域歷史暫存器 |
| bimodal / 2-bit predictor | 兩位元飽和計數器預測器 |

## 所以呢

這節的核心訊息是**「正確」和「快」是兩種不同的性質，要用兩套方法驗證**。效能驗證的手法和功能驗證其實一樣——獨立的參考模型 + 逐筆比對——只是比對的對象從「答案」變成「命中率／準確率」。

三個實用結論：分支方向預測是唯一還有明顯改善空間的部分（11% vs 其他 <1%）；Gshare 要夠大才贏得過 bimodal；GHR 的更新時機是一個真實踩過的坑。下一節 21.4 做總結。
