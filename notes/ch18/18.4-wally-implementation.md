# 18.4 Wally Implementation

> 原書 p.748–764（Chapter 18: Extensions: Zb* & Zk* (Bit Manipulation and Cryptography)）
> 涵蓋 18.4.1 ALU Modifications for Bit Manipulation（Zba/Zbb/Zbc/Zbs）、18.4.2 ALU Modifications for Cryptography（Zbkb/Zbkx/Zknd/Zkne/Zknh/Zkt）、18.4.3 Controller Modifications

## 這節在講什麼

前兩節列出幾十條新指令，這節看它們怎麼塞進 Wally 的整數 ALU。整體結構很清楚：ALU 外面包一層 `bitmanipalu`，裡面掛幾個小模組（`zba`、`zbb`、`zbc`、`zbs`、`zbkb`、`zbkx`、`zknde`、`zknh`），最後用一個 `BSelect` 多工器在「原本的 ALU 結果」和「這些模組的結果」之間選。值得注意的是成本分布**極不平均**——大部分模組只是接線和幾個閘，但 Zbc 的乘法陣列和 AES 的 S-box 查表很貴。

## 關鍵點

### 四個設定參數與 Wally 的組態

> "The ZBA_SUPPORTED, ZBB_SUPPORTED, ZBC_SUPPORTED, and ZBS_SUPPORTED configuration options determine which bit manipulation instructions are supported, if any. The Wally rv32gc and rv64gc configurations support all four flavors, and the other configurations support none."
> — p.748–750

中文解釋：全開或全關，沒有中間狀態的組態。

### bitmanipalu 的四大改動

> "Zba: Preshifter to shift A left by 0, 1, 2, or 3 bits. For RV64, conditionally zero-extend A for .uw instructions. Zbb: Block for min/max, counting, extension, combining, and byte reversal. The shifter is also enhanced to support rotations. Zbc: Block for carry-less multiplication. Zbs: Decoder to produce one-hot mask from B. Reduction OR block for bit extract operations."
> — p.751

中文解釋：Fig. 18.21 的藍色方塊就是這些。注意四者的性質不同：
- **Zba 改的是既有資料路徑**（A 輸入前加一個 preshifter）
- **Zbb 改的是既有的 shifter**（讓它支援旋轉）＋一個新模組
- **Zbc 是完全獨立的新模組**
- **Zbs 只是一個 decoder + 一個大 OR 閘**，然後複用既有的 AND/OR/XOR

### BSelect 多工器與 bitreverse

> "When any of the bit manipulation extensions are supported, the ALU uses a BSelect multiplexer to choose ALUResult from the regular ALU (PreALUResult) or from the bit manipulation modules. ... The bitreverse module reverses the bits in A to produce RevA by using wires only, not gates. Bit reversal is used for counting trailing zeros in Zbb and for carry-less multiplication in Zbc."
> — p.752

中文解釋：`bitreverse` **只用接線、不用閘**，所以是零成本。它一份被兩個地方共用：`ctz`（把位元反轉後數前導零）和 `clmulh`（後面會講）。這種「用免費的反轉換取昂貴的硬體複用」是這節反覆出現的手法。

（邊欄提到一個實務細節：Verilog 沒有反轉匯流排的優雅寫法，只能用 generate loop 一位一位接。）

### 旋轉靠擴充 funnel shifter 的來源產生器

> "The zbb module extends the funnel shifter source generator from Section 7.1.3.3 to support rotates."
> — p.752

中文解釋：這是一個漂亮的複用。第 7 章的 funnel shifter 本來就是「把兩個字接成一個雙倍寬的字，然後從中取出一段」。Table 18.12/18.13 只是換掉「接什麼」：
- `srl` 接 {0, A}、`sll` 接 {A, 0}、`sra` 接 {符號延伸, A}
- **`ror` 接 {RotA[62:0], RotA[63:0]}、`rol` 接 {RotA[63:0], RotA[63:1]}** —— 把 A 自己接在自己後面

換句話說，**旋轉幾乎不用新硬體，只要在來源產生器多加幾個多工器輸入**。Example 18.4 完整走了一遍 `rorw 0x01234567_C9ABCDEF, 8` 的過程。

### 反相邏輯運算完全免費

> "For inverted operations (orn, andn, xnor), the ALU performs A op B̄ using the inverter already available from subtraction, so no new datapath hardware is required. The ALU controller drives SubArith = 1 to select B̄ as the second ALU operand."
> — p.753

中文解釋：**零新增硬體**，只是控制訊號的新組合。這是 18.2 說「硬體上基本免費」的具體兌現。

### zbb 裡的四個子模組

> "Fig. 18.22 shows the zbb module. ... The min/max (min, minu, max, maxu) operations select either A or B based on either the less than (lt) or less than unsigned (ltu) flag from the ALU."
> — p.753

中文解釋：min/max **複用 ALU 既有的比較旗標**，自己只需要一個多工器。四個子模組：
- **MinMax**：一個多工器 + 複用 `lt`/`ltu`
- **ext**：`sext.b`/`sext.h`/`zext.h` 三選一
- **cnt**（Fig. 18.23）：含 `popcnt` 和 `lzc` 兩個模組
- **byteop**（Fig. 18.25）：`orc.b` 和 `rev8`

### popcnt 用 CSA 樹

> "In general, the module uses an XLEN:2 tree of carry-save adders (CSAs), followed by a carry propagate adder (CPA). The leading zero counter is simply a priority encoder with a binary output."
> — p.754

中文解釋：Fig. 18.24 是 8 位元版本。這和第 15 章乘法器用 CSA 樹壓縮部分積是同一個技巧——**把 XLEN 個 1 位元的數字加起來，用 CSA 樹壓成兩個數再做一次 CPA**。`ctz` 則完全複用 `lzc`：把 `RevA` 餵進去數前導零就等於數原本的尾隨零。

`byteop` 更便宜（Fig. 18.25）：`orc.b` 是每個位元組一個 8:1 OR 閘，`rev8` 是一堆接線。

### clmul：CSA 陣列換成 XOR 陣列

> "Carry-less multiplication is similar to ordinary multiplication from Fig. 15.4(a) but does not propagate carries between columns. Hence, the full adders reduce to simple XOR gates to sum the carries within a column modulo 2. Only the least significant half of the multiplier is necessary to obtain an XLEN-sized result."
> — p.755

中文解釋：Fig. 18.26 的 4 位元 `clmul` 陣列，每個格子是一個 AND + XOR（取代普通乘法器的 full adder）。少了進位鏈，所以**又小又快**——但陣列本身還是 N²/2 個閘。

### clmulh 靠反轉複用同一個陣列

> "If the blue bits are flipped horizontally and vertically as shown in Fig. 18.27(b), we see they have the same structure as Fig. 18.26 except that the inputs are reversed, Y is shifted left by 1, and then the outputs are reversed: clmulh = rev(rev(X) @ (rev(Y) << 1)). Hence, clmulh is executed on the same clmul module by bit-reversing and shifting the inputs. clmulr is similar to clmulh but omits the shift on Y: clmulr = rev(rev(X) @ rev(Y)). Hence, clmulh = clmulr >> 1."
> — p.755

中文解釋：這是整節最巧妙的一手。乘積的高半部在結構上是低半部**上下左右翻轉**後的樣子，所以把輸入反轉、算完再把輸出反轉，就能用同一個陣列算出高半部。三種 carry-less 乘法**共用一份 `clmul` 陣列**（Fig. 18.28），只多兩個 `bitreverse` 模組（而 `RevA` 還是現成的）。

### Zbc 的實際代價：模擬變慢

> "Code Example 18.14 shows the Verilog for the carry-less multiplier. SystemVerilog lacks a built-in idiom, so the module uses two nested loops to create the N²/2 AND and XOR gates. Unfortunately, for N = 64, the inner loop is evaluated nearly 2,048 times. Zbc slows down rv64gc simulations by at least 20% because of these loops."
> — p.756

中文解釋：這是一個很誠實的工程揭露。硬體上 Zbc 只是一堆閘，但**在 Verilog 模擬器裡那 2,048 次迴圈迭代要花真實時間**——整個 rv64gc 回歸測試慢 20%。這提醒一件事：RTL 的模擬成本和實際晶片面積是兩回事。

### Zbs：一個 decoder 打天下

> "The Zbs extension uses a decoder to create a mask with a single one in the column specified by B: CondMaskB = 1 << B. The ALU then performs logical operations: bset: rd = A | CondMaskB; bclr: rd = A & ~CondMaskB; binv: rd = A ^ CondMaskB; bext: rd = |(A & CondMaskB)"
> — p.757

中文解釋：**四個指令共用一個 decoder，然後完全複用既有的 OR/AND/XOR**。唯一的新硬體是 `bext` 需要的 XLEN:1 OR 閘。這是這章成本最低的擴充。

### 密碼學模組的四個新方塊

> "Zbkb: Extension to bit manipulations for cryptography beyond Zbb. Zbkx: Block for permutations instructions. Zknde: Block for AES decryption and/or encryption. Zknh: Block for SHA-2 operations."
> — p.757

中文解釋：Fig. 18.29 把 `BSelect` 從 2 位元擴成 4 位元，多選 `zbkb`、`zbkx`、`zknde`、`zknh` 四路結果。

### zbkb：全是接線

> "The zipper module contains a rat's nest of wiring to interleave bits and a 2-input mux to choose zip or unzip. The packer also contains wiring to rearrange the bits and a 3-input mux to choose among the flavors of pack. brev8 simply contains wiring to reverse bits within the bytes."
> — p.758

中文解釋：「a rat's nest of wiring（一團亂線）」很傳神。Fig. 18.30 的三個子模組加起來只有接線和幾個多工器——**零邏輯閘**。注意 `packw` 只有 RV64 有、`zip`/`unzip` 只有 RV32 有。

### xperm 的實作

> "A xpermk module of size k (4 or 8) produces n = XLEN/k chunks of k-bit outputs by selecting from one of n k-bit chunks of the input A based on an index in the corresponding k-bit chunk of the input B. If the index exceeds n (i.e., its upper bits are nonzero), the index is illegal and the chunk is set to 0. This is done with n k-bit n:1 multiplexers, and some OR-AND logic for illegal indices."
> — p.759

中文解釋：Fig. 18.32 的 rv32 `xperm8`（k=8、n=4）：四個 4:1 多工器，每個由 B 對應位元組的低 2 位元控制，再用一個 OR 閘檢查高位元是否非零（非零就把輸出 AND 成 0）。Code Example 18.15 用 SystemVerilog 的 part-select 寫法簡潔表達（`A >> {B[i+:8], 3'b0}` 就是右移 8 的倍數）。

RV64 的 `xperm8` 是 8 個 8:1 多工器，成本隨 XLEN 平方成長（n 個 n:1 多工器）。

### AES 硬體的真正成本：S-box 表

> "The largest portion of the modules is the S-boxes, which are 256 entry × 8-bit lookup tables. RV64 uses 8 S-box and 8 inverse S-box tables, while RV32 only uses one of each and only delivers 1/8th of the throughput."
> — p.760

中文解釋：這是整章最貴的東西。RV64Zknd+Zkne 要 **16 張 256×8 的查表**（8 張正向 + 8 張反向），也就是 16 × 2048 = 32,768 位元的組合邏輯。RV32 只要 2 張，但吞吐量只有 1/8。這直接量化了 18.2.7 講的 RV32/RV64 策略差異的代價。

### zknde32 的結構

> "The zknde32 module shown in Fig. 18.33 selects the byte from the 32-bit input. The aes32e and aes32d modules handle encryption and decryption steps, respectively. Either could be omitted if only Zkne or Zknd is supported. zknde32 then selects the desired operation, rotates the result into place, and XORs it into a running result."
> — p.761

中文解釋：這完全對應 18.2 講的 `aes32esmi` 演算法五步。Fig. 18.34 的 `aes32e` 裡面：`aessbox8`（查一次 S-box）→ `aesmixcolumns8`（式 18.4：`{3 1 1 2}a = {xa ⊕ a, a, a, xa}`，只要一次 GF(2⁸) 乘 x 和一次 XOR）→ 一個多工器在最後一輪跳過 MixColumns。

### zknde64 的結構

> "However, the hardware works on 8 bytes at a time rather than 1 byte, achieving eight times the throughput but requiring 8 sbox and invsbox modules rather than one of each. Because it works on the entire word, it does not need the logic from Fig. 18.33 to select a byte or to roll the output into place and XOR it with a running total."
> — p.762

中文解釋：RV64 版反而**在控制上更簡單**（不用選位元組、不用旋轉、不用累加），只是 S-box 多了 8 倍。Fig. 18.36 的 `aes64e`：`aesshiftrows64`（純接線，實作式 18.2）→ 8 個並行 S-box（其中 4 個和 `aes64ks1i` 共用，放在 `aessboxword` 裡）→ 兩個 `aesmixcolumns32` 各處理一欄（式 18.3）。

> "aes64d is similar to aes64e, but it uses inverse operations. It contains all 8 inverse S-boxes because none are shared with key scheduling. Inverse-MixColumns contains 12 Galois field multipliers because the inverse matrix coefficients from Fig. 18.13 are larger."
> — p.762

中文解釋：這就是 18.1.2.6 說「解密比加密貴」的具體數字——**InvMixColumns 需要 12 個 GF 乘法器**（因為係數是 0x0e、0x0b、0x0d、0x09，不是好處理的 01/02/03），而且反向 S-box 一個都不能和 key scheduling 共用。

`aes64im` 只是跳過前面幾步、對兩個 32 位元字做 InverseMixColumns。`aes64ks1i` 和 `aes64ks2` 「相對小」——前者查 round constant、旋轉 32 位元、送去 `aessboxword` 查 S-box、再 XOR round constant；後者只是兩個 32 位元 XOR。

### Zknh：全部算完再選

> "Fig. 18.38 shows the sha512_64 module. It supports four instructions, each of which need three 64-bit rotations or shifts. Thus, it performs all 12 rotations and shifts, chooses the three needed for the given instruction, and XORs them together."
> — p.763

中文解釋：這是一個「反正旋轉是接線，全部做出來再選比較簡單」的設計。Fig. 18.38 裡 12 個旋轉/移位全部無條件產生（零成本，都是接線），然後三個 4:1 多工器依 `ZKNHSelect` 挑出這條指令要的三個，最後一個 XOR。**整個模組只有三個多工器和一個 XOR 樹。**

`zknh64`（Fig. 18.37）裡有 `sha512_64` 和 `sha256` 兩個模組，SHA-256 的結果要符號擴展成 64 位元。RV32 的 `zknh32` 類似，但 `sha512_32` 要從兩個 32 位元暫存器的移位結果拼出 64 位元結果的上半或下半。

### Zkt 不用做任何事

> "Wally implements all relevant instructions with constant latency, so it inherently satisfies the Zkt extension. Division and remainder have variable latency, but they are not part of the Zkt specification."
> — p.764

中文解釋：呼應 18.2 講的——Zkt 是一個承諾而非硬體。Wally 天生就滿足。

### controller 的改動

> "When any of the bit manipulation or cryptography extensions are supported, the IEU (integer execution unit) controller instantiates the BMU control (bmuctrl) module that decodes the supported instructions. It produces control signals used by the bit manipulation modules in Section 18.4.1, along with an IllegalBitmanipInstrD signal."
> — p.764

中文解釋：解碼邏輯獨立成 `bmuctrl` 模組，不去汙染原本的 `controller`。`IllegalBitmanipInstrD = 0` 表示找到合法指令——**這個訊號要回饋給主 controller**，因為只有兩邊都說「我不認得」才該發非法指令例外。

## 名詞表

| 名詞 | 意思 |
| --- | --- |
| `bitmanipalu` | 包在 ALU 外層、容納所有 Zb*/Zk* 模組的封裝 |
| `BSelect` | 在原 ALU 結果與各擴充模組結果之間選擇的多工器 |
| `PreALUResult` | 原本 ALU 的結果（未經 BSelect） |
| `bitreverse` / `RevA` | 位元反轉模組（純接線）／A 的反轉版 |
| preshifter | Zba 在 A 輸入前加的 0/1/2/3 位元左移器 |
| funnel shifter source generator | 決定「把哪兩個字接起來」的邏輯，旋轉靠擴充它實作 |
| `popcnt` / `lzc` | 人口計數（CSA 樹 + CPA）／前導零計數（優先編碼器） |
| `byteop` | 處理 `orc.b` 與 `rev8` 的模組 |
| `CondMaskB` | Zbs 的 one-hot 遮罩，= 1 << B |
| `zipper` / `packer` | Zbkb 的位元交錯／拼接子模組，純接線 |
| `xpermk` | k = 4 或 8 的 crossbar permutation 模組 |
| part-select notation | SystemVerilog 的 `B[i+:k]` 語法 |
| `zknde32` / `zknde64` | RV32 ／ RV64 的 AES 加解密模組 |
| `aessbox8` / `aessboxword` | 單位元組 S-box ／ 四位元組並行 S-box（與 key scheduling 共用） |
| `aesmixcolumns8` / `aesmixcolumns32` | 一個位元組／一整欄的 MixColumns |
| `aesshiftrows64` | 純接線實作的 ShiftRows |
| `sha512_64` / `sha256` / `sha512_32` | Zknh 的三個子模組 |
| `bmuctrl` | bit manipulation unit 的解碼模組 |
| `IllegalBitmanipInstrD` | 回報「這不是合法的 Zb*/Zk* 指令」 |

## 所以呢

這一整章的硬體成本分布很值得記住：**Zba、Zbb（除了 popcnt）、Zbs、Zbkb 幾乎都是接線和既有硬體的複用；Zbc 是一個 N²/2 的閘陣列；AES 是 16 張查表。** 也就是說「加位元操作」很便宜、「加密碼學」有實質代價，而其中大部分代價集中在 S-box。這也解釋了為什麼規格把 Zkne 和 Zknd 分開、為什麼 RV32 願意接受 1/8 的吞吐量。下一節 18.5 做總結。
