## 關鍵點

### GCC 工具鏈的組成

> "GCC is a high-quality free open-source toolchain that includes cross-compilers to
>  build RISC-V programs from another platform such as an Intel-based Linux computer.
>  The toolchain and its associated software include an assembler and C compiler
>  (gcc); the core C library (newlib or glibc); a debugger (gdb); and binary
>  utilities, including a disassembler (objdump)."
> — p.91

中文解釋：**"cross-compiler"（交叉編譯器）是關鍵詞**——
在 x86 機器上產生 RISC-V 程式。這是嵌入式開發的常態。

工具鏈四件套：**gcc（編譯+組譯+連結）、C 函式庫、gdb（除錯）、objdump（反組譯）。**

**所有 GCC 工具都有 `riscv64-unknown-elf-` 前綴**（p.92 邊欄），
命名規則是 GNU Target Triplet：**`cpu-vendor-abi-`**
- `riscv64`：CPU（**注意即使做 RV32 也用 riscv64**，因為 multilib 支援兩種，靠 `-march` 切換）
- `unknown`：vendor（因為 GCC 不綁特定 Linux 版本）
- `elf`：ABI（由 ELF 檔定義）

`riscv64-unknown-elf-gcc` 用的是輕量級標準 C 函式庫 **newlib**。

### 完整的第一個循環（3.3.1）

中文解釋：Code Example 3.1（p.92）的 `example.S`：
```asm
.section .text.init
.globl rvtest_entry_point    # 讓其他檔案看得到這個標籤
rvtest_entry_point:          # linker 期望的程式起點標籤
    li a0, 42                # a0 = 42

self_loop:
    j self_loop              # 無限迴圈
```

**三步驟：**

**1. 組譯連結**
```bash
$ cd $WALLY/examples/asm/example
$ riscv64-unknown-elf-gcc -o example -march=rv32i -mabi=ilp32 -nostartfiles \
  -mcmodel=medany -T../../link/link.ld example.S
```

**2. 反組譯檢查**
```bash
$ riscv64-unknown-elf-objdump -D example
example:     file format elf32-littleriscv
80000000 <rvtest_entry_point>:
80000000:  02a00513    li    a0,42
80000004 <self_loop>:
80000004:  0000006f    j     80000004 <self_loop>
```
**程式起點是 0x80000000**（呼應 2.4 節的記憶體映射）。

**3. Spike 互動模擬**
```bash
$ spike --isa=rv32i -d example
```
`-d` 是互動除錯模式。**按 Enter 逐條執行**，`reg 0 a0` 印出 hart 0 的 a0（應為 0x2a = 42），
`q` 離開。

**一個容易嚇到人的細節**（p.93）：
Spike 會在 0x1000 插入一段啟動碼（`auipc`、`addi`、`csrr`、`lw`、`jr`）
來初始化 a0 和 a1，然後才跳到 0x80000000。**那幾條不是你的程式。**
另外會出現 "warning: tohost and fromhost symbols not in ELF" 警告——正常，
因為這個簡單程式沒宣告 HTIF（見 3.3.8）。

**副檔名慣例**（p.92 邊欄）：
C 原始碼 `.c`、組語 `.S`、目的檔 `.o`、執行檔 `.elf`（或無副檔名）。

### Linking 與 ELF（3.3.2）

> "GCC compiles source code files into *object* files and then automatically *links*
>  one or more object files, libraries, and startup code together to form an
>  *executable* file. The object files contain machine language code and also
>  *unresolved external references* to other object files or libraries."
> — p.93

> "To save space, the linker only links in the required parts of the library.
>  Startup code may initialize the registers, including the stack and global pointers
>  sp and gp, as well as set up an exception handler. The linker *relocates* the
>  object files into a file with instructions at consecutive addresses and resolves
>  the references between files to create the executable file."
> — p.93

中文解釋：**linker 做三件事，要記住：**
1. **解析未定跨檔參照**（unresolved external references）
2. **relocate**：把各個目的檔排到連續的位址
3. **只連結用得到的函式庫部分**（省空間）

另外 **startup code** 會初始化 `sp`、`gp` 和例外處理器——
**這就是為什麼前面的指令要加 `-nostartfiles`**（我們自己來，不要 GCC 插）。

> "riscv64-unknown-elf-gcc and most Linux-based systems represent both object and
>  executable files as ELF files, which contain a 52- or 64-byte header followed by
>  program and section header tables and the code and data that these headers point
>  to. The file header begins with the magic number 0x7F 45 4C 46, indicating that it
>  is an ELF file, followed by bytes specifying {32/64}-bit format, little or big
>  endianness, the code ISA (instruction set architecture), the entry point address
>  where the program should begin executing, and the size and location of the program
>  and section header tables."
> — p.93

中文解釋：**ELF = Executable and Linkable Format**，目的檔和執行檔用同一種格式。

**magic number `7f 45 4c 46`**——後三個 byte 是 ASCII 的 "ELF"（0x45='E', 0x4C='L', 0x46='F'）。

用 `readelf -a` 看 metadata（p.94）。簡單範例的關鍵欄位：
```
Magic:   7f 45 4c 46 01 01 01 00 ...
Class:                ELF32
Data:                 2's complement, little endian
Type:                 EXEC (Executable file)
Machine:              RISC-V
Entry point address:  0x80000000
```

**常見的 section（p.94、Table 3.4）：**

| Section | 內容 |
| --- | --- |
| `.text` | 程式碼 |
| `.data` | **已初始化**的變數 |
| `.rodata` | 唯讀資料（已初始化的常數） |
| `.bss` | **未初始化**的變數 |
| `.symtab` | 符號表（標籤的位址） |
| `.riscv.attributes` | RISC-V 屬性（如需要哪個版本的 ISA） |

**`.data` 和 `.bss` 的區分很實用**（p.104）：
`int salary = 110000;`（有初值）→ **`.data`**；
`double matrix[3][3];`（沒初值）→ **`.bss`**。

`.bss` 的由來（p.104 邊欄）：**block starting symbol**。
歷史上是「由符號標示的未初始化資料區塊」。
**現代系統會把 `.bss` 初始化為 0**，避免未初始化變數造成的不確定行為——
但邊欄也說「謹慎的程式設計師仍然會在使用前初始化變數」。

（`.bss` 不佔檔案空間，只在 header 記錄需要多少，載入時才配置——
從 p.113 的 section header 看得到它的 Type 是 **NOBITS**。）

### ABI：不只是呼叫慣例（3.3.3）

> "An *application binary interface* (ABI) is the standard that defines how programs
>  communicate during function calls and system calls, including:
>  - The binary format of executables and object and library files
>  - Which instruction set (ISA) is supported
>  - The size, layout, and alignment of data types
>  - The calling convention for how arguments are passed to functions in registers or on the stack
>  - OS calling conventions
>  - Code models of how instructions access a label in the program"
> — p.95

中文解釋：**ABI 的範圍比「呼叫慣例」大很多**，這份清單值得記。

**ABI vs API 的差別**（p.95）：
- **API**（application programming interface）：函式庫**暴露給程式的函式與變數**
  （例如 C 函式庫的開檔、印字、三角函數）
- **ABI**：**編譯器建構程式時使用的慣例**（例如哪些暫存器用來傳參數）

**白話：API 是原始碼層級的契約，ABI 是二進位層級的契約。**

**資料型別大小（Table 3.1，p.96）**——命名規則是 **i = int, l = long, p = pointer**：

| Data Type | ilp32 | ilp32f | ilp32d | lp64 | lp64d |
| --- | --- | --- | --- | --- | --- |
| `int` | 32 | 32 | 32 | 32 | 32 |
| `long` | 32 | 32 | 32 | **64** | **64** |
| pointers | 32 | 32 | 32 | **64** | **64** |
| `char` | 8 | 8 | 8 | 8 | 8 |
| `short` | 16 | 16 | 16 | 16 | 16 |
| `float` | n/a | 32 | 32 | n/a | 32 |
| `double` | n/a | n/a | 64 | n/a | 64 |

**`ilp32` = int/long/pointer 都 32 bit；`lp64` = long 和 pointer 是 64 bit（int 仍是 32）。**
呼應 2.1 節 W 後綴指令存在的理由——`int` 在 64 位元系統仍是 32 bit。

尾綴 **f / d 表示浮點參數用浮點暫存器 `fa0-fa7` 傳遞**（p.96）。

**資料對齊規則**（p.96）：
"Data types are aligned to address boundaries that are a multiple of their size"——
位址 0x3002 對 `char` 和 `short` 合法，對 `int` 或 `long` 不合法。

**GCC 需要知道 ABI 才能產生正確程式碼**，例如決定用 `lw` 還是 `ld` 載入 `long`（p.96）。

### 呼叫慣例摘要（3.3.3 續）

> "The RISC-V base integer calling convention (ilp32 or lp64) defines how functions
>  pass arguments and use registers. In these ABIs, a function passes up to eight
>  arguments in registers a0-a7. These registers need not be preserved. Functions can
>  return results in a0 (and a1 if the result is 2XLEN wide). If a function needs more
>  arguments than can be passed in a0-a7, the remainder are passed on the stack."
> — p.96

中文解釋：補充 2.1 節沒說到的細節：
- **最多 8 個參數用暫存器傳**，超過的放堆疊
- **回傳值在 a0**；如果是 2×XLEN 寬（例如 RV32 上的 64-bit），**用 a0 和 a1 兩個**
- `s0` 也可以當 **frame pointer**（存取堆疊上的變數）
- **`gp`（x3）是 global pointer，用來存取全域變數**（p.96）

### 系統呼叫的實際做法（3.3.3 續）

> "When running on a platform with an OS and supervisor mode, user-mode programs call
>  the OS by placing the syscall number in a7 and any other arguments in a0-a5 and
>  then use ecall (environment call instruction) to cause a trap and elevate privilege
>  to supervisor mode. The trap handler in the OS (typically, Linux) kernel receives
>  this ecall and looks at a7 and the arguments to perform the appropriate system call,
>  then places any return result in a0, and performs sret to return to the user-level
>  program."
> — p.96–97

中文解釋：**系統呼叫的完整協定，值得背：**
```
a7 = 系統呼叫編號
a0-a5 = 參數
ecall           → trap 到 S-mode
（OS handler 執行）
a0 = 回傳值
sret            → 回到 U-mode
```
呼應 2.3 節的 trap 機制。

範例：`open(pathname, flags)` 的兩個參數放 a0 和 a1，
回傳 **file descriptor**（OS 開檔表的索引），之後 `read`、`write`、`close` 都用它（p.97）。

### Code model：medlow vs medany（3.3.3 續）

> "The RISC-V ABI prefers to access global variables using an immediate offset from
>  the global pointer because this is tight and fast code. The two's complement
>  immediate is only 12 bits, so if there are too many global variables, they cannot
>  all be accessed with this short offset (−2048 to +2047 bytes). Instead, the code
>  must explicitly calculate the address."
> — p.97

> "The *small* model uses 32-bit *absolute addresses* and thus is suitable for RV32.
>  It is not position independent, so the linker must change addresses when relocating
>  code. The *medium* model, suitable for RV64, generates *PC-relative addresses*.
>  It uses the auipc instruction to add a signed 32-bit offset to the program counter,
>  and thus can access variables and code within ±2 GiB of the current instruction.
>  It is position-independent, so the code does not have to be changed if it is
>  relocated."
> — p.97

中文解釋：**兩種 code model 的差別很清楚：**

| Model | 旗標 | 位址方式 | 位置無關 | 適用 |
| --- | --- | --- | --- | --- |
| **small（medlow）** | `-mcmodel=medlow` | 32-bit **絕對位址**（`lui` + offset） | ✗ | RV32 |
| **medium（medany）** | `-mcmodel=medany` | **PC 相對位址**（`auipc` + offset，±2 GiB） | **✓** | RV64 |

**先理解為什麼需要它們**：全域變數優先用 `gp` 加 12-bit 偏移存取（範圍只有 ±2 KB）。
**全域變數太多時 12-bit 不夠**，就要另外算位址——這時就分成兩種算法。

Code Example 3.2 和 Fig. 3.2（p.97–98）的對照非常清楚：
```c
long a;           // 在 0x129c0
long b[2000];     // b[1000] 在 0x14978
int main(void) { return a + b[1000]; }   // main 在 0x10104，gp = 0x131a0
```

**`a` 兩種模型都一樣**（在 gp 的 ±2 KB 內）：
```asm
ld a5, -2016(gp)     # 0x131a0 - 2016 = 0x129c0 ✓
```

**`b[1000]` 不同**（`b` 有 2000 個 8-byte 項，太大）：
```asm
# medlow（絕對位址）
lui a5, 0x15         # a5 = 0x15000
ld  a0, -1672(a5)    # 0x15000 - 0x688 = 0x14978 ✓

# medany（PC 相對）
auipc a0, 0x5        # a0 = 0x10104 + 0x5000 = 0x15104
ld    a0, -1932(a0)  # 0x15104 - 0x78c = 0x14978 ✓
```
**兩者都到 0x14978，但 medany 用的是 `auipc`（相對 PC），所以程式搬家也不用改。**

最後一句提醒（p.99）：
**"Although programs normally follow the ABI, the ISA does not require this."**
——**ABI 是軟體慣例，不是硬體規定。** 硬體不能假設回傳位址一定在 x1。

### SBI：OS 呼叫韌體（3.3.4）

> "The OS kernel can invoke platform runtime firmware via the supervisor binary
>  interface (SBI). This firmware abstracts platform-dependent operations so that the
>  OS does not need to change from one platform to another."
> — p.99

中文解釋：呼應 2.3.6 節的 Fig. 2.7 三層堆疊。SBI 呼叫的例子（p.99）：
**設定計時器、送 IPI（處理器間中斷/軟體中斷）給其他 hart、
遠端 fence 同步、啟動或停止 hart、重開機、讀效能計數器、查版本。**

**做法跟 ABI 系統呼叫平行**（p.99）：
```
a7 = SBI 呼叫編號（EID, extension ID）
a6 = FID（function ID）
其他參數放 a 暫存器
ecall           → trap 到 M-mode
a0 = 錯誤碼，a1 = 回傳值
mret            → 回到 OS
```
**注意跟 ABI 的差別**：SBI 用 **a7 + a6 兩個**（EID + FID），
回傳用 **a0（錯誤碼）+ a1（結果）兩個**，而且是 `mret` 不是 `sret`。

例子：`sbi_set_timer` 的 EID 是 0x54494D45（"TIME" 的 ASCII！），FID 是 0。
計時器是 CLINT 這種只能在 machine mode 存取的記憶體映射周邊（呼應 2.4 節）。

**"SBI calls are primarily made by the OS, so programmers rarely use them."**（p.99）

### -march 與機器架構（3.3.5）

> "RISC-V has many ISA flavors, so GCC needs to be told which one to target....
>  GCC uses the -march (machine architecture) flag to indicate which instructions the
>  compiler can produce, such as -march=rv32gc. Note the letters are lowercase for GCC."
> — p.99–100

> "Whereas in rv32imac, the mul instruction is legal, in rv32i using mul produces an
>  "Unrecognized opcode" compiler error because the processor hardware does not support
>  the multiply/divide extension (M). Similarly, the C statements int a, b, c; a = b * c;
>  compile into mul s0, s1, s2 in rv32imac, but in rv32i, they compile into a library
>  call to a multiplication routine using a sequence of shifts and adds."
> — p.100

中文解釋：**這個例子很重要，它展示了「擴充不存在時會怎樣」——有兩種結果：**
1. **寫組語用 `mul`** → **編譯錯誤**（Unrecognized opcode）
2. **寫 C 用 `*`** → **編譯成函式庫呼叫**（用移位和加法做乘法，慢很多但能跑）

**注意 GCC 的 `-march` 用小寫字母**（`rv32gc`，不是 `RV32GC`）。

**Table 3.2（p.100）機器架構與 ABI 對照**（藍字是 Wally 的預設組態）：

| Architecture | Synonym | ABI |
| --- | --- | --- |
| **rv32e** | | **ilp32e** |
| **rv32i** | | **ilp32** |
| rv32im / rv32iac / rv32imac | | ilp32 |
| rv32imafc | | ilp32f |
| **rv32imafdc** | **rv32gc** | **ilp32d** |
| **rv64i** | | **lp64** |
| rv64im / rv64ic / rv64iac / rv64imac | | lp64 |
| **rv64imafdc** | **rv64gc** | **lp64d** |

**規律很清楚**：**有 F 就用 f 尾綴的 ABI，有 D 就用 d 尾綴**——
因為浮點參數要用浮點暫存器傳（呼應 Table 3.1）。

用法：`-march=rv32i -mabi=ilp32` 或 `-march=rv64gc -mabi=lp64d`。
也可以寫更長的名字加其他擴充：`-march=rv64gc_zba_zbb_svpbmt`（用底線分隔）。

### GCC 的四個步驟與選項（3.3.6）

> "riscv64-unknown-elf-gcc is both a C compiler and assembler. It is invoked as a
>  single command, but under the hood it performs four steps:
>  - **Preprocess**: Insert #include files and substitute #define macros with their values
>  - **Compile**: Turn each C program into assembly language
>  - **Assemble**: Turn each assembly program into an ELF object file
>  - **Link**: Join all the object files together, relocate sections to desired addresses,
>    resolve cross-references, and produce an ELF executable file"
> — p.101

中文解釋：**四步驟：預處理 → 編譯 → 組譯 → 連結。** 一個指令做完四件事。

**Table 3.3 GCC 選項（p.101）——這張表最實用：**

| 選項 | 意思 |
| --- | --- |
| `example.S` | 原始檔。`.S` = 組語，`.c` = C |
| `-o example` | 輸出執行檔名稱 |
| `-march=rv32i` | 機器架構 |
| `-mabi=ilp32` | ABI（要和架構相容，見 Table 3.2） |
| `-mcmodel=medany` | 中型 code model（32-bit 相對位址）；`medlow` 是小型（絕對位址） |
| **`-nostartfiles`** | **不要讓組譯器插入啟動碼**，只組譯 `example.S` 裡的程式 |
| `-T` | 指定 linker script 的路徑 |
| `-g` | 產生除錯符號（除錯時能看到原始碼） |
| `-static` | 靜態連結函式庫，避免動態函式庫 |

### Linker script（3.3.6 續）

中文解釋：Code Example 3.3（p.102）的 `link.ld`：
```
OUTPUT_ARCH( "riscv" )
ENTRY(rvtest_entry_point)
SECTIONS
{
  . = 0x80000000;
  .text : { *(.text.init) }
  . = ALIGN(0x1000);
  .tohost : { *(.tohost) }
  . = ALIGN(0x1000);
  .data : { *(.data) }
  .data.string : { *(.data.string)}
  . = ALIGN(0x1000);
  .bss : { *(.bss) }
  _end = .;
}
```

**讀法**：`.` 是「目前位址」的意思。
- `. = 0x80000000` → 從這裡開始
- `.text : { *(.text.init) }` → 把所有檔案的 `.text.init` 放進 `.text` section
- `. = ALIGN(0x1000)` → **對齊到 4 KiB 邊界**

**為什麼對齊 4 KiB？** 書上說明：
**"which is the size of a page if virtual memory is used (see Chapter 11)"**（p.102）
——**page 大小。** 這樣每個 section 可以獨立設定權限（第 11 章）。

**不指定 `-march` 和 linker script 會怎樣**（p.102）：
架構變成系統相關（通常是 rv64gc，**會產生壓縮指令**），
起始位址變成 **0x10078**。範例輸出顯示格式變 `elf64`，跳躍變成 16-bit 壓縮指令 `a001`。

### Makefile（3.3.6 續）

> "Typing the compile command is tedious and error prone, and reconstructing all the
>  compiler flags later would be difficult. We avoid these problems by creating a
>  Makefile along with the source code."
> — p.103

中文解釋：Code Example 3.4（p.103）：
```makefile
example.objdump: example
	riscv64-unknown-elf-objdump -D example > example.objdump

example: example.S
	riscv64-unknown-elf-gcc -o example -march=rv32i -mabi=ilp32 -mcmodel=medany \
		-nostartfiles -T../../link/link.ld  example.S

clean:
	rm -f example example.objdump
```

**Makefile 的觀念（p.103）：**
- 每個區塊是一個 **recipe（配方）**
- **冒號後面是 dependency（相依）**：`example.objdump` 依賴 `example`，`example` 依賴 `example.S`
- **make 會自動判斷什麼需要重建**（檔案改了才重跑）

`make` 建置、`make clean` 清除。Makefile 語法在 Appendix B.5.4。

**進階寫法（Code Example 3.8，p.110）用變數：**
```makefile
TARGET = sumtest
$(TARGET): $(TARGET).S sum.S
	riscv64-unknown-elf-gcc -g -o $(TARGET) ...
```
邊欄點出好處（p.109 邊欄）：**用 `TARGET` 變數，改程式名只要改一行**，
而 Code Example 3.4 的 `example` 出現在很多地方，每個都要改。

>  *directives*. For RISC-V GCC, single-line comments begin with // or #. Multiline
>  comments begin with /* and end with */. Labels end with a colon (:)."
> — p.103

**Sections**

**Other**

### Spike：黃金參考模型（3.3.8）

> "Spike was the original *golden reference model* of the RISC-V instruction set
>  architecture: it served both as a simulator and as a reference against which other
>  RISC-V hardware or software implementations can be compared. Sail has replaced
>  Spike for this purpose, but Spike is more convenient to use."
> — p.105

> "Both are instruction set simulators, so they only simulate the function of the
>  instructions (not the actual hardware) and, thus, are not cycle accurate. They
>  ignore delays such as cache misses, memory transactions, and so on."
> — p.105

中文解釋：**"golden reference model"（黃金參考模型）的定義要記住：
不只是模擬器，更是「別人拿來比對的標準答案」。**

**現在 Sail 才是正式的黃金參考，Spike 只是比較好用。**

書上很有趣地吐槽（p.105）：
**"Spike shockingly lacks a user manual, but brief instructions can be found at [Spike]."**

名字由來（p.105 邊欄）：Spike 得名自完成橫貫大陸鐵路的**金道釘（golden spike）**。
邊欄還補了一句很誠實的話：
**"The term golden is contentious because it implies perfection, and even the best
reference model never perfectly matches a nontrivial written specification."**

**Table 3.5 Spike 指令（p.106）——實用速查：**

| 指令 | 作用 |
| --- | --- |
| **Enter** | 逐條執行 |
| `reg 0 t0` | 印出 hart 0 的 t0（**也可印 CSR**：`reg 0 mstatus`） |
| `fregs` / `fregd` | 印單/雙精度浮點暫存器 |
| `mem 80000004` | 印**實體位址** 0x80000004 的內容 |
| `mem 0 80000008` | 印 core 0 的**虛擬位址** 0x80000008 的內容 |
| `until <condition>` | 執行到條件成立 |
| `while <condition>` | 條件成立時持續執行 |
| `run` | 持續執行並印出 PC 和指令 |
| `rs` | 靜默執行（不印） |
| **Ctrl-c** | 暫停並回到互動除錯模式 |
| `q` | 結束 |
| `help` | 列出可用指令 |

**注意 `mem` 有兩種形式**：`mem <addr>` 是實體位址，`mem <core> <addr>` 是虛擬位址。

**所有 Spike 的值都是十六進位**（p.105）。

進階用法範例（p.105）：
```
: until pc 0 80000004
: until reg 0 a0 2a
: while mem 0 80000020 1
```

邊欄的實務建議（p.106 邊欄）：
Spike 透過 HTIF 支援系統呼叫但文件很差、用 `pk`（proxy kernel）處理、
透過 OpenOCD 接 gdb 但**在作者的環境不可靠**。
**"If your program is complicated enough to need these features, you may be better
off running with QEMU."** ——**程式複雜到需要這些功能時，改用 QEMU。**

### HTIF：讓程式能告訴模擬器「我做完了」（3.3.8 續）

> "A RISC-V program used for simulation or testing typically ends with an infinite
>  loop, so it doesn't wander into undefined instructions. Therefore, a Spike
>  simulation will also end by looping indefinitely. Spike provides a basic *host
>  target interface* (HTIF) which, among other features, allows a program to signal
>  completion. To do so, a program must declare an 8-byte .dword at a label called
>  tohost. In Spike, a write of 1 to this address causes the program to terminate
>  successfully. A write of 3 causes it to print *** FAILED *** and terminate."
> — p.106

中文解釋：**問題**：裸機程式沒有 OS 可以「結束」，所以都用無限迴圈收尾。
那模擬器怎麼知道跑完了？

**解法：HTIF。** 宣告一個叫 `tohost` 的 8-byte 位置，寫入約定的值：

| 寫入值 | 意義 |
| --- | --- |
| **1** | **成功結束** |
| **3** | 印出 `*** FAILED ***` 並結束 |
| **任何偶數** | 觸發系統呼叫（數值被解讀為指向系統呼叫參數陣列的指標） |

系統呼叫例子（p.106）：**編號 64 是 sys_write**，三個參數是 file descriptor、
字串指標、長度。**fd 0/1/2 分別是 stdin/stdout/stderr。**

**`tohost` 的位址不重要**（p.106 邊欄）——
Spike 只是偵測「寫到符號表中叫這個名字的位址」。

### Signature：把記憶體內容 dump 出來比對（3.3.8 續）

> "Spike also has a *signature* mechanism to write the contents of a block of memory
>  to a file upon completion. Typically, the signature block should have a series of
>  words that are only correct if the program ran properly. The signature block in a
>  .data section is delimited by begin_signature: and end_signature: labels."
> — p.107

中文解釋：**signature 是自動化測試的核心機制**：
程式把「只有跑對才會正確」的結果寫進一塊記憶體，
模擬結束後 dump 成檔案，**跟預期輸出 diff**。

```bash
$ spike +signature=example.signature.output +signature-granularity=4 example
```
`granularity=4` 表示每行 4 bytes、十六進位。

**這個機制就是第 3.7 節官方測試套件的運作原理。**

### 效能量測用的 CSR（3.3.9）

> "RISC-V has several CSRs used for performance measurement. instret indicates how
>  many instructions have been retired (i.e., completed). cycle indicates how many
>  clock cycles have passed. The csrr reg, CSR pseudoinstruction reads a CSR into reg,
>  an integer register."
> — p.107

中文解釋：**兩個基本計數器：**
- **`instret`**：**退休（完成）的指令數**（呼應 2.3 節的 retired）
- **`cycle`**：經過的時脈週期數

**讀法：`csrr reg, CSR`**（pseudoinstruction）。

**重要陷阱（p.107 邊欄）：**
> "In Spike, cycle and instret both advance by one each cycle and have the same value
>  because one instruction is executed in each cycle. In a real processor with a CPI
>  other than 1.0, the two will differ."

**在 Spike 上 cycle 永遠等於 instret**（因為 ISS 不是週期精確的，見 3.1 節）。
**要量真正的 CPI 必須用邏輯模擬器或真硬體。**
Spike 上的 `instret` 只能用來數指令數，不能用來算效能。

邊欄也提到（p.107 邊欄）：RISC-V 有可組態的效能計數器可量測
cache miss、分支預測錯誤等微架構事件（第 8.4.3.1 節）。

### 完整範例：sumtest（3.3.10）

中文解釋：**這個範例把前面所有東西串起來**，值得完整讀。
`$WALLY/examples/asm/sumtest`，RV64 程式，兩個檔案。

**`sumtest.S`（Code Example 3.5，p.108）的結構：**
```asm
.global rvtest_entry_point
rvtest_entry_point:
    la sp, topofstack      # 初始化堆疊指標
    la t0, N               # 取得 N 的位址
    ld a0, 0(t0)           # 載入 N（8-byte，RV64）
    csrr s8, instret       # 呼叫前的指令數
    jal sum                # 呼叫 sum(N)
    csrr s9, instret       # 呼叫後的指令數
    sub s9, s9, s8         # 差值 = 呼叫期間執行的指令數
    la t0, begin_signature
    sd a0, 0(t0)           # 把 sum(N) 存進 signature
    sd s9, 8(t0)           # 把指令數存進 signature

write_tohost:
    la t1, tohost
    li t0, 1               # 1 = 成功，3 = 失敗
    sd t0, 0(t1)           # 送出成功訊號

self_loop:
    j self_loop

.section .tohost
tohost:   .dword 0
fromhost: .dword 0

.data
N:  .dword 4

.EQU XLEN,64
begin_signature:
    .fill 2*(XLEN/32),4,0xdeadbeef   # 用 0xdeadbeef 初始化
end_signature:

.bss
    .space 512
topofstack:
```

**七個值得學的技巧：**
1. **`la` 是 pseudoinstruction**，組譯成 `auipc` + `addi`（PC 相對），p.107
2. **RV64 用 `ld`/`sd`（8-byte）**，不是 `lw`/`sw`
3. **用 `csrr instret` 前後相減量測函式的指令數**
4. **`.bss` 保留 512 bytes 當堆疊，`topofstack` 在最高位址**（堆疊往下長）
5. **signature 預先填 `0xdeadbeef`**——邊欄說明理由（p.108 邊欄）：
   **這個值明顯不像任何合理的計算結果，所以「沒被寫到」一眼就看得出來。**
6. **`.EQU XLEN,64` 定義常數**，讓 `.fill` 的大小可以隨 XLEN 調整
7. **`tohost` 放在自己的 `.section .tohost`**（linker script 有對應條目）

**`sum.S`（Code Example 3.6，p.109）** 是被呼叫的函式，
標準的 callee-saved 樣式（呼應 2.1 節 Code Example 2.11）：
```asm
sum:
    addi sp, sp, -16     # 開堆疊空間
    sd s0, 0(sp)         # 保存 s0, s1
    sd s1, 8(sp)
    ...
done:
    mv a0, s0            # 回傳值放 a0
    ld s0, 0(sp)         # 還原
    ld s1, 8(sp)
    addi sp, sp, 16
    ret
```

**預期結果（Code Example 3.7，p.109）：**
```
000000000000000A     # sum(4) = 1+2+3+4 = 10 = 0xA
000000000000001D     # 執行了 29 = 0x1D 條指令
```

書上的計算值得看（p.109）：
**"Counting instructions, we see the call to sum takes 13+4N instructions,
including the jal and one of the csrr instructions. Remember that bgt executes
one last time when the for loop exits. So, for N = 4, the expected return value is
sum(4) = 1+2+3+4 = 10 = 0xA, and the number of instructions executed is 29 = 0x1D."**

**注意 "bgt executes one last time when the for loop exits"** ——
算指令數時最容易漏掉迴圈最後一次的條件判斷。

**建置與測試（p.110）：**
```bash
$ make clean   # 刪除舊檔
$ make         # 建置並反組譯
$ make sim     # 用 Spike 模擬並比對 signature
Signature matches! Success!
```

`make sim` 的實作（Code Example 3.8，p.110）：
```makefile
sim:
	spike +signature=$(TARGET).signature.output +signature-granularity=8 $(TARGET)
	diff --ignore-case $(TARGET).signature.output $(TARGET).reference_output || exit
	echo "Signature matches! Success!"
```

邊欄解釋了那個 `|| exit` 的巧妙之處（p.110 邊欄）：
**OR 運算子（`||`）是惰性的**——`diff` 相同時回傳 TRUE，惰性 OR 就跳過 `exit`，
於是印出 Success；**不同時 `diff` 回傳 FALSE，就執行 `exit` 停下 make**。
**一行達成「成功才繼續」。**

### 從反組譯讀出的細節（3.3.10 續）

中文解釋：Code Example 3.9（p.111–112）的反組譯值得逐項對照（p.110 說明）：
- **格式是 elf64**
- **含 16-bit 壓縮指令**，例如 0x8000003c 的 `li`（機器碼只有 4 個十六進位數字 `4285`）
- **`la` 組譯成 `auipc` + `addi`**：
  ```
  80000000: 00003117  auipc sp,0x3
  80000004: 20010113  addi  sp,sp,512    # 80003200 <_end>
  ```
- **堆疊指標初始化為 0x80003200**，是 `.bss` section 的最高位址
- **linker 把 `sumtest` 和 `sum` 合併成單一連續的 text section**
- 資料區：**`N` 在 0x80002000，16-byte 的 signature 在 0x80002008**

還有一個有趣的觀察（p.112 邊欄）：
**`objdump -D` 會把資料區也「反組譯」成無意義的指令**——
`deadbeef` 被解讀成 `jal t4,...`。
**用 `-d`（小寫）只會顯示預期含有指令的 section。**

**ELF metadata（Code Example 3.10，p.112–114）** 的重點：
- `Flags: 0x5, RVC, double-float ABI` ——**旗標記錄了用哪個 ABI**
- Section header 列出 `.text`、`.tohost`、`.data`、`.bss`、`.riscv.attributes`、
  除錯段（`.debug_*`，因為用了 `-g`）、`.symtab`、`.strtab`
- **`.bss` 的 Type 是 NOBITS**（不佔檔案空間）
- 符號表有 28 個項目，包含 `topofstack`、`N`、`begin_signature`、`tohost`、
  `self_loop`、`sum`、`rvtest_entry_point` 等
- 屬性段：
  ```
  Tag_RISCV_arch: "rv64i2p1_m2p0_a2p1_f2p2_d2p2_c2p0"
  Tag_RISCV_priv_spec: 1
  Tag_RISCV_priv_spec_minor: 11
  ```
  **意思是：RV64GC（各擴充的版本號寫在後面，`2p1` = version 2.1），
  特權規格 1.11。**

## 所以呢

**這節建立了整本書的日常工作循環：
`make`（組譯連結）→ `objdump`（檢查機器碼）→ `spike`（模擬）→ `diff` signature（驗證）。**
三個最實用的東西：
1. **GCC 四個關鍵旗標**：`-march`、`-mabi`、`-mcmodel`、`-nostartfiles`
2. **HTIF + signature 機制**——這是所有自動化測試（第 3.7 節）的基礎
3. **`csrr instret` 量指令數**，但記得 **Spike 上 cycle == instret，量不到真正的 CPI**
