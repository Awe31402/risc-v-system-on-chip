# 22.1 Principles

> 原書 p.784.e48–784.e52（Chapter 22: Linux）
> 涵蓋 22.1.1 Embedded Linux Hardware Requirements、22.1.2 Bootloader、22.1.3 Device Tree、22.1.4 Kernel、22.1.5 Root Filesystem、22.1.6 Init、22.1.7 Shell

## 這節在講什麼

第 22 章讓 Wally 跑真正的 Linux。這不只是「好玩」——書上開宗明義說這是**最好的系統級測試**：

> "Booting a Linux operating system (OS), in addition to being practical, is a good system test because it shows that all major subsystems of the processor work together, including the basic core, control and status registers (CSRs), exceptions, memory management, and peripherals."
> — p.784.e48

22.1 是概念背景：一台機器從通電到出現登入提示，中間有哪些階段、每個階段的產物叫什麼。這節幾乎沒有 RISC-V 內容，是純粹的 Linux 系統知識。

## 關鍵點

### OS 的三大職責

> "Boot the computer when it turns on; Protect hardware and other processes from faulty or malicious processes; Provide resources to processes: Process and thread management and scheduling; Memory management; File system management; Peripheral device drivers; Security; User interface"
> — p.784.e48–e49

中文解釋：這三項正好對應前面幾章的硬體——**保護**靠第 8 章的特權模式與第 11 章的 PMP/PMA，**記憶體管理**靠第 11 章的虛擬記憶體，**排程**靠第 20 章 CLINT 的計時器中斷，**裝置驅動**靠第 20 章的周邊。

### RTOS 與 general-purpose OS 的分野

> "Real-time operating systems typically do not support virtual memory because a page fault causes a long and unpredictable delay and because the system usually lacks secondary storage and enough memory to require complex management."
> — p.784.e49

中文解釋：**RTOS 不用虛擬記憶體的理由是「延遲不可預測」**，不是「做不到」。即時系統的核心要求是「保證在有界時間內回應」，而 page fault 要去磁碟抓資料，時間完全無法保證。這是一個很好的「需求決定架構」的例子。

FreeRTOS、VxWorks 是常見的 RTOS。

> "Linux has become popular for complex embedded systems, such as televisions and printers, because it provides many powerful functions such as networking and scheduling, runs on most processors with memory management units (MMUs), has a wide set of device drivers, is free and open source, and has a large community of experts. Linux also has a real-time OS flavor called Preempt RT that guarantees a response within a bounded time."
> — p.784.e49

中文解釋：注意「runs on most processors **with MMUs**」——**Linux 需要 MMU**，這就是為什麼第 11 章的虛擬記憶體是跑 Linux 的前提。

> "Linux has evolved to encompass more than 28 million lines of source code with contributions from more than 20,000 developers. As of 2025, about 46,000 lines of code are specific to supporting RISC-V."
> — p.784.e49

中文解釋：2800 萬行裡只有 4.6 萬行是 RISC-V 專屬的（0.16%）——**這就是移植到新架構可行的原因**，絕大部分程式碼是架構無關的。

### build system：把整套系統自動組出來

> "Open-source build systems, also simply called build systems, automate this process. They produce a bootloader, kernel, and root file system. They often involve a cross-compiler, so they could build on an x86 PC or server but compile the OS to run on RISC-V or ARM. Contemporary build systems include Buildroot, Yocto, EmbToolkit, OpenEmbedded, OpernWrt, PTXdist, and Tizen."
> — p.784.e49

中文解釋：記住 build system 的**三個產物**——bootloader、kernel、root filesystem。這三樣東西是後面所有小節的主軸。Wally 用 Buildroot。

### 硬體最低需求

> "Embedded Linux runs on most 32- and 64-bit processor architectures with MMUs. It is easiest to configure with at least 16 MiB of RAM and 8 MiB of Flash memory storage, although it can be squeezed into smaller systems"
> — p.784.e50

中文解釋：**16 MiB RAM + 8 MiB Flash** 是舒適的下限。Wally 用 256 MiB（下一節會看到）。還需要一個終端介面（通常是 RS-232 序列埠——第 20 章的 UART 就是為此而存在）和一個載入軟體的方式（SD 卡、USB、序列埠或 JTAG）。

### 開機為什麼要分階段

> "When a processor first powers on or resets, it begins in the most privileged mode and sets the program counter to some address called the reset vector. The system must have a small ROM or Flash memory at this address containing zero stage bootloader (ZSBL) code to start the boot process. The DRAM controller is not yet initialized, so the boot loader initially has access only to a small on-chip SRAM and the boot ROM. Booting is typically divided into several stages, each of which brings up more capabilities for the system and transfers code for the next phase from nonvolatile storage into RAM until the boot loader can load the Linux kernel into DRAM and transfer control to it."
> — p.784.e50

中文解釋：**分階段的根本原因是「剛通電時什麼都還沒初始化」**——DRAM 控制器還沒設定好，所以連 DRAM 都不能用，只有晶片內的小 SRAM 和 boot ROM。所以只能用一小段程式碼，把能力一層一層疊上去。

（邊欄：bootloader 這個詞來自「pull yourself up by your bootstraps」——自己拉自己的鞋帶把自己提起來。這個「不用現成程式碼就要跑起 OS」的矛盾，正是這個俏皮說法的來源。後來縮寫成 "booting"。）

### Device Tree：把硬體描述從程式碼裡抽出來

> "Historically, this information was compiled into the kernel, such that changing the hardware could require recompiling the OS. In the 1980s, Sun Microsystems defined the Open Firmware specification including a device tree, which is a data structure that describes the hardware configuration"
> — p.784.e50

中文解釋：**這是整節最重要的概念**。問題是：kernel 怎麼知道這台機器有多少 RAM、UART 在哪個位址、有幾顆 CPU？

- **舊做法**：編進 kernel 裡 → 換硬體就要重新編譯 kernel
- **device tree**：做成一份獨立的資料檔，bootloader 把它傳給 kernel

device tree 描述的內容：CPU 核心數與型號、DRAM 大小、周邊的種類與版本、**記憶體映射上的位址**、周邊對應到哪條中斷線。

> "They are described by human-readable text files with a .dts suffix. A device tree compiler converts them to a more compact binary format called a device tree blob or flattened device tree (FDT) with a .dtb suffix. Typically, the bootloader loads the FDT and passes it to the kernel."
> — p.784.e51

中文解釋：`.dts`（人寫的文字檔）→ 編譯 → `.dtb`（緊湊的二進位）。**bootloader 把 FDT 的位址放進一個暫存器傳給 kernel**——下一節會看到 Wally 的 ZSBL 把它放進 `a2`。

### kernel：一份映像跑遍所有硬體

> "One of the principles of Linux is that a common kernel image can run on a wide variety of hardware with different numbers and types of cores and peripherals, without requiring recompilation. The kernel calls an underlying firmware layer that provides a standardized interface to platform-dependent tasks such as starting and stopping cores. It uses the device tree to define the set of peripherals."
> — p.784.e51

中文解釋：**兩個抽象層讓「一份 kernel 跑遍天下」成為可能**：
- **device tree** 處理「有哪些硬體」
- **firmware（SBI）** 處理「怎麼操作平台相關的東西」

這正是下一節 OpenSBI 存在的理由。

> "The kernel is often kept in nonvolatile storage in compressed format. After being loaded, it decompresses itself, enables virtual memory, and calls start_kernel(), which in turn initializes device drivers, enables interrupts, mounts a root file system, and then starts the idle process, scheduler, and init process."
> — p.784.e51

中文解釋：kernel 啟動的五個動作，順序有意義——**先開虛擬記憶體，才能做後面的事**。

kernel 的四種檔案格式：
- `vmlinux`：靜態連結的 ELF，適合反組譯與除錯
- `vmlinuz`：`vmlinux` 用 zlib 壓縮
- `Image`：`vmlinux` 的純二進位（去掉 ELF 標頭與符號表），**可直接開機**
- `zImage`：`Image` 壓縮版

### root filesystem 與 BusyBox

> "The Linux kernel loads a root filesystem into RAM containing a minimal set of nonkernel programs necessary to boot. The filesystem is called rootfs or initramfs. It is kept in a .cpio (Copy In and Out) format archive."
> — p.784.e51

中文解釋：kernel 本身不含 `ls`、`sh` 這些指令，要從 rootfs 拿。

> "Core Linux utilities such as ls, cp, and init collectively take a fair amount of disk space. To reduce the size of the root filesystem, small embedded Linux systems often use a program called BusyBox that performs most of the basic functionality of these utilities while being much smaller (e.g., ∼6 MB) by leaving out unnecessary features and sharing code across utilities. Each of the regular utilities in /bin is actually a symbolic link to /bin/busybox, which interprets the command line and performs the functions."
> — p.784.e52

中文解釋：**BusyBox 是「一個執行檔假扮成一百個指令」**。`/bin/ls`、`/bin/cp`、`/bin/sh` 全都是指向 `/bin/busybox` 的符號連結，BusyBox 看自己被用什麼名字呼叫（`argv[0]`）來決定要做什麼。這樣共用的程式碼（參數解析、錯誤處理、libc）只需要一份，整包才 6 MB。

### init：第一個 U-mode 程式

> "The first U-mode process is called init (short for initialization). It has a process ID of 1 and is the parent of all other Linux processes. It is called a daemon process, which runs in the background independent of the control of interactive users."
> — p.784.e52

中文解釋：**PID 1，所有其他行程的祖先**。它讀 `/etc/inittab` 決定開機要跑哪些程式（通常是各種 daemon：`nfsd`、`sshd`、`httpd`、`lpd`）。`systemd` 是比較現代的替代品，用平行啟動來縮短開機時間。

（邊欄：daemon 這個名字來自 Maxwell's daemon——熱力學裡那個不斷分類分子的想像生物。唸作 "dee-mon" 不是 "day-mon"。）

### shell

> "init typically then launches a login shell with job control so that the user can log in, issue commands, and use <Ctrl-c> to terminate a running program. Linux offers various shells, with bash currently being the default on most distributions. ash is a lightweight version of bash provided by Busybox."
> — p.784.e52

中文解釋：走到這一步就是登入提示出現了——**開機完成**。

## 名詞表

| 名詞 | 意思 |
| --- | --- |
| RTOS | real-time OS，保證有界回應時間，通常不用虛擬記憶體 |
| Preempt RT | Linux 的即時版本 |
| build system | 自動產生 bootloader、kernel、rootfs 的工具（Buildroot、Yocto…） |
| cross-compiler | 交叉編譯器，在 x86 上編出 RISC-V 執行檔 |
| reset vector | 重設後 PC 指向的位址（Wally 是 0x1000） |
| ZSBL | zero stage bootloader，放在 boot ROM 的第一段程式碼 |
| bootstrap / booting | 自己把自己提起來的比喻 |
| U-Boot / GRUB | 嵌入式／PC 常見的 bootloader |
| device tree | 描述硬體配置的資料結構 |
| `.dts` / `.dtb` | device tree 原始碼／編譯後的二進位 |
| FDT (flattened device tree) | 扁平化裝置樹，即 `.dtb` |
| Open Firmware | Sun 在 1980 年代定義的規格，device tree 的源頭 |
| mainline / longterm kernel | 主線核心（9–10 週一版）／長期維護版（約一年一版） |
| `start_kernel()` | kernel 解壓並開啟虛擬記憶體後呼叫的初始化函式 |
| `vmlinux` / `vmlinuz` / `Image` / `zImage` | ELF ／壓縮 ELF ／純二進位／壓縮二進位 |
| rootfs / initramfs | 根檔案系統，載入 RAM 的最小程式集合 |
| `.cpio` | Copy In and Out，rootfs 的封存格式 |
| BusyBox | 把幾十個工具合成一個執行檔，靠符號連結區分 |
| init | 第一個 U-mode 行程，PID 1，所有行程的祖先 |
| daemon | 背景常駐程式 |
| `/etc/inittab` | init 的設定檔 |
| `systemd` | 較新的 init，平行啟動以縮短開機時間 |
| `bash` / `ash` | 常見的 shell ／ BusyBox 提供的輕量版 |

## 所以呢

一台機器從通電到登入提示的路徑是：**reset vector → ZSBL → firmware → kernel → rootfs → init → shell**，其中 device tree 貫穿全程，負責告訴每一層「這台機器長什麼樣」。這個分層的價值在於**一份 kernel 映像能跑在各種硬體上**——device tree 描述有什麼、firmware 抽象怎麼操作。

下一節 22.2 把這張地圖填上 Wally 的具體數字：ZSBL 只有 72 位元組、OpenSBI 在 0x80000000、kernel 在 0x80200000、整個開機要執行約五億條指令。
