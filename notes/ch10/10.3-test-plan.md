## 關鍵點

### 目前只靠「順便測到」

> "**The Wally caches are currently exercised through the ordinary instruction tests and Linux boot.
>  Section 21.3.1 describes cache performance verification.**"
> — p.442

中文解釋：**「ordinary instruction tests and Linux boot」——這就是全部了。**

**兩種測試各自能涵蓋什麼：**

| 測試 | 能測到 | 測不到 |
| --- | --- | --- |
| **一般指令測試** | 基本的讀寫正確性 | **替換策略、flush/invalidate、多層 miss** |
| **Linux boot** | **大量真實的存取樣式**（5.5 億條指令，呼應 2.8.4 節） | **corner case 仍然隨機** |

**這和第 9.4 節（匯流排）的狀況一樣：
「主要靠正常使用順便測到」。**
（呼應 5.1.1 節：ad-hoc 測試能建立基本信心，但不保證完整。）

**沒有測到的東西可以從 10.1 節推出來，值得自己列一下：**
- **pLRU 替換策略的正確性**（特別是 Example 10.5 那種樹狀更新）
- **Thrashing 情境**（Code Example 10.2 那種）
- **Dirty line 的 evict 與寫回**
- **`fence.i` 的 flush + invalidate**
- **Uncacheable 位址的處理**（PMA）
- **壓縮指令跨 line 的 spill**

（其中幾項會在第 12、13、14 章的測試裡間接涵蓋到。）

### 功能驗證 vs 效能驗證

> "**Section 21.3.1 describes cache performance verification.**"
> — p.442

中文解釋：**這裡出現了一個重要的區分：**

| 類型 | 問什麼 | 在哪 |
| --- | --- | --- |
| **功能驗證** | **答案對不對？** | 本節（靠一般測試） |
| **效能驗證（PV）** | **快不快？miss rate 合不合理？** | **第 21.3.1 節** |

**為什麼 cache 需要獨立的效能驗證：**

**cache 是一個「錯了也不會出錯」的元件**——
即使替換策略寫錯、命中率極差，**程式的結果仍然完全正確**，只是變慢。
**所以功能測試抓不到 cache 的效能 bug。**

（呼應 8.3 節 Table 8.6 的 "PV" 縮寫：performance verification，
以及 2.8.4 節 Table 2.7 列出的 Cache PV 和 BranchPred PV 測試。）

**這是 cache 和分支預測器共有的特性：
它們都是「非架構狀態」（呼應 2.7 節），
丟掉仍然正確，所以正確性測試碰不到它們的效能。**

## 名詞表

| 名詞 | 意思 |
| --- | --- |
| Cache performance verification（PV） | 效能驗證。檢查命中率等效能指標是否符合預期（第 21.3.1 節） |

## 所以呢

**這節只有兩句話，但點出了一個重要的驗證觀念：**

**Cache 是「非架構狀態」——寫錯了程式還是跑出正確答案，只是變慢。
所以一般的功能測試（比對 signature）完全抓不到 cache 的問題。**

**因此需要獨立的「效能驗證」（第 21.3.1 節）：
量測命中率、miss 次數，和預期值比對。**

**這個觀念也適用於分支預測器**（第 13 章）——
同樣是非架構狀態，同樣需要獨立的 PV 測試。
