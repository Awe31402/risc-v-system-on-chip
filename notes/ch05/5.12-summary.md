# 5.12 Summary

> 原書 p.247（Chapter 5: Design Verification）

## 這節在講什麼

第 5 章總結，五段。

**前兩段講「為什麼驗證這麼重要」（成本論證），
中間兩段回顧手段，最後一段是全章最有份量的一段——關於謙卑。**

**整章最該記住的數字在第一句：驗證的工作量接近晶片設計其他所有環節加起來的兩倍。**

## 關鍵點

### 驗證的工作量：其他所有環節加起來的兩倍

> "**Logic verification now accounts for nearly twice as much effort as all the other elements
>  of chip design combined.** Although customers expect software to contain bugs and are
>  accustomed to frequent updates, **they need hardware to work reliably.** Serious hardware
>  bugs that require creating a new mask set and fabricating new chips cost millions of dollars
>  in engineering costs and even more in opportunity costs when a chip is late to market."
> — p.247

中文解釋：**這個數字比 5.1 節開頭那句「驗證工程師約佔團隊一半」更強**——
**人數一半，但工作量是其他全部的兩倍。**

**軟硬體的根本差異講得很清楚：**
- **軟體**：客戶預期有 bug，習慣頻繁更新
- **硬體**：**客戶需要它可靠地運作**

理由是成本結構：**嚴重的硬體 bug 要重做光罩、重新流片，
工程成本數百萬美元，而晶片延遲上市的機會成本更高。**
（呼應 5.1.1 節：Pentium FDIV 召回花了 4.75 億美元。）

**最後一句是本節最精煉的洞見：**
> "**Defining the set of features that must be tested, the test vectors that exercise these
>  features, and the expected results is harder than coding the features themselves.**"

**「定義該測哪些功能、用什麼測試向量、預期結果是什麼——
這比實作那些功能本身還難。」**

**這三件事正好對應 5.2 節 DV plan 的三個欄位**（功能描述、所需激勵、檢查方法）。

### 手段回顧：從最便宜到最完整

> "**Lint tools save a great deal of debugging time** by warning the designer of bad code, such
>  as undriven signals, combinational loops, and mismatched port sizes. The next verification
>  step is to simulate the design in a testbench that applies test vectors and logs any
>  discrepancies. Verification engineers also measure code coverage to ensure that the test
>  vectors exercise every part of the code."
> — p.247

> "**Regression testing runs the full suite of tests after each code change to ensure that a new
>  feature doesn't break the existing system; this is important to know right away because it is
>  much easier for a developer to fix bugs in code as it is being written than for somebody else
>  unfamiliar with the buggy code to isolate and fix the bug later.**"
> — p.247

中文解釋：**四個步驟的順序就是成本由低到高：
lint → testbench 模擬 → 程式碼覆蓋率 → 回歸測試。**

**回歸測試那段給了「為什麼要立刻知道」最好的理由：**
**「開發者在寫程式的當下修 bug，比別人事後去隔離和修理陌生程式碼裡的 bug 容易太多。」**

**這句話把 always-working 策略（5.1.6 節）的價值講清楚了——
它省的不是機器時間，是人的時間，而且是「對的那個人」的時間。**

### RISC-V 專屬的驗證流程

> "The RISC-V Architecture Test Special Interest Group provides the riscv-arch-test suite of
>  programs that exercise each unprivileged instruction and produce a signature for each test.
>  Wally's testbench loads each program into memory and runs it on the Verilog, then checks that
>  the signature in memory matches expectations. **Wally also uses its own wally-riscv-arch-test
>  suite to exercise privileged instructions, CSRs, exceptions, and the virtual memory system.**"
> — p.247

中文解釋：**兩套測試的分工再確認一次**（呼應 3.7 節）：
- **`riscv-arch-test`（官方）**：非特權指令
- **`wally-riscv-arch-test`（自訂）**：**特權指令、CSR、例外、虛擬記憶體系統**

**官方測試涵蓋不到特權架構，這是整本書反覆提到的缺口。**

### Lock-step 的價值再確認

> "Wally also uses the Imperas lock-step-compare to run programs and check that the architectural
>  state (memory, PC, registers, and CSRs) in the Verilog model matches the Imperas reference
>  model after each instruction. **This methodology has caught many subtle errors that are
>  difficult to detect with signature-based verification.**"
> — p.247

中文解釋：呼應 5.6 和 5.11.9 節（至少找到 20 個 bug）。
**關鍵詞是 "subtle errors"（微妙的錯誤）——
signature 抓得到明顯的錯，抓不到微妙的錯。**

### 最後一段：關於謙卑（全章最有份量的話）

> "**Despite best efforts at verification, any system complicated enough to be interesting almost
>  certainly has bugs lurking. An experienced design team has the humility to recognize human
>  imperfection.** Complex systems often have firmware-programmable configuration (known as
>  "chicken bits") to disable or work around components that turn out to be defective."
> — p.247

中文解釋：**這段值得完整記住，它是整章的態度總結。**

**「任何複雜到有趣的系統，幾乎必然潛伏著 bug。
有經驗的設計團隊有謙卑去承認人的不完美。」**

（這和 2.8 節邊欄「我們有信心 bug 還在」、
2.10 節「三年的努力，仍確信有未發現的 bug」完全一致——
**全書三次用不同方式說同一件事。**）

**但這不是消極，而是導向一個具體的工程對策：**

**"chicken bits"（膽小位元）**——
**韌體可程式化的組態位元，用來停用或繞過事後發現有缺陷的元件。**

**這個名字很傳神**：設計者「膽小」到會預先準備逃生門。
**它的邏輯是：既然一定會有 bug，那就設計成「出事時能關掉它」。**

**這是驗證思維的最後一層：
不只是「盡力找出 bug」，還要「假設找不完，預留補救手段」。**

（實務上，chicken bit 常用來關掉某個最佳化功能——
效能變差但至少能正確運作，而且不必重做光罩。）

## 名詞表

| 名詞 | 意思 |
| --- | --- |
| Mask set | 光罩組。重做要花數百萬美元 |
| Opportunity cost | 機會成本。晶片延遲上市的損失 |
| **Chicken bits** | **韌體可程式化的組態位元，用來停用或繞過有缺陷的元件** |

## 所以呢

**第 5 章的核心數字：驗證的工作量接近晶片設計其他所有環節加起來的兩倍。**

三件帶得走的事：

1. **最難的不是實作功能，而是「定義該測什麼、怎麼測、預期結果是什麼」**——
   這就是 DV plan 存在的理由。

2. **立刻跑回歸的價值不在機器時間，在人的時間**：
   **寫的當下修 bug，比事後讓別人修陌生的程式碼容易太多。**

3. **最後那段的態度**：複雜到有趣的系統一定有 bug，
   所以除了盡力驗證，還要**預留 chicken bits 當逃生門**。
   **「假設自己會失敗，並為此做準備」是成熟工程的標誌。**
