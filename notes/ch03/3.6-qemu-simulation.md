# 3.6 QEMU Simulation

> 原書 p.127–133（Chapter 3: RISC-V Software Tool Flow）
> 涵蓋 3.6.1 Simulating with QEMU、3.6.2 Debugging With GDB

## 這節在講什麼

QEMU：**速度光譜最快的那一端**（約 10 億指令/秒），
靠的是 **JIT（just-in-time）翻譯**把 RISC-V 指令翻成主機的 x86 指令。

兩個子節：
- **3.6.1**：怎麼跑，以及一個重要的陷阱——**QEMU 預設的指令計數是錯的**
- **3.6.2**：**接 GDB 做原始碼層級除錯**，這是 QEMU 最實用的能力

**QEMU 的定位：要開 OS、要用 GDB 除錯、要跑得快，就用它；
要權威答案就用 Sail，要精確週期數就用邏輯模擬器。**

## 關鍵點

### QEMU 的定位與速度來源

> "QEMU is a powerful open-source emulator that handles many different computer
>  architectures including RISC-V. It performs just-in-time translation from the
>  architecture being simulated to the architecture of the host computer running QEMU
>  (e.g., from RISC-V to x86). Thus, it can run on the order of 1 billion instructions
>  per second, which is fast enough to comfortably boot an OS and an order of magnitude
>  faster than Spike."
> — p.127

> "It also interfaces to GDB to facilitate debugging, and emulates peripherals
>  (e.g., a timer) that are important for booting an OS. QEMU is not a golden model for
>  RISC-V, but no known discrepancies exist."
> — p.127

中文解釋：**速度的來源是 JIT 翻譯**（呼應 2.3 節的 binary translation）：
不是逐條解譯，而是**把一段 RISC-V 程式碼翻成等效的 x86 程式碼，然後直接跑**。
翻譯一次、執行多次，所以快。

**三個關鍵能力：**
1. **快到可以舒服地開 OS**（比 Spike 快一個數量級）
2. **模擬周邊**（計時器等，開 OS 必需）——這是 emulator 而非 ISS 的定義（3.1 節）
3. **接 GDB**

**最後一句的措辭要注意**：
**"QEMU is not a golden model for RISC-V, but no known discrepancies exist."**
——**不是權威（那是 Sail），但目前沒發現不一致。**
這是很誠實的說法：可以信任，但出爭議時以 Sail 為準。

名字唸法（p.127 邊欄）：kyoo-EM-yoo、kee-moo、kwemu 或逐字母念。
是 **Quick EMUlator** 的縮寫。

### 執行 QEMU

中文解釋：基本指令（p.127）：
```bash
$ cd $WALLY/examples/asm/sumtest
$ qemu-system-riscv64 -S -M virt -nographic -bios none -kernel sumtest
```

**Table 3.7 執行選項（p.128）——這張表要記：**

| 選項 | 作用 |
| --- | --- |
| **`-S`** | 啟動時**暫停在程式開頭**（PC 不動） |
| **`-M virt`** | 用**通用的虛擬 RISC-V 平台**，而非特定開發板（呼應 2.4 節的 memory map） |
| **`-nographic`** | 關掉圖形視窗，**把虛擬序列埠導到 console** |
| **`-bios none`** | **跳過載入 OpenSBI BIOS，以裸機模式執行** |
| `-kernel sumtest` | 把程式載入記憶體 |
| **`-icount 0`** | **啟用虛擬指令計數器，以取得正確的週期數**（代價是模擬變慢） |
| `-gdb tcp::1234` | 接 GDB 做單步除錯 |

**`-bios none` 的意義**：QEMU 預設會載入 OpenSBI（M-mode 韌體，呼應 2.3.6 節的 SBI），
裸機測試不需要它。

### QEMU monitor 指令

中文解釋：**"Just after invoking QEMU, it will appear to hang."**（p.127）
——**一開始看起來像當掉，這是正常的**（因為 `-S` 讓它停住了）。

**按 Ctrl-a 然後 c 進入 monitor。**

**Table 3.8 QEMU 指令（p.128）：**

| 指令 | 作用 |
| --- | --- |
| **Ctrl-a, 然後 c** | 進入 monitor |
| `info registers` | 印出所有通用暫存器 |
| `x <address>` | 顯示該位址的記憶體 |
| `x /2xg <address>` | **以十六進位顯示兩個 double word** |
| `c` | 繼續執行 |
| `q` | 結束模擬 |

**卡住時的逃生方法**（p.127 邊欄）：
> "As you are learning to use QEMU, it will often seem to lock up when you press the
>  wrong keys. Kill it with `killall qemu-system-riscv64` in another terminal window."

**`x /2xg` 的格式解讀**：`2` = 兩個、`x` = 十六進位、`g` = giant（8 bytes）。

### 重要陷阱：QEMU 預設的指令計數是錯的

> "Now the signature shows a sum of 0x0a (10) and an instret value of 0x48470! The sum
>  is correct, but the number of instructions retired is wildly inaccurate. QEMU by
>  default relies on the host processor's performance counters, which run at a much
>  different rate."
> — p.127

中文解釋：**這是本節最重要的警告。**

同一支程式：**Spike 報 29 條指令（0x1D），QEMU 預設報 0x48470 條——差了上千倍。**

**原因**：QEMU 預設直接用**主機處理器的效能計數器**，
而主機（x86）跑的是翻譯後的程式碼，**完全不是 RISC-V 的指令數**。

**解法：加 `-icount 0`**（p.128）：
```bash
$ qemu-system-riscv64 -M virt -nographic -bios none -kernel sumtest -icount 0
Ctrl-a c
(qemu) x /2xg 0x80002008
0000000080002008: 0x000000000000000a 0x000000000000001d
```
**現在 instret 是 0x1d，和 Spike 一致。**

（注意這次**省略了 `-S`**，讓它直接跑完。）

**代價是模擬速度變慢**——這是速度和精確度的典型取捨。
**（但即使用 `-icount 0`，QEMU 仍然不是週期精確的**，只是指令數正確而已，
週期數要靠邏輯模擬器——呼應 3.1 節。）

### 用 GDB 除錯（本節最實用的部分）

> "QEMU can interface with the GDB debugger to single step through a program or use
>  breakpoints. The interface is made with a TCP network connection to the QEMU virtual
>  machine."
> — p.128

中文解釋：**兩個終端機的做法：**

**終端機 1（啟動 QEMU 並等待 GDB）：**
```bash
$ qemu-system-riscv64 -S -M virt -nographic -bios none -kernel sumtest -gdb tcp::1234
```
**注意這裡 `-S` 是必要的**——要停住等 GDB 連上。

**終端機 2（啟動 GDB 並連線）：**
```bash
$ riscv64-unknown-elf-gdb -ex "target remote :1234" -iex "file sumtest"
```
**`-iex "file sumtest"` 載入符號表**，這樣才能用名字（如 `&begin_signature`）
而不是位址（p.129）。

**連接埠選擇**（p.129）：通常 1234 就行，
被佔用時挑 **1024–49151** 範圍內的其他埠。

**Table 3.9 GDB 指令（p.129）——實用速查：**

| 指令 | 作用 |
| --- | --- |
| `info all-reg` | 印出所有整數暫存器 |
| `x <address>` | 印出該位址的記憶體 |
| **`x <name>`** | **用符號表的名字印記憶體**（如 `x/2xg &begin_signature`） |
| **`stepi`** | **單步執行一條指令** |
| **Enter** | **重複上一個指令**（單步時超好用） |
| **`b <function>`** | **在函式設中斷點**（用名字） |
| `b <address>` | 在指令位址設中斷點 |
| `c` | 繼續執行 |
| Ctrl-c | 暫停程式 |
| **`set $pc=<address>`** | **設定 PC**（例如設成 0x1000 重新開始） |
| `q` | 結束除錯 |

其他在範例中出現的實用指令：
- **`display /i $pc`**：每次停下來自動顯示目前指令（p.130）
- **`s`**（step）、**`n`**（next）：C 層級的單步（進入函式 / 跳過函式）
- **`p <變數>`**（print）：印出變數值

### GDB 實際操作的觀察

中文解釋：書上的除錯記錄（p.130–131）有幾個值得學的片段：

**（1）看得到 bootloader 跳進主程式**（p.130）：
```
=> 0x1000:  auipc t0,0x0
...（幾條 bootloader）
=> 0x1014:  jr  t0
rvtest_entry_point () at sumtest.S:6
6           la sp, topofstack    # Initialize stack pointer
=> 0x80000000 <rvtest_entry_point>:  auipc sp,0x3
```
**有符號表之後，GDB 會顯示對應的原始碼行**（`sumtest.S:6` 那行）。

**（2）用名字檢查記憶體**（p.130、131）：
```
(gdb) x/2xg &begin_signature
0x80002008:  0xdeadbeefdeadbeef   0xdeadbeefdeadbeef     ← 執行前
...
0x80002008:  0x000000000000000a   0x00000017658e47a8     ← 執行後
```
**執行前是 `0xdeadbeef`（初始值），執行後第一個變成 0x0a（sum = 10）。**
**第二個（指令數）是個亂七八糟的大數**——正是前面說的 QEMU 預設計數問題。

**（3）設中斷點、繼續、檢查暫存器**（p.131）：
```
(gdb) b self_loop
Breakpoint 1 at 0x80000042: file sumtest.S, line 23.
(gdb) c
(gdb) info all-reg
a0    0xa    10          ← 回傳值正確
sp    0x80003200         ← 堆疊指標
ra    0x8000001c         ← 回傳位址
```

**（4）重新開始執行**（p.131）：
```
(gdb) set $pc=0x1000
(gdb) b sum
(gdb) c
```
**把 PC 設回 0x1000 就能重跑**，不用重啟 QEMU。

### 除錯 C 程式要換旗標

> "To simulate a C program, change -g to -gdwarf-2 in the Makefile to generate
>  appropriate debugging symbols for C variables."
> — p.132

中文解釋：**這個細節很容易踩到**：
組語程式用 `-g` 就夠，**C 程式要用 `-gdwarf-2`** 才能看到變數。

C 除錯的實際樣子（p.132）：
```
(gdb) b main
(gdb) c
Breakpoint 1, main () at sum.c:17
(gdb) s              ← step，進入函式
19    setStats(1);
(gdb) n              ← next，跳過函式
20    s[0] = sum(4);
(gdb) s
sum (N=N@entry=4) at sum.c:11
(gdb) p N            ← 印變數
$1 = 4
(gdb) p result
$3 = 1
```
**可以直接印 C 變數的值，而且會顯示原始碼行號。**

**一個常見的困惑**（p.133）：
```
(gdb) p s[0]
$4 = <optimized out>
```
**`<optimized out>` 表示這個變數被最佳化掉了，看不到值。**
（呼應 3.4 節：`-O2` 會把整個計算消掉。）
**除錯時常常需要降低最佳化等級才看得到變數。**

另外書上提醒（p.132）：**QEMU 會卡在 `printf` 那行**——
因為 `printf` 透過 HTIF 做系統呼叫，在 `while (fromhost == 0)` 等待（p.133）。
用 Ctrl-C 中斷可以看到它停在 `syscalls.c:28`。

## 名詞表

| 名詞 | 意思 |
| --- | --- |
| QEMU | Quick EMUlator。開源模擬機，約 10 億指令/秒 |
| Just-in-time translation | JIT 翻譯。把被模擬的指令翻成主機原生指令再執行，故速度快 |
| `-M virt` | 使用通用虛擬 RISC-V 平台而非特定開發板 |
| `-bios none` | 跳過 OpenSBI BIOS，以裸機模式執行 |
| `-nographic` | 關閉圖形視窗，序列埠導向 console |
| **`-icount 0`** | **啟用虛擬指令計數器以取得正確指令數**；預設值是錯的 |
| QEMU monitor | Ctrl-a 然後 c 進入的互動介面 |
| `-gdb tcp::1234` | 開啟 GDB 的 TCP 連線埠 |
| `stepi` / `s` / `n` | 單步一條指令 / C 層級進入函式 / C 層級跳過函式 |
| `-gdwarf-2` | 除錯 C 程式所需的符號格式（取代 `-g`） |
| `<optimized out>` | 變數被編譯器最佳化掉，除錯器看不到值 |

## 所以呢

**QEMU 的兩個實務要點：**
1. **預設的指令計數是錯的（差上千倍），必須加 `-icount 0`**——
   因為它預設用主機的效能計數器。
2. **接 GDB 做原始碼層級除錯是 QEMU 最有價值的能力**：
   設中斷點、單步、印變數、用符號名稱看記憶體。
   除錯組語用 `-g`，**除錯 C 要改成 `-gdwarf-2`**，而且要降低最佳化等級
   才不會看到一堆 `<optimized out>`。

三個模擬器的選用原則到此完整：**QEMU 快且能除錯、Spike 方便、Sail 權威。**
