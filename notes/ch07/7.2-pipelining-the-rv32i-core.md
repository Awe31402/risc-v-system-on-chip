## 關鍵點

### Pipeline 的目的與代價

> "The cycle time of the single-cycle processor is limited by the longest path to execute an
>  instruction, including fetching the instruction, reading from the register file, performing an
>  ALU operation, accessing data memory, and writing the result back to the register file.
>  **Pipelined processors shorten the cycle time and improve throughput by separating the processor
>  into multiple pipeline stages; hence, the next instruction can start before the current one
>  completes. This introduces a set of *hazards* when one instruction depends on the results of a
>  previous instruction that has not yet completed.**"
> — p.317

中文解釋：**單週期的週期時間 = 一條指令完整走完全程的時間**（五個動作串在一起）。
**Pipeline 把它切開，讓下一條指令提早開始——代價就是 hazard。**

### 相對於單週期的四個改變

> "Wally uses a classic five-stage pipeline: Fetch, Decode, Execute, Memory, and Writeback.
>  It thus adds four pipeline registers to the single-cycle processor (see Fig. 7.10) to prevent
>  the results of one stage from entering the next stage before the rising edge of the clock.
>  **These registers are called *nonarchitectural state* because they are added for implementation
>  reasons and don't hold information visible to the programmer.** The main differences between the
>  pipelined and single-cycle processors include:
>  - **A hazard unit**, which resolves pipeline hazards using stalls and flushes
>  - **Pipeline registers** with enable and clear inputs to stall or flush the pipe
>  - **Bypass multiplexers** to forward results from previous instructions
>  - **Forwarding logic** controller to drive bypass multiplexers
>  - **Control and data signals are staged** through the pipeline to remain associated with their
>    instruction
>  - **Signal name suffixes** (F, D, E, M, and W) indicate the pipeline stage"
> — p.318–319

中文解釋：呼應 2.7.2 節，但多了細節。**六項改變：**

| 改變 | 作用 |
| --- | --- |
| **hazard 單元** | 用 stall 和 flush 解決危障 |
| **pipeline 暫存器**（有 enable 和 clear） | 可被 stall 或 flush |
| **bypass 多工器** | 轉發前面指令的結果 |
| **forwarding logic** | 驅動 bypass 多工器 |
| **控制與資料訊號都要 staged** | 跟著它們的指令一起前進 |
| **訊號名後綴 F/D/E/M/W** | 標示所在級（呼應 4.3.1.2 節） |

**「非架構狀態」的定義再次出現**（呼應 2.7 節）：
**pipeline 暫存器是為了實作而加的，程式設計師看不到。**

**一個值得注意的設計決定（p.318 邊欄）：**
> "**PCLinkE = PCE + 4 is recomputed in the Execute stage rather than being pipelined along from
>  PCPlus4F through Decode and Execute stage registers. The cost of duplicating the PC incrementer
>  is less than the cost of storing an additional XLEN bits in the Fetch and Decode pipeline
>  registers.**"

**重算比傳遞便宜**——多一個加法器比多兩個 XLEN-bit 暫存器划算。
**這是 pipeline 設計的常見取捨：重新計算 vs 一路傳遞。**

### 暫存器檔案的分半時序

> "The IROM, register file, and DTIM read asynchronously during the Fetch, Decode, and Writeback
>  stages, respectively. DTIM and register file writes occur in the Writeback stage. **The DTIM is
>  written at the beginning of the Writeback stage (at the rising clock edge). But register file
>  writes occur later, at the falling clock edge in the middle of the Writeback stage, because
>  ResultW isn't available until after that stage's initial rising clock edge. Thus, register file
>  writes occur in the first half of the Writeback stage, and asynchronous register reads occur in
>  the second half of the Decode stage (after register file writes complete).**"
> — p.319

中文解釋：呼應 2.7.2 節的「前半寫、後半讀」技巧。
**這裡給了更精確的理由：`ResultW` 要到 Writeback 級開始的上升緣之後才有效，
所以暫存器檔案在時脈下降緣（Writeback 級的中間）才寫。**

**Trap 與 Writeback 的關係（p.319 邊欄）——很重要的設計原則：**
> "Chapter 8 introduces CSRs and traps. **In a processor with traps, it is important to update the
>  state of the system *after* all hazards have been resolved. Otherwise, there is a risk that if a
>  trap occurs, part of the state has changed before the trap did not, leaving the system in an
>  inconsistent state. Waiting to *commit* (complete) all changes to the architectural state
>  (registers, memory, and CSRs) until the Writeback stage avoids such problems.**"

**「所有架構狀態的改變都等到 Writeback 級才提交」——
這是處理 trap 的關鍵前提**（第 8 章會用到）。

### 同步記憶體帶來的新問題

> "All but the smallest memories use synchronous reads for performance and area efficiency."
> — p.319

中文解釋：呼應 4.2.3.3 和 6.2.3 節。**Wally 用 `DTIM_SUPPORTED` 和 `IROM_SUPPORTED`
組態參數啟用同步記憶體。**

**Fig. 7.12（p.320）比較兩種時序：**

| | **非同步讀（a）** | **同步讀（b）** |
| --- | --- | --- |
| 位址何時穩定 | **Memory 級開始**（`IEUAdrM`） | **Execute 級**（`IEUAdrE`，要提前 setup） |
| 讀取何時發生 | Memory 級內，位址穩定後 | **Memory 級開始的時脈上升緣** |
| 寫入 | Writeback 級開始的上升緣 | 同左 |
| 額外硬體 | — | **`DTIMAdr` 多工器** |

**書上的解釋（p.319）：**
> "**Fig. 7.12(b) uses a memory with synchronous read. Writes still occur at the start of the
>  Writeback stage, but reads occur on the rising edge of the clock at the start of the Memory
>  stage. Hence, the address must set up earlier for reads so that the read address, DTIMAdr, is
>  available before the rising edge of the clock at the beginning of the Memory stage. Thus, the
>  DTIMAdr mux chooses the DTIM address as IEUAdrE for reads and IEUAdrM for writes.**"

**關鍵：讀取用 `IEUAdrE`（Execute 級），寫入用 `IEUAdrM`（Memory 級）。**

**這製造出一個新的結構危障（p.320）：**
> "**The DTIM address (A) must set up in the Execute stage for reads and in the Memory stage for
>  writes. So, performing a read after a write causes a pipeline hazard because they both need to
>  access the address port in the same cycle — that is, while the store is in the Memory stage and
>  the load is in the Execute stage.**"

**store 後緊接 load 會衝突**——兩者同時需要位址埠。
（這就是 7.2.2.3 節的 `StoreStallD`，也呼應 2.8.1 節說的「store 後緊接 load 要 stall 一週期」。）

**Table 7.8（p.320）DTIM 存取的三級分工，很清楚：**

| 級 | DTIM 讀 | DTIM 寫 |
| --- | --- | --- |
| **Execute** | **計算並設定記憶體位址：`IEUAdrE` = 基底 + 偏移** | 計算並設定記憶體位址 |
| **Memory** | **從 `IEUAdrE` 同步讀出 `ReadDataM`** | **設定 `IEUAdrM`、`WriteDataM`、`MemRWM`** |
| **Writeback** | **把 `ReadDataW` 寫進暫存器檔案** | **把 `WriteDataM` 同步寫進 DTIM** |

**IROM 也有同樣的問題（p.321）：**
> "The IROM has a similar issue as the DTIM: the address for synchronous reads must setup before the
>  Fetch stage. Hence, the IROM must be read with **`PCNextF` rather than `PCF`**. Therefore,
>  **the reset is applied to the PCNextF mux rather than the PCF register**, as shown in Fig. 7.14."

**IROM 用 `PCNextF` 而非 `PCF` 讀取，所以 reset 要施加在 PCNextF 多工器上**
（Fig. 7.14，p.321：PCNextF 是個 3 選 1，00 = PCPlus4F、01 = IEUAdrE、1x = 0（reset））。

**兩個記憶體都加了 chip enable 來在 stall 時保持舊值**（p.320）。

### 完整的 hazard 範例（Fig. 7.15）

中文解釋：**Fig. 7.15（p.322）是本章最重要的一張圖。程式是：**
```asm
addi t0, zero, 42
ori  t1, t0, 1
lb   t2, 0(t0)
and  t3, t2, t0
beq  t3, zero, else
sb   t3, 0(t0)
xori t4, t3, 1
...
else: sub t5, t1, t4
```

**書上的逐條分析（p.322–323），值得完整跟一遍：**

**（1）`addi` — 無相依**
> "The addi instruction has no dependencies. **In cycle 1, the instruction memory (IM) fetches the
>  addi. In cycle 2, the register file/sign extender reads the operands 0 and 42. In cycle 3, the
>  ALU executes 42 + 0 = 42. In cycle 4, the data memory is unused. In cycle 5, the register file
>  writes 42 to t0.**"

**（2）`ori` — RAW hazard，從 Memory 級轉發**
> "The ori instruction depends on t0. In cycle 3, it reads t0 from the register file but gets an
>  outdated value because the addi instruction won't write t0 until cycle 5. **This is called a
>  *read after write* (RAW) data hazard.** The pipeline solves the hazard in cycle 4 by **forwarding
>  t0 from the Memory stage of the addi to the Execute stage of ori** so the correct value is used."

**（3）`lb` — 從 Writeback 級轉發**
> "The lb instruction also depends on t0.... This time, the pipeline solves the hazard in cycle 5 by
>  **forwarding t0 from the Writeback stage of the addi to the Execute stage of lb.**"

**（4）`and` — 兩個相依，一個免費、一個要 stall**
> "The and instruction depends on both t0 from addi and t2 from lb. **addi writes t0 to the register
>  file in the first half of cycle 5 (i.e., at the falling edge of clock), so and reads t0 correctly
>  in the second half of cycle 5, and no forwarding is necessary.** Unfortunately, **t2 comes from
>  the data memory and is not yet available when and wants it at the start of cycle 6. Thus, the
>  hazard unit must stall the pipeline during cycle 6: and remains in the Decode stage, and beq
>  remains in the Fetch stage. On cycle 7, t2 is now available and is forwarded from the Writeback
>  stage of lb to the Execute stage of and.**"

**這一段展示了三種不同的解法在同一條指令上：
t0 靠「前半寫後半讀」免費解決，t2 要 stall 一週期再轉發。**

**（5）`beq` — control hazard，flush 兩條**
> "The beq must predict whether to take the branch.... **our simple pipelined processor always
>  predicts that the branch is not taken and adds 4 to PC as usual. Thus, it fetches sb in cycle 7
>  and xori in cycle 8. By cycle 8, the beq executes and determines if t3 = 0. If so... the branch
>  should have been taken. The hazard unit then flushes the sb and xori instructions and fetches sub
>  in cycle 9.**"

**Flush 的實作方式（p.323）：**
> "**Flush is performed by clearing the flushed instruction's pipeline registers or at least all
>  those that contain write enables such as RegWrite or MemWrite, so that the flushed instruction
>  changes no state and behaves as a nop.**"

**「至少要清掉含有寫入致能的那些」——因為只要不寫任何狀態，
那條指令就等於什麼都沒做。**

### Pipeline 暫存器：`flopenrc`

> "As shown in Fig. 7.13, each pipeline register takes a stall and flush signal. For example,
>  the register between the Decode and Execute stages takes StallE and FlushE to stall or flush the
>  instruction entering the Execute stage. Implicitly, **all registers are also synchronously
>  resettable to begin at a known initial state.** Thus, pipeline registers typically use flip-flops
>  with enable, reset, and clear (flopenrc) as shown in Fig. 7.16. **Stall drives the enable (en)
>  pin. Flush drives the clear pin. Synchronous reset has highest priority, initializing Q to 0 even
>  if en = 0. Enable has next priority, recirculating Q when disabled.**"
> — p.323

中文解釋：**優先序：reset > enable > clear。**

| 訊號 | 接到哪 | 意義 |
| --- | --- | --- |
| **`Stall`（反相）** | **enable** | stall = 不致能 = 保持舊值 |
| **`Flush`** | **clear** | flush = 清成 0 |
| `reset` | 同步 reset | 最高優先，即使 en = 0 也清成 0 |

**Fig. 7.16（p.323）的電路：D 先和 `~clear` 做 AND，
再經過一個 enable 多工器（1 選 D、0 選 Q），最後和 `~reset` 做 AND 進正反器。**

**兩個實作註記（p.323 邊欄）：**
> "**Clear has the lowest priority in this implementation, although clear and reset could be ORed
>  together in an alternate register design.**
>  **Enable uses a multiplexer in this implementation, although it could be ANDed with clk in an
>  alternate register design. Such clock gating requires a latch on the enable to prevent clock
>  glitching, as well as CAD tools to model the gated clock delay for setup and hold time analysis.**"

**用多工器實作 enable 比用 clock gating 簡單**——
clock gating 需要 latch 防止時脈毛刺，還需要工具支援 gated clock 的時序分析。
（呼應 2.8 節：Wally 不支援 clock gating。）

### 轉發邏輯

> "The pipelined processor adds forwarding logic to the controller, as shown in Fig. 7.17, to forward
>  results from later stages (Memory and Writeback) to the Execute stage. The forwarding logic outputs
>  are combinational. **The pipeline forwards a result to the Execute stage if a source register in
>  the Execute stage (Rs1E or Rs2E) matches the valid destination register in a later stage (RdM or
>  RdW). A destination register is valid if it is nonzero (writes to register 0 are ignored). If the
>  source register matches destinations in multiple stages, the pipeline picks the earliest one,
>  which corresponds to the most recent instruction.**"
> — p.324

中文解釋：**轉發的三個判斷條件：**
1. **來源暫存器（Rs1E/Rs2E）等於後面某級的目的暫存器（RdM/RdW）**
2. **那一級確實會寫入**（`RegWriteM`/`RegWriteW`）
3. **目的暫存器不是 0**（寫 x0 會被忽略）

**而且「多個級都符合時選最早的那一級」——因為那是最近的指令。**

**`ForwardAE` 的邏輯（p.324）：**
```
if      ((Rs1E == RdM) & RegWriteM) & (Rs1E != 0)   # Mem stage
          ForwardAE = 10
else if ((Rs1E == RdW) & RegWriteW) & (Rs1E != 0)   # WB stage
          ForwardAE = 01
else      ForwardAE = 00                             # No forwarding
```
**`ForwardBE` 的邏輯完全對稱，只是用 `Rs2E`。**

**注意 Memory 級的優先序比 Writeback 高**（`if` 在前）——
**因為 Memory 級的指令比較新。**

### 兩種結構危障

**（1）Load-use hazard**
> "The result of a load instruction is not available until the end of the Memory stage. A dependent
>  instruction requires the result by the start of the Execute stage. Therefore, **a load immediately
>  followed by use requires a one-cycle stall. This is called a *structural hazard* because the
>  structure of the pipeline cannot forward the load result to the next instruction.** This can be
>  detected in the Decode stage (LoadStallD) by checking if the instruction in the Execute stage is a
>  load (indicated by bit 1 of the memory read/write enable signal, MemRWE[1] = 1) and if that load
>  destination register matches either source register in the Decode stage (MatchDE = 1)."
> — p.324

```
MatchDE    = (Rs1D == RdE | Rs2D == RdE)
LoadStallD = MemRWE[1] & MatchDE
```

**（2）Store-load structural hazard**（同步記憶體造成的）
> "As discussed in Section 7.2.1, the synchronous DTIM needs the read address to setup in the Execute
>  stage and the write address to setup in the Memory stage. **This creates another structural hazard
>  that a DTIM store cannot immediately be followed by a load because both would need the address
>  port at the same time.** This StoreStallD is detected when the instruction in the Execute stage is
>  a store (MemRWE[0]) and the instruction in the Decode stage is a load (MemRWD[1])."
> — p.324–325

```
StoreStallD = MemRWE[0] & MemRWD[1]
```

**兩個 stall 都在 Decode 級偵測**，因為那是「還來得及擋住」的最後一級。

### Hazard 單元的四塊架構（本節精華）

> "The hazard unit monitors various hazards that cannot be resolved by forwarding, such as load-use
>  dependencies and taken branches. Fig. 7.18 shows the general architecture of the hazard unit."
> — p.325

中文解釋：**Fig. 7.18（p.326）的四個區塊，這個架構要記住：**

```
Signals that      ┌──────────────────┐                    ┌─────────────────┐
cause flushes ──→ │ Flush Cause      │─ FlushXCause ─────→│ Combine Flush   │──→ FlushX
                  │ Generation       │                    │ FlushX =        │
                  ├──────────────────┤   ┌──────────────┐ │ FlushXCause or  │
Signals that      │ Stall Cause      │──→│ Propagate    │ │ previous stage  │
cause stalls  ──→ │ Generation       │   │ Stalls       │ │ is latest       │
                  │ Stall stage X if │   │ StallX =     │ │ stalled stage   │
                  │ flush doesn't    │   │ StallXCause  │ └─────────────────┘
                  │ have priority    │   │ or any future│──→ StallX
                  └──────────────────┘   │ stage stalled│
                                          └──────────────┘
```

**四塊的職責（p.325–326）：**

| 區塊 | 做什麼 | 原理 |
| --- | --- | --- |
| **Flush Cause Generation** | 計算每一級的 `FlushXCause` | 哪些級可能要被 flush |
| **Stall Cause Generation** | 計算每一級的 `StallXCause` | **「如果 flush 沒有優先權才 stall」** |
| **Propagate Stalls** | **某一級 stall 時，前面所有級都要 stall** | **防止指令堆疊** |
| **Combine Flush** | **flush 最後一個被 stall 的級之後的所有級** | 見下 |

**Propagate Stalls 的邏輯（p.326）：**
> "**When a stage stalls, all previous stages must also stall to prevent piling up. The Propagate
>  Stalls block stalls all stages prior to a stalled stage.**"

**Combine Flush 的邏輯（p.326）——這個最巧妙：**
> "**Finally, when a pipeline stage is stalled, the next stage should be flushed unless that stage is
>  also stalled. The Combine Flush block flushes all stages with a FlushXCause or after the latest
>  stalled stage.**"

**為什麼「stall 的下一級要 flush」？**
因為那一級即將接收的指令是重複的（前面那級卡住沒往前送），
**所以要在管線裡插一個氣泡（bubble）。**

**分支的處理（p.326）：**
> "**Branches and jumps are taken in the Execute stage. So, upon a taken branch or jump, two
>  instructions (those in the Fetch and Decode stages) must be flushed from the pipeline.**
>  PCSrcE indicates that a branch or jump is taken (in addition to selecting PCNextF = IEUAdrE,
>  the calculated target address)."

```
FlushDCause = PCSrcE
FlushECause = PCSrcE
```

**Flush 優先於 stall（p.326）：**
> "**Flushes have priority over stalls, so flushes gate the stall cause. The pipeline stalls in the
>  Decode stage for a load or store stall, unless the stage is flushed by the earlier logic
>  (FlushDCause or FlushECause).**"

```
StructuralStallD = LoadStallD | StoreStallD
StallDCause      = StructuralStallD & ~FlushDCause
```

**理由很直觀：如果那條指令反正要被丟掉，就沒必要為它 stall。**

**Fig. 7.19（p.327）是實際的邏輯電路：**
- **Propagate Stalls 的 OR 閘把 stall 往前傳**（`StallD` → `StallF`）
- **Combine Flush 的 AND 閘偵測「最後一個未被 stall 的級」**
  （`LatestUnstalledD`、`LatestUnstalledE`）
- **OR 閘把 FlushXCause 和 LatestUnstalled 合併**

**書上的例子（p.326）：**
> "**For example, if only Fetch and Decode are stalled, Execute is the latest unstalled stage and
>  must be flushed.**"

**一段很誠實的警告（p.326 邊欄）：**
> "**The hazard unit is one of the most difficult parts of the processor to get right, especially
>  when we add traps, multicycle bus and cache operations, etc. It has been the source of many subtle
>  bugs during the Wally design, which means it might still have other subtle bugs lurking.
>  Unfortunately, we know of no systematic way to design a provably correct hazard unit.**"

**「hazard 單元是處理器最難做對的部分之一……我們不知道有任何系統化的方法
可以設計出可證明正確的 hazard 單元。」**
（呼應 5.12 節的謙卑態度。）

### 效能分析：CoreMark 的 CPI

> "(7.15) Execution Time = Number of instructions × CPI × T_C"
> — p.327

> "**For a given processor and suite of programs, referred to as a benchmark, the cycle time and
>  number of instructions are constant, so CPI determines performance.**"
> — p.327

中文解釋：呼應 1.6、2.7 節的效能公式。
**固定處理器和 benchmark 時，CPI 就決定效能。**

**Table 7.9（p.328）CoreMark 的指令組成（rv32im、無分支預測）：**

| 類型 | 指令數 | 佔比 | **CPI** |
| --- | --- | --- | --- |
| R- 或 I-type ALU | 1,320,259 | **49.7%** | **1** |
| Jumps / returns | 46,750 | 1.8% | **3** |
| **Branches** | 588,905 | **22.2%** | **1.84** |
| Loads / stores | 698,738 | **26.3%** | **1.41** |
| **Total** | **2,654,652** | 100 | **1.32** |

**CPI 的完整推導（p.328），這段一定要跟一遍：**
> "**Branches are taken 41.9% of the time. Our static branch predictor predicts not taken;
>  therefore, misprediction rate is 41.9%. Each misprediction requires an additional two cycles to
>  flush the two instructions in the Fetch and Decode stages after the branch target address is
>  calculated in the Execute stage. Jumps always require three cycles: one to execute the jump and
>  two to flush the next two instructions. The performance counters indicate that 40.1% of loads
>  cause a use after load stall.**
>  Thus, the CPI for R-/I-type ALU operations is 1, **jumps is 3, branches is 1 + 0.419 × 2 = 1.84,
>  and loads/stores is 1 + 0.401 × 1 = 1.40.** The overall CPI is then a weighted sum of these CPIs:
>  **CPI = (0.497 × 1) + (0.018 × 3) + (0.222 × 1.84) + (0.263 × 1.41) = 1.32.**
>  This approximates CoreMark's reported CPI: # clock cycles / # instructions = 3,36,604 / 2,654,652
>  = 1.27."

**逐項拆解：**

| 類型 | CPI 的來源 |
| --- | --- |
| ALU | **1**（理想） |
| **Jumps** | **3** = 1（執行）+ 2（flush 兩條） |
| **Branches** | **1 + 0.419 × 2 = 1.84**（**41.9% 的分支會成立，每次錯誤預測罰 2 週期**） |
| **Loads/stores** | **1 + 0.401 × 1 = 1.41**（**40.1% 的 load 造成 use-after-load stall，罰 1 週期**） |

**加權：0.497×1 + 0.018×3 + 0.222×1.84 + 0.263×1.41 = 1.32**

**這個計算很值得學，因為它示範了「從指令組成和懲罰次數推算 CPI」的方法。**

**三個值得記住的實測數字：**
- **分支成立率 41.9%**（所以「永遠預測不成立」的錯誤率就是 41.9%）
- **每次分支預測錯誤罰 2 週期**（Fetch 和 Decode 兩條被 flush）
- **40.1% 的 load 後面緊接著用到結果**

**改進空間（p.328 邊欄）：**
> "**Adding a branch predictor in Section 13.3 improves the branch CPI. Adding bit manipulation
>  instructions reduces the instruction count. Together, these improve the overall CPI to 1.14** as
>  described in Section 21.1."

**1.32 → 1.14**（第 13 章的分支預測器 + 第 18 章的位元操作指令）。

## 名詞表

| 名詞 | 意思 |
| --- | --- |
| Nonarchitectural state | 非架構狀態。pipeline 暫存器等為實作而加、程式設計師看不到的狀態 |
| **`flopenrc`** | 有 enable、reset、clear 的正反器。**優先序：reset > enable > clear** |
| **`PCNextF`** | IROM 用它讀取（而非 `PCF`），因為同步讀要提前 setup；reset 施加在此多工器 |
| `DTIMAdr` 多工器 | 讀取選 `IEUAdrE`、寫入選 `IEUAdrM` |
| **RAW hazard** | Read-after-write 資料危障 |
| **Structural hazard** | 結構危障。pipeline 的結構本身無法解決（load-use、store-load） |
| `ForwardAE` / `ForwardBE` | 轉發多工器選擇訊號：10 = Memory 級、01 = Writeback 級、00 = 不轉發 |
| `LoadStallD` | `MemRWE[1] & MatchDE`。load 後緊接使用 |
| `StoreStallD` | `MemRWE[0] & MemRWD[1]`。store 後緊接 load（同步記憶體的位址埠衝突） |
| **Flush Cause Generation** | 產生各級的 flush 原因 |
| **Stall Cause Generation** | 產生各級的 stall 原因（**flush 有優先權時不 stall**） |
| **Propagate Stalls** | **某級 stall 時，前面所有級都 stall** |
| **Combine Flush** | **flush 最後一個被 stall 的級之後的所有級**（插入氣泡） |
| CPI | Cycles per instruction。理想 pipeline 為 1 |

## 所以呢

**這節把單週期核心變成五級 pipeline，代價是整套 hazard 處理機制。**

四件最該帶走的事：

1. **同步記憶體製造了一個新的結構危障**：
   **讀取的位址要在 Execute 級 setup，寫入的要在 Memory 級——
   所以 store 後緊接 load 要 stall 一週期。**

2. **Hazard 單元的四塊架構**（Fig. 7.18）：
   **Flush Cause → Stall Cause（flush 優先）→ Propagate Stalls（往前傳）
   → Combine Flush（flush 最後一個 stall 級之後的所有級）。**
   書上坦承**沒有系統化的方法能設計出可證明正確的 hazard 單元。**

3. **轉發的三個條件**：來源暫存器相符、那一級確實要寫、目的不是 x0。
   **多級都符合時選最早的（最近的指令）。**

4. **CoreMark 的 CPI = 1.32**，而且推導過程很值得學：
   **分支成立率 41.9% × 罰 2 週期、load-use 率 40.1% × 罰 1 週期、
   jump 固定 3 週期，再依指令組成加權。**
