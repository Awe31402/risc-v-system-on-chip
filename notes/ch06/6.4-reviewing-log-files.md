# 6.4 Reviewing Log Files

> 原書 p.269–286（Chapter 6: Logic Synthesis）
> 涵蓋 6.4.1 synth.out、6.4.2 Mapped Output Files、6.4.3 QoR Reports、
> 6.4.4 Performance Reports、6.4.5 Power Reports、6.4.6 Area Reports、6.4.7 Other Reports

## 這節在講什麼

**怎麼讀合成產生的一大堆報告。**

七個子節對應七類輸出：
1. **`synth.out`**（6.4.1）：完整的執行 log
2. **mapped 目錄**（6.4.2）：合成的實際產物（netlist 等四個檔案）
3. **QoR 報告**（6.4.3）：**一頁看完關鍵結果**
4. **時序報告**（6.4.4）：**逐格追關鍵路徑——本節精華**
5. **功耗報告**（6.4.5）
6. **面積報告**（6.4.6）
7. **其他報告**（6.4.7）

**讀報告的順序建議：先看 `qor.rep` 抓全貌，有問題再去 `timing.rep` 追細節。**

### mapped 目錄：四個輸出檔

> "**DESIGN.sdc**: Synopsys Design Constraints file; uses Synopsys Tcl commands to provide the
>  design constraints, including the clock period, driver and load cells, delays from primary
>  inputs and outputs, and maximum fanout
>  **DESIGN.sdf**: Standard Delay Format file; gives the design timing suitable for further timing
>  analysis
>  **DESIGN.ddc**: an encrypted binary database file; contains the synthesis results that Synopsys
>  tools load for further analysis
>  **DESIGN.sv**: contains the synthesized Verilog netlist."
> — p.270

中文解釋：**四個檔案各有用途：**

| 檔案 | 格式 | 內容 |
| --- | --- | --- |
| **`.sdc`** | Synopsys Design Constraints | 設計約束：時脈週期、驅動與負載元件、輸入輸出延遲、最大 fanout |
| **`.sdf`** | Standard Delay Format | **設計時序，供後續時序分析用** |
| **`.ddc`** | 加密二進位資料庫 | 合成結果，供 Synopsys 工具載入（如 Design Vision） |
| **`.sv`** | Verilog | **合成出來的網表** |

**階層式合成的取捨（p.270）：**
> "**By default, our scripts run hierarchical synthesis, preserving the same module hierarchy and
>  signal names as in the original Verilog. This makes interpreting the results feasible, but it
>  also prevents cross-module optimizations**, which is described in Section 6.5.2."

**保留階層 = 結果好懂，但失去跨模組最佳化。**
（呼應 6.1 節的 flatten 取捨。）

**一個常見的警告（p.270 邊欄）：**
> "Design Compiler warns that `clk` is a high-fanout net because it drives so many flip-flops.
>  **Placement tools will handle it with a special clock-routing algorithm designed to balance
>  delay.**"

**時脈是高 fanout 網路的警告可以忽略**——擺放工具有專門的時脈繞線演算法。

### 從行為描述到網表：hazard 模組的實例

中文解釋：Code Example 6.2（p.274）是 `hazard.sv` 的行為 Verilog，
Code Example 6.3（p.275）是合成後的網表。**這組對照非常有教學價值。**

**原始碼（節錄）：**
```systemverilog
// Stalls and flushes
assign FlushDCause = TrapM | RetM | CSRWriteFenceM | BPWrongE;
assign FlushECause = TrapM | RetM | CSRWriteFenceM |(BPWrongE & ~(DivBusyE | FDivBusyE));
...
assign StallDCause = (LoadStallD | StoreStallD | MDUStallD | CSRRdStallD | FCvtIntStallD |
                      FPUStallD) & ~FlushDCause;
...
// Stall each stage for cause or if the next stage is stalled
assign #1 StallF = StallFCause | StallD;
assign #1 StallD = StallDCause | StallE;
...
// Detect the first stage that is not stalled
assign LatestUnstalledD = ~StallD & StallF;
...
// Flush the stage if the previous stage is the last one stalled or the system has reason to flush
assign #1 FlushD = LatestUnstalledD | FlushDCause;
```

**這段程式碼本身就值得讀**（呼應 2.7 節的 hazard 單元）：
- **stall 會往前傳播**：後面的級 stall 了，前面的也要 stall
- **`LatestUnstalledD = ~StallD & StallF`**：
  **「這一級沒 stall 但前一級 stall 了」= 這一級是最前面沒被卡住的那級**
- **flush 的條件是「前一級是最後一個被 stall 的」**

**合成後的網表（節錄）：**
```systemverilog
module hazard ( BPWrongE, CSRWriteFenceM, RetM, TrapM, ... );
  wire  n4, n6, n7, n8, n9, n10, n11, n12;
  sky130_osu_sc_12T_ms__inv_1 U2 ( .A(LSUStallM), .Y(n7) );
  sky130_osu_sc_12T_ms__inv_3 U3 ( .A(n6), .Y(FlushD) );
  sky130_osu_sc_12T_ms__nor2_1 U5 ( .A(IFUStallF), .B(LSUStallM), .Y(n10) );
  sky130_osu_sc_12T_ms__oai21_1 U8 ( .A0(BPWrongE), .A1(n4), .B0(n7), .Y(n9) );
  ...
endmodule
```

**三個觀察（p.273）：**
1. **「很多訊號被最佳化掉了」**——
   > "Many of the signals have been optimized out of the netlist because **the rv32e
   >  configuration does not have a multiply and divide unit (MDU), floating-point unit (FPU),
   >  or privileged unit. Hence many inputs, including MDUStallD, FPUStallD, and all the trap
   >  and control and status register (CSR) signals, are tied to 0 and can be ignored.**"

   **這就是 4.2.5.1 節「綁 0 讓合成器消掉」的實際效果。**

2. **合成出來的是具體的元件實例**，元件名稱裡有：
   函式（`inv`、`nor2`、`oai21`、`nand2`、`buf`）+ 驅動強度（`_1`、`_2`、`_3`、`_4`）

3. **`oai21` 是複合閘**（OR-AND-Invert），
   一個元件實作 `~((A0|A1) & B0)`——**比用三個基本閘快也小。**

**`#1` 延遲的處理（p.273 邊欄）：**
> "The #1 delays in the Verilog in Code Example 6.2 are included for simulation to help see
>  causality. **They are ignored by synthesis.**"

（呼應 4.2.4.4 節。）

**用 Design Vision 看電路圖（p.273）：**
```bash
$ design_vision-xg
```
File → Read 開啟 `.ddc` 檔 → 在 Logical Hierarchy 面板找到 hazard 單元 →
Schematic → New Schematic View → 雙擊符號看裡面的閘。
**Fig. 6.12（p.273）就是這樣產生的電路圖，和 Code Example 6.3 的網表完全對應。**

### QoR 報告：一頁看完關鍵結果

> "Quality of results (QoR) reports summarize key timing and area results. **Timing metrics
>  include the critical path slack (WNS), TNS, and any hold time violations. Area metrics include
>  the number and area of combinational, sequential, and buffer/inverter cells.**"
> — p.275

中文解釋：**Fig. 6.13（p.276）的 `qor.rep`，關鍵欄位（SKY130 上的 rv32e）：**

```
Timing Path Group 'clk'
  Levels of Logic:              37.000000      ← 關鍵路徑經過 37 層邏輯
  Critical Path Length:          3.030967
  Critical Path Slack:          -0.152755      ← 負的，沒過
  Critical Path Clk Period:      3.030303
  Total Negative Slack:        -57.774506
  No. of Violating Paths:      710.000000
  Worst Hold Violation:          0.000000      ← hold 沒問題
  No. of Hold Violations:        0.000000

Cell Count
  Leaf Cell Count:               8226          ← 總元件數
  Buf/Inv Cell Count:            2069          ← 緩衝器/反相器
  Combinational Cell Count:      7053
  Sequential Cell Count:         1173          ← 正反器

Area
  Combinational Area:       52579.678278
  Noncombinational Area:    42734.023876
  Buf/Inv Area:             10614.396889
  Cell Area:                95313.702154
```

**書上的解讀（p.275）：**
> "**the critical path goes through 37 levels of logic. The target clock period is 3.03 ns, but
>  the design has 0.15 ns of negative slack, so it does not meet timing and has a best achievable
>  clock period of 3.18 ns. The area is 95,313 μm², or about 0.3 mm on a side. The processor is
>  built from 8,226 cells, of which 1,173 are sequential (flip-flops), 2,069 are inverters or
>  buffers, and the rest are logic gates. Synthesis took about 2 minutes. Synthesis involves a
>  certain amount of random choice, and thus results vary slightly from run to run.**"

**五個要記住的讀法：**
1. **最佳可達週期 = 目標週期 + |負 slack| = 3.03 + 0.15 = 3.18 ns**
2. **面積 95,313 μm² ≈ 0.3 mm 見方**（開根號）
3. **8,226 個元件中，1,173 個是正反器、2,069 個是緩衝器/反相器**
   ——**緩衝器佔了 25%！** 這是驅動長線和高 fanout 的代價
4. **hold 違反是 0**（如果不是 0 就要緊張，呼應 6.1 節）
5. **合成有隨機成分，每次跑結果略有不同**

### 效能報告：逐格追關鍵路徑（本節精華）

> "The synthesis script uses the `report_timing` command to generate `timing.rep` that lists the
>  worst overall timing path and `per_module_timing.rep` that lists the longest path through each
>  of the various modules."
> — p.277

中文解釋：**rv32e 的關鍵路徑是什麼（p.277）：**
> "**For rv32e, the longest path involves a branch comparison in the Execute stage triggering a
>  branch that leads to a stall or flush.** In SKY90 and TSMC28, the stall endpoint is longest.
>  In SKY130, the flush path is 2 ps slower than the stall path, but the flush path is more
>  complicated to describe because it involves canceling an EBU transaction. Therefore, this
>  section describes the stall critical path."

**Fig. 6.14（p.277）把關鍵路徑用藍色標在 rv32e 核心的方塊圖上，
從 Decode 級的 regfile 一路穿到 Fetch 級的 InstrEReg。**

**報告的欄位定義（p.280），這段一定要懂：**

| 欄位 | 意義 |
| --- | --- |
| **Point** | 元件或網路（wire）的名稱 |
| **Fanout** | 這條 net 驅動的元件數 |
| **Cap** | 這條 net 的總電容 |
| **Trans** | **轉態時間**：輸出從 20% 升到 80% V_DD 要多久 |
| **Incr** | **這個元件貢獻的增量延遲** |
| **Path** | **累計到目前為止的總延遲** |
| **r / f** | 訊號是上升（rising）還是下降（falling） |

**元件命名的解讀（p.280）：**
> "For example, `sky130_osu_sc_12T_ms__inv_4` is an inverter from the OSU SKY130 12-track
>  medium-speed standard cell library with a **drive strength of 4. Higher drive cells are faster
>  at driving large loads but are larger, have more input capacitance, and consume more power.
>  Design Compiler optimizes drive strength to meet the target cycle time at the lowest area
>  cost.**"

**`<製程>_<庫>_<軌數>T_<速度>__<功能>_<驅動強度>`**

**完整的路徑追蹤（p.280），這段值得逐句跟：**

> "this report shows that the clock rises at time 0. After a 0.32-ns clock-to-Q delay through the
>  D flip-flop (dff), the Rs2E[0] signal falls. This ripples through five gates (xnor2, nand2,
>  inv, nand2, nor2) to compute the ForwardBE[1] forwarding multiplexer control signal at 0.72 ns.
>  The forwarding mux output is available at 1.24 ns. **The 32-bit comparator involves 10 levels
>  of logic, completing at 1.84 ns.** The output passes through various levels of the hierarchy and
>  changes names to ieu/FlagsE[0]; this name changing doesn't cause delay but is shown to help you
>  follow the logic. The branch logic computes PCSrcE, which rises at 2.18 ns, indicating that the
>  branch is taken. **The StallE signal falls at 2.62 ns because the taken branch does not stall
>  the Execute stage but causes a flush instead.** Finally, after traversing the enable/clear logic,
>  the D input of the InstrEReg flip-flop *arrives* at 3.06 ns. The flip-flop has a setup time of
>  0.15 ns. The target clock period in this example is 3.03 ns (333 MHz), so the D value is
>  *required* at 3.03 − 0.15 = 2.88 ns. **Hence, the circuit has negative slack, and the target
>  frequency cannot be met: slack = 2.88 − 3.06 = −0.18 ns. The actual achievable frequency is
>  1/(3.03 + 0.18 ns) = 311 MHz.**"

**把時間軸整理出來，這就是關鍵路徑的解剖：**

| 時間 | 事件 | 耗時 |
| --- | --- | --- |
| 0.00 ns | 時脈上升 | — |
| 0.32 ns | **Rs2E[0] 從 dff 輸出**（clock-to-Q） | 0.32 |
| 0.72 ns | **通過 5 個閘算出 ForwardBE[1]**（轉發控制） | 0.40 |
| 1.24 ns | 轉發多工器輸出可用 | 0.52 |
| **1.84 ns** | **32-bit 比較器完成（10 層邏輯）** | **0.60** |
| 2.18 ns | 分支邏輯算出 PCSrcE（分支成立） | 0.34 |
| 2.62 ns | **StallE 下降**（分支成立不 stall，改成 flush） | 0.44 |
| **3.06 ns** | **到達 InstrEReg 的 D 輸入** | 0.44 |

```
required = 3.03 − 0.15 = 2.88 ns
arrival  = 3.06 ns
slack    = 2.88 − 3.06 = −0.18 ns        ← 不過
實際可達頻率 = 1 / (3.03 + 0.18) = 311 MHz
```

**注意「名稱改變不造成延遲，但顯示出來幫助你追蹤邏輯」**——
這正是 4.3 節 Guideline 4.13 說「訊號名稱不要在模組邊界不必要地改變」的價值。

**兩個重要的補充：**

**（1）多條路徑幾乎一樣長（p.280）：**
> "**Many nearly equal critical paths exist, so if you repeat this experiment, you can expect a
>  different endpoint and a few picoseconds variation in timing.**"

（呼應 6.1 節：平衡良好的系統沒有單一瓶頸。）

**（2）False path（偽路徑）——很重要的概念（p.280 邊欄）：**
> "An astute reader may notice that the timing report shows InstrEReg's D input rising, but this
>  scenario causes D to fall (because a pipeline flush clears the contents of the register to 0).
>  **This is a *false path* because it is logically impossible. The timing analyzer does not
>  understand such logical correlations between signals and simply looks for the worst-case
>  scenario. It is possible to annotate paths as false to reduce timing conservatism, but the
>  falling D path is unlikely to be significantly better.**"

**False path = 邏輯上不可能發生，但時序分析器不知道，所以照樣算進去。**
**時序分析器只看拓撲，不理解訊號之間的邏輯關聯。**
可以手動標註為 false path 來減少過度保守，但要小心（標錯就漏掉真的問題）。

### Hold time 報告

中文解釋：Fig. 6.16（p.281）是 `mindelay.rep`：
```
Startpoint: lsu/ReadDataMWReg/q_reg[5]
Endpoint:   lsu/ReadDataMWReg/q_reg[5]
Path Type: min                                ← 注意是 min 不是 max

lsu/ReadDataMWReg/q_reg[5]/CK                 0.000000
lsu/ReadDataMWReg/q_reg[5]/Q       0.196276   ← t_ccq
lsu/ReadDataMWReg/U11/Y (mux2_2)   0.221080
lsu/ReadDataMWReg/q_reg[5]/D       0.221080
data arrival time                  0.221080

library hold time                 -0.050442   ← t_hold
data required time                -0.050442
slack (MET)                        0.271522
```

**書上的解讀（p.281）：**
> "The timing analyzer computes minimum delays through components when checking hold time.
>  **To get a min-delay report that shows hold time checks, uncomment the report_timing line in
>  synth.tcl that includes `-delay_type min`.** The mindelay.rep file in Fig. 6.16 shows the
>  shortest path from the output back to the enabled input of the ReadDataMWReg. The hold time is
>  −0.050 ns, and the contamination delay (earliest arrival time) is 0.221 ns, **so the hold time
>  is easily met with 0.271 ns of slack.**"

**注意 hold 分析用的是「最短路徑」和「汙染延遲」**（呼應 6.1 節），
而且 **hold slack = arrival − required**（方向和 setup 相反）。

**`library hold time` 是負的（−0.050 ns）**——
表示這個正反器的 hold 時間是負的（資料可以比時脈略早變化）。

### Clock uncertainty：把 skew 加進來

> "Design Compiler refers to clock skew as *clock uncertainty*, which degrades both max-delay and
>  min-delay constraints because the clock might arrive at a flip-flop either early or late.
>  **Change the uncertainty to 0.1 ns in synth.tcl by modifying `set my_uncertainty 0` to 0.1,
>  and then rerun synthesis.**"
> — p.281

中文解釋：**Design Compiler 把 clock skew 叫做 clock uncertainty。**

**加入 0.1 ns 不確定性後的效果（Fig. 6.17 和 6.18，p.282）：**

| | 無不確定性 | 有 0.1 ns 不確定性 | 變化 |
| --- | --- | --- | --- |
| **Setup slack** | −0.177 ns | **−0.303 ns** | **惡化 0.126 ns** |
| **Hold slack** | +0.271 ns | **+0.166 ns** | **惡化 0.105 ns** |

**兩個約束都變差**（呼應 6.1 節 Eq. 6.3 和 6.4）。

**書上還注意到（p.281）：**
> "Observe that the endpoint has also changed to a different register and that the arrival time is
>  now 3.08 ns rather than 3.05 ns **because of some randomness in the synthesis process.**"

**終點換了、到達時間也變了——因為合成有隨機性。**

**P&R 階段會修 hold（p.282）：**
> "During placement and routing, CAD tools may insert delay buffers to fix hold time violations."

### set_critical_range：避免假的關鍵路徑

**邊欄（p.281）解釋了一個實用技巧：**
> "**The `set_critical_range` command tells synthesis to keep some margin such that less critical
>  paths don't accidentally appear as the most critical. This helps the designer recognize which
>  paths are truly critical and which ones were just relaxed until they became critical.**
>  The synth.tcl file sets a critical range of 50 ps to emphasize the real critical paths by
>  attempting to give 50 ps of slack to noncritical paths. **Turning off set_critical_range before
>  the final synthesis run could save a little area and power for these less critical paths.**"

中文解釋：**問題**：合成工具會把非關鍵路徑「放鬆」到剛好滿足時序，
**結果所有路徑的 slack 都差不多，看不出誰才是真正的瓶頸。**

**解法**：`set_critical_range 50ps` 要求非關鍵路徑保留 50 ps 餘裕，
**這樣真正的關鍵路徑才會凸顯出來。**

**代價**：最終合成時關掉它可以省一點面積和功耗。

**兩種動態功耗的區分（p.282）：**
> "Dynamic power is categorized as *switching power* and *internal power*. **Switching power
>  accounts for the load capacitance (gates and wires driven by each cell), and internal power
>  accounts for the capacitance inside each cell.**"

| 類型 | 對應的電容 |
| --- | --- |
| **Switching power** | **元件驅動的外部負載**（閘和導線） |
| **Internal power** | **元件內部的電容** |

**注意 internal power（5.302 mW）遠大於 switching power（0.820 mW）**——
元件內部的切換佔了大部分。

**漏電 vs 動態的比例（p.283）：**
> "**Observe that the leakage power is 715 nW compared to dynamic power of (5.302 + 0.820) =
>  6.122 mW. In other words, leakage power is 0.012% of the dynamic power. When a system is
>  operating at full speed, leakage is typically negligible. However, leakage influences battery
>  life when the system is quiescent.**"

**漏電只佔動態功耗的 0.012%**——呼應 6.1 節：全速運作時漏電可忽略，
但閒置時它決定待機續航。

**各模組的佔比也值得看：IEU 61.4%、IFU 24.1%、LSU 10.8%。**

**活動因子的假設（p.284）：**
> "Power is estimated using Design Compiler's default activity factor of 1.0 (100%) for clocks and
>  0.1 (10%) for non-clock signals. **It also assumes equal probability of 0 and 1 states on each
>  node to compute leakage power. Activity factors can be determined more accurately by running a
>  simulation of the synthesized netlist on a real workload and recording the number of times each
>  node toggles in a VCD (Verilog Change Dump) file. See `wsim --vcd` and the MAKE_VCD mode in
>  testbench.sv. However, the results are highly sensitive to the workload; for example, the
>  CoreMark benchmark has no floating-point instructions and thus may predict no activity in the
>  FPU.**"

**更精確的做法：用真實工作負載模擬，記錄 VCD，算出實際的切換次數。
但結果對工作負載非常敏感——CoreMark 沒有浮點指令，會預測 FPU 完全沒活動。**

**能量比功率更有意義（p.284）：**
> "Power is computed at the target clock frequency and hence changes with the frequency target.
>  **Energy per cycle or operation is a more insightful metric because it is independent of
>  frequency.** Energy per cycle is obtained by multiplying the power by the target clock period.
>  In this case, the power is 6.122 mW, and the target frequency is 333 MHz, **so the energy is
>  6.122 × 10⁻³/333 × 10⁶ = 18 pJ/cycle.**"

**每週期能量 = 功率 / 頻率 = 18 pJ/cycle。
這個數字與頻率無關，所以比功率更適合比較設計。**

## 所以呢

**讀報告的順序：`qor.rep`（全貌）→ `timing.rep`（追關鍵路徑）→
`area.rep` / `power.rep`（看哪個模組吃掉資源）。**

四件最該帶走的事：

1. **`qor.rep` 的關鍵讀法**：**最佳可達週期 = 目標 + |負 slack|**；
   **hold 違反必須是 0**；緩衝器/反相器佔了 25% 的元件數。

2. **`timing.rep` 的逐格追蹤是核心技能**：
   Point / Incr / Path 三欄就能重建整條關鍵路徑的時間軸。
   **rv32e 的關鍵路徑是「分支比較 → PCSrc → Stall/Flush」，
   其中 32-bit 比較器佔了 10 層邏輯 0.60 ns。**

3. **False path 的概念**：時序分析器只看拓撲，不懂邏輯關聯，
   所以會報告邏輯上不可能發生的路徑。

4. **面積的分佈**：**IEU 佔 71%，其中超過一半是暫存器檔案。**
   **而 P&R 還要再多 10–30% 的面積。**

還有一個實用的度量選擇：**用「每週期能量」（pJ/cycle）而非功率（mW）
來比較設計，因為前者與頻率無關。**
