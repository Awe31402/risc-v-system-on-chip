# 13.2 Test Plan

> 原書 p.558–559（Chapter 13: Instruction Fetch Unit）
> 含 13.2.1 Correctness、13.2.2 Performance

## 這節在講什麼

**很短，但它明確區分了兩種驗證，而且理由很清楚。**

> "**The IFU test plan stresses the branch predictor and instruction cache to verify both correctness and
>  performance.**"
> — p.558

**這是全書第一次把「正確性」和「效能」兩種驗證並列成兩個子節**——
因為 IFU 的兩個主要元件（I$ 和分支預測器）**都是非架構狀態**，
**錯了不會讓程式跑錯，只會變慢。**

## 關鍵點

### 正確性驗證

> "**Wally presently uses the riscv-arch-test regression tests to verify instruction operation, including branches
>  and jumps. When the IFU and LSU both include caches, the Zifence riscv-arch-test checks the correctness of
>  `fence.i`, which synchronizes LSU updates to instruction memory; the test does this by first storing a new
>  instruction to instruction memory, which will be held in the data cache, then preforming a `fence.i`, and finally
>  fetching the new instruction.**"
> — p.558

中文解釋：**兩件事：**

| 測試 | 測什麼 |
| --- | --- |
| **riscv-arch-test 回歸測試** | 指令運作，**包括分支和跳躍** |
| **Zifence 測試** | **`fence.i` 的正確性** |

**`fence.i` 測試的設計值得學（三步驟）：**
```
1. store 一條新指令到指令記憶體  → 它會留在【資料 cache】裡
2. 執行 fence.i                  → flush D$ + invalidate I$
3. 抓取那條新指令                → 應該看到新的值
```

**這個測試精確地針對「I$ 和 D$ 不一致」這個問題**
（呼應 10.1.8、10.2、10.4.2.6 節）。
**如果 `fence.i` 沒實作對，第 3 步會抓到舊指令。**

### 效能驗證

> "**The CoreMark and Embench benchmarks are small enough to fit entirely in the cache, so they do not meaningfully
>  stress the memory system. Section 21.3.1 describes instruction cache performance verification.
>  Section 21.3.2 describes branch predictor performance verification. Figs. 13.6 and 13.8 show good agreement
>  between Wally and a theoretical branch predictor.**"
> — p.558–559

中文解釋：**第一句是個重要的警告：**

**「CoreMark 和 Embench 小到完全裝得進 cache，所以它們無法有意義地壓測記憶體系統。」**

**這說明了 benchmark 的選擇問題：**
- 這兩個 benchmark 適合測 **CPU 核心的效能**
- **但不適合測 cache 和記憶體系統**——因為根本不會 miss
（呼應 9.4 節：要測匯流排就得挑「工作集大於 cache」的程式。）

**兩種效能驗證分別在：**

| 驗證 | 在哪一節 |
| --- | --- |
| **指令 cache 效能驗證** | **21.3.1 節** |
| **分支預測器效能驗證** | **21.3.2 節** |

**驗證的方法（從 13.1 節的圖可以看出）：**
**Fig. 13.6 和 13.8 把 Wally 的實測結果和「理論分支預測器」（CModel）並排，
兩條曲線吻合就表示實作正確。**

**這是效能驗證的典型做法：不是「比對答案」，而是「比對統計特性」。**
（呼應 13.1.3 節：「Wally 和理論結果吻合得很好，
差異來自做預測和更新表之間的 pipeline 延遲」。）

### 為什麼 IFU 需要兩種驗證

中文解釋：**把兩個子節放在一起看，邏輯很清楚：**

| 元件 | 正確性問題 | 效能問題 |
| --- | --- | --- |
| **I$** | **`fence.i` 沒做對 → 抓到舊指令 → 程式跑錯** | miss rate 太高 → 變慢 |
| **分支預測器** | **恢復邏輯沒做對 → 抓錯指令沒被 flush → 程式跑錯** | 準確度太低 → 變慢 |

**注意：兩者都同時有正確性和效能兩個面向。**
- **cache 的「內容」是非架構狀態（錯了沒關係），
  但 `fence.i` 的「同步機制」是正確性問題**
- **分支預測器的「猜測」是非架構狀態，
  但「猜錯時的恢復」是正確性問題**

**所以 13.2.1 測的是「恢復機制」，13.2.2 測的是「猜得準不準」。**

## 名詞表

| 名詞 | 意思 |
| --- | --- |
| Zifence riscv-arch-test | 測試 `fence.i` 正確性的官方測試 |
| CModel | 理論分支預測器模擬器，用來和 Wally 的實測結果比對（第 21.3.2.1 節） |

## 所以呢

**這節雖短，但區分了兩種驗證，而且理由很清楚：**

1. **正確性驗證的重點是 `fence.i`**——
   測試方法是「store 新指令（進 D$）→ `fence.i` → 抓取」，
   精確針對 I$ 和 D$ 的不一致問題。

2. **效能驗證要另外做**，因為 **CoreMark 和 Embench 小到完全裝得進 cache，
   根本不會 miss**——它們測不到記憶體系統。

3. **效能驗證的方法是「和理論模型（CModel）比對曲線」**，
   而非比對單一答案。Fig. 13.6 和 13.8 就是這樣做的。

**一個貫穿的觀念：I$ 和分支預測器都同時有「正確性」和「效能」兩個面向——
猜錯沒關係（非架構狀態），但「猜錯之後的恢復」必須正確。**
