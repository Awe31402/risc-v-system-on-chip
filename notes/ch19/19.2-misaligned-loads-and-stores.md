# 19.2 Misaligned Loads and Stores: Zicclsm

> 原書 p.775–778（Chapter 19: Other Extensions）
> 涵蓋 19.2.1 Test Plan、19.2.2 Wally Implementation

## 這節在講什麼

預設情況下，RISC-V 對非對齊（misaligned）的載入/儲存會丟例外，由 trap handler 用一連串較小的對齊存取模擬。Zicclsm 擴充表示「這顆 hart 用硬體處理非對齊存取，可能慢但不會 trap」。RVA20 之後的 profile 都要求它。

這節的重點是實作：Wally 在 LSU 裡加一個 `align` 模組，並且把快取的讀寫匯流排**加寬一倍**。真正麻煩的是 **spill**——非對齊存取跨越快取線邊界時，要分兩次請求再把資料拼起來。

## 關鍵點

### 預設行為與 Zicclsm 的承諾

> "By default, RISC-V produces a misaligned-load or misaligned-store exception when the address is not a multiple of the size of the element being accessed. For example, lw t0, 6(x0) produces a misaligned-load exception because address 6 is not a multiple of the 4-byte word size."
> — p.775

中文解釋：軟體模擬的版本（書上的例子）要四條指令：`lh` 讀低半字、`lh` 讀高半字、`slli` 把高半字移到上半、`or` 合併。加上 trap 進出的成本，慢得很誇張。

> "The Zicclsm (load/store misaligned) extension indicates that a hart handles misaligned loads and stores to cacheable coherent memory in hardware. They may be handled slowly, but they will not trap. Even with Zicclsm, misaligned atomic memory operations (AMOs) might still trap."
> — p.776

中文解釋：三個限制值得注意：
1. 只保證**可快取的一致性記憶體**（所以 memory-mapped I/O 不算）
2. 「可能很慢」——這是相容性保證，不是效能保證
3. **原子操作仍可能 trap**，因為跨快取線的原子性難以保證

### 為什麼 profile 要求它

> "The RVA20 and later profiles require support for Zicclsm. This is valuable for porting legacy code, which may contain misaligned structures, and which becomes unacceptably slow if each misaligned access traps."
> — p.776

中文解釋：理由是**移植舊程式碼**。x86 從來就允許非對齊存取，所以大量既有程式碼（尤其是網路封包解析、檔案格式處理、packed struct）充滿非對齊存取。如果每次都 trap，效能會爛到不能用。

### 測試的兩難

> "No load or store can produce {Load/Store}MisalignedFaultM when Zicclsm is enabled, so the misaligned riscv-arch-tests will not function correctly. To test both Zicclsm and misaligned faults, Wally rv64gc enables Zicclsm, but rv32gc does not."
> — p.776

中文解釋：這是一個有趣的驗證困境——**啟用 Zicclsm 就測不到「非對齊例外」的正確性**，因為根本不會發生例外。解法和第 16 章「兩種除法器組態」一樣：讓 rv64gc 和 rv32gc 走不同路，回歸測試就能同時涵蓋兩種行為。

專屬測試 `WALLY-misaligned-access-01.S` 「窮舉所有位元組偏移、存取大小、load 與 store 的組合，以及足夠跨越 64 位元組快取線邊界的記憶體存取」——測試策略就是窮舉所有邊界情形。

### 實作的兩個核心改動

> "It doubles the width of the cache read and write buses and adds the align module to shift misaligned data into the correct position. If the address spills across two cache lines, it issues requests to both lines and merges the data for loads."
> — p.776

中文解釋：
1. **加寬匯流排**：`WORDLEN` 從 `LLEN = max(FLEN, XLEN)` 變成 `LLEN*2`。這樣只要存取沒跨線，一次請求就能拿到足夠的資料，再移位取出要的部分。
2. **`align` 模組**：處理移位與 spill。

> "To support Zicclsm, Wally extends WORDLEN to LLEN*2, which allows the cache to output the entire access in one request for misaligned addresses within a single cache line."
> — p.776

中文解釋：這是**用面積換簡單**——加寬一倍的資料路徑（多工器、暫存器）換取「大多數非對齊存取仍是單次請求」。

### align 模組的基本運作

> "It computes ByteOffsetM as IEUAdrM modulo the access size. If this offset is nonzero for a read or write, it asserts MisalignedM and shifts read or write data by ByteOffsetM bytes to align the data."
> — p.776

中文解釋：Fig. 19.7 的資料路徑。`ByteOffsetM` 就是位址的低幾位元（依存取大小決定取幾位）。讀取時右移、寫入時（用 rotate）左移。注意寫入用的是 **rotate 而不是 shift**，因為跨線的部分要繞回來給下一次請求用。

### spill：跨快取線的情況

> "A spill (ValidSpillM) occurs when a misaligned address (MisalignedM) is in the last native-sized access of a cache line (PotentialSpillM). During a load spill, the align FSM asserts SpillSaveM to capture the DCacheDataWordM into register ReadDataWordFirstHalfM. SelSpillE is also asserted to increment IEUAdrSpillE by the size of the cache line in bytes."
> — p.777

中文解釋：spill 的判定是兩個條件的 AND——**非對齊**且**位於快取線的最後一個原生大小存取位置**。因為匯流排已經加寬成 LLEN*2，只有真的碰到線尾才會跨出去。

load spill 的流程（Fig. 19.8 的兩態 FSM：Ready → Spill）：
1. Ready 狀態：第一次請求拿回前半，用 `SpillSaveM` 存進 `ReadDataWordFirstHalfM` 暫存器
2. 轉到 Spill 狀態，`SelSpillM` 讓 `IEUAdrSpillM` 加上一條快取線的位元組數
3. MMU **重新做位址轉換**（因為可能跨頁！）得到 `PAdrM`
4. 快取輸出後半，和存起來的前半串接，再用 `ShiftAmount` 移位取出

store spill 比較簡單：「快取用 `LSUWriteDataM` 的低位元寫入字的下半部」——也就是分兩次各寫一半。

**特別注意第 3 步**：跨快取線也可能跨頁，所以第二次請求必須重新走 TLB。這是 spill 真正麻煩的原因，不只是拼資料而已。

### 原子操作仍會 trap

> "Misaligned atomic operations still throw a store/AMO-misaligned fault."
> — p.776

中文解釋：呼應前面的限制。要讓一個跨越兩條快取線的讀-改-寫保持原子性，需要的機制（鎖住兩條線、處理中途的失效）遠超過這個實作的複雜度預算。

## 名詞表

| 名詞 | 意思 |
| --- | --- |
| Zicclsm | load/store misaligned，宣告硬體支援非對齊存取 |
| misaligned access | 位址不是存取大小倍數的存取 |
| `align` 模組 | LSU 裡處理非對齊移位與 spill 的模組 |
| `WORDLEN` | 快取讀寫匯流排寬度，Zicclsm 下擴成 LLEN*2 |
| `LLEN` | max(FLEN, XLEN) |
| `ByteOffsetM` | 位址對存取大小取模的餘數 |
| `MisalignedM` | 這次存取是非對齊的 |
| spill | 非對齊存取跨越快取線邊界 |
| `PotentialSpillM` / `ValidSpillM` | 位於線尾／確定會跨線 |
| `SpillSaveM` | 把第一次請求的資料存起來 |
| `ReadDataWordFirstHalfM` | 存放 spill 前半資料的暫存器 |
| `SelSpillE` / `SelSpillM` | 選擇加了一條快取線位移的位址 |
| `ShiftAmount` | 從串接的雙倍寬資料中取出目標的移位量 |
| align FSM | 兩態機（Ready / Spill） |

## 所以呢

Zicclsm 是一個「語意很簡單、實作很囉唆」的擴充。表面上只是「不要 trap」，實際上要加寬整條資料路徑、加一個移位器、加一個 FSM，還要處理跨快取線時重新做位址轉換。書上「They may be handled slowly」這句話在實作層面看得很清楚——沒跨線的情況一個 cycle，跨線就要兩次完整的快取存取加一次額外的 TLB 查詢。下一節 19.3 的 Svinval 則是相反的例子：語意複雜，但在 Wally 上實作起來是零成本。
