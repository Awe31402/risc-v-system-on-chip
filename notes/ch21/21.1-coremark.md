# 21.1 CoreMark

> 原書 p.784.e24–784.e30（Chapter 21: Benchmarking）
> 涵蓋 21.1.1 Porting CoreMark、21.1.2 CoreMark Compiler Flags、21.1.3 Instruction Set Impact

## 這節在講什麼

第 21 章講「怎麼知道處理器跑得好不好」。這聽起來很簡單，但書上第一句就警告：這是一個「remarkably subtle problem（非常微妙的問題）」。

21.1 講 CoreMark——EEMBC 出的嵌入式處理器效能基準。這節除了介紹怎麼跑，更重要的是揭露了 benchmark 的**兩個陷阱**：編譯器旗標對分數的影響大到驚人，以及為了拿高分可以做出違反 benchmark 規則的修改。

## 關鍵點

### benchmarking 為什麼微妙

> "The goal of benchmarking is to quantify the performance of a computer. This turns out to be a remarkably subtle problem [Hennessy19]. Different programs run better on different computers, and small programs are notoriously susceptible to clever optimizations."
> — p.784.e24

中文解釋：兩個根本困難。第一，**沒有單一的「效能」**——同一台機器跑某些程式快、某些慢。第二，**小程式容易被特化最佳化**，測出來的是「編譯器有多會針對這個 benchmark 最佳化」而不是「處理器有多快」。

### synthetic benchmark 的名聲

> "'[Synthetic benchmarks] are discredited today, usually because the compiler writer and architect can conspire to make the computer appear faster on these stand-in programs than on real applications.' —David Patterson & John Hennessy [Hennessy19]"
> — p.784.e24（邊欄）

中文解釋：「conspire（串通）」這個字用得很重。CoreMark 和 Dhrystone 都是 synthetic benchmark（合成基準）——不是真實應用，而是「模仿真實應用的特徵」寫出來的小程式。這一節後面的內容會證明這句批評是對的。

### CoreMark 測什麼

> "CoreMark from EEMBC is a widely used and freely available benchmark to measure embedded processor performance. It performs the following steps that exercise the execution units, memory system, and branch predictor: List processing: find and sort; Matrix multiplication; State machine: parsing an input stream; Cyclic redundancy check (CRC)"
> — p.784.e24

中文解釋：四個部分各自壓力測試不同的東西——串列處理壓記憶體與分支、矩陣乘法壓 ALU 與快取、狀態機壓分支預測器、CRC 壓位元運算。

> "CoreMark was developed in 2009 to address limitations of an earlier benchmark called Dhrystone, which was overly susceptible to compiler and library optimizations. Both are small synthetic benchmarks (as opposed to real applications) ... Both avoid floating-point arithmetic, whose performance is highly dependent on whether the processor has a floating-point unit."
> — p.784.e24

中文解釋：CoreMark 是為了修正 Dhrystone 的問題而生的——但從後面的內容看，它自己也沒完全免疫。**刻意避開浮點**是重要設計決定：不然有 FPU 和沒 FPU 的處理器分數差距會淹沒其他因素。

### 怎麼跑

> "$ cd $WALLY/benchmarks/coremark / $ make ... make run invokes Verilog simulation with the same wsim command and testbench.sv as used in verification tests. However, CoreMark is slightly different in that it terminates with an ecall rather than with a write_tohost."
> — p.784.e25–e26

中文解釋：模擬大約兩分鐘。

### 分數怎麼算

> "CoreMark runs a specified number of iterations (default 10) and measures the number of clock cycles required to execute. The CoreMark/MHz score is 1,000,000 * ITERATIONS/cycles. In this run, it is 1,000,000 * 10/2,972,203 = 3.36."
> — p.784.e26

中文解釋：**CoreMark/MHz 是「每 MHz 每秒能跑幾次迭代」**——除掉時脈頻率的影響，只比較微架構的效率。這是正確的比較方式：一顆 3 GHz 的處理器如果 CoreMark/MHz 比較低，表示它是靠頻率而不是靠設計取勝。

### 效能計數器揭露了什麼

> "The cycles per instruction (CPI) is the number of clock cycles divided by the number of instructions retired; this is measured with mtime/minstret = 2,972,203/2,589,000 = 1.14. The difference mtime − minstret = 383,203 is the number of excess cycles caused by pipeline hazards. The performance counters show this includes 262,774 load stalls caused by the 2-cycle load-use latency, 26,087 store stalls, and 66,966 branch mispredictions causing pipeline flushes (11% branch misprediction rate)."
> — p.784.e26

中文解釋：這段是整節最有價值的部分——**把 CPI 1.14 拆解成具體的原因**：

| 來源 | 週期數 | 佔額外週期的比例 |
| --- | --- | --- |
| load-use 停頓 | 262,774 | 69% |
| 分支預測錯誤 | 66,966 | 17% |
| store 停頓 | 26,087 | 7% |
| 其他（乘除、快取失誤） | 剩餘 | 7% |

**最大的效能殺手是 load-use latency**（第 7 章講的兩週期載入延遲），不是分支預測錯誤。這對設計者是很實際的指引——想改善效能，優先處理載入延遲。

> "The working set fits into the cache, and the cache was already warmed up, so very few cache misses occur."
> — p.784.e26

中文解釋：這是 benchmark 的一個限制——CoreMark 太小，整個資料集塞得進快取（D$ misses 只有 76 次，對比 698,750 次存取）。**所以它幾乎測不出記憶體系統的好壞**。

（邊欄：「`mcycles` 會比 `mtime` 更正確，但在 Wally 上兩者相同。」——因為 Wally 的 `mtime` 每個時脈週期加 1。）

### 移植 CoreMark 要做什麼

> "The GETMYTIME macro for Wally is defined as: #define GETMYTIME(_t) (_t = *(volatile ee_ptr_int*)0x0200BFF8) This macro reads a 64-bit word from 0x0200BFF8, which is the mtime register in the CLINT."
> — p.784.e26

中文解釋：移植 benchmark 到裸機（bare-metal）平台主要就是提供三樣東西：**計時**（讀 CLINT 的 `mtime`）、**輸出**（寫 UART 的 THR）、**啟動程式碼**。`_send_char` 函式就是 20.4 節 `uartSend` 的翻版。

### 一個為了分數而違反規則的修改

> "A key to performance in RV64 is to redefine the ee_u32 datatype from unsigned to signed in core_portme.h: typedef signed int ee_u32; ... When compiling for RV64, unsigned 32-bit integers are expensive because bits 63:32 must be cleared to 0 after each operation using left and right 32-bit logical shifts or zext.w. The upper bits don't matter, so changing to signed integers allows RV64 to use its default sign extension, giving a 13% CoreMark speed boost. This change is in violation of CoreMark requirements but is widely done in RISC-V 64-bit benchmarks."
> — p.784.e27

中文解釋：**這段是整章最誠實也最重要的揭露。** 把 `unsigned` 改成 `signed` 拿到 13% 的速度提升——而這**違反 CoreMark 的規定**，但「在 RISC-V 64 位元 benchmark 上被廣泛採用」。

技術原因很清楚：RV64 的 32 位元運算（`addw` 等）預設做**符號**擴展，所以 signed 的 32 位元運算是天然的；unsigned 則需要每次運算後清掉高 32 位元，多一條 `zext.w`。

這印證了前面 Patterson & Hennessy 那句「編譯器作者和架構師可以串通」——**看到 CoreMark 分數時，要問的第一個問題是「他們改了什麼」**。

### 編譯器旗標的影響

> "CoreMark scores are strongly dependent on the compiler and, to boost performance scores, some compilers have been tuned with optimizations only applicable to CoreMark. But vendors are required to post their compiler version and flags along with their scores."
> — p.784.e27

中文解釋：「只對 CoreMark 適用的最佳化」——這是明目張膽的針對性作弊。EEMBC 的對策是**強制公布編譯器版本與旗標**，讓別人能檢驗與重現。

Table 21.1 的旗標清單有 20 多個，Wally 用的是改自 Western Digital SweRV（現稱 VeeR）核心的設定。幾個關鍵的：
- `-O3`：高度最佳化，用程式大小換速度
- `-funroll-all-loops`、`-finline-functions`：展開迴圈、內聯函式（都是拿大小換速度）
- `-falign-functions=16`、`-falign-jumps=4`：對齊以改善快取與取指行為
- `-mbranch-cost=1`：告訴編譯器分支的代價約等於一條指令
- `-mtune=sifive-3-series`：針對類似 SiFive 3 系列的管線最佳化

### 指令集的影響：最有資訊量的一張表

> "Table 21.2 shows the CoreMark performance for rv{32/64}i, im, imc, imb, gc, and gcb Wally configurations. The configurations use a software multiplication subroutine (i.e., rv64i achieves only 1.02 CoreMarks/MHz vs. 2.85 for rv64im)."
> — p.784.e27

中文解釋：Table 21.2(a)(b) 的數字非常有說服力：

| 組態 | RV32 CM/MHz | RV64 CM/MHz |
| --- | --- | --- |
| i | 1.20 | 1.02 |
| im | 3.28 | 2.85 |
| imc | 3.26 | 2.83 |
| imb | **3.36** | **3.06** |
| gc | 3.26 | 2.83 |
| gcb | 3.30 | 2.98 |

四個重要結論：

1. **乘法指令（M）帶來 2.7 倍的提升**（1.20 → 3.28）。這是整張表最大的差距——沒有硬體乘法器就得呼叫軟體副程式，CoreMark 的矩陣乘法會被拖垮。

2. **壓縮指令（C）反而讓效能略降**（3.28 → 3.26）：

> "imc and gc performances are nearly identical because CoreMark does not use floating-point or atomic instructions. They are slightly slower than im because compressed instructions can cause cache line spills."
> — p.784.e27

中文解釋：C 擴充省了程式大小，但 16 位元指令會造成**跨快取線的 spill**（第 7 章、第 10 章講過），多花週期。這是一個 code size 與 speed 的取捨。

3. **位元操作（B）帶來 8% 提升**（3.28 → 3.36）——呼應第 18 章開頭引用的數字。

4. **RV64 比 RV32 慢**：

> "rv64 configurations are slower than rv32 configurations because extra code is sometimes needed to handle 32-bit variables."
> — p.784.e27

中文解釋：這很反直覺——64 位元居然比 32 位元慢。原因就是前面講的：CoreMark 用大量 32 位元整數，在 RV64 上需要額外的擴展指令。**這說明「位元數多 ≠ 比較快」，要看程式實際用什麼型別。**

### 產生這些結果的工具

中文解釋：有腳本自動跑完所有組態並整理成 CSV。

## 名詞表

| 名詞 | 意思 |
| --- | --- |
| benchmark | 基準測試，量化電腦效能的標準程式 |
| synthetic benchmark | 合成基準，模仿真實應用特徵的小程式（非真實應用） |
| CoreMark | EEMBC 2009 年推出的嵌入式處理器基準 |
| Dhrystone | CoreMark 的前身，過度容易被編譯器最佳化 |
| EEMBC | Embedded Microprocessor Benchmark Consortium |
| CoreMark/MHz | 每 MHz 的分數，除掉時脈頻率影響 |
| CPI | cycles per instruction，= mcycle / minstret |
| `minstret` / `mtime` / `mcycle` | 已退休指令數／系統時間／時脈週期數 CSR |
| load-use latency | 載入後立即使用造成的停頓（Wally 為 2 週期） |
| bare-metal | 裸機，沒有作業系統 |
| `GETMYTIME` | CoreMark 移植時要提供的計時巨集 |
| `ee_u32` | CoreMark 的 32 位元整數型別，RV64 上改成 signed 可加速 13% |
| `zext.w` | 零擴展 32 位元到 64 位元（Zba 指令） |
| cache line spill | 指令跨越快取線邊界，需要兩次取指 |
| `coremark_sweep.py` | 自動跑所有 ISA 組態的腳本 |

## 所以呢

這一節給了兩個層面的收穫。**技術面**：Wally 的 CPI 1.14 主要來自 load-use 停頓（69%）；M 擴充是最大的效能來源；C 擴充換到程式密度但略損效能；RV64 在 32 位元密集的程式上反而吃虧。**方法面**：benchmark 分數不是客觀事實——編譯器旗標、資料型別的微調（甚至違規的微調）都能大幅改變結果，所以看分數時必須同時看設定。下一節的 Embench 就是為了修正這些問題而設計的：用真實程式、用幾何平均、同時測速度與大小。
