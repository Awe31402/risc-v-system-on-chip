# 5.3 Lint

> 原書 p.203–204（Chapter 5: Design Verification）

## 這節在講什麼

**Lint = 靜態程式碼分析。不跑模擬，只讀程式碼就找出問題。**

本節很短，核心論點只有一句：**同樣的 bug，lint 幾秒鐘抓到，
模擬要等它造成微妙的錯誤再從波形反推根本原因。**

內容是三件事：
1. **lint 會抓哪八類問題**（這份清單本身很有價值，是「常見 Verilog 錯誤」的目錄）
2. **有哪些工具**
3. **假警告怎麼處理**（`lint_off` / `lint_on`）

## 關鍵點

### 為什麼要 lint：時間成本的差距

> "Debugging a large design is time-consuming. **Engineers save a lot of time by detecting
>  problems during static code analysis (compilation) rather than through simulation.**
>  HDL simulators such as Questa indicate some errors and warnings that should always be
>  corrected, but dedicated code analysis tools called *linters* are more comprehensive and
>  faster."
> — p.203

中文解釋：這句話和第 5 章導論那句是同一個論點（p.194）：
> "It is much faster to fix these problems immediately than to wait for one to cause a
>  subtle bug and then track down the root cause by studying waveforms."

**關鍵詞是 "static code analysis"（靜態分析）——不執行程式碼就分析它。**
**對比：模擬是動態的，要真的跑，而且只能發現「這次執行有經過」的問題。**

**模擬器自己也會報一些錯誤和警告，但專門的 linter 更完整也更快。**

### Lint 抓的八類問題（很有價值的清單）

> "Some of the types of warnings flagged by lint tools include:
>  - Unsynthesizable logic
>  - Unintended latches and combinational loops
>  - Undeclared, unused, and undriven signals
>  - Mismatched port sizes
>  - Always and case statement gotchas such as missing defaults
>  - Poor coding style
>  - Deprecated Verilog constructs
>  - Mismatched vector sizes in assignment"
> — p.203

中文解釋：**這八類幾乎完全對應第 4 章講過的陷阱，可以當第 4 章的檢查清單：**

| Lint 警告 | 對應第 4 章的哪一段 |
| --- | --- |
| **不可合成的邏輯** | 4.2 節：可合成子集；4.3.6 的 `function`/`task` |
| **意外的 latch 與組合迴路** | **4.2.2.2 的 latch inference**（`always_comb` 漏賦值） |
| **未宣告、未使用、未驅動的訊號** | **Guideline 4.6：宣告所有訊號**（打錯字變成新訊號） |
| **埠大小不符** | Guideline 4.11–4.15 的埠連接 |
| **always 和 case 的陷阱，如漏掉 default** | **4.2.2.2：`case` 缺 `default` → latch inference** |
| 糟糕的編碼風格 | 4.3 節整節 |
| **已棄用的 Verilog 構造** | 4.2 節：`reg`、`wire` 是歷史包袱 |
| 賦值時向量大小不符 | 4.2.4.1：省略位元寬度的 gotcha |

**「組合迴路」（combinational loop）是這裡新出現的概念**：
組合邏輯的輸出繞回自己的輸入，形成沒有正反器的迴路。
**這在同步設計中絕對不允許**（呼應 Guideline 4.26），
因為它會震盪或鎖存出不確定的值。

### 工具選擇

> "Many lint tools exist, with Ascent Lint from Real Intent and Synopsys SpyGlass Lint being
>  current commercial market leaders. Design teams often produce customized lint rule sets
>  reflecting their organization's coding standards. **Wally uses Verilator lint because it
>  is free and good enough to catch many bugs.**"
> — p.203

中文解釋：

| 工具 | 定位 |
| --- | --- |
| **Ascent Lint**（Real Intent）、**SpyGlass Lint**（Synopsys） | 商用市場領導者 |
| **Verilator lint** | **免費，而且「足夠好，能抓到很多 bug」**——Wally 用這個 |

**"good enough to catch many bugs" 這個措辭很誠實**：
免費工具不如商用完整，但**投資報酬率很高**。
（對自學者是好消息——呼應 3.1 節：Verilator 是免費必備工具之一。）

**"Design teams often produce customized lint rule sets reflecting their organization's
coding standards."** ——**風格規範（4.3 節）可以變成 lint 規則自動檢查。**
這是把人工審查自動化的典型做法。

### 假警告的處理：局部關閉

> "Lint tools produce spurious warnings on certain types of code. For example, Verilator
>  warns about incomplete case statements without a default even if the value is set
>  elsewhere in an always_comb block. To turn off a specific lint warning, place the
>  following comment in the SystemVerilog code. CASEINCOMPLETE is the name of the warning
>  being waived."
> — p.203

```systemverilog
// verilator lint_off CASEINCOMPLETE
```

> "It is wise to turn the warning back on after the code that would cause the warning:"
> — p.204

```systemverilog
// verilator lint_on CASEINCOMPLETE
```

中文解釋：**兩件事要記住：**

1. **假警告是存在的**。書上給的例子很典型：
   `always_comb` 區塊裡如果在別處已經設過值，
   Verilator 仍會抱怨 `case` 不完整——**這是誤報。**

2. **關掉之後一定要開回來。**
   `lint_off` 後面沒有 `lint_on` 的話，**後面所有程式碼的這類警告都會被吞掉**——
   真的有問題時也不會報。

**這是「豁免要盡量局部」的原則**，和軟體的 `// noqa`、`#pragma warning` 同理。

### 最重要的實務準則

> "**A good designer keeps the design lint clean every time it is checked in to reduce bugs
>  and prevent warnings that confuse other designers.**"
> — p.204

中文解釋：**「每次簽入時都保持 lint 乾淨」。**

理由有兩層：
1. **減少 bug**（直接效益）
2. **避免警告混淆其他設計者**（間接但更重要）

**第二點是關鍵**：如果基準線上就有 50 個警告，
新出現的第 51 個就沒人會注意到——**警告一旦變成雜訊，就失去價值了。**

（這也對應 5.1.6 節的 always-working 策略：**保持乾淨是持續的紀律，不是最後的清理。**）

## 名詞表

| 名詞 | 意思 |
| --- | --- |
| **Lint / linter** | 靜態程式碼分析工具。不執行就找出問題，比模擬快得多 |
| Static code analysis | 靜態分析（在編譯階段），對比模擬的動態分析 |
| Combinational loop | 組合迴路。組合邏輯輸出繞回輸入且無正反器；同步設計中不允許 |
| Unintended latch | 意外的閂鎖。`always_comb` 有路徑未賦值時產生（見 4.2.2.2） |
| Spurious warning | 假警告。工具誤報 |
| `lint_off` / `lint_on` | 局部關閉／重新開啟特定警告 |

## 所以呢

**Lint 是投資報酬率最高的驗證手段：幾秒鐘的靜態分析，
抵得過幾小時的波形追查。**

三件實務要點：
1. **那八類警告就是第 4 章陷阱的檢查清單**——
   latch inference、未宣告訊號、缺 default、埠大小不符都在裡面。
2. **Verilator lint 免費且夠用**，自學者可以直接用。
3. **每次簽入都保持 lint 乾淨**——不是為了完美，
   而是**讓真正的新警告不被雜訊淹沒**。豁免要用 `lint_off`/`lint_on` 成對包住。
