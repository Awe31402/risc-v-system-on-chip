# 22.2 Buildroot Linux on Wally

> 原書 p.784.e52–784.e70（Chapter 22: Linux）
> 涵蓋 22.2.1 Building Buildroot Linux、22.2.2 Source/Binary/Disassembled Files、22.2.3 Linux Memory Map、22.2.4 Linux Boot Overview、22.2.5 Zero Stage Bootloader、22.2.6 OpenSBI Firmware、22.2.7 Kernel、22.2.8 Root File System、22.2.9 Device Tree、22.2.10 Init Process、22.2.11 Trap Handlers

## 這節在講什麼

22.1 畫了地圖，這節填上 Wally 的具體數字。最有價值的是 **Table 22.4 的開機里程碑表**——它把五億條指令的開機過程標出十幾個關鍵點，每個點都對應到某一章講過的硬體功能。

這節也是全書最好的「軟硬體交會處」教材：CSR 怎麼被 OS 使用、PMP 怎麼隔離 firmware、虛擬記憶體怎麼在執行中被打開（trampoline）、一個軟體中斷為什麼要四次 trap。

## 關鍵點

### Buildroot：十分鐘建出一整套 Linux

> "Although it is possible to build your own Linux system manually, it is faster and more maintainable to use an automated system to build these from source code in a configurable way. ... We use Buildroot, which supports RISC-V and produces the OpenSBI bootloader/firmware, Linux kernel, and root filesystem for embedded Linux."
> — p.784.e52

中文解釋：`cd $WALLY/linux && make`，約十分鐘。產出裝在 `$RISCV/buildroot`（預設 `$RISCV = /opt/riscv`）。

### 五個開機元件

> "Table 22.2 summarizes the components of the boot process. ... The ZSBL is a few bytes in ROM at address 0x1000. In a real system, it would load more code from nonvolatile storage, but in this system, it just jumps to the OpenSBI firmware already in memory. This firmware contains the rest of the bootloader, which initializes the hardware (informed by the device tree) and M-mode traps, then jumps to the Linux kernel. The kernel enters S-mode, turns on virtual memory, and initializes services. The kernel then loads init from the root file system on the RAM disk and starts it as the first U-mode process."
> — p.784.e54

中文解釋：**這段是整章的骨架**，注意權限模式的變化：

```
ZSBL（M-mode，0x1000）
  → OpenSBI firmware（M-mode，0x80000000）：初始化硬體、設 M-mode trap、設 PMP
  → Linux kernel（S-mode，0x80200000）：開虛擬記憶體、初始化服務
  → init（U-mode）：從 rootfs 啟動
```

**M → S → U 一路降權**，每一層都為下一層準備好環境再交棒。這就是第 8 章特權架構的實際用途。

### 記憶體配置

> "Table 22.3 gives the Linux address space layout."
> — p.784.e56

中文解釋：

| 元件 | 實體位址 | 大小 |
| --- | --- | --- |
| ZSBL | 0x1000 | **72 B** |
| OpenSBI firmware | 0x80000000 | 268 KiB |
| Linux kernel | 0x80200000 | 83 MiB |
| Root filesystem | 0x88200000 | 71 MiB |
| Device tree | 0x8FE00000 | 2 KiB |

**ZSBL 只有 72 位元組**——18 條指令。這具體說明了 22.1 講的「分階段」：第一階段小到可以放進最簡陋的 ROM。

Wally 的 RAM 從第 A 章預設擴大到 **256 MiB（0x80000000–0x8FFFFFFF）**，才裝得下 kernel + rootfs + 執行中的行程。

device tree 放在記憶體頂端附近（頂端往下 0x100000–0x1000000），**為了避開呼叫堆疊**。

### 一個關鍵的位址雙重身分

> "Observe that the kernel is at physical address 0x80200000 even though it is compiled assuming a virtual address of 0xFFFFFFFF80000000. Hence, the PC will be different running the kernel before and after virtual memory is turned on."
> — p.784.e56–e57

中文解釋：**kernel 有兩個位址**——載入時的實體位址 0x80200000，和編譯時假設的虛擬位址 0xFFFFFFFF80000000。所以「打開虛擬記憶體」這一瞬間，PC 的意義就變了。這是後面 trampoline 技巧要處理的問題。

kernel 放在虛擬位址空間的最高處（前面全是 1），U-mode 程式放在低位址——這是典型的 kernel/user 空間切分。

### SBI：kernel 與硬體之間的抽象層

> "When the kernel needs to access bare hardware, it calls the OpenSBI supervisor binary interface, which runs in M-mode and gives a standardized supervisor execution environment for the OS to access the platform-dependent raw hardware, such as changing the timer; writing a character to a console; or starting, stopping, or synchronizing harts."
> — p.784.e57

中文解釋：**SBI 之於 RISC-V，就像 BIOS/UEFI 之於 PC**。它讓同一份 kernel 能跑在不同廠商的 RISC-V 晶片上——kernel 只要呼叫 `sbi_console_putchar()`，不用知道 UART 在哪個位址、暫存器怎麼排。

### 開機規模與里程碑表

> "Linux boot involves executing about half a billion instructions, although about 80% of them are for decompressing the root filesystem."
> — p.784.e57

中文解釋：**五億條指令，其中 80% 只是在解壓 rootfs**。這個比例很有意思——真正的「開機邏輯」其實只有一億條左右。

| 875,488 | 0x80008a44 | `csrw mideleg, 222` — **委派中斷給 S-mode** |

### ZSBL 的 18 條指令

> "A RISC-V processor boots in M-mode. Although the RISC-V reset vector is nominally platform dependent, Spike, QEMU, the SiFive FU540, and Wally start the PC at 0x1000 and execute a short segment of code that jumps to another address (typically 0x80000000). ... This bootloader sets a0 to the mhartid, a1 to the address of the device tree, a2 to a data structure that includes the Linux kernel address and then jumps to the OpenSBI firmware at 0x8000000."
> — p.784.e57

中文解釋：Code Example 22.2 的完整 ZSBL：

```asm
0x1000: auipc t0, 0        # t0 = 0x00001000
0x1004: addi  a2, t0, 0x28 # a2 = 0x00001028（指向資料結構）
0x1008: csrr  a0, mhartid  # a0 = 本 hart 的編號
0x100c: ld    a1, 32(t0)   # a1 = 0x87000000（device tree 位址）
0x1010: ld    t0, 24(t0)   # t0 = 0x80000000（firmware 起點）
0x1014: jr    t0           # 跳過去
```

**三個暫存器就是完整的交接協議**：`a0` = 我是哪個 hart、`a1` = device tree 在哪、`a2` = 其他參數在哪。這是 22.1 講的「bootloader 把 FDT 傳給 kernel」的具體形式。

### OpenSBI：boot hart lottery

> "All RISC-V harts power up in random order, but the initial firmware boot occurs on only one hart. Thus, one of the harts is selected through a lottery (accessing shared memory) to be the boot hart, while the others sleep."
> — p.784.e60

中文解釋：**多核心開機的經典問題**——所有核心同時醒來，但初始化只能做一次。解法是用共享記憶體做一個「樂透」（實務上就是一個原子操作，第 17 章的 AMO），搶到的當 boot hart，其他的去睡覺，等 boot hart 叫醒（`wake_coldboot_harts` 發 IPI）。

OpenSBI 的初始化函式清單（`sbi_init`）很長，值得注意幾個：
- `sbi_hart_init`：初始化 `mstatus`、FPU、**trap delegation**
- `sbi_console_init`：設定 UART baud rate
- `sbi_hart_pmp_configure`：**設定 PMP 隔離 domain**
- `sbi_hart_switch_mode`：最後一步，進入 S-mode 的 kernel

### UART 初始化的九次存取

> "Wally uses the generic platform, which examines the flattened device tree to find the system has an ns16550a-compatible UART (see Section 20.4) at a clock frequency of 3.6864 MHz. The device tree does not specify the baud rate, so it defaults to 115200"
> — p.784.e62

中文解釋：**這是 device tree 實際運作的最好例子**——firmware 讀 device tree 發現 `compatible = "ns16550a"`，就去用 UART8250 驅動程式。硬體換了只要改 device tree。

Table 22.5 的九次存取完全對應第 20.4 節講的 16550 暫存器：關中斷 → 設 DLAB → 寫除頻係數低/高位元組 → 清 DLAB 並設 8N1 → 開 FIFO → 關 modem 控制 → 讀 LSR 清錯誤 → 讀 RBR 清殘留資料 → 清 scratchpad。

### PMP 怎麼保護 firmware

> "The PMP registers are configured with pmpaddr0 = 0x2003fff, pmpaddr1 = 0xffffffffffffff, and pmpcfg0 = 0x1f18. This sets regions 0 and 1 to naturally aligned power-of-two (NAPOT) sizes. Region 0 spans physical addresses 0x80000000-0x8001FFFF, encompassing the SBI. The access bits are all 0, so this 128-KiB SBI memory space is secured against read, write, and execute access by S- and U-mode programs. Region 1 spans all of physical memory and has read, write, and execute access"
> — p.784.e63

中文解釋：**兩個 PMP region 就完成了 firmware 的自我保護**：
- Region 0：SBI 所在的 128 KiB，**權限全 0**（S/U 完全不能碰）
- Region 1：整個記憶體，權限全開

因為 PMP 是**先匹配先贏**，region 0 在前面，所以 SBI 那塊被擋住，其他地方放行。

邊欄示範了 NAPOT 的解碼（第 11 章講過）：`pmpaddr0 = 0x2003fff` 尾端有 14 個 1，所以大小是 2^(14+3) = 2^17 = 128 KiB；去掉那些 1 再左移 2 得到起始位址 0x80000000。

> "Notably, the S-mode kernel has direct access to I/O peripherals. The kernel prohibits mapping U-mode virtual addresses to peripheral physical addresses, so U-mode programs must access peripherals through OS calls rather than by direct memory-mapped I/O."
> — p.784.e63

中文解釋：**U-mode 的隔離不是靠 PMP，是靠頁表**——kernel 單純不幫 U-mode 建立指向周邊的頁表項。兩層機制各司其職。

### trampoline：在執行中切換到虛擬記憶體

> "It then calls relocate_enable_mmu ... which writes the satp to enable virtual memory. The instruction fetch immediately after the satp write causes a page fault because PC = 0x80201054 is not a valid virtual address. The trap vector stvec is preset to the next instruction in the program at the correct virtual address 0xffffffff80001054, so the program continues properly. This switch from machine physical addressing to supervisor virtual addressing is called a trampoline because the trap handler immediately bounces the program into the kernel code."
> — p.784.e64

中文解釋：**這是整節最精巧的一招，值得完全理解。**

問題：`csrw satp` 執行完的下一個 cycle，虛擬記憶體就生效了。但 PC 還是實體位址 0x80201054，這在新的頁表裡不是合法的虛擬位址 → **page fault**。

解法（Code Example 22.3）：
1. **先**設 `stvec` = 0xffffffff80001048（同一條指令的**虛擬**位址）
2. 設一個「trampoline 頁表」，讓實體與虛擬都能用
3. 寫 `satp`
4. 立刻 page fault → 跳到 `stvec`
5. **`stvec` 指的正好就是原本要執行的下一條指令，只是用虛擬位址**
6. 程式若無其事地繼續跑，但 PC 已經在虛擬位址空間了

**把 page fault 當成跳板用**——這就是 trampoline 這個名字的由來。之後再載入真正的 kernel 頁表（`satp = 0x9000000000848b30`）、把 `stvec` 改指向 `handle_exception`、`sscratch` 設 0 標示「目前在 kernel 裡」。

### rootfs 與 device tree

> "All the executable commands are symbolic links to the BusyBox root file system, which parses the command line and executes the appropriate command."
> — p.784.e65

中文解釋：Fig. 22.1 列出整個檔案系統——`/bin` 下幾十個指令全是 `-> busybox`，正是 22.1 講的。

> "Fig. 22.2 lists the Wally device tree ... It shows that physical memory begins at address 0x80000000 and has a size of 0x10000000 = 256 MiB. There is one CPU with a clock and timer timebase frequency of 0x1C9C380 = 30 MHz. The CPU supports all the standard extensions and SV48 virtual memory. The SoC has a UART, PLIC, and Core-Local Interruptor (CLINT) at specified addresses in the memory map. Linux uses the compatible fields to determine which device drivers to use."

中文解釋：Fig. 22.2 的 `.dts` 檔值得細看——`riscv,isa-extensions` 那一長串正是這本書前 19 章講過的所有擴充（i、m、a、f、d、c、zba、zbb、zbc、zbs、zicbom、zicboz、zicond、zicsr、zifencei、zihpm、zkn、zkt、sstc、svinval、svnapot、svpbmt…）。**這份 device tree 就是整本書的成果清單。**

### 為什麼一個軟體中斷要四次 trap

> "Only the CLINT can set the machine software interrupt, but the OS needs to process this interrupt in S-mode, so it takes two traps to send a software interrupt and two more to receive."
> — p.784.e69

中文解釋：**這是特權分層的實際代價**。完整路徑：

**送出端（2 次 trap）**：
1. U-mode 行程 `ecall` → S-mode Linux 的 `sbi_send_ipi`
2. Linux 再 `ecall` → M-mode OpenSBI 的 `sbi_send_ipi()`，它去設 CLINT 的 `MSIP`

**接收端（2 次 trap）**：
3. `MSIP` 觸發 M-mode 軟體中斷 → OpenSBI 的 `_trap_handler` → `sbi_ipi_process()` 清掉 `MSIP`、設 `sip.SSIP`
4. `sip.SSIP` 觸發 S-mode 中斷 → Linux 的 `handle_exception` → `do_irq` → `riscv_software_interrupt()` 清 `sip.SSIP`，通知目標行程

**四次 trap 只為了送一個訊息。** 原因是硬體的中斷來源在 M-mode（CLINT），但處理它的軟體在 S-mode。

### Sstc：消除計時器中斷的兩次 trap

> "The OS scheduler uses timer interrupts to determine when to switch between threads. ... Thus, the supervisor timer interrupt trap overhead saves and restores registers twice. The timer interval is configurable but can be as often as every millisecond, so the overhead can be significant. The Sstc extension reduces this overhead by sending an S-mode timer interrupt directly to the Linux kernel without involving M-mode firmware."
> — p.784.e69–e70

中文解釋：計時器中斷有同樣的兩層問題，而且**每毫秒就發生一次**——開銷很可觀。Sstc 擴充（第 8.2.5.4 節）加了 `stimecmp` 暫存器，讓計時器**直接設 `sip.STIP`**，完全跳過 M-mode。這是一個為了消除軟體開銷而加的硬體功能，很好的取捨案例。

（外部中斷沒這個問題——PLIC 可以直接送給 supervisor context，設 `sip.SEIP`。這正是第 20.3 節講的 hart context 設計的價值。）

## 所以呢

這一節把前 21 章的硬體全部串起來使用了一次：CSR（第 8 章）、虛擬記憶體與 PMP（第 11 章）、原子操作（第 17 章，boot hart lottery）、CLINT/PLIC/UART（第 20 章）。

三個最值得記住的技巧：**ZSBL 用三個暫存器完成交接**、**PMP 用兩個 region 讓 firmware 保護自己**、**trampoline 把 page fault 當跳板切換定址模式**。而四次 trap 送一個軟體中斷，則具體量化了特權分層的代價——以及 Sstc 這種擴充為什麼值得加。
